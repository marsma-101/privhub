# PrivHub 项目上下文贯穿改造方案（选项目后所有功能限定在当前项目）

> 日期：2026-08-30 · 状态：**方案待确认后实施**
> 问题来源：用户反馈「选 A 项目后点搜索，项目就没了，等于搜全部文件——超出用户项目权限边界」

---

## 一、问题现状（代码事实）

### 1.1 前端丢项目上下文的 3 个入口（frontend/index.html nav）
```js
openTrash()    { nav.setActiveView('trash');    nav.project = null; ... }  // ← 清空
openSearch()   { nav.setActiveView('search');   nav.project = null; ... }  // ← 清空
openFavorites(){ nav.setActiveView('favorites');nav.project = null; ... }  // ← 清空
```
打开搜索/收藏/回收站视图时把 `nav.project` 置 null → 项目上下文丢失。

### 1.2 前端视图调用 API 不传 project（各插件 client）
| 视图 | 调用 | 现状 | 问题 |
|---|---|---|---|
| 搜索（F09） | `/api/search?q=` | **不传 project** | 服务端按「全部可见项目」搜（scope.project 空 → visible 全量） |
| 全文（F17） | `/api/fulltext/search?q=` | **不传 project** | 同上，全量可见项目 |
| 收藏（F02） | `/api/favorites` | 全局列表 | 展示跨项目收藏，且 GET 无可见项目过滤 |
| 回收站（F06） | `/api/trash-list` | 全局列表 | 跨项目（按 deletedBy 过滤） |

### 1.3 服务端现状（权限是安全的，但语义是「全可见」）
| 接口 | project 参数 | 过滤逻辑 | 结论 |
|---|---|---|---|
| `/api/search` | ✅ 支持 | project 指定时限定；空 = 全部 visible | 安全但语义全局 |
| `/api/fulltext/search` | ✅ 支持 | 同上（searchFulltext scope.project） | 安全但语义全局 |
| `/api/trash-list` | ❌ 无 | 按 deletedBy 过滤 | 需加 project 过滤 |
| `/api/favorites` GET | ❌ 无 | 按 username 过滤，**未按可见项目过滤** | 需加 project + 可见过滤 |

> 用户权限模型（core）：
> - `visibleProjects(user)`：admin 全部；普通用户 user.projects（白名单）
> - `canAccess(user, project)`：服务端每个文件接口都校验
> **服务端不会真正越权**——搜索结果的 project 一定 ∈ visible。但「选 A 项目却搜出 B/C 项目结果」在体验上是错的，且收藏/回收站列表未按可见项目过滤属于展示层越权。

## 二、目标行为（项目上下文贯穿）

```
用户选中「A项目」→ 进入文件视图
  ├─ 点 🔍 搜索     → 搜索范围 = A项目 内部（API 传 project=A项目）
  ├─ 点 🔎 全文     → 全文范围 = A项目 内部（API 传 project=A项目）
  ├─ 点 ⭐ 收藏     → 只显示 A项目 内的收藏
  ├─ 点 🗑️ 回收站   → 只显示 A项目 内的回收条目
  └─ 点其他功能面板 → 内部项目下拉默认 = A项目（已有）

未选项目时：
  ├─ 点 🔍/⭐/🗑️   → 视图内提示「请先选择一个项目」（或回项目选择屏）
  └─ 不进行全局搜索（杜绝跨项目混淆）
```

**核心原则**：
1. `nav.project` 是**全局项目上下文**，进入搜索/收藏/回收站视图时**不再清空**（保留）
2. 搜索/全文/收藏/回收站 API 调用**始终带 project 参数**
3. 未选项目（project=null）时，这些视图显示空态引导「先选项目」，不发起全局查询
4. 后续向量库/本地库（规划中）：一律按项目隔离建库/检索（本项目上下文机制是前置）

## 三、改动清单

| # | 位置 | 改动 | 类型 |
|---|---|---|---|
| 1 | 骨架 nav.openSearch/openFavorites/openTrash | **保留 nav.project**（删掉 `= null`） | 前端 |
| 2 | 骨架 openSearch/openFavorites 视图切换 | 若 project 为 null → 视图内空态（由各 client 处理） | 前端 |
| 3 | F09 搜索 client | `/api/search?q=&project=<nav.project>`；空态引导；标题显示「当前项目：X」 | 插件 |
| 4 | F17 全文 client | `/api/fulltext/search?q=&project=<nav.project>`；同上 | 插件 |
| 5 | F02 收藏 client | `/api/favorites?project=<nav.project>` 过滤显示；空态引导 | 插件 |
| 6 | F06 回收站 client | `/api/trash-list?project=<nav.project>` 过滤显示 | 插件 |
| 7 | F02 收藏服务端 | GET/DELETE/POST 增加 project 过滤 + 可见项目校验（canAccess） | 插件（服务端） |
| 8 | F06 回收站服务端 | trash-list 支持 project 参数 + 可见校验 | 插件（服务端） |
| 9 | 测试 | check-project-context.mjs：选 A 项目 → 搜索只见 A 项目结果；user1 跨项目不可见 | 测试 |

## 四、权限边界（本次严格保证）

- **不改** core 的 `visibleProjects/canAccess`（已正确）
- 收藏/回收站服务端新增的过滤用现有 `svc.visibleProjects` + `canAccess`：
  - favorites GET：`list.filter(f => visible.includes(f.project))`（防已失去权限的收藏残留展示）
  - favorites POST：`canAccess(u, project)` 校验（防手工伪造收藏无权限项目）
  - trash-list：`?project=` 时 `canAccess` 校验 + 过滤；无参数时保持现状（或也按 visible 过滤）
- 搜索/全文：前端传 project，服务端原有逻辑已保证 project ∈ visible（若传了无权项目 → 结果为空，安全）

## 五、与「未选项目」的交互细节
- `nav.project === null` 时点搜索/收藏/回收站：
  - 视图正常打开，但内容区显示「📁 请先选择一个项目」+ [去选择项目] 按钮（回到项目选择屏）
  - 不做全局搜索——彻底杜绝「未选项目 = 全量」的隐式越权感
- 项目选择屏保留（上一轮已实现），作为所有项目相关功能的起点
