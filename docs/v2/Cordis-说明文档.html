Cordis 插件框架 · 技术说明

一份面向开发者的、与具体业务解耦的 Cordis 运行规则说明

适用读者：希望基于 Cordis 搭建可插拔插件系统的工程师与 AI-Agent  ·  核心包：cordis  ·  开源：cordiverse/cordis

1. Cordis 是什么

Cordis 是一个轻量级的插件化应用框架（Node.js / 浏览器均可运行）。它的职责只有一个：以一套统一、可预测的契约，把"插件"这种松散的扩展单元组织成一棵有层级、有依赖、可热插拔的运行时。

它最初是为聊天机器人框架 Koishi 抽离出来的底层内核（同一作者 shigma），因此天生为"大量独立功能模块共存、互不污染、可单独启停"的场景设计。

它解决的核心问题

  • 依赖编排：插件 A 依赖插件 B 提供的某项能力，框架按依赖图自动决定启动顺序，缺依赖则不启动。
  • 隔离与共享：每插件有自己的上下文（Context），既能共享全局服务，又能被隔离出独立子环境。
  • 通信解耦：插件之间尽量不直接互相引用，而是通过事件总线通信。
  • 可逆副作用（可插拔基石）：插件注册的一切资源（监听器、定时器、连接）都能在卸载时被逆序、彻底清理，删除插件不留垃圾。

核心特性一览

  • 零运行时强依赖，体积很小。
  • Service 机制：把"可复用能力"以类型安全的方式挂到上下文上。
  • inject 声明式依赖：框架据此做拓扑排序与按需卸载。
  • 5 种事件分发模式（emit / parallel / serial / bail / waterfall）。
  • 上下文树：fork / isolate / group 提供多级隔离。
  • effect 与生命周期钩子，保证副作用可撤销。

2. 快速开始

安装

# npm
npm install cordis
# pnpm
pnpm add cordis

最小可运行示例

import { Context } from 'cordis'

// 1. 创建一个根上下文
const ctx = new Context()

// 2. 定义一个最简单的函数插件
const hello = (ctx) => {
  ctx.on('ready', () => {
    console.log('Cordis is ready')
  })
}

// 3. 把插件挂到上下文
ctx.plugin(hello)

// 4. 触发启动（emit 事件驱动各插件就绪）
ctx.emit('ready')

关键点

  • new Context() 是所有插件的挂载根；它本身也是一棵可派生子上下文的树。
  • ctx.plugin(plugin, config?) 返回一个可释放对象（disposable），调用它即可卸载该插件。
  • Cordis 是事件驱动的：很多行为由 emit 事件触发，而非命令式调用。

3. 核心概念模型

Cordis 的世界由五个要素构成，理解它们的关系就理解了整个框架：

概念是什么角色
Context（上下文）插件挂载的环境单元，本质是插件树的节点提供 plugin()、事件、服务访问等 API；可派生子 Context
Plugin（插件）一段被注册到 Context 的扩展单元三种形态之一（函数 / 对象 / Service 子类）
Service（服务）可复用的能力单元，挂到 Context 上供其他插件消费通过 inject 被依赖，是"共享能力"的标准载体
Event（事件）插件间解耦通信的通道跨插件尽量只走事件，不直接引用彼此
Effect（副作用）插件注册时产生的外部资源占用必须可被逆序清理，是可插拔的基石

一张心智图

Root Context ──挂载──▶ 多个 Plugin
每个 Plugin 在 apply(ctx) 中：
  • 消费 Service（通过 inject 拿到 ctx.xxx）
  • 监听 / 触发 Event
  • 注册 Effect（监听器、定时器、连接等）
卸载时：Effects 逆序清理 → 服务依赖重算 → 缺失服务的插件自动停。

4. 插件的三种形态

Cordis 对"插件"的定义非常宽松，只要是以下三种形态之一即可被 ctx.plugin() 接受。

形态一：函数插件

最简洁的形式，直接是一个函数，接收 ctx（及可选 config）。

const myPlugin = (ctx, config) => {
  ctx.on('ready', () => {
    console.log('config value:', config?.foo)
  })
}
ctx.plugin(myPlugin, { foo: 42 })

形态二：对象插件

带 apply 方法的对象，可声明 name、inject、using 等元数据。这是最常用、最规范的形式。

export const myPlugin = {
  name: 'my-plugin',
  inject: ['database'],   // 声明依赖的服务
  apply(ctx, config) {
    // 此时 ctx.database 已被框架注入
    ctx.on('ready', async () => {
      await ctx.database.get('users')
    })
  },
}

形态三：Service 子类插件

当插件本身要对外提供能力时，继承 Service 基类，用 super(ctx, 'key') 把能力以 ctx.key 的形式暴露给其他插件。

import { Service } from 'cordis'

export class DatabaseService extends Service {
  constructor(ctx) {
    super(ctx, 'database')   // 暴露为 ctx.database
  }
  get(table) { /* ... */ }
  set(table, row) { /* ... */ }
}

// 注册这个服务插件
ctx.plugin(DatabaseService)

形态选择的经验法则

  • 只在启动时做点小事 → 函数插件。
  • 大多数业务功能 → 对象插件（带 apply + inject）。
  • 这个插件要被别的插件依赖 → Service 子类，提供 ctx.xxx。

5. 服务注入系统（核心机制）

服务系统是 Cordis 实现"能力复用 + 依赖治理"的核心。它解决了两个问题：能力怎么暴露，以及依赖怎么被框架管理。

5.1 提供一项服务

继承 Service，在构造函数里 super(ctx, '服务键名')。之后任何声明了 inject:['服务键名'] 的插件，都会拿到 ctx.服务键名。

class Logger extends Service {
  constructor(ctx) { super(ctx, 'logger') }
  info(msg) { console.log('[info]', msg) }
}
ctx.plugin(Logger)
// 其它插件：inject:['logger'] → ctx.logger.info(...)

5.2 消费一项服务（inject 声明依赖）

inject 数组里的每一项，框架都会尝试从当前上下文解析；解析到的服务会挂到 ctx 上供 apply 使用。

const consumer = {
  inject: ['logger'],
  apply(ctx) {
    ctx.on('ready', () => ctx.logger.info('consumer ready'))
  },
}

5.3 依赖解析与启动顺序

框架自动做的事

  • 拓扑排序：插件按"被依赖者先启动"的顺序初始化。
  • 缺失依赖不启动：若某插件 inject 的服务始终不存在，该插件不会启动（而不是崩溃），也不会报错阻断全局。
  • 按需卸载：当一个服务插件被卸载，依赖它的插件会被框架自动逆序卸载；服务重新挂上后又会自动恢复。

5.4 拦截已有服务（intercept）

不修改原服务源码，就能在其方法前后插入逻辑——这是"在不污染原服务的前提下增强能力"的标准手段。

// 不改动原 Logger，而是拦截它的 info 方法
ctx.intercept('logger', {
  info(ctx, msg) {
    // 在原始 info 之前/之后插入行为
    return ctx.logger.info.call(this, `[intercepted] ${msg}`)
  },
})

重要约束

增强能力应当通过 intercept 或新建一个独立 Service，不要直接往已有 Service 实例上挂载新属性（如 ctx.logger.newMethod = ...）。直接挂载会破坏"服务即契约"的边界，导致依赖关系脱离框架管理、卸载时无法被追踪清理。

5.5 服务重命名 / 别名

Service 支持 provide 与 rename 机制，让"同一个实现"以不同键暴露，或解决多实例命名冲突。具体由插件元数据 name / 构造时的键名控制。

6. 事件系统

事件是插件之间解耦通信的主通道。Cordis 提供 5 种分发模式，语义各不相同：

方法语义返回值 / 用途
ctx.on(ev, fn) / ctx.emit(ev, ...)注册 / 触发监听器触发即广播；最基础的发布订阅
ctx.parallel(ev, ...)并行调用所有监听器不关心返回值；适合"通知大家做点事"
ctx.serial(ev, ...)串行依次调用逐个 await；适合有先后依赖的处理链
ctx.bail(ev, ...)串行调用直到某监听器返回非 null返回第一个有效结果即停止；类似"短路求值"，适合"取第一个能处理的人"
ctx.waterfall(ev, init, ...)串行把上一步返回值传给下一步管道式加工数据；适合"层层修改同一份数据"
 
// 注册监听器
ctx.on('message', (text) => console.log('got:', text))

// 触发（多个监听器并行收到）
ctx.emit('message', 'hello')

// waterfall：把数据流经多个插件依次加工
ctx.on('process', (data) => ({ ...data, a: 1 }))
ctx.on('process', (data) => ({ ...data, b: 2 }))
const result = await ctx.waterfall('process', { base: 0 })
// result => { base:0, a:1, b:2 }

设计建议

跨插件通信优先走事件，而非互相 inject。这样删除任何一个功能插件，都不会因为"被别人直接引用"而引发连锁崩溃——这正是可插拔性的关键。

7. 上下文隔离

Context 是一棵树。根 Context 可以派生出子上下文，子上下文继承父的环境，但拥有独立生命周期。Cordis 提供三种隔离手段：

7.1 fork —— 复制一份上下文

const child = ctx.fork()
child.plugin(somePlugin)   // 只挂在这个子上下文里
// 卸载子上下文不会动父上下文的其他插件

7.2 isolate —— 按命名空间隔离

ctx.isolate(namespaces, callback) 创建一个隔离上下文，callback 内拿到的 ctx 与全局配置/服务按给定命名空间隔离。常用于"让同一插件的不同实例互不影响"。

ctx.isolate(['myPlugin'], (isolatedCtx) => {
  isolatedCtx.plugin(myPlugin, { /* 该命名空间专属配置 */ })
})

7.3 group —— 分组隔离（多实例）

插件可声明 group: true，配合 isolate 为每组数据/每个租户派生出独立的服务实例与子 Context。适合"一个插件按多份配置同时运行多份"的场景。

注意

group 相关的 API 在部分 cordis 版本中标记为 unstable。若仅需要"插件间互不污染"，通常靠事件 + 服务注入已足够，未必需要引入 group 这一层。

8. 生命周期与可插拔性

8.1 apply 与卸载回调

插件在 apply(ctx, config) 中注册一切。若 apply 返回一个函数，该函数即卸载时调用的清理回调。

const plugin = {
  apply(ctx) {
    const timer = setInterval(() => console.log('tick'), 1000)
    const off = ctx.on('event', handler)

    // 返回清理函数：卸载时逆序执行
    return () => {
      clearInterval(timer)
      off()
    }
  },
}

8.2 effect —— 可逆副作用的推荐写法

ctx.effect(fn) 注册一个会产生副作用的初始化，fn 返回自己的清理函数。框架统一管理这些 effect 的逆序释放。

apply(ctx) {
  ctx.effect(() => {
    const off = ctx.on('ready', () => {})
    return () => off()   // 卸载时执行
  })
}

8.3 卸载顺序

可插拔的基石

  • 卸载一个插件时，它注册的所有 effect 与 apply 返回的清理函数被逆序执行。
  • 依赖该插件服务的其他插件，由框架自动逆序卸载。
  • 结果：删掉一个插件目录 / 取消一次注册，运行时零残留——这正是"想到功能就加插件、不需要就删插件"的工程前提。

8.4 Service 的生命周期钩子

Service 子类可覆写 onApply / onDispose 钩子，在服务被挂上 / 摘下时执行初始化与清理，便于管理连接池、文件句柄等重资源。

9. 插件加载与组织

Cordis 本身不强制任何目录结构，加载本质就是一次次 ctx.plugin() 调用。常见的组织方式有两种：

9.1 入口显式注册

在应用入口处集中列出插件清单并注册。简单、可控，适合插件数量不多时。

import { Context } from 'cordis'
import { Logger } from './plugins/logger'
import { Auth } from './plugins/auth'
import { Files } from './plugins/files'

const ctx = new Context()
ctx.plugin(Logger)
ctx.plugin(Auth)
ctx.plugin(Files)

9.2 配置驱动的 Loader（推荐用于大量插件）

当插件数量变多（例如几十个功能模块），用一份配置描述"要加载哪些插件、各自配置是什么"，由 Loader 扫描并批量 ctx.plugin()。这种方式天然支持：

  • 目录即插件：约定"每个子目录是一个插件"，Loader 扫描目录自动发现，新增插件只需新建目录。
  • 声明式启停：在配置里增删一行即可启用 / 禁用某个插件，无需改代码。
  • 补丁式注入：通过 patch 描述文件（如 *.patch.yml 类约定）向某上下文插入插件，常用于在不动原包的前提下挂扩展。

组织建议

无论用哪种方式，每个插件自包含（自带 manifest / 入口 / 所需后端）是核心原则。Loader 只负责"发现 + 注册"，不关心插件内部实现。这样新增功能 = 增加一个自包含插件目录 + 在加载清单里登记，完全不动其他插件。

9.3 一个自包含插件的最小结构

plugins/
  my-feature/
    manifest.json        // 声明 id / 名称 / 挂载点 / 入口
    index.ts             // 插件主体（apply + inject）
    server/              // 可选：该插件私有的后端能力
    package.json         // 可选

10. 设计哲学小结

把前面所有机制串起来，Cordis 的设计哲学可以浓缩成几条，理解它们比记 API 更重要：

① 服务即契约

能力通过 Service 显式暴露，依赖通过 inject 显式声明。框架据此管理生命周期，而不是靠开发者手动维护引用。

② 通信靠事件，不靠互相引用

插件之间尽量只通过事件总线交互。一个插件消失，不会让另一个插件因为"找不到被引用对象"而崩溃。

③ 副作用必须可逆

effect + 返回清理函数的 apply，保证任何插件卸载时都干净退出。这是"可插拔"真正成立的前提。

④ 增强用拦截，不污染原服务

要扩展已有服务，用 intercept 或新建独立 Service，而不是直接往实例上挂属性——守住"服务即契约"的边界。

⑤ 目录即插件，清单即编排

让 Loader 按目录自动发现插件，用声明式清单控制启停。新增功能变成"加一个自包含目录"，维护成本线性可控。
