# PrivHub 上传查重（内容重复/近似提示 + 近似族删除开关）——2026-10-13

> 来源：改进方案 §3.3（Q6）与 §3.5（Q7）。对应任务 #15 / #16。
> 验收（方案原文）：§3.3「**同一文件传两次，第二次给出"内容重复"提示**」；
> §3.5/Q7「查重页对近似类**默认不勾选、只提示**」。

---

## 1. 解决什么

改造前，上传是**完全盲的**：同一份文件传两次、或者同一份文档的多个版本，
系统一声不吭地都收下。"哪个文件是重复的"只能在事后翻查重页（`/rag/dup`）才知道，
而查重页只认**语料库已摄取**的文件（要跑过一遍解析/向量化），刚上传的还不在里面。

于是最常见的重复来源——"手滑传了两遍"——要在几分钟后才被发现。

本批做两件事：

1. **上传当下就给提示**：上传接口按内容指纹在**同项目内**查一次，
   把"与已有文件内容相同 / 高度相似"回带在响应里，前端一条 toast 说完（§3.3 轻量版）。
2. **近似/版本族可以勾进删除流程，但默认不勾**（§3.5 / Q7）：查重页的"近似 / 版本族"
   分区此前是只读的（未拍板就不替用户做主）；现在管理员（或开关打开后的用户）
   可以勾选删除，**默认保持全不勾、只作提示**。

## 2. 明确不做：物理去重（这是 Q6 的答案）

方案 §3.3 的完整形态是"复用密文 + 引用计数"（nowen 的做法：命中同 hash 就复用物理文件、
只克隆一条元数据行，靠引用计数决定何时 `unlink`）。**本批不做**，理由写在方案里也成立：

- PrivHub 是**加密存储**（`PHENC1` 头），`isEncrypted` 的 size 记账依赖文件长度；
  两处引用同一份密文，就要同时重做记账与**回收站语义**（删除一份不能真删密文、
  最后一份要能回收）——风险面大，且收益（省磁盘）对局域网文档场景不迫切。
- 只提示不落盘**零风险**：不动上传主链路，不动加密存储，不动回收站，
  删掉这个功能也不需要数据迁移。

> 所以本批的定位是：**"告诉你重复了"，而不是"帮你只存一份"**。

## 3. 指纹模型（三层，为什么是三层）

`plugins/privhub-svc-dup/src/core.ts`：

| 层 | 字段 | 算法 | 用来判 |
|---|---|---|---|
| 原始 | `h` | 流式 `sha256`（上传时顺带算，不额外读盘） | 内容**一字不差** |
| 归一 | `n` | `sha256(normalizeText(text))` | 只差换行/空白/BOM/零宽字符 |
| 近似 | `s` | MinHash-16 签名（4-gram，步长 2） | 高度相似（相似度 ≥ 0.9） |

- **归一化** `normalizeText`：去 BOM、去零宽字符、`\r\n?` → `\n`、行尾空白、
  压缩 3 个以上空行为 2 个 —— 与查重页既有算法**同源同口径**
  （方案 §3.2 的 `normalizeText`，`svc-rag/src/index.ts` 早就在用）。
- **near 只对"文本类"文件算**：判据是**有没有 NUL 字节**（不是看扩展名）。
  NUL 出现在前若干字节即视为二进制，`n`/`s` 都不算 —— 否则每个 `.zip` 都会
  被当成"高度相似的乱码"乱报。
- **上限**：`NEAR_MAX_BYTES = 2MB`。超上限的只算原始 `h`（流式，不吃内存）。
  这是刻意的取舍：near 要把明文留在内存里做 n-gram，2MB 之上得不偿失，
  而"大文件一字不差"仍由 `h` 覆盖。
- **near 命中上限** `NEAR_HITS_CAP = 5`：一屏提示不需要第 6 条。

MinHash 用的是**分带**（`MINHASH_BANDS = 4`，16 个特征分 4 带）而不是全签名比对：
band key 进桶，只在同桶里比 `sigSimilarity`，避免 O(项目文件数) 全扫。
`MINHASH_FEATURES = 16` 是"够用且能被 4 整除"的折中（漏检率对"版本族"场景可接受）。

## 4. 索引与生命周期

L2 服务 `privhub-svc-dup`（`ctx.dup`）维护三张倒排表 + 一张正排表，
落 `data/dup-index.json`（**密文**，经 `ctx.storage`）：

- `byFile`：`kFile(project, path)` → 指纹（正排，删除/改名靠它）
- `byRaw` / `byNorm`：精确命中（`kRaw`/`kNorm` → bucket → `kFile[]`）
- `byBand`：近似命中（`kBand(project, band)` → bucket → `kFile[]`）

**派生数据，随时可丢**：索引只由"上传过什么"决定，重扫磁盘即可重建。
因此读取用严格 `readJsonStore`（D4：损坏 → 隔离存证 + 记 `corrupt` 标志 + 抛错），
写走 `assertStoreWritable(!corrupt, file)`——**读坏过就拒绝写，绝不覆盖**；
但**绝不因为索引出问题而挡住任何上传**（上传主链路里对查重的调用整体 `try/catch` 旁路）。

**跟随文件生命周期**（`file:changed`，与 svc-links 同一套并发口径）：

| action | 处理 |
|---|---|
| `created` / `saved` | 由上传路由显式 `register()`（事件里没有指纹） |
| `renamed` / `moved` | `moved(project, old, new)`：换 key；`new` 以 `old + '/'` 开头时**同前缀的子项一起搬**（目录改名） |
| `deleted` / `purged` | `forget(project, path)` |

**有界**：`MAX_ENTRIES = 20000`，超了按 `at`（最久未触碰）淘汰 —— 淘汰只是让老文件
下次上传时再登记一遍，不影响正确性。

**项目内隔离**：所有 key 都带 `project` 前缀，`check()` 只在同项目内查。
跨项目口径是 Q8（§3.5）的事，本批不做。

## 5. HTTP 面 + 开关

没有新路由。查重挂在**既有上传路由**的返回里
（`privhub-files/src/index.ts` 的 `/privhub/api/upload`）：

```
POST /privhub/api/upload
→ { ok:true, size, duplicates:[{path,size}], near:[{path,score}] }
```

- `duplicates` / `near` **只在功能开关 `dup.prompt` 对本人为 `read` 及以上时才回带**；
  关掉就整两个键都不出现（不是空数组——"没有这个能力"和"查了没查到"要能区分）。
- `check()` 结果**排除自己**，且只查**同项目**。
- 查重失败**不影响上传**：整段 `try/catch`，出错只 `logger.warn`，照常返回 `{ok:true,size}`。

**前端**（`privhub-files-upload/client/index.js`）：上传完成后，若有命中，
用 `warn` 色 toast 说一句（**不打断、不阻止**）：

> 内容重复：`报告.md` 与已有 `docs/报告.md` 内容相同，两份都保留了，可自行删除其一

**查重页近似族删除开关**（§3.5 / Q7）：

- 服务端在 `GET /privhub/api/rag/dup` 的结果里新增 `allowNearDelete: boolean`
  —— **单一事实来源**，由 `ctx.cap.can(user, 'dup.near.delete', 'write')` 算出。
- 管理员**恒为 true**（用户全局规则：对管理员全开放）；
  普通用户 `userDefault = 'none'` ⇒ 默认 false ⇒ 界面**只提示、不渲染勾选框**。
- 打开开关后，近似 / 版本族分区**每份文件**出现"保留 / 删除"单选，
  且**默认全不勾**（`load()` 里 `keep['n'+g]=0`）——"一键套用策略"**跳过** near 组，
  半自动也不越界（Q7 明确不建议让近似类默认参与删除）。

功能开关两项登记在 `plugins/privhub-svc-cap/src/core.ts`（分组「查重」）：

| 功能 id | 标题 | 普通用户默认 |
|---|---|---|
| `dup.prompt` | 上传期重复提示 | `read`（能用；需要时关） |
| `dup.near.delete` | 近似/版本族可勾选删除 | `none`（默认只提示） |

`dup.prompt` 默认 `read` 的依据是用户全局规则：**功能要全 → 对管理员全开放 →
对用户理论上能全开放但要做开关**。`dup.near.delete` 是**危险写操作**（能把"看着像"
的文件一键删进回收站），按既有口径（危险的写默认 `none`）保守给。

## 7. 诚实边界（没做 / 已知限制）

- **不做物理去重 / 引用计数**（见 §2）：提示只是提示，磁盘上仍是两份。
- **索引只覆盖"上传过的文件"**：历史存量文件在**第一次重新上传**前不在索引里；
  查重页（`/rag/dup`，走语料库）覆盖的是另一批（摄取过的）。两者**口径不同、互不替代**，
  这是本批刻意的边界（重扫全盘建索引属另一件事，且与"派生数据可丢"的设计相冲）。
- **近似判定只在同项目、≤2MB、文本类**：跨项目是 Q8；大文件只判一字不差；二进制只判一字不差。
- **near 阈值 0.9、指纹 16 特征 / 4 带**是经验值，未在真实语料上调过；
  可能对"短文档"偏松或偏紧。
- **界面只做了代码接线，没在真实浏览器里点过**：
  toast 文案、近近似族勾选框的显隐（`allowNearDelete` 真/假两态）、
  只读态「只提示」徽标的**视觉效果**没有浏览器自动化验证——本批只断言了服务端契约
  （`duplicates`/`near`/`allowNearDelete`）与前端确实读用了这些字段。
- **`dup.near.delete` 打开后的真实删除**走的是**既有**的查重页删除链路
  （`applyStrategy` / `toggleDel` / 后端删除接口），本批只改"能不能勾"，未改删除动作本身。
- 本批**没在真实数据上跑过**：全部验证在隔离实例（3190）+ 临时测试项目上完成。
