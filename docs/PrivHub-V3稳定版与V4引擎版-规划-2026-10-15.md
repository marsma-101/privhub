# PrivHub V3 稳定版 与 V4 引擎版 —— 版本划分与联动规划（2026-10-15）

> 来源：主人 2026-10-15 的诉求 —— 「把『系统能挂载其它智能体引擎』定成 **V4**；V4 之前先把 V3 做成
> 能投产的**稳定版**；不想用智能体软件的人用 V3，想把引擎挂进系统的人用 V4；并要考虑 **V4 的改进/bug
> 修复如何同步回 V3** 这个架构问题。」本文件是**方案**（待拍板），批准后才动实现代码。
>
> 基线：`privhub/package.json` = **3.2.0**（2026-10-15）｜62 插件目录 / 149 条后端路由 / 38 注册路由的插件 /
> 38 个 slot / 22 视图｜回归全绿。权威账本见 [`PrivHub-开发状态与路线图.md`](PrivHub-开发状态与路线图.md)。

---

## 0. 给非技术读者的一页话

**两句话讲清区别：**

- **V3 = 文档中枢（没有"引擎"）**。它把文件、权限、存储、检索、看板、审计这一套做扎实；外面的 AI 软件
  **可以来连它**（拿一把钥匙读写它授权的数据），但**它自己不养引擎、不驱动 AI**。不需要 AI 软件的人，
  用 V3 就够了，且这是能长期维护的**稳定版**。
- **V4 = 在 V3 身上加一层"引擎挂载层"**。你把外部智能体引擎（宿主机上的 Claude Code / opencode /
  Cherry Studio、或一个 OpenAI 兼容端点、或本地 Ollama）**接进来**，让 PrivHub 用它们干活：
  让管家替你整理项目、让问答改用你指定的引擎、让引擎去处理看板上的待办。

**一个关键的省心设计**：V3 与 V4 **不是两个代码库**。它们是**同一份代码**，差别只在"引擎层要不要装、开关要不要开"。
这样做的好处：V4 修的一个 bug，回移给 V3 几乎是**自动的**（同一行代码），不会出现"改了这边忘了那边"。

## 2. V3 / V4 怎么划

### 2.1 一句话定义

| | **V3 = 文档中枢（Document Hub）** | **V4 = 引擎版（Engine Edition）** |
|---|---|---|
| 是什么 | 文件 + 权限 + 存储 + 检索 + 看板 + 审计 + 运维 | V3 **全部内容** + 一层"引擎挂载层" |
| 智能体 | **只作为"外部客户"**：拿钥匙来读/写它被授权的范围（本项目 Agent API 已有） | **再加上"被挂进来当能力用"**：管家 / 引擎注册表 / 应用内引擎视图 |
| 谁用 | 不想在系统里跑 AI 软件的人 | 想把手边引擎接进系统的人 |
| 稳定性 | **长期维护版（LTS）**，只收修复、不加功能 | 持续演进，新功能落这条线 |

> **边界的一句话判据**：*"别人来连我"属 V3；"我去驱动引擎 / 引擎来管我"属 V4。*
> 所以现有 **Agent API 网关（`files-agent` + `pha_` 钥匙）留在 V3** —— 它只是把 PrivHub 的数据
> 按权限暴露给外部；而**管家车道（`butler` + `/butler/*`）、MCP 转接器、引擎注册表属 V4**。

### 2.2 ⚠️ 命名冲突（**必须先解决**）

仓库里 **"V4" 这个词已经被占用**：`PrivHub-交互融合方案-整体设计.md` 自称「**V4 交互重构候选**」，
`docs/v3/README.md`、`架构与功能说明.md:266` 也都把它叫"V4 候选"。那是**界面交互**的重构，和"引擎挂载"
不是一回事。若两件事都叫 V4，文档会彻底乱。

**建议**：把版本线**只留给产品版本号**，交互那件事改名。

| 旧叫法 | 新叫法（建议） |
|---|---|
| 「V4 交互重构候选」（交互融合方案） | 「**交互融合（UI 演进候选，非版本线）**」——它将来随某个 V3.x 或 V4.x 落地，不单独占版本号 |
| ——（本次新定义） | **V4 = 引擎版**（Engine Edition） |

### 2.3 边界怎么划 —— 三层"图层表"

V3/V4 的差别收敛成一张表。**L0/L1 是共享层（两版一模一样的文件）；L2 是 V4 独有层。**

| 层 | 内容 | 归属 |
|---|---|---|
| **L0 地基** | `src/`（`main.ts`/`web-server.ts`）、`privhub-core`、`svc-storage`/`acl`/`audit`/`events`/`search`/`meta`/`watermark`、`privhub-auth`、`privhub-files`、`privhub-trash`、`privhub-admin*`、`privhub-shell*`、`frontend/index.html` | **V3/V4 共享**（冻结新功能，**只收修复**） |
| **L1 能力** | `svc-model`/`svc-rag`/`svc-office`、`files-*` 家族、`project-dashboard`、`task-board`、`task-calendar`、`webhook`、`svc-cap`/`admin-cap`、`svc-links`、`svc-dup` | **V3/V4 共享**（V3 内置；V4 同样内置） |
| **L2 引擎** | ① 管家车道：`files-agent` 内 `butler` 相关路由 + `agent.butler*` 开关组；② `privhub/mcp/`（MCP 转接器 + 安装脚本）；③ **新**：`plugins/privhub-engine-*`（引擎注册表 + 适配器）；④ **新**：应用内 `engine-view` slot | **V4 独有** |

**边界要"写成代码"，不靠自觉**：

1. 新增 `privhub/engine-layer.json` —— 一份**清单**，列出所有 L2 路径（目录 / 文件 / cap 名 / slot 名）。
2. `tests/integrity.mjs`（**只增不改**）新增三条断言：
   - **L0/L1 文件不得 import L2 路径**（防止地基悄悄依赖引擎层，那样 V3 就漏装了）；
   - **L2 清单与实仓一致**（多一个少一个都报红）——防止有人把引擎目录忘进清单；
   - **V3 组装下 `agent.butler*` 九项开关恒为 `none`、`engine-view` slot 不出现**。
3. `scripts/build-deploy.ps1` 加 `-Edition v3|v4`：`v3` 打包时**不含** `privhub/mcp/` 与 `privhub-engine-*`，
   并对管家开关强制 `none`。

> **落地取舍（需拍板）**：管家①地基已进代码，它躺在 `files-agent` **内部**（不是独立目录），"物理剔除"很别扭。
> 因此建议 **V3 里"代码在、开关默认关、界面卡片隐藏"**（用 §2.3-2 的断言 3 把"开不了"钉死），
> V4 再"开闸 + 补 ②③④ + 加注册表"。这样省一次危险的目录手术，且 V3 用户完全看不见引擎层。

## 3. 联动架构 —— V4 的改进/修复怎么同步回 V3

> 这是主人明确点名的架构问题。答案：**单主干 + 维护分支 + 图层隔离**。

### 3.1 分支 / 标签模型

```
main ─────●───────●─────────●──────────●───────▶  （V4 开发线，永远最新）
          │       │         │          │
       v3.5.0  v3.5.1    v3.6.0     v3.x.y        （release/3.x 维护分支上的补丁标签）
          │
     （V3 稳定版在此切出）        release/4.x ──●──●─▶  （V4 稳定线）
```

- **`main`** = V4 开发主干。所有新功能、所有修复都先落这里。
- **`release/3.x`** = V3 维护分支，在 V3 稳定版（建议 tag `v3.5.0`）那一刻切出，此后**只接受回移**。
- **`release/4.x`** = V4 稳定线。
- **`feat/T-001`**（现存的历史分支）→ 收工后删除，避免第三源。

### 3.2 什么能回移到 V3（准入规则）

| 能回移 ✅ | 不能回移 ❌ |
|---|---|
| 安全修复（ACL / 会话 / 存储 / 越权） | 任何新功能、新插件、新路由 |
| 数据完整性修复（并发、损坏、迁移） | 只服务 V4 引擎层的改动 |
| L0/L1 的 bug 修复 | 破坏 V3 数据格式或接口契约的改动 |
| 依赖无关的性能 / 稳定性修复 | 需要新依赖的改动 |

> 判据一句话：**"修 bug 可以，加东西不行。"** 回移后 V3 只升**修订号**（`3.5.1`、`3.5.2`…），
> 永不升次版本——"稳定版"的含义就是它不再长大。

### 3.3 回移机制（三步，可脚本化）

1. 修复在 `main` 上**先落**（一个提交做一件事，便于挑选）。
2. `git cherry-pick <sha>` 到 `release/3.x`（冲突极小——见 §3.4 为什么小）；提交信息带 `[backport 3.x]` 标记。
3. 在 `release/3.x` 上跑一次全量回归 + 打 `v3.5.x` 标签 + 同步 V3 部署包。

### 3.4 为什么回移会"几乎不冲突"——靠图层隔离

- **绝大多数修复落在 L0/L1**（地基与能力层）。这两个层**两版逐字节相同**，cherry-pick 命中同一上下文，
  冲突概率极低。
- **V4 独有改动全在 L2**（`engine-layer.json` 清单里的路径）。这些文件在 V3 里**根本不存在**，
  所以"V4 的功能提交"**天然不会**碰到 `release/3.x` 的任何文件——你甚至 cherry-pick 不过去，
  这正是我们要的"物理隔离"。
- 剩下唯一会冲突的情况：一个提交**同时**动 L0 与 L2。**规则**：这种提交必须**拆成两个**——
  L0 部分（可回移）+ L2 部分（不回移）。§2.3-2 的 integrity 断言会在 CI 意义上逼你这么做。

### 3.5 版本号与产物

| | V3 | V4 |
|---|---|---|
| 版本号 | `3.x.y`（冻结后**只增 y**） | `4.x.y` |
| 产物 | `deploy/privhub-v3/`（`-Edition v3` 打的包） | `deploy/privhub-v4/`（`-Edition v4`） |
| 数据 | **同一套数据格式**，可原地升级 V3 → V4；**不支持 V4 → V3 回退**（V4 可能写了 V3 不懂的引擎配置） | 同左 |
| 部署包 | 必须与 `package.json` 版本一致（解 OPS-02/OPS-03） | 同左 |

> **升级方向**：V3 → V4 是"加装引擎层"，不改已有数据；V4 → V3 属降级，需**先导出、再重装**，
> 由文档明确告知。这样"两版共存、各自维护"才成立。

## 4. 从今天走到 V3 稳定版，再到 V4

### 4.1 阶段 1：把 V3 做成稳定版（建议 3.3.0 → 3.5.0 → 冻结）

| 步 | 做什么 | 产出 |
|---|---|---|
| 1 | **收口 13 段**（按 §4.2 分批：批 C → 3.3.0、批 D → 3.4.0、批 E 管家① → 3.5.0） | 代码 = 版本号 |
| 2 | **解 OPS-02**：重打两个部署包、核对 3181、跑 `integrity.mjs --release`（**保留 `data/` 与 `secret.key`**） | 3181 跑上新代码 |
| 3 | **补发布闸门**（OPS-03）：`run-all` 校验 `package.json` 与 `CHANGELOG` 一致 | 版本号不再能造假 |
| 4 | **裁决 4 项悬空安全项**（S14/S15/F3/GC-15）：修 或 显式"接受并登记" | 安全面有明确结论 |
| 5 | **落 §2.3 图层表 + integrity 三条断言** | V3/V4 边界被钉死 |
| 6 | **打 `v3.5.0` 稳定标签、切 `release/3.x`** | V3 LTS 诞生 |

> 其中**只有第 2 步需要主人显式授权**（它要动 `deploy/` 与 3181）。其余都是仓内动作。

### 4.2 阶段 2：V4 起步（引擎层）

| 批 | 内容 | 复用盘点 |
|---|---|---|
| **V4-a** | **管家 ②③④**（已方案确认）：内容整理 + 内部管理、模型/检索、运维/安装体验 + 看门狗 + 一键接线卡 | 方案见 `PrivHub-宿主机智能体管家-MCP-方案-2026-10-13.md` §9 |
| **V4-b** | **引擎注册表**：`plugins/privhub-engine-*` —— 统一"引擎描述符"（id/类型/端点/密钥/能力标签）+ `EngineAdapter` 接口（`listEngines` / `invoke` / `health`） | 与插件模型同构：**加一个引擎 = 加一个 adapter 文件** |
| **V4-c** | **应用内引擎视图**：RAG 问答可选引擎、写作助手、看板待办交给引擎处理 | 复用 `svc-rag` / `svc-model` / `task-board` |

**为什么 V4-b 是"加文件而不是改核心"**：一套 `EngineAdapter` 接口把"接哪个引擎"变成**可插拔**，
和你今天"加一个插件目录 = 加一个功能"完全一致。这样 V4 的引擎类型增长**不会**往 L0/L1 里渗代码，
§3.4 的"回移不冲突"才长期成立。

### 4.3 V3 稳定版的验收标准（"能投产"的硬指标）

1. **代码 = 版本号**：`CHANGELOG` 无 `[未发布]` 段；`package.json` 与部署包一致。
2. **回归全绿**：`node tests/run-all.mjs --spawn` 全 0 失败；`--release` 通过。
3. **部署包可上线**：3181 核对版本、会话校验在包内生效、`data/` 与 `secret.key` 完好。
4. **文档数字真实**：README / 架构说明 / 路线图 的口径与实测一致。
5. **安全面有结论**：4 项悬空项 已修或已显式接受并登记。

## 6. 诚实边界与风险

- **范围可能不小**：V4（尤其管家 ②③④）是"新开一条能力通道"，四批合计远超前面任一单；本文件把它定为**独立版本线**，
  正是为了**不让它拖住 V3 稳定版**。
- **"单主干 + 维护分支"需要纪律**：cherry-pick 若长期只挑一半，V3 会慢慢烂。§2.3 的 integrity 断言是最低限度的护栏，
  不能替代"每个修复都问一句：V3 要不要？"的习惯。
- **数据格式一旦在 V4 分叉**（引擎配置写进共享 JSON），回退 V3 会出问题——所以 §3.5 明写"**单向升级**"。
- **3190/3191 隔离实例验一切**，绝不碰 3180/3181 的真实数据。
- 本文件对"V3 稳定版"的判定基于**当前仓内状态**；OPS-02 未解前，V3 "稳定"只是**源码层**稳定，
  **部署层**仍需一次受控的重新打包。
