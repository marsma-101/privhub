## 1. 一句话结论

**这个前端有一个"名义上的单一状态源"（`nav.activeView`），但代码层面没有把这条纪律落地：`nav` 里有 3 组镜像状态 + 2 个只写不读的死状态，视图渲染是一条 16 分支的手写条件链；而真正的病灶在异步操作——打开/重命名/移动/删除/收藏/标签/上传这 7 类动作里，进度、成功、失败三态**没有统一契约**，失败又分三种结局：报错、报"假成功"、或伪装成"没有数据"。**

一句话再压缩：**它不是"状态管得乱"，是"状态说了话，但没人负责把话说完"。**

## 4. 改进建议

排序口径：**改一处要动几行 × 用户多久撞一次 × 撞上后能不能自己绕开**。P0 限 5 条。

### P0-1 · 从回收站/搜索/收藏切回文件视图，目录会显示成"空文件夹"

- **【问题】** `nav.openTrash()` / `openSearch()` / `openFavorites()` 都会执行 `nav.entries = []`（为了不让上一个视图的清单串到下一个视图，这个动机是对的）。但**没有任何一处代码在切回 `files` 视图时把 `entries` 取回来**：`setActiveView('files')`（`:460–470`）只重置 `rightOpen/selected/preview`，不碰 `entries`、也不调 `openDir`。于是用户从回收站点回 📁 文件图标后，看到的是 `panel.js:446–452` 那个**"此文件夹下没有文件"空态 + 上传按钮**——而文件夹里明明有文件。列表要等用户下一次点击左侧目录树或面包屑才会回来。
  - 更坏的是：那个空态**自带"⬆ 上传文件"按钮**。用户在"我的文件不见了"的状态下，屏幕上最大的按钮是"上传"。
  - 对照：`backToWelcome()`（`:499–506`）同样清空 `entries`，但它同时把 `project` 置为 `null`，会走到欢迎页分支，所以**不产生假空态**——只有"切视图"这条路径漏了。
- **【证据】**
  - 清空：`privhub/frontend/index.html:625`（`openTrash`）、`:631`（`openSearch`）、`:636`（`openFavorites`）
  - 不补：`privhub/frontend/index.html:460–470`（`setActiveView` 全文）
  - 假空态：`privhub/plugins/privhub-files-explorer-v3/client/panel.js:445–452`
  - 数据源只在 `openDir` 里写：`privhub/frontend/index.html:489`
- **【改法】** 三条路，按代价从低到高，**选一条即可**：
  1. **最省（1 行）**：在 `setActiveView` 里，当 `v === 'files'` 且 `nav.project !== null` 且 `nav.entries.length === 0` 时，`void nav.openDir(nav.project, nav.path)`——
     ⚠️ 但这会**丢掉 `openTrash` 等三处的清空动机**吗？不会：清空是为了"离开文件视图"，回来时重取反而是正确语义。
  2. **更准（3 行）**：`openTrash` / `openSearch` / `openFavorites` 三处**不要清 `entries`**，改为清 `nav.checked`（那个才是真正会串的东西）。`entries` 是"当前目录的清单"，与"当前视图是哪个"无关。
  3. **最省心（0 行代码 + 1 条断言）**：若不想动行为，至少让空态**区分"还没取过"与"取回来是空的"**——目前 `listLoading=false && entries.length===0` 无法区分此二者。
- **【验收】** 进到 `项目A / 合同`（里面有文件）→ 点图标栏 🗑️ → 再点图标栏 📁 → **列表仍是原来那批文件**，不出现"此文件夹下没有文件"。
- **【成本】** **小**（1–3 行，1 个文件，不动插件、不动布局、不动契约）。
- **【与既有条目的关系】** 五份方案与账本**均未提此条**。它不是 P0-5（URL/刷新）——那条讲 F5，这条讲**同一会话内点一下图标就丢**，触发成本低得多。

### P0-2 · 8 处 `r.ok` 判定缺失，接口失败一律伪装成"没有数据"

- **【问题】** 骨架给了统一的错误归一（`api()` 保证失败也返回 `{ok:false, error:'可读中文'}`，`:364–385`），但**消费端大面积不用它**：只取数据字段、不判 `ok`，失败时得到一个假空数组/假 `undefined`，界面于是显示"空"或"无数据"。用户看到的结论从"出错了，可以重试"退化成"这里本来就没有东西"——**这比报错更坏，因为它消灭了用户的下一步动作。**
- **【证据】**（每条都是我亲自打开看过的）

  | # | 位置 | 写法 | 失败时用户看到 |
  |---|---|---|---|
  | 1 | `privhub-files-search/client/index.js:70` | `this.hits = r.ok ? r.hits : []` | "没有匹配「q」的内容"（`:122`） |
  | 2 | `privhub-files-search/client/index.js:73` | 同 | 同 |
  | 3 | `privhub-files-tags/client/index.js:69` | `this.tagFiles = r.ok ? r.files : []` | "无文件"（`:130`） |
  | 4 | `privhub-files-tags/client/index.js:35` | `if (r.ok) this.allTags = r.tags`（无 else） | "该项目暂无标签"（`:124`） |
  | 5 | `privhub-shell-favorites/client/index.js:41` | `if (r.ok) this.all = r.favorites`（无 else） | "当前项目还没有收藏"（`:77`） |
  | 6 | `privhub/frontend/index.html:641` | `if (r.ok) { nav.trashList = r.trash … }`（无 else） | "当前项目回收站是空的"（`trash-ui:65`） |
  | 7 | `privhub-files-upload/client/index.js:76–80` | `ensureDirs` 的 catch 注释写"已存在则忽略" | 目录**没建成**的失败被当成"已存在"，后续上传逐条失败 |
  | 8 | `privhub-files-explorer-v3/client/ops.js:153` | `catch { /* 树加载失败 */ }` 后 `loading=false`，`tree` 仍是 `[]` | 移动弹窗里只有"🏠 项目根目录"一项，看起来就是全部可选目标 |

  - 附带**同类但已做对的反例**（可供抄写）：`index.html:490–491`（A6 注释："接口失败不再静默假空"）；`trash-ui:47–50` 与 `favorites:62` 的 `bus` 刷新是主动重取，不是等用户。
- **【改法】**
  1. **最小统一**：给这 8 处各加一个 `else` 分支，把 `r.error` 落到**视图自己的一行**上（不要只弹 toast——toast 2.6 秒就走，用户回头再看还是"空"）。建议在这些视图的 `.main-head` 右侧加一个常驻的 `⚠ 读取失败 · 重试`，把已有的 `load()` / `doSearch()` 挂回去。
  2. **不改文案只改类型（更省）**：把 `if (r.ok) this.all = r.favorites` 改成 `this.all = r.ok ? r.favorites : null`，模板里 `v-else-if="all === null"` 显示错误、`v-else-if="all.length === 0"` 显示空态。**空与错是两个状态，不能共用一个值。**
  3. **加一条静态检查**（防复发）：`integrity.mjs` 里加一条"`api(` 的返回值必须出现在 `r.ok` / `.catch` / `await` 三者之一的同一语句块内"的粗检查——本项目已有 50 条这类检查，多一条成本极低。
- **【验收】** 断网或让某个接口返回 500，逐个打开搜索/收藏/标签/回收站：**每个视图都出现可读的错误提示与重试入口**，不出现"暂无/还没有/无匹配"。
- **【成本】** **小**（8 处各 1–4 行；文案与重试按钮是新增，但都是视图内部）。
- **【与既有条目的关系】** 对**搜索结果**只说"无清除筛选"空态（`01-don-norman.md` P2-1）；对**标签**只说空态没出口。**"失败被伪装成空"这条无人提**，且它是这 4 个视图共同的**根因**——修根因比修 4 处空态更省。

### P0-3 · 收藏：不等结果就报"已加入收藏"，而写入失败被整段静默

- **【问题】** 两处叠在一起，构成一个**必然报假成功的链路**：
  1. 触发方 `doFavorite()` **不 await、不看结果**，`bus.emit('fav:add', …)` 之后**立刻** `toast('已加入收藏 ⭐')`（`ops.js:201–202`）；
  2. 接收方是**模块级监听 + 全局 try/catch**：`if (r.ok) bus.emit('favorites:changed')`，失败落进 `catch { /* 静默：失败不影响主流程 */ }`（`favorites:17–22`）。
  → 于是**只要收藏写盘失败，用户 100% 看到"已加入收藏 ⭐"，并且再也找不到那个文件在哪**（收藏列表里没有它）。这是本轮我在交互层看到的最坏一类缺陷：**系统说它记住了，其实没记住。**
  - 另有一处同源问题：`remove()`（`:44–48`）**完全不看 `r.ok`，无论成败都 `await this.load()`**——用户点"取消收藏"，弹的是"取消失败"还是"没有失败"无法区分；列表刷新后条目还在，用户会以为"点不动"。
- **【证据】** `ops.js:197–203`（乐观 toast）、`favorites:17–22`（静默 catch）、`favorites:44–48`（`remove` 无判定）。反例：`files-tags:62–64` 至少 `else toast('保存失败')`——**同类功能里，收藏是做得最差的那个**。
- **【改法】**

### P0-5 · 异步没有"进行中"概念：同一个按钮可以在请求飞行中被点第二次

- **【问题】** 全仓只有**批量操作**（`batchBusy`，`panel.js`）和**移动弹窗**（`busy`，`ops.js:158`）两处做了重入保护。**其余所有异步动作都没有**，用户在"点了没反应"的窗口里会再点一次：
  - **`doMoveSubmit` 对话框关了、按钮还在**：`:156–170` 在 `await` 期间没有任何 `busy` 之外的界面反馈（`busy` 只 `:disabled` 了按钮，**文案不变**），而 `panel.js:573` 的确定按钮**始终写"确 定"**，与批量操作那三条 `{{ batchBusy ? '处理中…' : … }}`（`:438–440`）不一致。
  - **`doDelete`（单条）完全没有 `busy`**：`:171–196` 没有任何重入保护，菜单虽然先关了，但批量删除按钮/其他入口仍可再次触发同名删除。
  - **标签勾选 `toggleTag` 没有在途保护**（`tags:45–49`）：`点击 A → 点击 B` 时，两次 `save()` 都基于**同一个旧的 `currentTags`** 计算新数组，后返回的那次覆盖前一次——**用户的第一个标签会消失**。这是典型的 lost update。
  - **`openDir` 连点两个目录**：两次请求都写 `nav.entries`（`index.html:487–489`），**没有请求序号**，先返回的后写就会被后返回的前写覆盖——用户在 B 目录看到 A 目录的清单。
  - **`loadContent` 同源**（`content.js:11–45`）：快速切标签时旧响应可覆盖新标签的内容。`panel.js:401` 的 `content.key === activeTab.key` 守卫**只能防"显示错内容"，不能防"新内容被旧内容盖掉"**——因为守卫拦的是显示，不是写入。
- **【证据】** `ops.js:156–170`（无文案变化）、`panel.js:573`（按钮不做态）、`ops.js:171–196`（单条删除无 busy）、`tags:45–55`（无在途保护）、`index.html:477–493`（`openDir` 无序号）、`content.js:11–45`（无序号）
- **【改法】** 按代价分三档，**建议至少做第 1、2 档**：
  1. **统一的"操作中"约定（小）**：凡是会改数据的按钮，在飞行中 `:disabled` **且**改文案为"处理中…"。现成范本就在同一个文件里（`panel.js:438–440`）。涉及 `panel.js:573`、`ops.js:171–196` 的菜单项。
  2. **请求序号（小，收益最大）**：给 `nav` 加一个 `_dirSeq`，`openDir` 里 `const seq = ++nav._dirSeq; …; if (seq !== nav._dirSeq) return`；`loadContent` 同理（`store._contentSeq`）。**约 4 行，消掉两类"内容串台"**。
  3. **标签保存改为"就地替换"（中）**：`toggleTag` 不再基于 `currentTags` 整体覆盖，而是把**单个 tag 的增删**当作一次独立请求（或本地先乐观更新、成功后以服务端返回为准），避免整表覆盖。**第 3 档可缓做**——它是真并发问题，但触发需要用户快速连点。
- **【验收】**
  - 在 200ms 延迟下连点两个不同目录，**列表内容与面包屑一致**（不出现 A 的面包屑配 B 的清单）。
  - 快速连点两个不同标签，**两个标签都在**。
  - 点"删除"后立刻再点一次，**只发生一次删除**，且按钮上能看到"处理中"。
- **【成本】** **小**（第 1、2 档合计约 10 行）/ **中**（含第 3 档）。
- **【与既有条目的关系】** 五份方案均**未提"进行中态"与"请求序号"**。这是本角度（状态管理）独有的一栏。

- **【问题】** 内容区确实有 `error` 态（做对了，见 §3.1），但**它的出口是死的**：`:405` 只把 `content.error` 渲染成一行文字。想重试只有一条极隐蔽的路——标签行右侧 `⋯` 菜单里的"字号"区**下面**（`panel.js:383–396` 里 `reloadActive` 甚至**没有作为菜单项渲染**，`:161` 定义了 `reloadActive` 但模板中检索不到调用点）。
  - 也就是说：**打开一个 200MB 的文件超时/失败后，用户看到的是一句错话，且没有任何按钮**。
- **【证据】** `panel.js:404–405`（错误只有文字）、`panel.js:161`（`reloadActive` 定义）、`panel.js:383–396`（菜单里无该入口；**模板全文已读，确认没有**）
- **【改法】** 在 `:405` 那个分支里加一个按钮「↻ 重新加载」调 `reloadActive()`——**方法已经写好了，只差一个按钮**。约 2 行。
- **【验收】** 打开一个会导致读取失败的文件，**错误文字下面有一个按钮**，点它会重新发起读取（loading → ready/error）。
- **【成本】** **小**（2 行，1 个文件）。

## 7. [存疑] / 未实测项 · 本角度的适用边界

### 7.1 我必须说清楚的边界（这是本报告最重要的一节）

**本轮是纯读代码：没有浏览器、没有截图、没有真人、没有埋点。**

因此，本报告里**每一个"问题"都只证到了一半**：

| 我能证的（代码层） | 我**证不了**的（用户层） |
|---|---|
| 某处源码**没有**进行中态（一句 `v-if` 都没有） | **用户因此多点了一次、或以为卡死** |
| `openDir` 在切回 files 时**没有被调用** | **用户真的会在意列表变空**（他可能顺手点一下目录树就绕过去了） |
| `r.ok` 判定在 8 处缺失 | **接口失败的真实频率**——如果局域网内接口几乎不失败，这 8 处就是"永远不触发的 bug" |
| `.file-table-row` 没有 `tabindex` | **有键盘用户在等这个功能**（很可能一个都没有） |
| 3 秒轮询没有 `beforeUnmount` | 它是否真的在用户切视图后仍在跑（**取决于 Vue 条件渲染是否销毁组件——`v-else-if` 链是销毁的，但我没实测**） |
| 收藏失败被静默 | 收藏接口**实际会不会失败** |

**所以：本报告所有条目的"优先级"是我按"代码里能证的严重度"排的，不是按"用户撞上的频率"排的。** 这与五份顾问方案面临的是同一个缺口——`00-汇总与拍板建议.md` 第 6 节把它写成"五视角共同的盲区"，我完全同意，并在此**第 6 次**诚实地重复一遍。
