## 0. 一句话结论

**迁前音视频**（`.mp3` / `.mp4` / `webm` / `mkv` …）**没有任何预览**：`kindOfExt` 一律回 `unknown`、`preview-raw` 的 mime 表里一个音视频扩展名都没有 ⇒ 界面上只能得到一句"该文件类型不支持在线查看"。本批按 nowen-note 的做法补齐，**分三层**：

1. **后端认媒体**：`file-exts.ts` 新增 `AUDIO_EXTS`（8 项）/ `VIDEO_EXTS`（10 项）/ `MEDIA_EXTS`（18 项，= 两者之并），`kindOfExt` 多一个 `'media'` 取值；`preview-raw` 的 `mime` 表补齐 18 条，**键集有断言钉死**。
2. **Range 才叫能播**：给媒体单开一条分支 —— 整段带 `Accept-Ranges: bytes` 流式下发；带 `Range` 就回 **206 + `Content-Range`**；三种坏区间回 **416 + `Content-Range: bytes */total`**。**图片 / PDF 一个字节都没动**（同一套区间用例对它们发过去，实测仍是 200 整段，§3.1 ④）。
3. **前端原生播放 + 诚实兜底**：`<video controls preload="metadata">` / `<audio …>`，**绝不** fetch 成 Blob（会丢 Range/206）；对"多半播不了"的容器（`mkv/avi/mov/qt/3gp/3g2`）画**兜底说明 + 下载入口**，既不是黑屏、也不是一句含糊的"不支持"。

**最容易做错、本批专门立断言钉住的那一处**：`total` 必须是**明文长度**。盘上是 `PHENC1` 密文（20 字节头 + 16 字节 tag），拿 `stat().size` 当 total **一个字节都不报错**，只是**浏览器算出的偏移整体错位、从头就播花**。阴性对照 NC-A 把这一行换回去 ⇒ 8 条断言变红（含 `Content-Range` 里露出的 `bytes */4132`）。

- **两条既有断言的期望值被改**（用户显式授权，逐条见 §3.1）：`tests/file-exts.mjs` 的分类用例 `['a.mp3','unknown'] → ['a.mp3','media']`；`preview-raw` 的 mime 键集 `IMAGE_EXTS ∪ {pdf}` → `∪ {pdf} ∪ MEDIA_EXTS`。**这是本批唯一动过的既有断言**，两条都**只会更严**。
- 不动 manifest / 插槽 / 打包链 / 数据格式；`data/`、`data-files/` **只读**；版本号 **3.1.3 不动**。
- **本批经用户明确授权执行了 git 提交与推送**（原话见 §6.1）—— 这是与 16 批不同的一处，说明写在 §6。

> ⚠ **"看着对不对"一律未实测**（§5）：仓库里没有浏览器测试、前端走 CDN ⇒ 本批能证明的是**协议层行为**（状态码 / 头 / 逐字节内容）、**面板模板能编译**、**分类与标签分派的口径**。**哪几种容器在真实浏览器里真能放出来、兜底支路长什么样、进度条拖拽顺不顺**，这一层**判不了**。

## 1. 动机

用户原话（2026-10-09，紧接 16 批之后）：

> 「ok，改进方法我建议你参照nowen-note的方法来进行改进」

要改的是**迁前就存在的空洞**（不是新需求）：`file-exts.ts` 里当时有一行备案写着"音视频——**故意不做**"。现在做掉，并且做成 nowen-note 那样**两层分开**：

| 病根 | 为什么危险 |
|---|---|
| 后端根本不认媒体：`kindOfExt` 回 `unknown`、mime 表无媒体键 | 界面只能给出**与"坏文件"同一句**文案。用户拿到的是"不支持"，**没有任何出路**（连"下载后用播放器打开"的入口都没有） |
| 没有 `Range` 支持 | `<video>` 拖进度条发的是**字节区间**请求；回不了 206 就只能**整段下载完**才允许 seek —— 几十 MB 的文件表现是"点了播放半天不动" |
| 密文 + `stat().size` 当 total（本批新引入的风险点） | 密文盘上比明文多 36 字节。用盘上长度当 total，**浏览器告到服务端的区间全部偏移 36 字节**：不报错、不 416，只是**画面/声音全花**。这是本批最需要断言兜住的一条 |
| 若照抄"能播的都直接上 `<video>`" | 浏览器解不了 `mkv/avi/mov` 这类容器 ⇒ **黑屏**（nowen-note 的原话：宁可降级到"下载提示"也不要黑屏） |

## 5. 未实测 / 判不了的（如实列）

1. **哪几种容器真能放出来，一律未实测**：本仓没有浏览器测试、没有真实媒体样件。`NATIVE_VIDEO_EXTS = ['mp4','m4v','webm','ogv']` 是**容器层面**的保守估计；`mkv` 里装 H.264 在部分浏览器其实能放，但**编解码器不一概而论**，故不放进白名单（宁可画兜底说明）。**"mp4 在用户那台机器上确实能放"这件事，本批没有证据链**。
2. **兜底支路与播放器的观感未实测**：那段说明在界面上长什么样、`<video>` 在铺满布局里高度怎么算、`audio` 的 560px 上限够不够 —— 一条都没看过。仓库里没有浏览器 ⇒ 能证明的只有"模板能编译 + CSS 落到了盘上"。
3. **nowen-note 的字幕 / poster / MediaExperienceBridge 有意没做**（§2.1）：视频没有封面图、没有字幕轨道。用户若需要，是另开的增强项。
4. **部分区间的密文读取是"未认证"的（如实说明，不是疏忽）**：GCM 的 tag 在文件末尾，**只有读到 EOF 才能校验**。带 `Range` 的响应校验不了完整性和真实性 —— 中段密文被改坏时，用户可能拿到**乱码字节**而不是一个错误。整段（无 `Range`）读取会自然走到末尾 ⇒ tag 校验生效。这条**写进了 `svc-storage` 的 `readRange` 注释**，不是本报告才补的。
5. **大文件未实测**：本批探针一律 **4096 字节**。整段走 `createReadStream` 流式（不整读进内存，这是**源码事实**），但"200 MB 的视频能不能流畅拖进度条""密文跳过前 N 字节的 CPU 成本在 N=100MB 时什么表现"**都没测**。`readRange` 的成本是 **O(end)**（按偏移线性），这是加密格式决定的（密文不可随机 seek）——`【推断】`：体验上"越往后拖越慢"，本批**未复现**。
6. **`Range` 与 `If-Range` / `ETag` 的配合没做**：nowen-note 提过 `If-Range`（文件变了就别拿旧区间）。本批的取向是**不做**：区间读不出来时回 416，浏览器会重发一次不带 `Range` 的请求（能自愈，见 `files/src/index.ts:169-174` 的注释）。**"自愈"这条路径未实测**（没有浏览器）。
7. **HEAD / OPTIONS 未做方法闸**：`preview-raw` 本来就没有方法检查（HEAD 由 Node 自行丢弃响应体），本批沿用，未加。
8. **观感的最后一层——"点开一个 mp4 到底出不出画面"——必须由人来点一次**。本批能给的最强结论是：**协议层（状态码/头/字节）与分类层（kind/mime/标签分派）都实测过了**，前端模板能编译，`answer.url` 直接交给 `<video src>`（**没有 Blob 中转**）。
9. **生产实例未部署**：本批只跑隔离实例与静态检查；**未跑 `scripts/build-deploy.ps1`、未碰 `deploy/`**（与 16 批同一条）。`【推断】`：生产要生效需按部署脚本走一次；本批未做。
