> 编制：萧潇｜日期：2026-09-20｜源码基线：v3.1.1（版本号唯一来源 `privhub/package.json`，本批**未新开版本号**）

## 0. 一句话结论

**「有些文件无法打开」的主因不是缺库，而是三件事**：① **五份各自维护的扩展名白名单互不一致**（同一份 `.markdown` 在全文索引里有、在预览里没有；`.ts` 在预览里有、在版本快照里没有）；② **旧版 Office 有两个硬缺口**（后端 `OFFICE_EXTS` 里**根本没有** `.xls` / `.ppt`）；③ **`.doc` 明明解析失败却报「成功」**，界面把一个"兜底提示句"当正文显示——用户看到的就是"打不开"。
铺满问题已按既有范式修好：**新增一个宿主自己的形态状态类 `.v3-content--fill`**，状态由宿主自己派生、规则写在宿主自己的样式里，**插件零参与、契约形状零改动、骨架零改动**。

### 2.5 三条**实测**发现（都可复核，且都指向具体行号）

**① `.ico`：前后端两张图片清单不一致 ⇒ 图片走了 iframe 分支**
后端 `imgExts` 含 `ico`（`privhub-core/src/index.ts:769`），前端 `kindOf` 的图片清单不含（`utils.js:11`）⇒ 实测前端渲染分支 = **`iframe.v3-pdf`**（本该是 `img.v3-img`，因此**没有点击放大**）。
修法是一行：`utils.js:11` 的图片数组补 `'ico'`。**本批没改**（这属于"能力/格式"改动，不是布局改动；本批只做了"铺满判据不挂在 kind 上"，让它在当下也铺满）。

**② `.doc`：解析失败却返回 `ok:true`，界面把"兜底提示句"当正文显示**
`privhub-svc-office/src/office-lib.mjs:31-66` 的 `readDoc` 是三级链：`word-extractor`（真 .doc）→ **Python 兜底 `scripts/doc2md.py`** → 兜底文案。实测（隔离实例把 `scripts/` 也链进去之后）：

```
hand-rtf伪装.doc  43B  → /office/read ok kind=doc，提取正文 42 字 = 「[无法提取 DOC 文本]（请用 Word/WPS 打开后另存为 docx 再上传）」
hand-s.doc       512B  → /office/read ok kind=doc，提取正文 42 字 = 同上
```

**并且**【实证】本机的 `python.exe` / `python3.exe` **只是 Microsoft Store 的占位别名**（`C:\Users\Administrator\AppData\Local\Microsoft\WindowsApps\python.exe`，执行即提示"Python was not found"）⇒ **第三级 Python 兜底在这台机器上永远不会工作**。这就是"用户数据里那 41 个测试 .doc 全都打不开"的完整机制（另 1 个真 .doc 是否可读见 2.5 第②条末尾的【未实测】说明）。
> 这一条**不是布局问题、也不是缺库问题**，是本批最有价值的发现：它同时解释了两个抱怨（"有些文件无法打开" + "格式兼容性"）。
> **本批未修**（属功能改动，需主子点头；建议见 §3.3 第①条）。

**③ pdfkit 生成的 PDF 被 `pdf-parse` 判为 `bad XRef entry`**
实测：`gen-pdf.pdf`（pdfkit 0.15 生成，1333B）→ `/office/read` = `fail: 解析失败: bad XRef entry`；而真身样本 `real-pdfparse.pdf`（80,953B）→ `ok kind=pdf, text 20213 字`。
**对阅读无影响**（前端 PDF 走 `iframe` + `/preview-raw`，不经 `office/read`）；**对 RAG / 全文抽取有影响**（`privhub-svc-rag` 用同一条 `office.read` 链）。【推断】pdf.js/pdfs 系解析器对某些 xref 写法严格；建议日后用更多真实 PDF 复核后再决定是否换解析器。

## 3. 可补的库 / 插件（全部按「无打包链 + 纯 ESM 或预构建 vendor 文件」这个形态评估）

**先记住两条项目已验证的合法套路**（两者都被本项目在用）：

1. **`<script src>` + 预构建 UMD**：`office2` 把 `univer.bundle.js`(10.47MB)、`docx-preview.js`(0.07MB)、`jszip.js`(0.09MB) 放在自己 `client/vendor/` 下，由自己的 `view.html` 引入（【实体】实测该目录 4 个文件）。**插件目录内的所有文件都由宿主静态服务** ⇒ 天然满足硬约束 3（卸载=删目录、零残留）。
2. **纯 ESM 直接 `import`**：项目本身就是这个形态（浏览器 `import('/privhub-plugins/<插件>/index.js')`，模块间相对 import）。**多文件 ESM 只要同在一个插件目录里就能直接跑**，不需要打包。

> ⚠️ 一条**必须点明**的张力：**重新构建那 10.5MB 的 `univer.bundle.js` 需要一个外部构建步骤**。预构建产物（vendor）不违背"无打包链"，但"为了加 pptx 而重打一份 bundle"在流程上等于引入构建链 —— 这一点在 §3.3 第④条里我明确标为**不建议现在做**。

**① 把「纯文本白名单」补齐，并顺手把它收敛成一处**（0 字节、0 依赖）

**② 音视频走原生标签**（0 字节、0 依赖）

- 顺带要补 `/preview-raw` 的 mime 表（`privhub-files/src/index.ts:90-93`）。

**③ fflate（33KB，MIT）做「容器类只读预览」**
- 一次覆盖 `.zip`（列目录 + 单文件预览）+ `.odt/.ods/.epub`（抽正文）+ 可作 `.docx/.xlsx` 的兜底读法。
- 33KB 是整个候选表里最便宜的一项，**MIT 干净**，`umd/index.js` 可直接 `<script src>`，也提供纯 ESM。
- 落地形态：建议做成**一个独立插件**（自包含、可整体装卸），而不是塞进 explorer-v3 —— 但要知道这是**新插件**（目录 + manifest + `viewers.register` 一条声明），不是改一行。

| 不做 | 理由 |

## 5. **[未实测] / 只能实机看**（本批最要紧的免责项）

**这份仓库里没有任何浏览器测试**（`tests/run-all.mjs` 跑的是 HTTP 套件 + "在 Node 里 import 前端模块 / 编译模板"的静态套件）。所以下面这些**我一条都没验**，必须由主子在真机上看：

1. **铺满之后的真实观感与尺寸**：图片在**竖图/横图/超宽图/超长图**四种比例下是否真的"居中且不超出"、`max-height:100%` 在真实 flex 布局里是否按预期解析（我推断成立：`.main` 是 `display:flex; flex-direction:column`，`.v3-content` 有确定高度 ⇒ 子元素百分比高度可解析；**但没在浏览器里看过**）。
2. **PDF 在真机上的高度**：去掉 `calc(100vh-260px)` 后，浏览器内置 PDF 阅读器在 iframe 里是否**正好铺满**、会不会出现**内层滚动条与外层滚动条打架**、`overflow:hidden` 会不会把 Chrome PDF 查看器自带的侧栏/工具条裁掉一部分。**这一条最需要实机看**（我对 Chrome PDF 查看器在受限 iframe 里的行为只能推断）。
3. **深色主题下的 PDF**：PDF 页面是白底，去掉内容区自绘背景后，深色主题下"白页 + 深色留白"的对比观感。
4. **切换瞬间的闪烁**：从 md 切到图片/PDF 时，类名由 `v3-content` → `v3-content--fill` 是否有一帧可见的布局跳动（`fillLayout` 是响应式 data，理论上与内容同帧，但**没实测**）。
5. **lightbox（点击放大）**：`@click` 与光标形状未改，理论上不受影响；但它与新的 `img` 尺寸规则是否互相干扰（例如放大后关闭回到"铺满"状态）**没实测**。
6. **`.v3-img-wrap` 的兜底**：铺满形态下的 flex 居中与"非铺满时 `text-align:center`"这两套规则是否有某一刻同时生效导致居中错位。

## 6. 我这个角度的适用边界

- 我这轮看到的是**"从接口到界面状态"这条链**，看不到的是**渲染出来的像素**（见 §5）。凡涉及"好不好看、挤不挤、闪不闪"，我的结论一律是推断。
- 矩阵覆盖 **58 个扩展名 / 63 个样本**，但**每个扩展名基本只有一个样本**（少数两个）。真实文件里的**变体**（加密 PDF、扫描件 PDF、带宏的 .doc、多页 TIFF、分段 mp4、加密 zip）**没有覆盖** —— 这些正是"同一个扩展名有的能开有的不能开"的常见来源。
- 真实语料我**只读了文件名与体积**（只读扫一遍扩展名分布），**没有读任何文件内容**，也没有解密任何数据。所以"用户撞到的是哪一类"属于**推断**（依据是扩展名分布 + 实测到的机制），不是实证到具体文件。
- 候选库的**体积与许可证是实测的**（npm registry + 解包量过），但**"接进去之后好不好用"没有验**：fflate 解 epub 的容错、utif 解真实扫描件 TIFF 的成功率、pptx-preview 的保真度、heic2any 在真实 iPhone 照片上的耗时 —— 这些都要**先做原型再定**。凡我给 ★ 的评级，都是"成本/收益"的判断，不是"已验证可用"的结论。
