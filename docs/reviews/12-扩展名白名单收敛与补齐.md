## ① 一处定义放在哪、为什么；每个用途各自派生成什么、为什么这么派

### 一处定义：`privhub-core/src/file-exts.ts`（**新文件**）

**为什么放 core**：本项目既有惯例就是「插件用相对路径 import `privhub-core/src/index`」（【实证】`files-fulltext/src/index.ts:25`、`files-versions/src/index.ts:18` 等）；`privhub-core` 是唯一持有共享状态的枢纽插件，`src/` 下多一个**纯逻辑、零依赖**的文件不改变任何装配顺序。基础集合只写一次：

| 集合 | 取值（【实体】） |
|---|---|
| `TEXT_EXTS` | `txt md markdown json jsonl js ts tsx html htm css xml yaml yml toml ini conf csv tsv log sql py java c cpp go rs sh bat ps1 vue ipynb env`（33 项） |
| `IMAGE_EXTS` | `png jpg jpeg gif webp svg bmp ico`（8 项） |
| `MARKDOWN_EXTS` | `md markdown` |
| `OFFICE_EXTS` | `doc docx xlsx pptx pdf`（与 `privhub-svc-office/src/index.ts:22` 同值） |

判定入口也收在这里：`normExt` / `extOfName` / `kindOfExt` / `isPreviewTextExt` / `isImageExt` / `isMarkdownExt`，以及集合工具 `minus` / `union`（`minus` 减到不存在的名字会**当场抛错**，见 ⑤）。

### 逐用途派生（**没有合并成一个大集合**——各用途语义本来就不同）

| 用途 | 派生式（**显式**） | 消费方（改后） | 为什么这么派 |
|---|---|---|---|
| **预览** | `PREVIEW_TEXT_EXTS = TEXT_EXTS ∪ EDITABLE_TEXT_EXTS` | `privhub-core/src/index.ts:753`（`readFileForPreview`） | 最宽的一份：只问「字节是不是纯文本」，不问「能不能编辑」。并集 ⇒ 不会出现「能编辑却打不开」 |
| **全文索引** | `VERSION_TEXT_EXTS = PREVIEW_TEXT_EXTS − ENV_EXTS` | `files-fulltext/src/index.ts:36` | 「进索引」比「能打开」代价高、且错的进索引会污染检索；配置族 `.env` 是密钥载体，不进索引 |
| **版本快照** | 同上（**同一份**） | `files-versions/src/index.ts:44` | 索引与快照要覆盖的范围本来就该一致（迁前两者不一致：23 项 vs 17 项） |
| **向量化** | `RAG_TEXT_EXTS = PREVIEW_TEXT_EXTS − (ENV_EXTS ∪ RAG_EXCLUDED_EXTS)`，`RAG_EXCLUDED_EXTS = jsonl tsv ipynb` | `svc-rag/src/index.ts:52` | 进向量库还要切块+embed+落库，代价最高；`.jsonl`/`.tsv` 是逐行记录与表格（切块语义稀碎）、`.ipynb` 是 JSON 结构体（正文散在 `cells[].source`）。**迁前就不在，本批保持现状**（属产品判断，不替主子决定） |
| **智能体读写** | `files-agent` 的 `TEXT_EXT = TEXT_EXTS − SENSITIVE_EXTS`（敏感族清单**仍留在** `files-agent/src/index.ts:41`，本批未搬） | `files-agent/src/index.ts:47` | 能力与预览同等，但**敏感文件豁免**；语义没变（`TEXT_EXT` 只用于「写覆盖时走快照还是 `.bak-` 备份」的分流） |
| **智能体覆盖前快照** | `AGENT_SNAPSHOT_EXTS = EDITABLE_TEXT_EXTS` | `files-agent/src/m2.ts:310` | 单列一份，因为**它比 versions 窄**（智能体写的是沙箱，非快照类型走 `.bak-` 备份，是既有分级）。与迁前 17 项手写清单只差 `html`（`html`/`toml`/`java`/`c`/`cpp`/`htm` 按「不扩权」留在不做快照那一侧） |
| **界面分类（图片/Office/Markdown）** | 前端 `EXT.IMAGE_EXTS` / `EXT.OFFICE_EXTS` / `EXT.OFFICE_KIND_EXTS(=Office−pdf)` / `EXT.MARKDOWN_EXTS` | `utils.js:26-33`；`panel.js` 的 `isOfficeFile`、`ops.js` 的右键编辑分支 | 前端只能拿到**投影**，见下 |
| **界面可编辑** | `EDITABLE_TEXT_EXTS`（前端 `EXT.TEXT_EDIT_EXTS` 与 `edit-md` 的 `EDITABLE_TEXT_EXTS`） | `utils.js:36`、`edit-md/client/index.js:176` | **有意比预览窄**：本批只补【预览】，不新增编辑入口。`md` **必须留在里面**（`edit-md` 的 `openEditor()` 第一句就是这道闸，拿掉会让「右键 .md 选编辑」点了没反应）；`html`/`htm` 预览出源码，给编辑入口会误导 |

### 前端怎么办（**硬约束逼出来的，不是偷懒**）——这是本批唯一"一处定义要分两侧"的地方

后端 import 走得通，**浏览器侧走不通**，两条独立证据：

1. **静态服务映射只到 `client/`**：【实体】`src/web-server.ts:191` 的正则 `/^\/privhub-plugins\/([^/]+)\/(.+)$/` + `:211` 的 `join(base, pluginName, 'client', file)` ⇒ `/privhub-plugins/<插件>/src/…` 一律 404；
2. **`tests/integrity.mjs` 有既有硬断言**：【实体】`tests/integrity.mjs:379-389` 要求 `explorer-v3` 的 client 模块**只引用同目录文件**（`escapeHits` 必须为 0）。

我还实测排除了"绕出去"的两条路（所以没走）：
- **`../../../privhub-core/src/file-exts.ts` 这种相对 import 到别的插件**：【实证】`new URL('../../../privhub-core/shared/file-exts.js', 'http://…/privhub-plugins/privhub-files-explorer-v3/client/utils.js')` 在 WHATWG 规范下会被折叠成 `/privhub-core/shared/file-exts.js`（浏览器同规范）⇒ 必然 404；
- **`.ts` 直接给浏览器**：【实体】`src/web-server.ts` 的 `MIME` 表没有 `.ts` ⇒ 回落到 `application/octet-stream` + `x-content-type-options: nosniff` ⇒ 浏览器拒绝执行。
- 全仓**零**跨插件 client import（【实证】对 `plugins/*/client/*.js` 搜 `from '../` 命中 0 处），**不新开这条先例**。

⇒ 于是前端侧的做法是「**每侧一份单点定义 + 一致性由断言钉住**」，并在 `file-exts.ts` 文件头「前端怎么办」一节写清；两侧取值**逐项同值**由 `tests/file-exts.mjs` 第②③组断言守着（`.ico` 那次不一致就是这么被抓住并复验的）。

## ⑤ 防漂移断言 + 阴性对照真实输出

### 断言做法：`tests/file-exts.mjs`（**59 条**，5 组 + 1 组 mime 键集）

| 组 | 做法 | 为什么这样才"会红" |

| ③ 前端两份可编辑清单一致 | `edit-md/client/index.js` 的 `EDITABLE_TEXT_EXTS` 与 `utils.js` 的 `EXT.TEXT_EDIT_EXTS`、又与后端 `EDITABLE_TEXT_EXTS` 三方比对 | 迁前这两份"靠注释互相提醒"，现在靠断言 |
