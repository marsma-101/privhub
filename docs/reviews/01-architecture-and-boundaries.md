# 01 · 架构与边界

> 评审角度：**系统切成哪些块、每块的边界在哪、块之间怎么连、依赖朝哪边流**

## 1. 一句话结论

**块切得基本没错，错的是块与块之间的缝：所有块间契约都以「字符串 + 手写名单」的形式散落在调用点。**

一处功能，要同时对上 5 份手写名单：装配名单 17 项（`main.ts:46-51`）、后端路由 113 条、权限裁决白名单 37 条（`admin-acl:57-119`）、骨架视图白名单 14 个（`index.html:748-764`）、骨架硬编码的插槽渲染分支 27 条（`index.html:997-1094`），外加前端 187 处 `/privhub/api/` 字面路径。

于是「新增一个插件」的真实成本**不是建目录**（文档承诺的 `插件实现规则.md:320`「无需改骨架一行代码」），而是**找齐所有名单并同步**；而漏改一处**不报错**，只表现为某个入口静默失灵。这不是 50 个插件切错了，而是**缝没有单一真源**。

## 3. 现状判定

### 3.1 做对了的

1. **「目录即插件」的发现式装配真的成立。** 前端插件代码从不写回主页面，装配由服务端扫目录决定：`shell/server/index.ts:42-76` 现场扫 `client/manifest.json`，`index.html:832-868` 按清单 `import`，卸载 = 删目录。我实测 32/31/41/28 与交底口径完全吻合——**这套机制是这个项目最值钱的资产**。
2. **import 层面的依赖是干净单向量、无环。** 全仓 29 处跨插件 import 只有两个目标：`../../privhub-core/src/index`（27 处）与 `../../privhub-svc-audit/src/index`（2 处，且是 `import type`）；没有任何 `A→B→A`，也没有插件反向 import 宿主 `src/`【实证·三方勘察，我抽验了 `shell/server/index.ts:12` 的 `tokenOf` 与 `admin-acl:40` 的 `json/readBody/tokenOf`，成立】。
3. **已知的循环依赖被显式识别并留了注释规避。** `web-server.ts:91-96` 与 `main.ts:190-194`：`core inject webServer`，若 webServer 反向 inject `privhub` 即成立环，于是改成宿主在 `privhub.ready` 之后注入一个校验闭包。**这是本项目里唯一一处"用依赖反转解决环"的正例**，且注释写清了原因。
4. **`files-explorer-v3` 的模块拆分是这个项目里最规范的先例。** `client/index.js:1-39` 只是装配入口（39 行），并在 `:19` 明确写出**单向依赖链**：`deps → utils → store → {content, tabs} → ops → tree → panel → 本文件`；`store.js:1-27` 只放状态、`deps.js` 收敛外部依赖。**E2「大文件拆分」的 explorer-v3 部分实际已完成**（账本仍标 ⬜，建议更新）。
5. **插槽机制在"同槽多组件"上是对的。** `index.html:841` 用数组累积，`office-editor` 槽有 8 个插件共存（office2 / office-ui / versions / comments / invite / publish / mdpage / dataview），这是**唯一一处真正做到"多插件扩展同一位置"的扩展点**。

### 3.2 做错了的

**（A）L1「六枢纽各提供一个域 Service」不成立——三层里的 L1 名不副实。**
文档开篇的设计哲学①写「6 枢纽各提供一个域 Service（`privhub`/`auth`/`admin`/`files`/`trash`/`shell`）」(`插件架构.md:15`)。实测：全仓只有 11 个真实服务注册点，L1 里**只有 `core` 注册了 `privhub`**（`core/src/index.ts:303`），`auth`/`files`/`trash`/`admin`/`shell` **一个都没注册成 Service，也无人 inject**（命令实证：0 次）。
⇒ L1 这层里其实装了三种不同的东西：①纯状态服务（core）②带内置界面的域插件（auth 有登录框、admin 有 `view:admin` 图标栏入口）③页面外壳（shell）。**它们被归为同一层，是因为一起被写出来，而不是因为接口性质相同。** L2 才是名副其实的一层（10 个真服务）。而 L1 与 L3 的实际分界线，就是 `main.ts:46-51` 那 17 个目录名。

**（B）三处依赖倒挂，全部不以 import 表达（所以静态检查看不见）。**

| 倒挂 | 证据 | 方向 |
|---|---|---|
| `admin-acl` 硬编码 10+ 个别家插件的路由路径 | `admin-acl:57-119`（37 条，含 files/trash/versions/comments/office/mdpage/dataview/publish） | 治理方 → 被治理方的**内部路径** |
| `admin-acl` 直接操作 `webServer` 的**私有** `routes` Map | `admin-acl:124-126`（强转取 `routes`）、`:193-196`（还原时直接改写） | L2 → 宿主的私有状态 |
| `auth`（L1）读 `data/settings.json`，而该文件由 L3 `shell-settings` 加密写入 | `auth/src/index.ts:30-42`（路径硬编码在 `:31`，注释 `:21-22` 自陈"由 shell-settings 加密落盘"） | L1 → L3 的**数据格式** |
| 多插件直读写别人的 `data/*.json`（`files-agent` 写 `versions.json`、`git-backup` 硬编码 16 个插件的数据文件名） | 子智能体实证（**我未亲核**，标【实证·三方勘察】） | L3 ↔ L3 数据文件 |

**（C）横切关注点（权限裁决）没有落点，只能靠"名单 + 猴补"。**
`admin-acl:180-200` 把 `svc.route` 整个换掉（`origRouteFn` → `wrappedRoute`，`ctx.effect` 卸载时还原），配合 `:57-119` 的路径名单决定哪些路由受管辖。三个后果：①**必须先挂载**，否则它管不到后来注册的路由——这条顺序只由 `main.ts:39` 的一句注释保证（`main.ts:167-168` 确实排在 auth/files/trash/admin 之前）；②名单漏一条就是**静默透传**（`admin-acl:134-135`：`if (!methods) return handler`），这正是 `改进建议` F2 记录的"37 条白名单 vs 113 条注册"漂移的**结构性原因**；③它读写了宿主的私有状态，而 `web-server.ts:142-148` 的路由表**没有任何所有权与冲突检测**。

**（D）前端纵向入口是宿主的闭集——这是本视角下最"名不副实"的一处扩展点。**
`index.html:748-764` 的 `openBarItem` 里是 14 个**硬编码字符串**；白名单之外的 `view` 点了**什么都不发生**（函数无 `else`，无日志、无 toast）。渲染侧同样硬编码：`:997-1094` 有 **27 条** `<component v-for="c in slotComps['某名字']">` 分支，每条都要再对一次 `nav.activeView === '某名字'`。
⇒ 插件声明 `slots:[...]` 与 `barItems[].view` 看起来是"声明式扩展点"，但**取值域被宿主封闭枚举了**：新插件只有落进这 14 个 view / 27 个插槽名才"存在"，否则要改 `index.html` 两处。
**必须说清的一件好事**：我实测 14 个 `view` 与白名单**当前完全对齐**（无死图标、无死分支）——所以这是**潜在**风险，不是**正在**发生的故障。但代价是：任何新纵向入口都要动宿主。

**（E）4 个插槽骨架根本不认，整张注册表被透传给一个插件。**
31 个插槽里，骨架渲染 27 个（28 条分支含一条已退役的 `tabs`），剩下 4 个（`admin-settings`/`admin-tags`/`admin-template`/`admin-trash`）在 `index.html` **没有任何渲染分支**，而是由 `:1049` 把整张 `slotComps` 注册表当 prop 交给 `privhub-admin-console`，由它自己挑着渲染。
⇒ 插槽契约出现**第二个消费者**，且这个消费者拿到的是"全量注册表"——等于把宿主的渲染决定权外包给了一个普通插件。这是全项目边界最模糊的一处。

**（F）`shell` 过载，且它其实不可卸载。**
`shell` 同时承担：①服务端 manifest 聚合 + 未登录分级返回 + view 冲突检测（`shell/server/index.ts:42-76,99-107`）②客户端 4 个骨架组件（`client/index.js:161-166`）③图标栏容器 + **分组白名单**（`client/index.js:76` 写死 `['settings','admin','acl','audit']`、`:81` 写死 `['admin','settings']`）④高亮判定里又写死 4 个业务视图（`:85-94` 的 `files`/`trash`/`search`/`favorites`）。
更关键：`index.html:997-1024` **硬编码了它的 4 个插槽名**（`project-tabs`/`user-area`/`app-iconbar`/`welcome`）。删掉 `privhub-shell` 目录，图标栏容器就没了——**"删目录即卸载"在这里不成立**。它在事实上是**宿主的一部分**，只是住在 `plugins/` 里。

**（G）同一条安全判据被两处各自实现，且判据是"未校验的自述字段"。**
「未登录时放行哪些插件的静态资源」在两处各写了一遍：`web-server.ts:120-139`（`authSlotDirs()`，按 `manifest.slots` 是否含 `auth`）与 `shell/server/index.ts:99-107`（同样按 `slots.includes('auth')` 过滤清单）。`web-server.ts:115` 的注释自己承认这是"**同一条判据**"，理由是"避免两处规则漂移"——**但它的做法是复制一份，而不是共用一处**。
更值得记一笔：`privhub-shell/client/manifest.json:6` 声明 `"slots": ["auth", ...]`，而 `shell/client/index.js:161-166` 导出的 slots 里**没有 `auth` 组件**。也就是说判据是"插件自己说的"，不是"插件真做了的"——`shell` 因此也进了免登录放行集合。今天只有 2 个插件在放行集合里（`auth`、`shell`），危害有限；但**判据没校验**这件事本身，是"名单病"的又一处。

**（H）路由注册没有所有权，且 disposer 是错的。**
`web-server.ts:88` 用 `Map<path, handler>`、`:142-148` 的 `register` 同路径**后注册直接覆盖**（无告警）、`_label` 参数被丢弃、返回的 disposer 只做 `routes.delete(path)`。
⇒ 若两个插件声明同一路径：后者的 handler 生效（静默），前者卸载时会把**后者的路由删掉**。今天 113 条路径去重后仍是 113（无重复），属潜在缺陷；但"插件边界"这件事在传输层**没有任何强制**：没有命名空间、没有归属校验。

**（I）契约漂移的零碎证据（顺手记录，便于对账）。**

- `index.html:1052` 与 `:1057` **两行条件完全相同**（`nav.activeView === 'admin' && slotComps.admin…`）⇒ `:1057` 是死代码（我亲自比对两行）。
- `插件实现规则.md:133` 说"当前实际 **13 个 view**"，我实测 **14 个**（多一个 `agent`）。
- `改进建议` E8 说骨架仍渲染退役的 `tabs` 插槽，行号记在 `:876`；实际已漂到 **`:1029`**（内容仍成立，行号需更新）。
- `插件实现规则.md:324` 承认 L1/L2 必须手工登记进 `CORE_PLUGINS`——**文档自己写了"两套规则"**，E1 已报，此处仅作交叉印证。

### 3.3 我看不出来的

## 4. 改进建议

### 4.1 先答七问（本视角规矩：答不全不动手）

**① 系统由哪些块组成？**（按"实际接口性质"而非按目录名重列）

| 块 | 一句话职责 | 现有名字 |
|---|---|---|
| **宿主** | 起 HTTP 服务、静态与插件资源映射、装页面骨架与总线、装配所有插件 | `src/main.ts`、`src/web-server.ts`、`frontend/index.html`（1130 行，**不属于任何插件**） |
| **状态服务** | 唯一持有账号/会话/回收站/文件根与权限判定 | `core` → `ctx.privhub`（32 个插件在消费） |
| **能力服务（10）** | 被多方复用的无界面能力：存储/事件/审计/ACL/水印/检索/元数据/协同/Office/模型 | `privhub-svc-*` |
| **域插件（带界面）** | 自带界面的域成员：登录框、用户管理 | `auth`、`admin` |
| **页面外壳** | 顶栏/用户区/图标栏容器/欢迎页（**事实上的宿主组件**） | `shell` |
| **功能插件（约 30）** | 一块用户可感知的功能，占一个插槽或几个视图 | `privhub-files-*`、`shell-*` 等 |
| **纯前端壳（7）** | 只有 `client/` 没有服务端（`admin-console`、`trash-ui`、`files-upload`…） | 无 `src/index.ts` |
| **归档** | 不参与装配 | `_retired-v2`（`main.ts:63` 按 `_` 前缀跳过） |

**② 边界表（每块负责什么、明确不负责什么）**

| 块 | 负责 | **明确不负责** | 现状偏差 |
|---|---|---|---|
| 宿主 | 装配、传输、静态、CSP、页骨架与桥 | 不含任何业务规则 | **它其实含业务规则**：`openBarItem` 的 14 个视图名、图标栏分组、27 条插槽渲染链都是"业务分发"写在宿主里 |
| `core`（`ctx.privhub`） | 账号/会话/文件根/权限判定、路由注册入口 | 不写业务功能；不暴露 HTTP 面（文档 `插件实现规则.md:192`） | 尚可。但 `route()` 把"注册"与"裁决"混在一起（见 P0-3） |
| 能力服务 | 提供 `ctx.<key>` 方法 | **不注册面向用户的界面** | `svc-rag` 破了这条（有自己的 `rag-view` + 2 个图标） |
| 域插件 `auth`/`admin` | 登录、用户与项目管理 | 不应被别的插件当**数据源** | `auth` 打破了：它读 L3 的 `settings.json`（`auth:30-42`） |
| 页面外壳 `shell` | 骨架组件 + manifest 聚合 | 不应认识任何**具体插件名** | 破了：`client/index.js:76,81,85-94` 写死了 6 个插件名/视图名 |
| 功能插件 | 一块功能 + 自己的前端在**自己目录内**（约束 3） | 不碰别人的 DOM（约束 5）、不直读别人的数据文件 | 三处破了（见 §3.2 B/D/E） |
| 传输层 `webServer` | 路由表、静态、请求体上限 | **不应知道插件的目录约定** | 破了：`web-server.ts:120-139` 扫 `client/manifest.json` 判放行 |

**③ 块之间怎么连？（四条缝）**

1. **服务注入**：`ctx.<key>`，11 个真实服务；**通道窄且好**（唯一被普遍消费的是 `privhub`）。
2. **HTTP 路由**：113 条精确路径，**前端与后端之间唯一接口面**（前端 187 处字面路径）。这是**当前最主要的连接方式**，也是契约最弱的一处（无清单、无类型、无命名空间）。
3. **前端总线 `bus`**：跨插件的正解（`trash:changed`、`entry:open`、`md:changed` 等，【实证·三方勘察】给出了完整收发矩阵）。**方向健康**。
4. **插槽 + `window.PrivHub` 桥**：插槽 31 个（27 个骨架认、4 个外包给 `admin-console`）；桥有 26 个键，插件还能自己往上挂键（`svc-rag` 挂了 `openRagDup`、`ragIntent`），于是桥成了**无owner的公共命名空间**。

**④ 数据怎么流、谁有写权？**
落盘数据分三层：①**加密文件区** `data-files/<项目|姓名>/`（`storage` 服务统一写，AES-256-GCM）②**`data/*.json` 共享文件**（`users`/`sessions`/`trash`/`audit.jsonl`/`settings.json`/`versions.json`/**评论/发布/邀请**…）③**各插件私有 jsonl**。
问题全在 ②：**没有一份"谁写哪个文件"的登记表**。`settings.json` 由 `shell-settings` 写、`auth` 读；`versions.json` 由 `files-versions` 与 `files-agent` 双方写。**多写者 + 无登记 = 依赖方向无法从代码读出。**（这条我建议列为"下一批"，不是现在。）

**⑤ 逻辑关系对吗？依赖是否单向、有无循环？**

- **import 层：单向、无环**（29 处收敛到 `core`，无 A↔B，无插件引用宿主）。这一层**是干净的**，值得记功。
- **但边界不是靠 import 守住的**。真实耦合走四条侧路：**共享数据文件**（§3.2B）、**HTTP 路径字符串**（113 条 vs 37 条名单）、**DOM 类名**（下条）、**`window.PrivHub` 全局键**。
- **前端存在已确证的双向耦合**（我亲自核对）：`explorer-v3` 定义 `.v3-content`（`styles.js:26`），`comments`(`index.js:112`)、`office2`(`index.js:41-60`)、`edit-md`(`index.js:220,270,274,428`) 三处**直接对它做查询/隐藏/插入**；反向，`edit-md` 创建 `.md-inline-root`(`index.js:429`)，而 `explorer-v3` 的 CSS **靠它来切换布局**（`styles.js:28,52-54`）。**这是双向隐式耦合，方向不单向，且已违反约束 5。**（`office2:58-59` 的注释还记录了这层耦合**曾经断过一次**——"原先以它为锚点的写法会找不到元素"。）
- 另一处：`explorer-v3/client/panel.js:317-319` 直接调 `window.PrivHub.openRagDup()`，而该键由 `svc-rag` 定义 ⇒ **L3 → L3 的直接调用**，违反项目自己的规矩「功能插件之间互不 inject，跨功能只走事件总线」（`插件架构.md:16`）。好在有降级（`:319` 弹"未就绪"），不会崩。

**⑥ 这样切为什么好？换一种切法差在哪？（取舍说明）**

现状的切法本质是：**按"一个交付单元 = 一个目录"切**，而不是按业务边界切。**在这个项目的前提下，这个切法是对的，我不建议推翻**——因为：
- 约束 2（无打包链，改完刷新即生效）与"AI 生成代码、作者非程序员"这两个前提，决定了**唯一的可行扩展单位就是目录**；
- 目录切法让"装卸插件 = 增删目录"成立，这是本项目最值钱的资产（§3.1-1）。

代价也来自同一处：**一个目录 = 一个界面位 = 一份数据 = 可能一条路由**，所以插槽 28/31 是 1:1 —— 横切的东西（权限、分发、契约校验）**无处安放**，只能变成名单。

被否的切法：

| 方案 | 差在哪 | 为什么否 |
|---|---|---|
| 按业务域（文件域/知识域/办公域/身份域）重切成 4-6 个上下文，每个自带服务与前端宿主 | 边界会漂亮很多，横切关注点有地方放 | 要动 L1 既成代码（`插件架构.md:27`「不拆、不动已实现」），要重排 30+ 插件的界面归属，**撞约束 1（不动交互布局）**；而且作者无团队无排期，收益只是"更整齐" |
| 把 6 枢纽拆成独立服务/进程 | 边界清晰、可独立伸缩 | **没有任何痛点支撑**：局域网单机、单人维护、无部署流水线。拆了换来网络调用、分布式失败、部署复杂度。架构通则是"默认不拆" |
| 引入打包链/前端框架，做真正的模块系统 | 能用类型与构建期检查消灭字符串契约 | **直接撞约束 2**（无打包链是特性） |
| **（推荐）保持目录切法，只把"名单"集中化：注册即声明** | 不改块、不改交互、不引入构建，只改缝 | 见 P0-1~P0-5。在"AI 生成代码 + 单人维护"的前提下，**可校验的单一真源比漂亮的层次值钱**——AI 改代码最容易犯的错就是漏改名单（`插件实现规则.md:330` 记录了 6 个插件被批量改坏的事故） |

**⑦ 怎么演进？现在做什么、什么留到以后？**

| 分期 | 内容 | 判据 |
|---|---|---|
| **现在（本轮，都不动交互、不动 L1 代码）** | P0-1 装配收口 · P0-2 路由注册契约 · P0-3 判据单点化 · P0-4 名单校验 · P0-5 视图分发收口 | 全是"少一份名单、多一行校验"的小改，任何一条都能独立上线 |
| **下一批** | P1-1 解 `explorer-v3` 的内容区耦合（**必须排在动渲染层之前**，与既有 U2 同批）· P1-2 三处依赖倒挂 · P1-3 `shell` 定位 | 会动渲染或动 L1，需要先有测试兜底 |
| **后话** | `svc-rag` 拆成"能力 + 界面"两个目录 · 数据所有权登记表 · 收回 `admin-console` 的整表透传 | 收益真实但不紧急；等管理控制台与 RAG 稳定后再动 |
| **不做** | 重切三层、拆服务、引入构建链、为"1:1 插槽"做合并 | 见第 5 节 |

### 4.2 改进建议（按投入产出比排序；P0 共 5 条）

---

#### P0-1｜让"装配"只有一个真源，并且**装配完要体检**

- **问题**：装配规则有两条——17 项手写名单（L1/L2 要改代码）与目录扫描（L3 不用改代码）。更麻烦的是三件相关的事从来没被一起解决：①**顺序靠人手维护**（`main.ts:150-183` 逐条 `await mount`），而文档却说"由 Cordis 按依赖图自动排序"（`插件架构.md:82`）②L3 按**目录名字母序**挂载（`main.ts:60` `sort(localeCompare)`）③扫描根取 `process.cwd()`（`main.ts:53`）。
- **证据**：`main.ts:46-51`（名单）、`:55-84`（发现）、`:58` 目录不存在时**直接返回空数组且不打任何日志**、`:60` 字母序、`:75` 成功打一行、`:77/:80` 失败才打。⇒ **启动目录不对（如从仓库根目录启动）时，L3 插件会一个都不装，日志上也看不出来。** 这正是 E1"漏改不报错"的**更深一层**：不止是名单，连"扫到没扫到"都没有断言。
- **改法**：三步，都是**加法**，不删现有机制。
  1. 每个插件在自己的 `package.json` 里自述 `"privhub": { "layer": "L1"|"L2"|"L3" }`（E1 已提此法，**此处不重复其论证**）；宿主据此分三层装配，删掉 `CORE_PLUGINS` 名单。
  2. **顺序不靠名单，靠依赖**：宿主读每个插件的 `inject`（本来就有），做一次拓扑排序；L1 内部若确有人工顺序（core 必须最先），用插件的 `requires`/`after` 字段显式表达，而不是靠 `main.ts` 里的行号。
  3. **装配后体检（这是本条的核心，"E1 没提"的部分）**：启动时打印一张表——`已装配 N 个 / 待定（依赖未满足）M 个 / 加载失败 K 个`，并在 M>0 或"扫描根下没有任何插件"时**显著告警**。验收标准就是**这张表必须能解释"为什么某个插件没起来"**。
- **验收**：①新建一个目录（不改任何代码）能被正常装配且出现在三层清单里 ②故意把 `PRIVHUB_ROOT` 指到错误目录时，启动日志明确报"扫描到 0 个插件，疑似根目录不对"，而不是静默裸奔 ③把某个 L2 插件的 `inject` 指向不存在的服务时，被列进"待定"而不是消失。
- **成本**：**中**（改 `main.ts` 装配逻辑 + 40 余个 `package.json` 加一个字段；不改任何插件业务代码）。
- **与约束的关系**：与 8 条约束**均不冲突**（不动交互、不引入构建、不改插件目录内结构）。

---

#### P0-2｜给路由注册立"所有权"规矩（这条是新增，`改进建议` E6 只讲了"只支持精确匹配"）

- **问题**：路由是插件与前端之间**唯一的接口面**（前端 187 处字面路径），但传输层对"这条路径归谁"**毫无概念**：注册表是个 `Map`，同路径**后注册直接覆盖**，没有告警、没有归属、没有命名空间。
- **证据**：`web-server.ts:88`（`Map<string, RouteHandler>`）、`:142-148`（`register`：`routes.set(path,…)` 覆盖；`_label` 参数**被丢弃**；disposer 只 `delete(path)`）；`core:314-316`（`svc.route` 只是 `ctx.effect` 包一层，把 `label` 传下去后就没了）；`main.ts:144-148`（路径前缀 `frontendDir`/`pluginsDir` 由宿主给，说明宿主已经在管资源归属，唯独路由没管）。
- **现实风险**：今天 113 条路径去重后仍是 113（**实测无重复**），所以**不是眼前故障**；但一旦重复，后果是"后者的 handler 顶掉前者 + 前者卸载时删掉后者的路由"——**两类静默错误**。另有一条既成事实：`/pub`（`files-publish:126`）是全仓唯一不在 `/privhub` 下的路径，说明**前缀约定靠自觉**。
- **改法**：
  1. `register` 发现同路径已存在时**抛错**（或至少醒目告警 + 保留先注册者），并让 `label` 真的被记录（用于报错信息）。
  2. disposer 改为"只有仍指向自己那个 handler 时才删"，避免误删。
  3. 约定命名空间：路径必须以 `/privhub/api/` 开头（`/pub` 作为显式豁免登记在一处）。
  4. 启动体检输出路由清单（插件 → 路径），这份清单同时就是 `改进建议` F3「API 契约文档」的自动初稿——**一箭双雕**。
- **验收**：①构造两条同路径注册，启动即报错并指出两个插件名 ②卸载其中一个插件后，另一个插件的路由仍可访问 ③启动日志可导出全部路径与归属。
- **成本**：**小**（只动 `web-server.ts` 的 `register` 与 `listen` 前的自检，约 30 行）。

#### P0-3｜把"放行哪些插件"的判据收成一处，并改成显式声明

- **问题**：同一条安全判据被两处各实现一遍，而且判据是**插件自述、没人校验**的字段。
- **证据**：`web-server.ts:120-139`（`authSlotDirs()`：扫 `client/manifest.json`，`slots` 含 `auth` 就放行）与 `shell/server/index.ts:99-107`（同一判据过滤清单）——`web-server.ts:115` 注释自认"与 shell 服务端 manifest 分级采用**同一条判据**"；而 `privhub-shell/client/manifest.json:6` 声明了 `"auth"`，`shell/client/index.js:161-166` 却**没有** `auth` 组件 ⇒ **声明与实现不一致，无人发现**，而它因此进了免登录放行集合。
- **改法**：①判据只留一处（建议放在宿主的一个"插件注册表"小服务里，`web-server` 与 `shell` 都从它取）②放行改为**显式最小权限**：manifest 里新增 `"public": true` 才放行（默认不放行），不再用"是否声明了某个 slot"这类**间接推断** ③装配体检时校验 `manifest.slots` 是否都有对应的 `export default slots` 组件，不一致就告警（这条能一次抓住 `shell` 这类漂移）。
- **验收**：①未登录访问任意插件资源，只有显式 `public:true` 的能取到 ②把 `shell` 的伪 `auth` 声明删掉后行为不变（因为它本来也不提供登录框）③声明与实现不一致时启动告警。
- **成本**：**小**（判据搬家 + 1 个字段 + 1 条校验）。
- **与既定优先级的关系**：本条偏安全侧。**按主子既定优先级（先功能与交互、S/D 类后话）可排在 P0-2 之后**，但它是"一处判据"的架构问题，所以仍放 P0。

#### P0-4｜给前端纵向入口一个真正的扩展点（回答"这是什么病、怎么治"）

- **这是什么病**：**宿主把"扩展点的取值域"封闭枚举了**——插件声明的是"我要一个入口"，但入口的**名字**必须出现在宿主代码里才有意义。架构术语叫"扩展点被宿主硬编码"，通俗说：**这不是扩展点，是一批预留好的坑位**。
- **证据**：`index.html:748-764`（`openBarItem` 里 14 个硬编码字符串，且**无 `else`**：白名单外的 view 点击后什么都不发生、不报错、不提示）；`:997-1094`（27 条渲染分支，每条都要再对一次视图名）；`shell/client/index.js:76,81`（图标栏分组写死 `['settings','admin','acl','audit']`）；`:85-94`（高亮判定写死 4 个视图）。
  **对账结果（我实测）**：14 个 view 与白名单**当前完全一致** ⇒ 无死图标、无死分支，**风险是潜在的而不是正在发生的**。这很重要：这条建议的价值是**把"以后不会出问题"变成"以后出问题也看得见"**，不是修一个已经在冒烟的故障。
- **改法**（方向与既有 U2 一致，但我把它拆成**可分步落地**的三步，避免一次动骨架）：
  1. **第一步（最小、当天可做）**：`openBarItem` 加兜底分支——凡是白名单外的 view，走一条通用路径（`nav.setActiveView(view)`）并 `console.warn` 一次"该 view 未被骨架显式登记"。这样**新插件不再静默失灵**，同时骨架不需要认识它。分组写死的两处同理：`slot:'admin-nav'` 已经是现成的显式声明，把 `client/index.js:76` 的 `new Set([...])` 改成按 `bi.slot==='admin-nav'` 判断即可（**去 4 个硬编码名字**）。
  2. **第二步（与 U2 合并）**：模板里的 27 条分支收敛为"`view` → 插槽名"的**一张表**，用 `v-for` 动态渲染；表可以从服务端 manifest 聚合结果里**直接推出来**（插件声明 `barItems[].view` + `slots[]`，宿主不必自己维护名单）。
  3. **第三步（后话）**：那 4 个骨架不认的 `admin-*` 插槽要么退役，要么正式登记为"由管理控制台渲染"的第二类插槽，**不再用"整张注册表透传"这种方式**（`index.html:1049`）。
- **验收**：①新增一个插件、声明一个新 `view`，**不改 `index.html`** 就能点开、能渲染 ②在骨架里搜不到任何具体插件的视图名或插件名 ③现有 14 个入口行为零变化。
- **成本**：第一步**小**；第二步**中**（与 U2 合并做可省一半）。
- **与约束的关系（必须写明的冲突）**：⚠️ **与约束 4「骨架只做容器与总线」有张力**。让骨架维护"视图→插槽"的表，等于骨架又多了"分发"职责。**折中方案**：这张表**不放在骨架里，放在 `shell` 服务端**——它本来就在做 manifest 聚合（`shell/server/index.ts:42-76`），让它在返回清单时**顺便把 view 与插槽的对应关系决议好**，骨架只消费一份"已经决议过的清单"。这样骨架仍是容器，`shell` 仍是插件，且满足约束 1（图标栏位置一律不动）。

#### P0-5｜承认 `shell` 是宿主的一部分，并把它的"具体插件知识"清出去

- **问题**：`shell` 是唯一一个**删不掉的插件**（删了图标栏容器就没了），却是 `plugins/` 里的一名普通成员；同时它里面写死了 6 个具体插件的名字/视图名（`client/index.js:76,81,85-94`）。**一个容器认识所有住户的名字**，这是容器与宿主没分清。
- **证据**：`index.html:997-1024` 硬编码它的 4 个插槽名（`project-tabs`/`user-area`/`app-iconbar`/`welcome`）；`shell/client/index.js:76,81`（分组白名单）、`:85-94`（4 个业务视图写死高亮逻辑）；`shell/server/index.ts:42-111`（聚合 + 分级 + 冲突检测）；另 `shell/server/index.ts:12` 从 `privhub-core/src/index` 深路径 import `tokenOf`（跨枢纽拿内部实现，L1↔L1 的内部耦合）。
- **改法**（两条路，**取舍我摆清，请主子拍板**）：
  - **路 A（省事，推荐先做）**：**不改目录位置**，只做两件事——①在文档与代码注释里把 `privhub-shell` 明确标为"宿主组件，不可卸载"（这样"删目录即卸载"的适用范围变得诚实）②把它认识的 6 个具体名字**清成零**（分组改用已声明的 `slot:'admin-nav'`，高亮改用"view 是否等于当前 activeView"这一个通用判据，个别特例（trash/search/favorites/files）改由 `barItems` 自己声明 `activeFlag`）。
  - **路 B（更彻底，后话）**：把 `shell` 一分为二——`壳（骨架组件 + 图标栏容器，归宿主）`与`manifest 聚合服务（一个普通 L2 服务，归插件）`。好处：宿主 ↔ 插件边界彻底清楚，聚合服务可被 `web-server` 共用（顺带解决 P0-3）。代价：动 `index.html` 与 `main.ts`，且撞"每个插件前端必须完全在自己的目录内"（约束 3）的美感。
- **验收**：①在 `shell/client/index.js` 里搜不到任何具体插件名或业务视图名 ②文档明确写清 `shell` 不可卸载的原因 ③（走路 B 时）删掉聚合服务插件后页面仍能渲染骨架。
- **成本**：路 A **小**；路 B **中**。
- **与约束的关系**：路 A 与 8 条约束**均不冲突**；路 B 与约束 3 有轻微张力（折中：骨架组件仍留在插件目录内，只把"服务"部分外移）。

## 5. 我建议**不要**做的

1. **不要为了层次好看去重切 L1/L2/L3。** 现在这三层的实际含义是"在不在 17 项名单里"，名字确实不副实；但把 6 枢纽重切成真正的限界上下文，要动既成代码、重排 30+ 插件的界面归属，**直接撞约束 1 与 `插件架构.md:27`「L1 不拆不动」**，而作者没有团队与排期。**把名字改准（文档里说清 L1 混装了三种东西）比把代码重切便宜一百倍，收益的九成都在这里。**
2. **不要把 6 枢纽拆成独立服务/进程。** 局域网 + 单机 + 单人维护 + 无部署流水线，**没有任何痛点支撑拆分**。拆了换来网络调用、分布式失败、部署复杂度。架构通则是"默认不拆，有痛点才拆"。
3. **不要引入打包链或前端框架来解决字符串契约。** 这条最诱人（类型检查确实能一次消灭 187 处路径字面量），但**直接撞约束 2**，而且本项目的"改完刷新即生效"正是靠无构建换来的。
4. **不要为"28 个 1:1 插槽"做插槽合并或抽象。** 插槽边界 ≈ 插件边界是**这个切法的自然结果**，不是病。真正该修的是"宿主只认 27 个插槽名"（P0-4），不是减少插槽数量。
5. **不要现在改 `view` 名字。** 既有五视角方案（库珀）已判断改名会连带骨架 if-else 与 `routes.js`；我补充一条实测：**当前 14 个 view 与白名单完全对齐**，改名的收益是"更贴业务"，风险却是"14 处入口同时失灵"。**先把分发机制修好（P0-4），名字的事以后再说。**

7. **不要动 `detail.js` 里那 7 个硬编码按钮。** 交底 §6-6 已声明它们是有意的临时代码。它们是"名单病"的又一例，但**已被显式豁免**，我尊重这个豁免（我这条只写在"不做"里，不重复计为问题）。

## 7. 我这个角度的适用边界

**这个角度能看到什么**：块与块之间的连接方式、依赖方向、谁能碰谁的内部、扩展点的开放与封闭、名单是否有单一真源、改一处要连带改几处。

**这个角度看不到什么**：

1. **看不到界面的实际样子**——我看的是源码与清单，不是跑起来的页面。任何"哪个入口更该放前面""用户能不能找到"的判断，**不是我的角度**（属诺曼/克鲁格/库珀）。
2. **看不到运行时的真实装配**（未启服务、未发请求）。
3. **判不了"该不该有这个功能"**（属 Shape Up 的角度）：我能说"这个扩展点是封闭的"，**说不了"这个入口该不该存在"**。
4. **判不了安全可利用性**（属安全角度）：我能说"放行判据没校验"，**说不了"利用它需要什么条件"**。
5. **判不了数据正确性**（属数据可靠性角度）：我能说"三处倒挂"，**说不了"哪一处会丢数据"**。
6. **我的建议全部以两个未验证前提为基础**：①作者仍是单人 + AI 生成代码（交底 §0）②约束 2「无打包链」在可预见期内不变。**这两个前提里任何一个变了，第 4 节的取舍要重做。**

**要判断 P0-1（装配收口）的真实风险，我还需要**：一次真实的启动日志（看 L3 到底发现了几个、有没有"待定"的插件）——**这一份日志比再读一千行装配代码更能定案**。
