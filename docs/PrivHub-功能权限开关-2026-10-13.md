# PrivHub 功能权限开关（管理员全开 / 普通用户单点开关）——2026-10-13

> 落地用户定下的全局规则：**「系统内部的功能向管理员全部开放；对普通用户，功能要全做出来，
> 但配一个可以简单切换的开关，需要关的时候能关上。」**
> 这条规则往后对同类问题一律照此办理——**不再逐个征询「普通用户要不要这个功能」**。

---

## 1. 解决什么

在此之前，「某个功能给不给普通用户用」被写成 **34 处散落的 `u.role !== 'admin'`**。
要调整任何一个，都得改代码、重启。本批把它收成**一张表**：

```
功能（feature） × 普通用户级别（none / read / write）
```

- **管理员恒为 `write`**（`levelFor()` 里 `role === 'admin'` 直接返回 `'write'`）——
  所以表里**只存普通用户那一列**，要调就是调这一列，单点、可逆。
- 界面：管理控制台 →「用户与权限」→「**功能权限**」，一张表，逐项下拉
  （不可用 / 只读 / 可读写），保存即刻生效，另有「恢复默认」。

**默认值口径（关键）**：每一项的 `userDefault` **等于本功能上线前的实际行为**，
所以开关表上线**本身不改变任何行为**；之后每一次翻转都是用户显式的决定。
界面上标「已改」的即为偏离默认。

## 2. 结构

### L2 服务 `privhub-svc-cap`（`ctx.cap`）

| 文件 | 职责 |
|---|---|
| `plugins/privhub-svc-cap/src/core.ts` | 纯逻辑：功能表 `FEATURES`、默认表、级别偏序、`levelFor`、`normalizeTable`。不认识 `ctx`。 |
| `plugins/privhub-svc-cap/src/index.ts` | `CapService extends Service`（键 `cap`），存 `data/capabilities.json`；`level/can/snapshot/set/setMany/reset/isCorrupt`。 |
| `plugins/privhub-svc-cap/cordis.patch.yml` | 装配声明（`config.file`）。 |

形态与既有 `privhub-svc-acl` 一致：**本服务不注册任何 HTTP 路由**，只被消费方 `ctx.cap.can(...)` 调用。

存储读走 `readJsonStore`（D4：损坏 → 隔离存证 + 记 `corrupt` 标志），写走
`assertStoreWritable(!corrupt, file)`——**读坏过就拒绝写，绝不把可能可恢复的配置清空**。
落盘经 `ctx.storage`，密文（`PHENC1` 头）。

### HTTP 面 + 管理面板 `privhub-admin-cap`

| 路由 | 门槛 | 说明 |
|---|---|---|
| `GET /privhub/api/cap/me` | 任意登录用户 | 返回「我」对所有功能的有效级别；**不设管理门槛**（否则前端拿不到自己的级别，界面没法隐藏入口） |
| `GET /privhub/api/cap/list` | 管理 | 功能清单 + 普通用户当前级别 + 是否已改 + 配置是否损坏 |
| `POST /privhub/api/cap/save` | 管理 | `{ feature, level }` 或 `{ table }`；返回 `changed` |
| `POST /privhub/api/cap/reset` | 管理 | 全部恢复默认 |

「管理」门槛 = `ctx.cap.can(u, 'admin.console', 'write')`——管理员恒通过；普通用户默认不通过。
**自洽**：将来若要让人代管开关，把 `admin.console` 的用户级别调成 `write` 即可。

管理控制台路由表新增条目 `access/features`（`plugins/privhub-admin-console/client/routes.js`），
slot `admin-cap` 由 `privhub-admin-cap/client/manifest.json` 声明。

**「只读界面用 read」**：审计面板、锁统计这类纯查看端点，需要的级别是 `read`——
这样把功能对用户设成「只读」时，面板看得见、改不了，符合直觉。

**保持原样（未迁移）的 `role !== 'admin'`**：都是「**作者本人或管理员**」的文件级判定，
不是系统功能级开关，不在本表范围内：

- `privhub-files-comments`（作者或管理员删评论）
- `privhub-files-publish`（创建者或管理员撤销发布）
- `privhub-files-office2`（锁持有者或管理员释放锁）
- `privhub-trash` 的行 76 / 98（删除者本人或管理员恢复/彻底删除）
- `privhub-project-dashboard/src/core.ts` 行 320（统计成员数时的角色过滤，非权限门）

> 依据用户事实：**文件级权限现实中是「人人相同」**（所有人对所有文件都能读能写），
> 差异只在**系统功能级**。故文件级 ACL 机制保留，但默认人人相同。

## 5. 前端接线

- `frontend/index.html`：
  - `window.PrivHub.cap`（`{ levels, loaded }`）+ `capCan(feature, need)`：
    管理员恒通过（与服务端 `levelFor` 一致）；普通用户按表判定；
    **未登录 / 未加载 / 网络失败一律按「不可用」**（失败收敛到最保守）。
  - `loadCap()` 拉 `/privhub/api/cap/me`；`refreshCaps()` = 拉表 + 重算图标栏。
  - `loadBarItems()`：manifest 的 barItem 若声明 `capFeature`，按开关过滤；
    未声明的沿用 `adminOnly` 旧口径。
  - 登录后与「恢复登录态」两处都先拉表再重算图标栏。
- 管理类 manifest 的 `admin-nav` 条目加了 `capFeature`（对应功能 id）：
  `privhub-admin`→`admin.users`、`privhub-admin-acl`→`admin.acl`、
  `privhub-admin-audit-panel`→`admin.audit`、`privhub-admin-cap`→`admin.console`、
  `privhub-files-template`→`admin.template`、`privhub-shell-agent-console`→`admin.agent.keys`、
  `privhub-shell-settings`→`admin.settings`、`privhub-webhook`→`admin.webhook`、
  `privhub-admin-console`→`admin.console`。
  （`privhub-admin-console` 与 `privhub-webhook` 同时保留 `adminOnly: true`，
  以兼容既有断言 `tests/admin-console.mjs:693`、`tests/integrity.mjs:376`。）

## 7. 诚实说明 / 已知边界

- **未加开关的既有管理面**：`privhub-files-tags`（标签管理）、`privhub-trash-ui`
  的 `admin-nav` 条目没有对应功能（既有人人可见，行为未变），因此未纳入本表。
  日后要收，往 `FEATURES` 加一行即可——这是本机制的设计目的。
- **纯界面验证留待浏览器**：本批只做了服务端行为 + 静态契约 + 前端代码接线；
  下拉切开关 → 图标栏/入口随之显隐的**视觉**效果未在真实浏览器里逐项点过。
- **`adminOnly` 与 `capFeature` 并存**：`loadBarItems` 里 `capFeature` 优先；
  两处并存是为了不动既有断言，语义上 `adminOnly` 已成为冗余声明。
- **「查重」两项（`dup.prompt` / `dup.near.delete`）不走 `capFeature` 界面过滤**，
  而是**服务端判定、结果回带**：`dup.prompt` 关掉时上传响应**不含** `duplicates`/`near`
  两个键；`dup.near.delete` 由 `/rag/dup` 回带 `allowNearDelete` 供界面决定渲不渲染勾选框
  （单一事实来源，避免前端自己算开关算反）。细节见 `docs/PrivHub-上传查重-2026-10-13.md`。
- **「管家」九项（`agent.butler*`）与前 22 项的用法不同**：它们不代表"普通用户能不能用某个界面功能"，
  而是**宿主机智能体管家车道自己的闸**。车道在服务端用一个 `role≠admin` 的**伪身份**去问
  `ctx.cap`（`plugins/privhub-files-agent/src/index.ts` 的 `BUTLER_ACTOR`），
  所以把这些值改成 `none` 就等于关掉对应能力 —— 这利用了"管理员恒 write、非管理员才看表"这条规则，
  让"总开关 + 分项开关"直接复用既有开关表与既有管理面板，**不另起一套存储**。
  默认全 `write`：车道的**真正闸门是钥匙本身**（须管理员显式签发、仅本机回环、可随时吊销），
  没有钥匙什么也做不了；开关是给"我要关的时候能关上"用的。
  细节见 `docs/PrivHub-宿主机智能体管家-MCP-方案-2026-10-13.md`。
  界面语义提醒：管理面板里这一组会显示为"普通用户级别"的列 —— 对管家组件而言，
  这一列读作"该能力对管家车道是否开放"。
