# PrivHub 管理控制台改进计划

> 版本：v1 · 2026-11-17 · 基线：3180（3.6.2 + 本轮前端改动）
> 依据：`docs/PrivHub-界面框架原型.html`（S23.x）、主人历次反馈、**实测数据**（下方每条都有测量结果）
> 现有截图：`docs/PrivHub-落地验证截图/管理控制台-重设计后.png`
>
> **✅ 实施状态（2026-11-17 当日完成）：六步全部落地并实测通过。**
> 验收结果：审计卡 3716 === stats 总数（原少报 3512 已修）；概览取数 28.4KB → **2.5KB**；
> 5 卡全有数字；顶栏搜索可跳 18 个管理页 + 用户/项目实体；全管理台仅 1 个搜索框；
> 卡片 role=link+tabindex=0 键盘可达；admin-console 回归 87 → **129 条**；
> run-all-3180 **11 套全绿**。截图：`管理控制台-重构完成.png`、`管理控制台-搜索跳转实测.png`。
> 顺带修掉两个实现期发现的坑：假 DOM 缺 el.value 导致 v-model 静默失效；
> 刷新令牌「>0 即强刷」导致缓存永久失效（改为令牌差值比较）。

## 零、先说结论

管理控制台现在是「**能用的**」，但有 **3 个真缺陷 + 4 个设计债**。
其中 **P0 两条必须修**（一个数据错误、一个假功能），其余按性价比排序。

| 优先级 | 问题 | 性质 | 影响 |
|---|---|---|---|
| **P0-1** | 审计记录数**少报 3512 条**（显示 200，实际 3712） | 数据错误 | 管理员据错误信息决策 |
| **P0-2** | 顶栏「搜索用户、项目、规则、日志」是**假功能**（点击只弹 toast） | 假功能 | 用户点了没反应，损耗信任 |
| P1-1 | 为 5 个数字拉 **28.4 KB**，其中 94% 浪费在审计全量 | 性能 | 每次进概览都拉一次 |
| P1-2 | 「系统运维」卡无数字（显示 `—`） | 信息缺失 | 5 张卡里 1 张是空的 |
| P2-1 | 两个搜索框（顶栏全局 / 概览功能）职责重叠 | 逻辑 | 用户不知道用哪个 |
| P2-2 | 侧栏折叠状态不持久 | 体验 | 每次进来要重新展开 |
| P3-1 | 概览无「最近活动」 | 功能 | 管理员进来不知道刚发生了什么 |

## 一、功能设计

### 1.1 P0-1 修数据准确性（**最高优先**）

**实测证据**
```
界面显示（拉全量 audit 列表取 .length）:  200 条
真实总数（/privhub/api/audit/stats）:  3712 条
少报: 3512 条
```

**根因**：`/privhub/api/audit` 默认只返回最近 200 条（`limit` 默认 200），
概览拿这个数组的 `.length` 当"总记录数"。**分页接口的页大小被当成了总数。**

**改法**：改用 `/privhub/api/audit/stats` 的 `entries` 字段（真实块数，且是 O(1) 读文件头）。

**顺带检查同类错误**：所有「用列表长度当总数」的地方都要审一遍。
已知 `trash-list` 返回 1 条且无 `total` 字段 → 回收站若将来分页，会踩同样的坑。

**验收标准**
- 概览「审计日志」卡显示值与 `/audit/stats.entries` 一致
- 新增回归断言：**卡片数字 === stats 接口的总数**（不是列表长度）

---

### 1.2 P0-2 顶栏搜索：要么做成真的，要么去掉

**现状**
```js
onSearch() {
  window.PrivHub.toast('全局搜索将在后续阶段接入（范围：用户、项目、规则、日志）', 'warn')
}
```
它挂在顶栏最显眼的位置、写着具体范围，但回车只弹一句"以后再做"。

**两个选择（建议 A）**

| 方案 | 做法 | 代价 |
|---|---|---|
| **A. 做成真的**（推荐） | 搜「页面 + 实体」两类：页面走本地 `navModel()` 过滤（0 成本）；实体走现有接口加 `q` 参数 | 需给 4 个接口加 `q`（各 1 行过滤） |
| B. 先降级为明确的"未启用" | 输入框改成禁用态 + 「即将上线」标签 | 最省，但顶栏一块空地 |

**建议 A 的分层实现**
1. **页面直达（立即生效，零后端改动）**：搜 `navModel()` 全部条目（含 `more` 里收起的），命中就跳。这已经能覆盖「用户管理 / 存储 / 审计」这类高频诉求。
2. **实体搜索（第二阶段）**：给 `/admin/users`、`/projects`、`/acl/rules`、`/audit` 加可选 `q`，命中高亮 + 跳对应页并带上搜索词。

---

### 1.3 P1-2 「系统运维」卡补真实指标

现在显示 `—`。可用的零成本真实指标（都已有接口）：

| 候选 | 接口 | 现状 |
|---|---|---|
| 存储卷数 + 文件数 | `/volumes/list` | ✅ 已有，返回 `volumes[].files` |
| 自检问题数 | `/doctor/check` | ✅ 已有，实测返回 `problems: 4` |
| 是否有可用更新 | `/update/status` | ✅ 已有（直连模式返回说明） |

**建议**：显示「**N 个卷 · M 个文件**」，自检有问题时追加红色「⚠ N 项待处理」。

---

### 1.4 P2-1 两个搜索框合并

**现状**：顶栏一个「搜索用户、项目、规则、日志」，概览页内又一个「搜索管理功能」。
两个框、两种语义、相邻 200px，用户不知道区别。

**建议**：**只保留顶栏一个**，让它同时支持「页面直达 + 实体搜索」；
删掉概览页内的那个（或改成"筛选卡片"的小图标输入，明确它只过滤卡片）。

**取舍**：原型 S23.1 要求"管理内搜索框常驻"，顶栏那个就是"常驻"——满足要求且不重复。

---

### 1.5 P3-1 概览增加「最近活动」

管理员进来第一个问题往往是"刚才发生了什么"。数据已有（审计日志），成本极低。

**建议**：卡片下方加一条「最近 5 条操作」（时间 + 人 + 动作），
取自 `/audit?limit=5`（实测 118B/条级别，很小）。

**为什么值得做**：它把概览从「静态导航页」变成「有信息量的落地页」。

## 二、性能设计

### 2.1 实测数据

| 接口 | 字节 | 耗时 | 用途 |
|---|---|---|---|
| `/admin/users` | 2010 | 5ms | 取 `.length` |
| `/projects` | 160 | 2ms | 取 `.length` |
| `/acl/rules` | 22 | 1ms | 取 `.length` |
| **`/audit`（全量）** | **26707** | **28ms** | 取 `.length` ← **94% 浪费** |
| `/trash-list` | 201 | 2ms | 取 `.length` |
| **合计** | **28.4 KB** | **44ms** | |

### 2.2 优化后

| 改动 | 效果 |
|---|---|
| 审计改用 `/audit/stats` | 26707 → ~150 B |
| 用户/项目/ACL 加 `limit=1`（若支持） | 各自降到 O(1) |
| **预期** | **28.4 KB → 2.5 KB（省 91%），44ms → 32ms** |

已实测验证过这条路径：`/audit?limit=1` 返回 **118 B**，`/audit/stats` 返回 **~150 B**。

### 2.3 缓存策略（可选，第二阶段）

概览数据变化不快（用户/项目/ACL 分钟级）。建议：
- **前端 30 秒内存缓存**：切走再切回来不重拉
- 提供「🔄 刷新」按钮强制拉取（已有）

**不要做的**：不要在后端加定时预计算——5 个数字的实时计算已经很便宜，
预计算会引入"数据陈旧"的新问题，得不偿失。

## 三、逻辑关系设计

### 3.1 三层信息架构（明确职责，避免重复）

```
┌─ 顶栏（全局，常驻）        ← 搜索一切（页面 + 实体）、返回文件、用户区
├─ 侧栏（导航，分 4 组）      ← 我在管理台的哪个位置
└─ 内容区
   ├─ 概览页 = 入口地图      ← 5 张职责卡 + 最近活动（不再放重复搜索框）
   └─ 各功能页 = 干活的地方
```

**原则**：**每一层只回答一个问题**
- 顶栏："我要找什么"（搜索）
- 侧栏："我在哪"（位置）
- 概览："我该去哪"（导航）
- 功能页："怎么做"（操作）

### 3.2 卡片的信息结构（统一四段）

每张卡固定包含，不允许有的有有的没有：

| 段 | 内容 | 为什么必须有 |
|---|---|---|
| 标题 | 职责名 + 图标 | 一眼识别 |
| 描述 | 这一域能干什么 | 新人不知道"内容治理"是什么 |
| 指标 | **1 个真实数字**（取不到显示 `—`，不显示 0） | 有信息量 |
| 直达 | 1-4 个小按钮 | 满足"≤2 步到任意子屏" |

### 3.3 状态一致性

| 状态 | 表现 |
|---|---|
| 加载中 | 骨架屏（已有） |
| 接口失败 | 显示 `—` + 卡片可点（**不要整页报错**，一张卡失败不该拖垮概览） |
| 全部失败 | 才显示整页错误（已有逻辑保留） |
| 无权限 | 该卡不渲染（不是显示 0） |

**当前缺陷**：`countOf` 失败返回 `null` 会显示 `—`（对），但若**部分**接口失败，
其余卡片正常、失败那张显示 `—`——**这个行为是对的，保持**。

## 四、前端显示要求

### 4.1 布局（已实现，需保持）

- 卡片：**固定 3 列**（1200px 以下 2 列，760px 以下 1 列）
- 最小高度统一 **168px**（避免内容长短不一导致卡片高低不齐）
- 卡片间距 14px，圆角、阴影沿用 admin 令牌

### 4.2 视觉层级（从强到弱）

```
数字（22px, 600）  >  标题（14px, 600）  >  描述（12px, muted）  >  直达按钮（11.5px, 边框胶囊）
```

**要求**：数字是扫视重点，必须最重；直达按钮是次要动作，必须最轻（不能比标题还显眼）。

### 4.3 无障碍与可读性

| 项 | 要求 | 现状 |
|---|---|---|
| 键盘可达 | 卡片可 Tab 聚焦、Enter 进入 | ⚠ **未做**，卡片是 `div @click` |
| 焦点可见 | 有 `:focus-visible` 轮廓 | ⚠ 未做 |
| 语义 | 卡片用 `role="link"` 或改 `<a>` | ⚠ 未做 |
| 对比度 | 描述文字 ≥ 4.5:1 | 需实测 |
| 不靠颜色传达 | 「待处理」不能只用红点 | 已有文字 |

**P1 建议补**：卡片改 `<button>` 或加 `tabindex="0" @keydown.enter`。

### 4.4 文案规范

- 描述句**不超过 22 字**（当前最长 26 字，会换行）
- 数字带单位（`12 个账号` 而不是 `12`）
- 取不到用 `—`（em dash），**不用 0、不用 N/A**

## 五、实施顺序与工作量

| 阶段 | 内容 | 预计改动 | 风险 |
|---|---|---|---|
| **第 1 步**（必做） | P0-1 数据准确性 + P1-1 性能（同一处改动） | `panels.js` 约 10 行 | 低 |
| **第 2 步** | P1-2 补「系统运维」指标 | `panels.js` + 1 接口调用 | 低 |

| **第 6 步** | P3-1 最近活动 | `panels.js` + 1 接口 | 低 |

**建议先做第 1+2 步**：既是修 bug、又是性能优化、改动小、能立刻验证。

## 七、我判不了的 / 需要你拍板的

1. **顶栏搜索**：做成真的（工作量中），还是先降级为"未启用"标签（工作量小）？
2. **「最近活动」**要不要？它会占用概览页一块空间，与"少占地方"的原则有张力。
3. **概览卡片点击**：现在是整卡可点进"最常用页"。要不要改成**整卡不可点、只有小按钮可点**？（避免误触，但也少了快捷）
4. **侧栏是否需要再收**：现在 8 项 + 3 个「更多」。如果还想更短，可以把「概览」也并进分组标题。
