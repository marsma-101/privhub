# PrivHub 工程化路线图

> 目标：把 PrivHub 从「功能扎实的原型」推进到「可投产、可维护、改得起、发得出」的工程状态。
> 编制：2026-10-07｜基线版本：3.1.3｜执行方式：分阶段、每步可回退、每步有实测证据。

## 0. 一句话诊断

项目的**功能块切得没错**（50 插件、112 路由、19 个测试套件都在），病在**工程脚手架几乎为零**：没有类型检查、没有 lint、没有 CI、没有单一质量门。于是"改坏了没人拦、连错了不吭声、发版靠人肉记得跑测试"。这不是玩具，是缺安全网的成熟躯体。

## 2. 四阶段

### 阶段 A · 质量门（进行中）
- **A1 基线**：加 `tsconfig.json` + `typescript` + 匹配 Node 22 的 `@types/node`，裸测全项目类型错误。✅ 完成（基线 265→校准 234）
- **A2 建立事件契约单一来源**：模块增强登记 5 个自定义事件，顺带修 `ctx.on('dispose')` 真 bug。✅ 完成（234→199）
- **A3 服务形状单一来源**：删除各插件对 `ctx.privhub` 的本地 `unknown` 影子类型，改用 core 的权威类型。（下一步，预计消掉 130+ 条）
- **A4 收尾**：消化剩余 arity/联合等零散错误，把 `strictNullChecks` 后的真实错误清零。
- **A5 一键质量门**：`npm run check` = typecheck + 契约完整性 + 全量回归。
- **A6 CI**：GitHub Actions 每次 push 自动跑门禁。

### 阶段 B · 契约与「出错会喊」
- manifest JSON schema 校验；启动自检报告（装了哪些插件 / 哪些失败 / 插槽·路由·ACL 白名单一致性）；路由与 ACL 白名单收敛为单一来源。

### 阶段 C · 可运维
- 配置集中（`.env` + 校验）；加密数据**备份/恢复**脚本；健康检查；Windows 进程守护；部署包同步（OPS-02，需显式授权）。

### 阶段 D · 发布纪律
- 每版打 git tag；CHANGELOG 流程自动化；依赖审计纳入门禁。

| 日期 | 批次 | 结果 | 证据 |

| 2026-10-07 | A1 基线 | 装 typescript@7.0.2 + @types/node@22；`npm run typecheck` 可跑；基线 **234**（strictNullChecks） | `npm run typecheck` |
| 2026-10-07 | A2 事件契约 + dispose 修复 | **234 → 199**；`keyof Events`/`dispose` 归零；修 5 处清理永不执行的真 bug | `plugins/privhub-core/src/events.ts` |

| 2026-10-07 | A4 清零剩余错误 | **33 → 0**；顺带修 4 个真 bug：`publish` 撤销崩溃、`rag` 近重复配对用错变量、`rag` 计数 `.length`、`files-agent` 限流冲突判断 | `npm run typecheck` 退出码 0 |

### A3/A4 顺带修出的真 bug（正是"没有类型检查"掩盖的）

1. **`files-publish` 撤销发布必崩**：`save(storage, list)` 被调用成 `save(list)` → `storage` 为 `undefined` → `storage.writeText is not a function`（CHANGELOG 早已记录此现象，非本批引入，本批修复）。
2. **`svc-rag` 近重复检测记录错配对**：`out.push({ a, b, score })` 里的 `b` 是**循环下标**（`for (let b=0;...)`）而非文档 id `b2` → 近重复列表内容错误。
3. **`svc-rag` 管理操作回执字段错**：`r.affected.length` 中 `affected` 是 `number`，取 `.length` 恒为 `undefined`。
4. **5 处卸载清理永不执行**：`ctx.on('dispose', ...)` —— cordis 不派发该事件（正确 API 为 `ctx.effect`），定时器/落盘清理从未触发。
