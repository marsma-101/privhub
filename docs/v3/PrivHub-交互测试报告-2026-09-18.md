## 二、结果总览

### 健康的部分（验证通过，重点确认无回归）

- **文件主链路全通**：上传 → 列表 → 预览 → 下载 → 重命名 → 删除 → 回收站 → 恢复，内容与文件名均一致（C1–C7）。
- **文件名边界稳健**：中文+空格 ✅、无扩展名 ✅、空名 400「文件名无效」✅、`../` 路径穿越被挡 ✅（C8–C12）。
- **路径穿越防线有效**：`download?path=../../data/users.json` → 404，未泄露（C13）。
- **权限隔离有效**：普通用户访问/写入未授权项目均 403；跨用户回收站条目彼此不可见（D5、V3）。
- **防暴力有效**：连续错误密码第 **6 次**起返回 `429 尝试过于频繁`（V7）。
- **插件前端资源有会话门禁**：未登录取 `privhub-admin` 前端源码 → `401 unauthorized`，带会话 → 200（V4/V5）。
- **智能体通道独立**：无 `X-Agent-Key` 调用 → 401，文案明确（D4）。
- **同名上传不静默覆盖**：第二次上传 → `409 同名文件已存在：×××（为避免覆盖，请改名后重新上传）`（V14）。
- **默认账号可用**：`admin/admin123`、`user1/user123` 均可登录（A4、V-附录）。

## 三、缺陷清单

严重级：**P0** 数据/安全风险 · **P1** 显著影响使用 · **P2** 体验瑕疵

### D-01 【P1】普通用户没有任何「修改自己密码」的途径

**复现步骤**

```bash
TOKEN=<普通用户 admin 之外任意账号的 token>
for p in /privhub/api/me/password /privhub/api/password /privhub/api/change-password /privhub/api/me/passwd; do
  curl -s -o /dev/null -w "$p → %{http_code}\n" -X POST -H "authorization: Bearer $TOKEN" \
       -H 'content-type: application/json' -d '{"oldPassword":"a","newPassword":"b"}' \
       http://127.0.0.1:3199$p
done
```

**预期**：系统提供改自己密码的能力（README 明确写着「首次启动自动生成默认账号 admin / admin123（**登录后请立即修改密码**）」）。

**实际**：4 条常见路径全部 `404`；全仓仅存在 `POST /privhub/api/admin/user-reset-password`（管理员重置**他人**）。设置页（`🤖` 与 `⚙`）与个人菜单均无此入口。

**证据**：
- 路由唯一性：`plugins/privhub-admin/src/index.ts:119`
- 设置页无相关代码：`plugins/privhub-shell-settings/client/index.js`
- 实测输出：`B8` 四条路径均 404

**初判**：功能缺失（非缺陷回归）。README 的「立即修改密码」是**空头指令**，用户唯一出路是找管理员重置。

**建议**：二选一——① 补 `POST /privhub/api/me/password` + 设置页入口；② 若有意不做，README 与首次登录提示改为「请联系管理员重置」。

### D-02 【P1】「个人空间」在前端数据里没有任何身份标识

**复现步骤**

```bash
curl -s -X POST -H 'content-type: application/json' \
  -d '{"username":"shenxy","password":"test123456","displayName":"申小丫"}' \
  http://127.0.0.1:3199/privhub/api/register          # 注册自动创建个人空间
curl -s -H "authorization: Bearer $TOKEN" http://127.0.0.1:3199/privhub/api/projects
curl -s -H "authorization: Bearer $TOKEN" http://127.0.0.1:3199/privhub/api/me
```

**预期**：新用户能分辨「哪个是我的私人空间」——它仅本人可见、不进索引、系统永不删除、且是智能体的可写沙箱。

**实际**：
- `/api/projects` → `{"ok":true,"projects":["申小丫","公共"]}` —— **纯字符串数组**，个人空间与普通项目长得一模一样。
- `/api/me` → 有 `personalDir:"申小丫"` 字段，但**前端没有任何一处使用它做标记**（全仓搜「我的空间」零命中，仅 `privhub-core/src/index.ts:89` 留有「前端据此在项目列表里标记『我的空间』」的设计意图注释）。
- 唯一线索藏在设置页小字：「你的文件夹名和它保持一致：申小丫（仅你本人可见）」。

**实测输出**：`B3`、`B4`

**影响**：用户会把「申小丫」当成一个普通项目；不知道它私人、不会被搜索/查重碰到、智能体往这里写。

**建议**：接口返回结构化项目列表（`[{name, kind:'personal'|'project'}]`）或在 `visibleProjects` 契约不变的前提下由前端用 `AUTH.user.personalDir` 比对渲染徽标——后者改动最小。

### D-03 【P1】个人空间的「全文搜索」恒为零结果，且无任何解释

**复现步骤**

```bash
# 1) 在个人空间上传一个文件
curl -s -X POST -H "authorization: Bearer $TOKEN" --data-binary '这是只应我自己看到的内容' \
  "http://127.0.0.1:3199/privhub/api/upload?project=%E7%94%B3%E5%B0%8F%E4%B8%AB&name=%E6%88%91%E7%9A%84%E7%A7%81%E5%AF%86%E7%AC%94%E8%AE%B0.txt"
# 2) 全文搜索它
curl -s -H "authorization: Bearer $TOKEN" \
  "http://127.0.0.1:3199/privhub/api/fulltext/search?q=%E7%A7%81%E5%AF%86&project=%E7%94%B3%E5%B0%8F%E4%B8%AB"
# 3) 对照组：文件名搜索
curl -s -H "authorization: Bearer $TOKEN" \
  "http://127.0.0.1:3199/privhub/api/search?q=%E7%A7%81%E5%AF%86&project=%E7%94%B3%E5%B0%8F%E4%B8%AB"
```

**预期**：要么能搜到，要么明确告知「个人空间不参与全文索引」。

**实际**：
- 全文搜索 → `hits=0`，`stats={"docs":0,"postings":0,"totalLen":0}`，**HTTP 200 无任何提示**；界面对应渲染「没有匹配『私密』的内容」（`plugins/privhub-files-search/client/index.js:126`）。
- 文件名搜索 → `hits=1`，正常命中该文件。（说明仅全文索引被排除，非权限问题）

**直接对比（同一类限制，两处口径不一致）**：
```bash
curl -s -H "authorization: Bearer $TOKEN" \
  "http://127.0.0.1:3199/privhub/api/rag/dup?project=%E7%94%B3%E5%B0%8F%E4%B8%AB"
# → 400 {"ok":false,"error":"查重仅针对项目，不作用于个人空间"}   ← 文案清晰，处理正确
```

**证据**：`B6`（全文，零结果无提示）、`V8`（文件名，正常）、`V1`（查重，有明确文案）
**代码位置**：`plugins/privhub-files-fulltext/src/index.ts:48,87`（跳过个人空间）

**建议**：搜索接口在 `isPersonalDir(project)` 为真时返回带 `notice` 字段的响应，前端据此显示「个人空间不参与全文检索，请用文件名搜索」。成本极低，闭环口径。

### D-04 【P2】图标栏底部管理入口的「身份」与文档不符，且冲突告警文案与实际情况相反

**复现步骤**

```bash
curl -s -H "authorization: Bearer $TOKEN" http://127.0.0.1:3199/privhub/api/shell/manifest \
 | node -e "let s='';process.stdin.on('data',d=>s+=d).on('end',()=>{const m=JSON.parse(s);m.manifests.forEach(p=>(p.barItems||[]).forEach(b=>{if((b.view||b.slot)==='admin')console.log(p.id,b.icon,b.title)}))})"
```

**预期**：底部固定管理组显示 🛠️「管理控制台」，点击进入管理控制台（文档《架构与功能说明》3.3 节所述）。

**实际**：清单中 `view: "admin"` 被两个插件声明，顺序为：

```
privhub-admin         👥 用户管理        ← 前端取第一个
privhub-admin-console 🛠️ 管理控制台
```

前端 `bottomItems` 用 `find()` 取**第一个**匹配项（`plugins/privhub-shell/client/index.js:80-83`），因此图标栏底部实际显示 **👥「用户管理」**，但点击进入的是**整个管理控制台**。用户看到的提示与结果不符。

**附带**：服务端启动日志确实打印了告警，但文案与事实相反——

```
[shell] barItems 冲突：view "admin" 由 privhub-admin 与 privhub-admin-console 同时声明，后者将覆盖前者
```

实测是**前者生效**（后者根本没有参与渲染决策；`seenViews` 仅用于冲突检测，不参与分发）。

**证据**：`E1`、服务端日志；代码 `plugins/privhub-shell/server/index.ts:57-62`

**建议**：① 二选一——把 `privhub-admin` 的 barItem 的 `view` 改为非 `admin`（它本来就是放进控制台侧栏的 `admin-nav` 项，不该再占图标位），或让 `bottomItems` 显式按 `id` 白名单取；② 修正告警文案为「（图标栏取首个匹配项，实际生效：`${prev}`）」。

### D-05 【P2】超长文件名上传失败时，错误正文回显服务器绝对路径

**复现步骤**

```bash
python -c "print('curl ...')" >/dev/null   # 构造 300 字文件名
curl -s -X POST -H "authorization: Bearer $TOKEN" --data-binary 'x' \
  "http://127.0.0.1:3199/privhub/api/upload?project=A%E9%A1%B9%E7%9B%AE&name=$(python -c "print('%E9%95%BF'*300)")%2Etxt"
```

**预期**：明确拒绝并说明原因（如「文件名过长」）。

**实际**：HTTP 400，但 `error` 字段是 Node 原生错误原文：

```
ENOENT: no such file or directory, open
'G:\program\dsh-SQL\.assistant\itest\root\data-files\A项目\长长长…（300字）….txt.part'
```

**证据**：`C11`
**影响**：① 把**服务器绝对路径（盘符、目录结构、部署位置）**回显给客户端，属信息泄露面；② 普通用户看不懂 ENOENT；③ 长文件名本应在校验层被拒，却走到了落盘阶段才失败。

**建议**：上传前对文件名长度（建议 ≤ 200 字节，考虑 NTFS 与中文编码）与非法字符做前置校验；错误兜底统一为面向用户的文案，不透传 `errno` 原文与路径。

### D-06 【P2】打开不存在的项目：管理员得到「静默空目录」，普通用户得到错误语义

**复现步骤**

```bash
# 管理员
curl -s -H "authorization: Bearer $ADMIN_TOKEN" \
  "http://127.0.0.1:3199/privhub/api/list?project=%E4%B8%8D%E5%AD%98%E5%9C%A8%E7%9A%84%E9%A1%B9%E7%9B%AExyz"
# 普通用户
curl -s -H "authorization: Bearer $USER_TOKEN" \
  "http://127.0.0.1:3199/privhub/api/list?project=%E4%B8%8D%E5%AD%98%E5%9C%A8%E7%9A%84%E9%A1%B9%E7%9B%AExyz"
```

**预期**：明确提示「项目不存在」。

**实际**：
- 管理员 → `200 {"ok":true,"entries":[]}` —— 界面呈现为**一个空项目**，用户会以为项目是空的（数据丢失错觉）。
- 普通用户 → `403 无权限访问该项目` —— 语义不准，实际是项目不存在。

**证据**：`V6`、E3 后续复核
**代码位置**：`plugins/privhub-core/src/index.ts` `canAccess`（管理员对任意合法名字放行）→ `listFiles` 对不存在目录返回空数组。

**建议**：`list` 在目录不存在时返回 404 + 「项目不存在或已被删除」，与「无权限」区分开。

### D-07 【P2】导出能力只能从 Markdown 编辑器进入，文件菜单里找不到

**复现步骤**

```bash
# 导出接口本身是好的，但只认 md
curl -s -H "authorization: Bearer $TOKEN" \
  "http://127.0.0.1:3199/privhub/api/export?project=A%E9%A1%B9%E7%9B%AE&path=%E6%B5%8B%E8%AF%95%E6%8A%A5%E5%91%8A-%E6%94%B9%E5%90%8D%E5%90%8E.txt&format=pdf"
# → 400 {"ok":false,"error":"仅支持 .md 文档导出"}   ← 接口文案清晰
```

**预期**：用户想「把 md 转成 Word/PDF 发给同事」时，能在文件上找到导出。

**实际**：唯一入口在 Markdown 编辑器内部（`plugins/privhub-files-edit-md/client/index.js:365`）；文件 ⋯ 菜单与右侧详情面板**都没有「导出」项**（详情面板的「🌐 生成页面」是 md→HTML 展示页，不是导出）。

**证据**：`V9`（接口可用且限制清晰）+ 静态核查（入口缺失）
**建议**：至少在详情面板或 ⋯ 菜单补一个「导出」入口，md 文件时可用、其它类型置灰并给出原因。

### D-08 【P2】详情面板按钮置灰时，只说明能力范围，不说明当前文件为何不可用

**实际**：`编辑 / 批注评论 / 生成页面 / 发布链接 / 版本历史` 均按类型置灰，提示语为「仅支持 md 文档」「仅支持文本类文件」——**未指出当前选中的是什么类型**。

**证据**：`plugins/privhub-files-explorer-v3/client/detail.js:192-197`（`title` 文案）+ 静态核查

**建议**：提示语补上当前类型，如「当前为 .xlsx，此功能仅支持 md」。零风险改动。

---

### D-09 【P2】界面从不显示版本号

**实际**：`/privhub/api/health` 可用并返回 version 字段（本轮测试实例因测试根缺 `package.json` 返回 `"unknown"`，**此为测试环境产物，不计为缺陷**），但**前端无任何一处调用它**（全仓搜 `health` 在客户端零命中）。

**影响**：用户报障、对文档、判断新旧版本均无依据。

**建议**：设置页（或管理控制台「概览」）展示版本号与运行时长。

## 四、更正记录（第一轮误判，已复核）

| 首轮判定 | 复核结论 | 原因 |
|---|---|---|
| ~~A6 未登录取插件源码 → 200，鉴权缺失~~ | **误判，实为无缺陷**：`privhub-auth`（登录框插件）本就在放行白名单内 | 探针选错了插件；用 `privhub-admin` 重测 → 401（V4） |
| ~~B7 个人空间查重 → 404，接口不存在~~ | **误判，实为无缺陷**：正确路由是 `GET /privhub/api/rag/dup`，返回 400 且文案清晰 | 探针路径拼错（V1） |
| ~~B10 未授权项目写入 → 405~~ | **误判，实为无缺陷**：上传接口方法为 POST，非 PUT；改 POST 后 → 403「无权限上传到该项目」 | 探针方法用错（V3） |
| ~~D3 无任何限流~~ | **误判，实为无缺陷**：第 6 次起 429 | 首轮仅试 8 次且未逐次记录状态码（V7 已量化） |

> 保留此表的目的：避免开发者按首轮结论去修不存在的问题。

## 五、测试局限与未覆盖项

1. **未做真实浏览器渲染验证**：本次为 HTTP 层黑盒 + 静态代码交叉印证，未驱动无头浏览器。所有「界面显示为…」的结论均以**接口返回 + 渲染代码**推证，未做像素级确认。
2. **未覆盖**：Office 文档预览/编辑、RAG 问答与向量化（依赖外部模型）、大文件与并发上传、多用户并发编辑锁、备份/恢复链路。
3. **限流策略**：为避免锁死 `admin`，限流探针使用不存在的账号；**未验证**账号锁定是否会被恶意触发而误伤真实用户。
4. **环境差异**：本机 Node v22.23.2，仓库声明实测为 v24.21.0；`better-sqlite3` 等原生模块版本差异未验证。
5. 测试实例为**独立数据根**，未接触 `privhub/data`、`privhub/data-files` 真实数据。

## 七、修复优先级建议（供排期参考，不代替决策）

| 优先级 | 缺陷 | 理由 |
