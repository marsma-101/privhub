## 二、职业转折：代理公司倒闭 → 独立（并纠正一个常见误传）

### 2.1 事实链（一手）

2018 年的转折**不是**"从 Clearleft 主动跳出来创业"，而是**被动的**：

- **[他说]** "在招聘流程里被磨了好几个月之后——因为我在的那家代理公司要倒闭了——我突然意识到我可以回去做自由职业。事实上，那感觉是最安全的选择，现在仍然如此。"（2023-10-31）
- **[他说]** "我以前的雇主在我女儿出生前 48 小时告诉我他们的公司失败了，你可以想象，那是地狱。"（同上）
- **[他说]** "搞笑的是，自由职业第一天，我做的是和前一天作为雇员时同一份 CSS 文件。"（同上）
- **[他做]** 2018-10-31 当天客户签了合同。
- **[他做]** 2018-11-29 注册 Set Creative Studio Ltd（公司号 11703292）。

**结论 [他做]**：他公开表述的职业转折剧本是「公司倒闭 → 短暂被雇→ 回到自由职业」，没有提过一段"主动离开知名公司去独立"的故事。

### 2.2 关于「前 Clearleft 前端开发者」这个前提

**⚠️ 存疑 / 未能核实。**

- 他本人的 About 页（bell.bz/about，2026 年现行版）**完全没有提 Clearleft**，只写了"在设计与 web 行业工作 15 年以上"、服务过 Google / NHS / Harley-Davidson / Oracle 等。来源：[他做] https://bell.bz/about/
- 他的 5 年/独立回顾、2021/2022/2023/2024 年度总结里也**没有出现 Clearleft**。
- **唯一命中的关联**：Clearleft 15 周年纪念页（timeline.clearleft.com，2021 年）里 **Andy Bell 以具名外部人士身份**提交了一句祝福语："我希望设计与开发已经成熟到超越热门工具，把焦点放回解决问题上。"来源：[他做] https://timeline.clearleft.com/ ——同期提交者还包括 Trys Mudford、Jeremy Keith 等 Clearleft 成员与大量外部友人，因此**这只能证明他与 Clearleft 有友好往来，不能证明雇佣关系**。
- 2019 年他的博客里还有一篇引用 Clearleft 的 Trys 与 James 的内容（"Fluid scale and tokens"），属于同业引述。

**[推断]** 萧潇的判断：任务书里"前 Clearleft 前端开发者"这个身份标签**缺乏一手佐证**，很可能是流传中的误传（他确实与 Brighton/Clearleft 圈子熟络，且与 Brighton 的 Cassie Evans 等人互动频繁）。**建议：在人物卡中不要把 Clearleft 写成他的履历事实**，或标注为"未经本人确认"。

**收入结构（[他做]）**：课程是主引擎；折扣活动是实际成交主力——**[他说]** "人们按原价买课的情况比你想的少得多。折扣活动往往就是让我们撑着的那个东西。"（https://bell.bz/its-been-a-very-hard-year/）

### 3.2 定价这一条最能看出价值排序

- **[他说]** 全价 **£249**，"£249 对我来说是天花板，因为再往上就是'得老板给你买'了"（beyond tellerrand 播客转录）。
- **[他做]** 支持购买力平价（PPP）折扣码（https://bell.bz/am-i-missing-your-country-with-our-purchasing-power-parity-system/）。
- **[他做]** 有专门的"说服你老板买课"邮件模板（piccalil.li/blog 系列）。
- **[他说]** "我们尽量让 Piccalilli 上的东西尽可能免费，而且**永远**不会 resort to paywall"（https://bell.bz/were-aiming-to-run-piccalilli-full-time/）。
- **[他说]** 作者分成："出版方常常给作者不到 20%，还要作者自己去推广自己的作品。我们不是这样。"（同上）

**[推断]** 他的商业判断里，"可负担"和"阅读体验"优先于"单位价格最大化"。可以验证的推论是：单课价格被他自己钉死在 £249 这个**个人可自付**的档位，且靠折扣周期而不是涨价来放大收入。

### 3.3 资助/众筹：被验证失败的那一半

- **[他说]** "我们的开放工作倡议一开始反响极好，但相比其他内容冷得离谱，到目前为止占我们总阅读量不到 4%。"
- **[他说]** "反馈好得难以置信，但真到要出钱的时候，支持远远不够……我们只能拔掉插头。"（2025-11）
- **[推断]** 这是本次调研里**最硬的"他做"证据之一**：一个他真心投入、公开背书、社区口碑极好的项目，他承认数据不行就关掉了——不是嘴上的"数据驱动"，是真关。

## 五、技术决策：CUBE CSS 的动机

### 5.1 他对既有方法论的不满（[他说]，2020-05-26 原文）

1. **对"CSS 不行"论的不满，落在语境缺失上**："如果有人保证 tech 里一定会有件事发生，那就是有人会宣称 CSS 干不了'大项目'，然后同一批人推荐的不是重 JS 方案就是一套全包 utility class（比如 Tailwind）。这些路子大多没错——我做早期原型挺喜欢 Tailwind 的——但建议的时候，'这是一个全新项目'这个语境总是被悄悄省略掉。"
2. **用数据反驳**：WordPress 约 36% 的网站，React 只有 0.3%。"记住这些数字很重要。"
3. **对 BEM 的定位**："BEM 本身很好，但它常常离 Cascading Style Sheets 越来越远。"CUBE 是**扩展** CSS，不是重造。
4. **对"组件库式设计系统"的批评**："狭义的、只看组件的隧道视野……那些其实不是设计系统，而是组件库。""更宽的 composition 常常胜过微观优化。"
5. **自我定位**："这不是一套文档厚重、结构复杂的 methodology……更像一种思考结构。"

来源：https://piccalil.li/blog/cube-css/ ；官方站 https://cube.fyi/

### 5.2 他给自己方法论划的边界（罕见的自我克制）

- **[他说]** "作为 CUBE CSS 的创造者我告诉你们，它**绝对不是**做事的正确方式……它只是对特定人、在特定语境下有帮助。"（2021-01-25，https://piccalil.li/blog/css-frameworks-hype-and-dogmatism/）
- **[他说]** "我很难说'你就该这么做，因为这是对的'，因为我不知道你的处境、你的代码库、你所在组织的目标。"（2025-03-27，https://piccalil.li/blog/if-it-works-its-right/）

### 5.3 Every Layout 的配套取舍（[他做]+[他说]）

- **[他做]** 定价 **$69**，含全部布局 + 生成器 + EPUB + Web Components 实现 + **终身免费更新**；免费开放 3 个布局（Stack / Sidebar / Switcher）与"rudiments"基础章节。来源：https://every-layout.dev/
- **[他说]** "几乎我们给 Every Layout 写的所有布局都是 `flex-basis` 驱动的……它不是'必须正好这么宽'，而是'这是理想宽度，你自己按情况判断'。"
- **[他说] 主动承认自己方案的长处与短处**："我们 2019 年写 Every Layout 时，Heydon 和我都在试图做出让浏览器替你做事的系统……但我知道'做浏览器的导师而不是微观管理者'并不适合所有人，所以我下面给一些对多数人管用的经验法则。"
- **[他说] 承认自己的方案也有维护债**：Piccalilli 的 header 用 CSS Grid 做的，"它很好看，但随着平台演化变得越来越笨重……命名区域（named areas）真的能缓解这类扩展问题。"
- **[他做]** 2025-07-10 他让 Heydon 在 Piccalilli 上重访 Every Layout 的 Sidebar 布局（"6 年后"），用 `:has()` 和选择器性能重新审视——**允许别人公开修正自己的作品**。来源：https://piccalil.li/blog/a-revisit-of-the-every-layout-sidebar-with-has-and-selector-performance/

## 六、`a-modern-css-reset` 的取舍

### 6.1 时间线与仓库现状（[他做]，GitHub API）

- 创建：2019-10-01（原属 `hankchizljaw/modern-css-reset`，后随账号改名到 `Andy-set-studio`）
- 代码最后变更是 **2021-01-18**（社区 PR：smooth scroll 只在页内聚焦时启用、尊重 `prefers-reduced-motion`）
- 最后两次 commit 是 2023-09-26 的两次 `Update README.md`——**README 被改成归档公告**
- 现状：`archived: true`，2,960 stars，419 forks，20 个未关 issue
- README 顶部原文：**"🚨 Important announcement: This version of the reset is now archived. You can read a more up to date one here."**

### 6.2 他**删掉**了什么（v1 → v2，可逐条对照）

| v1（2019）有 | v2（2023）情况 | 他的理由 |
|---|---|---|
| `ul[class], ol[class] { padding: 0; margin: 0; list-style: none }` | **删掉 padding 与 class 选择器**，改为只对 `ul[role='list']` / `ol[role='list']` 移除 list-style | "这造成了社区里的问题……**立刻移除 padding 和 margin 是我个人的偏好，但这东西已经爆炸式流行起来，那个理由再也站不住了**"（他的 issue #30 原文，2020-10-27） |
| `body, h1… { margin: 0 }` | 改为 `margin-block-end: 0`（用逻辑属性） | "总是倾向于剥掉 UA 的 margin，改用**更宏观的 flow 和 space**……用逻辑属性后我只移除尾部 margin，在生产里效果不错" |
| `body { text-rendering: optimizeSpeed }` | **删掉** | 未单独说明（v2 全文已无此属性） |
| `article > * + * { margin-top: 1em }` | **删掉** | 早期社区 issue #11 即反对这条（"我在 article 里不总是想要这个"），后续版本移除 |
| `input,button,textarea,select { font: inherit }` | 拆成 `font-family: inherit; font-size: inherit` | 更精确，避免连带继承其他 font 属性 |

### 6.3 他**保留**了什么，以及保留理由

| 保留项 | 他的理由（[他说]） |
|---|---|
| `*, *::before, *::after { box-sizing: border-box }` | "现在我们有灵活的布局、流体排版与间距，**这条规则不像从前那么有用了**。但项目里很少完全没有显式尺寸，所以它还是有一席之地。" ← 承认价值下降仍保留 |
| `html { text-size-adjust: none }`（含 `-moz-`/`-webkit-` 前缀） | 引用 Kilian 的说明；**明知前缀丑也留**："他也解释了为什么我们仍然需要那些丑前缀" |
| `ul/ol[role='list'] { list-style: none }` | Safari 的行为："如果你移除 list 样式，VoiceOver 的语义也一起没了。有人说这是 feature，有人说是 bug。我说这是蠢，但为了确保 `role` 被加上，我把它当成一个小小的奖励。" |
| `body { min-height: 100vh; line-height: 1.5 }` | **拒绝新单位**："用 `dvh` 很诱人，但如果你像 Ahmad 那样深挖，会发现它带来的问题比解决的多——这不是你希望 reset 干的事。`svh` 看起来比 `dvh` 好，但我对 `vh` 很满意。" |
| `h1–h4, button, input, label { line-height: 1.1 }` | 附带**自我警告**："如果你的字体上下延伸很大，这条值得删掉或改掉，否则会造成可访问性问题。" |
| `h1–h4 { text-wrap: balance }` | **主动标为不一定适用**："这条相当针对我们的项目……我想有人会觉得不合适，那你可能想删掉它。" |
| `:target { scroll-margin-block: 5ex }` | 附带条件："如果你有固定头部，你可能想调整这个。" |
| `a:not([class]) { text-decoration-skip-ink: auto; color: currentColor }` | "我们在工作室喜欢让链接默认继承文本的 `currentColor`，**如果你不这么做，那你大概想删掉它**。" |
| `textarea:not([rows]) { min-height: 10em }` | 粗指针（手指）场景下的可用性 |

### 6.4 一句话总结他的取舍判据（[他说] 原文）

> "重置这件事人们很较真，但实际上，浏览器现在真的好得不得了，你**可能根本就不需要一个**。我的建议是：从你找到的重置里挑你喜欢的部分，做一个**对你自己和你的团队**管用的。"

以及一句很关键的**非激进立场**：

> "我们也不会回头去客户项目上更新那个旧 reset，因为**那一个用着完全没问题**。"

来源：全部见 https://piccalil.li/blog/a-more-modern-css-reset/ ；他本人的 issue #30 https://github.com/Andy-set-studio/modern-css-reset/issues/30

### 6.5 三个"现实妥协"的实证（这比方法论更能说明判断标准）

1. **`0.01ms` 而不是 `0s`**（issue #5，2019-10-03，贡献者 atomiks 提出）：`prefers-reduced-motion` 里若把 duration 设为 0，`transitionend` 事件不再触发，会**打断依赖它的 JS**。→ 他合入并改成 `0.01ms` 保留在最终文件里，即今天 `modern-css-reset` 的代码。**为了不破坏功能而牺牲"理论上的纯粹"。**
2. **`ul[class]` 的 specificity 冲突**（issue #18 / #28）：社区反复指出 `ul[class]` 比重高于 `.flow > * + *`，导致 CUBE CSS 的 `.flow` 节奏失效。→ 他在 #30 里干脆**改掉自己的偏好**："立刻移除……是我个人的偏好，但这东西已经爆炸式流行起来，那个理由再也站不住了。"
3. **把 issue 锁住归档**：13 个 issue 全部 `locked: true`，等于**用关闭讨论来结束维护**。

**③ 他说"少依赖工具"（隐含），实际站点是无工具链反面教材**

> **这是他这条"少用工具"命题最直接的实证反驳。**

[他做] 2026 年他的个人站在重建中，他自己在公开连载里披露的实际栈：

- 三角化 monorepo（**Turborepo**）
- `apps/`：**Astro** 网站 + **Navi**（自研设计系统软件）
- `packages/`：CSS 系统、数据系统、设计 tokens、UI 组件/区域（Astro + Web Components）
- headless **WordPress** REST API 拉全部文章 + **Notion** + **AT Protocol / Bluesky**
- 图片走 CDN 替换、环境变量走根 `.env`
- 自写 `memoryCache.js`、自写多步 CLI 工具
- 追踪器：Fathom（唯一）

[他做] piccalil.li 本身的栈：[他说] "**Piccalilli 本身是用 TypeScript、Astro 和 JSX（通过 React）构建的**"（technologies-and-frameworks 一文）。这跟"少工具链"完全相反。

[他做] 同时，**他正把自己的站从 Eleventy 迁往 Astro**，并公开把 Astro 定为工作室首选平台（2026-04-22）。而他 2019–2023 年间是公开的"**Eleventy 超级粉丝**"（写过 Learn Eleventy From Scratch），Eleventy starter `hylia` 已经 archived。

**[推断] 结论**：他的真实判据**不是"工具多少"**，而是：
> 工具只要不伤害终端用户的体验（体积、性能、可访问性），就都可以用；他反的是"让用户付出代价的抽象"，不是"抽象"本身。

这是本次调研里**最值得写进人物卡的一句修正**——如果人物卡写成"极简工具链主义者"，会与可核对事实直接冲突。

**④ 方法论态度上的自相矛盾（轻）**

他一边说"不存在正确的方法论"、"我只是给建议"，一边在 2025 年说 CUBE CSS 是"**每一个项目里唯一的常量**"，工作室"所有人都非常熟练"。这不是错，但确实是"谦逊修辞"与"组织事实"的落差。来源：https://piccalil.li/blog/technologies-and-frameworks-we-use-in-our-design-studio/

**⑤ 反 AI 立场 vs 早期"AI 提升工作流"文章**

[他做] 他的博客列表里存在一篇 `14 ways to supercharge your workflow with AI`（2023-11 前后，位于 /blog/page/5）。该文现已不在 404 之外的常规抓取范围内，具体内容 **[未核实]**。按时间线它早于 2025-08 的《Our principles on AI》。**这条只能标为"时间线上的立场演变待核实"，不能直接判定为不一致。**

**⑥ "讨厌链接失效" vs 实际 404**

2021-12 他[说]保留 Piccalilli 文章是因为"我讨厌 link rot"；[他做] 2019 年那篇《Burnout – a long recovery》现在在 bell.bz 与 piccalil.li **都是 404**。

### 7.3 ⑦ 他说的"少依赖工具"其实是**别人的话**（重要澄清）

萧潇查遍他的一手文本，**没有找到**他本人主张过"网站不该有构建步骤"。他反复说的是：

- "**做浏览器的导师，而不是它的微观管理者**"（`buildexcellentwebsit.es`）

- "不要为了新东西而新东西：**如果某件事已经为你工作，就没有必要改**"（a-more-modern-css-reset）

**[推断]** 上述三条常被二手转述压缩成"极简 / 无工具链"，但原话里**没有反工具的成分**。这件事本身就该在人物卡里标注清楚，避免以讹传讹。

## 九、独立开发者的生存决策

### 9.1 结构：他选了"代理公司养活出版方"，而不是"出版方养活自己"

- [他说] "我们**没有外部融资**……LinkedIn 上的人管这叫 bootstrapped。"（2025-11）
- [他说] "我们**幸运地在 Agency 之外还有一块**，所以没有压力要让这玩意承担整个业务的收入。"（2026-06 播客）
- [他说] 反向逻辑："**有了课程的被动收入，压力真的减轻了**，让我们能专注最擅长的事……以前我们不得不接企业工作和后端/集成工作，那把我们榨干了。**问题是，那类活*付钱***。"（2024-12）
- [他做] 因此 2024–2025 的路线是：**课程收入 → 少接"只为钱"的企业集成活 → 聚焦品牌/前端/设计系统**。

**[推断]** 这是一个非常清晰的取舍：他宁可**同时经营两种生意**（代理 + 出版），也不愿让内容业务单独承担全部生存压力。而在 2021 年，正是因为让内容单独承担压力，才导致了公开的关停。

### 9.2 收入困境的公开记录（[他说]，时间序）

1. **2021**："我**不停地监控'收入'，这让人精疲力竭又有压力**。"
2. **2023**：客户端最冷清的一年，"询盘量最少"，但"我基本没慌，因为看起来全行业都是这样"。
3. **2024**：客户端"**还是**很难，但在一点点变好"。
4. **2025-07**："2025 年目前比 2020 年还难，我知道我不是唯一这么感觉的人。"
5. **2025-11**："**按原价买课的人比你想象的少得多。折扣活动往往就是让我们撑着的那个东西。**" 并公开 List 了三种求助方式（买课、转介、雇他们）。
6. **2026-06**："**去年比我们希望的冷清很多**。" 归因于：AI 带来的行业位移 + 经济下行 + 地缘不稳 + 裁员，**同时拒绝把它全部怪在 AI 上**。

### 9.3 财务心态的自陈（少见的坦白）

- [他说] "**对财务保持冷静（工人阶级出身永远不会消失）**" —— 这是他 2024 年的年度目标之一，自评"艰难转型，算半个达成"。
- [他说] "归根结底，我只想**过得舒服、养得起家**。Set 团队完全一样。我们不是想 Get Loaded™ 买极其没品的兰博基尼。"
- [他说] "我们是一个有家庭、有房贷/房租要还的四人团队。"

### 9.4 他把"生存"与"道德"绑在一起（并付出了成本）

- [他说] 拒接 AI 产品营销工作 → 而"**绝大多数询盘正是这类**"。
- [他说] 为 2025 黑五预热时坦言目标："要跑得和去年一样好或更好"，"**今年到目前为止，那还没发生。**"
- [他做] 结果：Black Friday 之后他[说]"我们的黑五销售**猛涨**，明年也有了好客户活"（2025-12-19）。

**[推断]** 生存策略总结为三条：①公司结构上双引擎（代理 + 出版）②价格与渠道上靠折扣周期而非涨价 ③道德上划死线并愿意为此少赚钱——但**第③条需要第①②条兜底**，且他自己已公开承认 2025 年一度兜不住。

## 十、矛盾与未解决之处（原样保留，不做调和）

1. **Clearleft 身份之谜**：任务前提是"前 Clearleft 前端开发者"，他本人所有一手材料里没有这个身份；Clearleft 官方 15 周年页里他只以**外部友人**身份出现。→ 未解决。
2. **Piccalilli：2021 说"完了，我不干了" vs 2023 说"它回来了" vs 2025 说"要全职做它"**。同一件事三年内三次公开定调，且每次都给了不同理由（第一次是倦怠，第二次是团队到位，第三次是商业逻辑成立）。→ 未调和。
3. **"我讨厌链接失效" vs 自己文章的 404**。
4. **Tailwind 立场前后不一**：2021 定性为"天真 + 不诚实的赚钱方式"，2025 说自己"什么都不 hate"、并把它列为工作室栈的一部分。
5. **"没有正确方法论" vs "CUBE CSS 是每个项目唯一的常量"**。
6. **"少做、慢做、可持续" vs 实际工作强度**：2020→2021→2022→2023→2024→2025 连续六年自评"工作太多/倦怠/翻车"，每年都立"少工作"的目标，2025 年仍然是"9 场演讲 + 26 万字 + 2 门课"。
7. **"保持小团队" vs "要让 Piccalilli 四人全职"**：前者是 2024 年撤回翻倍目标时的说法，后者是 2025 年的目标；两件事分别针对工作室和出版方，但用的人力和他的时间是同一份。→ 未解决。
8. **"我要少做表格多写 CSS" vs 同期启动的 monorepo/Astro/Navi 大型工程**。→ 未解决。
9. **`modern-css-reset` 的定位矛盾**：v2 文章说旧 reset"没有老化得很好"，但同一篇结尾说"我们不会回头去客户项目上更新那个旧的，因为**那一个用着完全没问题**"。
10. **反 AI 的绝对立场 vs 曾写过 "14 ways to supercharge your workflow with AI"**（2023-11）。该文内容未核实，无法判断是立场演变还是自我矛盾。
