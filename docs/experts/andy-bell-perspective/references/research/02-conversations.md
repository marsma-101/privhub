## 二、被追问时的回答方式（附具体片段）

以下六种是他的固定套路，按出现频率排。

### 2.1 先自嘲卸压，再给实质回答

被问到「为什么自己另立一套方法论，市面上已经那么多」——这是典型的质疑式追问：

> Drew：Why publish your own?
> **Andy**：Yeah, yeah. Why make your own? That's a very good question. I think those who know me well know **I like to sail against the tide a lot**. It's mainly because I tend to do lots of varied projects as well, in varied teams. So it's very hard, I've found, to work with BEM with a traditional developer…
> — [Smashing Podcast Ep.19](https://www.smashingmagazine.com/2020/06/smashing-podcast-episode-19/) [一手]

注意结构：**重复对方的追问 → 承认这是个好问题 → 给出真正的理由（跨团队/跨项目的人因素，不是技术优越性）**。

### 2.2 立刻把话说回对方身上，主动引入反方视角

被追问「CSS 和 JS 越来越缠在一起」时，他先说自己的不适，然后**主动替对方说出反对意见**：

> **Andy**：…they are becoming more and more entwined with each other, whether you like it or not. It's a common language for them. **As you can see by my face, very much not**, but there you go. **You're probably thinking, "Actually, I've been working with react quite a lot recently, so I'm the other way round." So I can see that as well.**
> — [Smashing Podcast Ep.19](https://www.smashingmagazine.com/2020/06/smashing-podcast-episode-19/) [一手]

**他不是在被追问后才退让，而是提前把对方的立场讲出来。** 这是他最有辨识度的习惯。

### 2.3 会说「我不确定」，而且说得干脆

面对「CSS Modules 和 web components 有关系吗」的直播间提问：

> **Andy**：CSS modules… As in the…? I don't think so. Is CSS modules the JS interface for CSS, innit? **No, I think that they're just part of the JS world. But I don't know. I'm not the person to really ask about that. It could be, but not my knowledge.**
> — [Some Antics, 2021-04-28](https://someantics.dev/dang-spicy-web-components/) [一手]

面对「custom element 和 web component 是不是一回事」：

> **Andy**：No. **I don't really know the scientific difference. I'm not a very smart person, Ben.**
> — 同上 [一手]

面对「constructor 在做什么」：

> **Andy**：…you construct the class. And **please don't ask a computer science question because I don't know the answer.**
> — 同上 [一手]

面对直播间问「Shadow DOM 到底在干什么」时的态度是直接给立场而不是知识：

> **Andy**：So… I'll be honest, **I'm not a fan of the shadow DOM at all.** I think it's got some benefits… But what I don't like is that not all CSS can be pulled in. You find yourself defining things twice, three times a lot.
> — 同上 [一手]

**归纳**：他区分「我不知道」和「我不喜欢」很清楚，两者都用第一人称直说，不糊。

### 2.4 被追问到「有没有缺点」时，用玩笑挡一下，再给真答案

Smashing 那一集，Drew 最后的追问是「用 CUBE 有没有什么你意识到的坏处？有什么问题是它不打算解决的？」他的第一反应是自嘲：

> **Andy**：Yeah. **This accent, Drew, it just won't go way, no matter what I do!** In all seriousness, I think CUBE's got as close as I can get to being happy with the front-end, which is saying a lot, I think. **You never know, things might change again.** This has evolved over more recent years. **Give it another five years, I'll probably be struggling with this and trying something else.** … **This definitely won't work for everyone as well, I know that for a fact. I know that from my comments. I don't expect it to work for everyone.**
> — [Smashing Podcast Ep.19](https://www.smashingmagazine.com/2020/06/smashing-podcast-episode-19/) [一手]

**「我知道这一点，我从我的评论区知道」**——他用反对意见当作自己的信息源，而不是当作攻击。

### 2.5 反问式回应（这个习惯确实存在，但用在具体技术问题上）

在 Some Antics 的直播里，每当 Ben 问「你会怎么用」这类开放式问题时，他高频地把问题折回去。典型：

> **Ben**：So what *are* the sort of things that you would use them for?
> **Andy**：So, contained… 'Cause if you go on, like, one of the articles on Piccalilli, **I'll show, I'll highlight in this a little web component.** So, those little FYI callouts — that's a web component!
> — [Some Antics](https://someantics.dev/dang-spicy-web-components/) [一手]

更直接的例子——被问「有没有推荐关注的 web component 库」时：

> **Andy**：Oh, I think I'd always reach for lit-html. Or Lit, as it's called, like you said, isn't it, now? **I got into web components. I made a site — I don't even know if it's still live. I'll have to check.** It's, like, webcomponents.club.
> — 同上 [一手]

**观察**：在**技术**追问上，他偏向「用现场演示替代抽象回答」；在**立场**追问上，他偏向「先讲自己的语境/经历，再给结论」。他不太用「那你觉得呢」式的对拆，而是用「我把我的现场给你看」。

### 2.6 用「我不知道 / 我不会预测」明确划界

被 Marc Thiele 追问「你够不够胆预测 AI 会走向哪」时：

> **Andy**：…**It's until I see some serious regulation, until I see some serious environmental changes.** I mean, the toothpaste is out of the tube, right? … **And if I was to predict then look, wait until the sort of quarter four numbers start coming in from the AI companies.** … **I think that's as broad as I'll go with the prediction.**
> — [beyond tellerrand #005](https://beyondtellerrand.com/blog/podcast-andy-bell-005) [一手]

他**不拒绝预测**，但会给预测加明确边界（「我只能讲这么宽」），并把预测挂在可观测的数字（Q4 财报）上，而不是情绪上。

## 四、改变立场的瞬间

这是他身上信息量最大的部分。以下每条都有原文，按「变了什么 → 证据 → 时间线」排。

### 4.1 对 Sass：从「别抛弃 Sass」到「我多年不用 Sass 了」

- **2019-09-18**（State of the Browser 演讲书面版）：
  > "**we don't have to abandon Sass because native language features are coming.** It's probably better to cautiously pre-compile your CSS and not force the browser to work as hard. … **The beauty of Sass is that you can have the best of both worlds.** … To me, it feels like a pretty perfect setup."
  > — [archive.hankchizljaw.com](https://archive.hankchizljaw.com/wrote/keeping-it-simple-with-css-that-scales/) [一手]
- **2020-06-30**（Smashing 播客）仍然："I do it with Sass."
- **2022-01-28**（Tailwind 试验）为了项目协作**主动放弃 Sass**：
  > "it's looking we can't really use Sass, which **I am a fan of** for keeping my CSS nice and organised. … so **I'll pass-up Sass**, just like the other developers are passing-up using Tailwind for everything."
  > — [bell.bz](https://bell.bz/i-used-tailwind-for-the-u-in-cube-css-and-i-liked-it/) [一手]
- **2025-04-24**（Kevin Powell）已经不用了：
  > "I've got that with like mixins. **I've not used SAS for years now and I've sort of learnt to work without mixins.** So I'm not, wouldn't say I'm overly enthusiastic about mixins, but when they do come around, like, unless you have a real need for them, then don't feel like you have to use them."
  > — [zencastr.com](https://zencastr.com/z/e0WhgZQ9) [一手]

**这是最干净的一次完整转向：立场从「Sass 是完美方案」变成「没有 mixin 我也能干活」。**

### 4.2 对 Tailwind：从「让我心脏病发作」到「我做了一个 Tailwind+CUBE 原型而且我喜欢」

- **2019-09-18**：
  > "An example that gives me **a heart attack** is Tailwind CSS generates over **40 thousand lines of CSS by default**. Bonkers."
  > — [Keeping it simple…](https://archive.hankchizljaw.com/wrote/keeping-it-simple-with-css-that-scales/) [一手]
- **2020-07-29**（Vienna 幻灯）把这个数字更新为更具冲击力的版本：
  > "Tailwind CSS default output: **80,936 lines** / **102kb** weight"
  > — [noti.st](https://noti.st/hankchizljaw/qUTfFB/present) [一手]
- **2021-04-28**（Some Antics）口径明显软化，并解释自己被误读：
  > "**I actually have. And this is, I think this is something that's quite misunderstood about me, is I don't actually have a problem with it.** I've used it for quite a few projects in the past. The thing I don't like, and the thing that always turns me off things, is… **Enthusiastic evangelism is a big turn-off for me.**"
  > — [someantics.dev](https://someantics.dev/dang-spicy-web-components/) [一手]
- **2022-01-28** 亲自动手做原型并公开改口：
  > "**I used Tailwind for the U in CUBE CSS and I liked it.** … **I'm very often accused of being a "Tailwind hater", but the reality is that I see flaws in using it for _everything_ and people don't like that.** I also vehemently dislike how it is marketed… which is often mistaken for "hate" of the whole project. I actually used Tailwind for a project _way_ back in 2018 when it was a much younger tool, so it's not like I haven't had exposure to it to form my opinions, which from that experience, **were not overly positive. That is less the case now**, as I've just demonstrated. … What Tailwind is though, is a tool that has **evolved _very nicely_**."
  > — [bell.bz](https://bell.bz/i-used-tailwind-for-the-u-in-cube-css-and-i-liked-it/) [一手]
- **2020-06-30**（Smashing）他其实早说过喜欢 Tailwind，只是常被忽略：
  > "I actually like Tailwind CSS. I think it does work, and I really like using it for **prototyping** because I can really put something out really quick. But I think it **just goes a little bit too far**, does Tailwind."
  > — [Smashing Ep.19](https://www.smashingmagazine.com/2020/06/smashing-podcast-episode-19/) [一手]

**注意**：这不是「从恨到爱」。他 2020 年就已经说喜欢了。真正的变化是：**2019 年他把它当反面教材用数字打，2022 年变成了「我用它，而且报告里列了我喜欢和不喜欢的具体条目」。** 呈现方式变了，不是立场翻了个面。

### 4.3 对「说自己是纯粹的 CUBE」：从自嘲到明显是玩笑

> Drew：So there's no such thing as pure CUBE?
> **Andy**：**The way I write it is pure CUBE, Drew. Everyone else is just a fake, it's just a weak immitation.** …
> Drew：Apart from to you, no-one can say, "That isn't textbook CUBE."
> **Andy**：**No, that's it. No-one can dispute that really, can they?** So, yeah, I'll go with that. Gives you a bit of clout or something…

### 4.4 方法论命名：C-BEUT → CUBE，他公开说前一个名字「是垃圾」

> "I did a talk… called Keeping it Simple with CSS that scales, and in there I sort of introduced an earlier version of it called **CBEUT, which was Cascade Block Element Utility Token. It was rubbish. I hated the name of it.** … I think CUBE is a little less rubbish."

2019 年书面版里他写的拼法是 **C-BEUT**（Cascade / Block / Element / Utility / Token），与播客里的 CBEUT 是同一物的不同写法。**[冲突保留]**。注意实质变化不止名字：**C-BEUT 没有 Composition（组合层），CUBE 把组合提到了第一位**。他自己解释这是 Every Layout 带来的：

I spotted a spacing mechanism that had been invested, which was very complicated, and I thought, "**This person has not learnt what padding is** because padding would actually fix this problem for them…" **That's not to be snidey about it.**

**他换框的方式是：从「工具问题」改成「学习问题」，并且补一句免责（"That's not to be snidey about it."）。**（本条也属于第五节：他回避的话题。）

## 六、谈无障碍与渐进增强时的原话

### 6.1 渐进增强：他的定义是「下限必须可用」

> **Andy**：**Progressive enhancement is my thing.** So, wherever you use, as long as what gets delivered to the front end is **HTML, functional HTML by default** — so if nothing else arrives down the pipe, you've still got a usable website that's **acceptable and accessible** — then it's all good. And you could use whatever you want to do… as long as what arrives, if the only thing that arrives is the HTML, it works, and you can use it. **And then everything else on top of that is a bonus.** So CSS — great, that works now it looks good. And then JavaScript, it's definitely a sort of **an additional sprinkling of functionality rather than the whole thing.** … even when I've built like React projects is being SSR to make sure that **if the client fails, which it will — there's, there's a will about it** — and then make sure they still work.
> — [That's My JAMstack, 2019-08-28](https://thatsmyjamstack.com/episodes/andy-bell/) [一手]

注意那个措辞修正：**"there's not a sort of might about it, there's a will about it"**——JavaScript 失败不是「可能」是「一定」。这是他谈渐进增强时最锋利的一句。

### 6.2 HTML 优先，且他对行业 HTML 水平有明确判断

> **Andy**：I think **one thing our industry is lacking big, big time on is knowledge of HTML**, especially — and CSS, but mainly HTML. … I see a lot of documentation, a lot of popular websites and code samples using **very poor markup**. … So there's definitely a space for — I'd say, **lazy developers, you don't want to learn markup**, because **it is the core thing on the website is HTML**, you know, you can't have a website without HTML. I think there's space for someone to just do it for them, to **put out an accessibility fire** as I like to call it — just **reduce one more opportunity for someone to have a miserable experience with assistive technology**…
> — [That's My JAMstack](https://thatsmyjamstack.com/episodes/andy-bell/) [一手]

**"reduce one more opportunity for someone to have a miserable experience with assistive technology"** — 这是他谈无障碍时最接近「情绪」的一句。

## 七、对组件框架（Vue / React）与组件级样式的立场

**这一节按任务要求逐条做如实记录，包括「他没表态」这个结论本身。**

### 7.1 【有明确表态】他个人做响应式项目会选 React

> **Andy**：**If I was to take a client project on tomorrow and the requirement was lots of reactivity, realistically, I'd probably pick React, because I know I can write all that out, no problem.** But if I really wanted to lean into, like, say it's part of a design system, straight away I'd be like, "Right, I need web components," so I'd use **Vue** or something like that as my application layer.
> — [Some Antics, 2021-04-28](https://someantics.dev/dang-spicy-web-components/) [一手]

**这是本次调研中他对 React / Vue 最直接的一次表态。** 注意它是**功能分工**的表态，不是好坏评价。

### 7.2 【有明确表态】对 Shadow DOM（组件级样式隔离的主要机制）持否定

> **Andy**：**I'm not a fan of the shadow DOM at all.** I think it's got some benefits. It's got that protective… The shadow DOM's a sort of response to people wanting, like, strict componentization and no outside influence coming into the component, which is cool. **But what I don't like is that not all CSS can be pulled in. You find yourself defining things twice, three times a lot.** And the way I do CSS is, like, CUBE CSS stuff, and that uses, like, a lot of references to tokens and stuff, so **I don't want to be pulling in the same CSS file every time I pull a component.** This is why, like, at the start I said I don't really use the shadow DOM, because I don't really find it very useful for the context that I work in.
> — [Some Antics](https://someantics.dev/dang-spicy-web-components/) [一手]

**这是「组件级样式隔离」问题最接近的核心表态**：他不反对隔离本身，他反对**隔离导致 token 体系要重复定义**。

### 7.3 【有明确表态】他建议把组件写成「只负责渲染的纯函数」

> **Andy**：a tip I can give just for any sort of, like, JS-driven development is, like, **try and treat your components as just components that do nothing but render results. So a component is almost, like, just a function that returns something back, and the something that it returns back is a bit of HTML.** If you write your components like that and really lean into, like, props being passed into them, you can put that component wherever you want and integrate it into whatever you want as well.
> — 同上 [一手]

这是他对**组件结构**最有内容的一次公开表态：**组件 = 接收 props、返回 HTML 的函数，无其他副作用。**

### 7.4 【有明确表态】React 的事件系统是障碍

> **Andy**：the one thing I see — now, I do a lot of design system stuff — is that, regardless even if there's a JavaScript framework being used, that web components are used to render the actual components themselves. So **I see this in a Vue context quite a lot.** … **It doesn't really work in React because React reinvented events for some unknown reason.**
> — 同上 [一手]

配套事实（他当场读的第三方数据）：他引用了 [custom-elements-everywhere.com](https://custom-elements-everywhere.com/)，指出 **React 支持度约 70%，Vue 与 Svelte 为 100%**，并评价：

> **Andy**：So React is still 70%, which is… **if you consider the amount of resources that get pumped into React, pretty poor, innit?** Especially you've got, I've never even heard of Riot.js, but there it is, rocking 100% support in there.
> — 同上 [一手]

### 7.5 【有明确表态】对「组件化」的批评：组件不等于设计系统

> "This is often where I see **narrow, component-only tunnel vision** fall short and really, these approaches are **less design systems, but more component libraries that solve a much narrower cohort of problems.**"
> — [piccalil.li/blog/cube-css](https://piccalil.li/blog/cube-css/) [一手]

> "the **LEGO blocks analogy isn't that relevant** in the wider context of design systems. It is very useful at explaining a component's role in an overall project, though."
> — 同上 [一手]

> "it doesn't matter how small your components are, at some point they're going to be pages, they're going to be views. **You cannot avoid that.**"
> — [Smashing Ep.19](https://www.smashingmagazine.com/2020/06/smashing-podcast-episode-19/) [一手]

### 7.6 【有明确表态】2023 年公开用数据贬低 React/Vue 的产业占比

> "**React is used by 4.0% of all the websites whose JavaScript library we know. This is 3.3% of all websites.** … **Vue.js is used by 0.9% … This is 0.8% of all websites.** … Even if you add together React and Vue, it's still **less than 5% of all websites.** … the difference between the majority of the web industry — AKA people slinging websites with WordPress etc — and the loud, but very small web industry is **huge.**"
> — [bell.bz/the-extremely-loud-minority, 2023-02-14](https://bell.bz/the-extremely-loud-minority/) [一手]

> "It's understandable to think that JavaScript frameworks and their communities are eating the web because places like Twitter are awash with very loud voices from said communities. Always remember that although a **subset of the JavaScript community** can be **very loud**, they represent a **paltry portion of the web as a whole**."
> — 同上 [一手]

> "**considering React has been around for a decade now, < 4% share of the top 10 million websites is _pathetic_**"
> — 同上 [一手]

**这是本次调研中他对 React/Vue 态度最尖锐的原文，出现在他本人写作中，不是播客即兴。** 有读者在 Adactio 上链接过这篇文章（[adactio.com/links/17526](https://adactio.com/links/17526)）。

### 7.7 【未核实 / 他没表态】Vue SFC 的 scoped CSS、React 的 CSS-in-JS 组件级方案

**结论：本次调研未找到他针对「Vue 的 `<style scoped>`」或「React 的 CSS-in-JS（styled-components / Emotion 在组件内写样式）」做过具体、正面表态的任何一手材料。**

- 他在 CUBE CSS Vienna 幻灯里把 "Just use Emotion / Just use Styled components / Just use CSS Modules" 作为**并列靶子**列出，这是**对「工具选择」的整体态度**，不是对**组件级样式机制**的技术评价。[一手，[noti.st](https://noti.st/hankchizljaw/qUTfFB/present)]
- 2019 年他对 CSS-in-JS 的批评是**成本/债务角度**（Wonga 贷款类比），**不是**「组件内写样式不合架构」的角度。[一手，[archive.hankchizljaw.com](https://archive.hankchizljaw.com/wrote/keeping-it-simple-with-css-that-scales/)]
- **【推断】** 综合 7.2 与 7.5，他对「组件级样式隔离」的**实际态度**是：不反对隔离，反对隔离破坏全局 token 体系。但**这个归纳是我做的，他没有用这个措辞说过。**

### 7.8 【重要】他自己的项目里是框架混用的，而且他不觉得这是问题

- Piccalilli 曾用 Eleventy，**2021 年重平台到 Next.js**，但**刻意不渲染客户端 JS**：
  > **Andy**："So I recently, this year, I replatformed the old Piccalilli site from **Eleventy to Next.js**. And all of the web components for Piccalilli, I just copied and pasted into the new project and it worked straightaway. **So I don't render any client-side JS on this project. I use Next as a sort of backend almost.**"
  > — [Some Antics](https://someantics.dev/dang-spicy-web-components/) [一手]
- 2018 年 JavaScript Jabber 官方对他的介绍原文：**"an independent designer and developer who uses React, Vue, and Node"**。[一手官方简介]
- 但他 2019 年也把 Gatsby 当反面案例讲（"[Gatsby 的] 一个 5,500 页的站点，构建要 45 分钟"）；同一次直播里他也承认"如果他们有一队 React 开发者，想要一个大家都能快速上手的工具，**我能理解**"。[一手]
- 2025 年他说自己**基本不做生产代码了**："generally **I don't really do any production work for the agency. Like it's very rare.**" — [Kevin Powell](https://zencastr.com/z/e0WhgZQ9) [一手]

**结论（如实记录）**：他对组件框架的立场是**分层且带条件的**——
对一个**新客户项目且重响应式**→ 会选 React；
对**设计系统**→ 选 web components，应用层用 Vue 或 Svelte；
对**自己 Piccalilli 的内容站**→ 用框架当后端，不出客户端 JS。
**他不是「反组件框架」的人。他是「反把框架当默认答案」的人。**

> — 同上 [一手]

### 8.6 他反复问的那个真问题

他 2019 年演讲结尾用了一个自我设问的环节，2025 年课程里仍然保留：

> "**Why didn't you use this tool? And why didn't you use that tool?** … all of these tools are really useful and all these new capabilities are really useful, but **unless there's a need for it, you don't have to necessarily learn it or you don't need to use it.** So like **don't force layers in unless you need to use layers and don't force nesting in unless you need to use nesting** and et cetera, et cetera. **It's like, try not to like use a feature because it's cool and new. Try to be more pragmatic about what features you want to use.**"
> — [Kevin Powell · General Musings, 2025](https://zencastr.com/z/e0WhgZQ9) [一手]

### 8.7 但——他对构建步骤并不一律反对

这一点容易被误读，必须单独标出：

> "**Basically, what I'm saying is we don't have to abandon Sass because native language features are coming. It's probably better to cautiously pre-compile your CSS and not force the browser to work as hard.** … why make it work harder just so you can have native nesting? **It smells like developer experience over user experience to me.**"
> — [Keeping it simple…, 2019](https://archive.hankchizljaw.com/wrote/keeping-it-simple-with-css-that-scales/) [一手]

**他的判据不是「有没有构建步骤」，而是「这个构建步骤是替浏览器省钱还是替开发者省事」。** 2019 年他因此支持 Sass；2025 年他不用 Sass 了，但规则没变——只是他发现没有 mixin 也能满足这个判据。[推断，基于两处原文的对照]

### 8.8 时代错位的批评方式

> "**Bye Bye AutoPrefixer we will not miss you**"（Vienna 幻灯）
> "**We've never had it better with browsers**"（mentor 幻灯）
> "**Old browsers will still get a good baseline experience**"

[一手，两处幻灯]

## 十、矛盾与未解决之处

**原样保留，不做调和。**

### 10.1 CUBE 是「唯一正解」还是「仅供参考」？

**同一集播客里两句话并置：**

> **Andy**：The way I write it is pure CUBE, Drew. Everyone else is just a fake, it's just a weak immitation.
> **Andy**（同一集）：**I don't expect it to work for everyone. I don't expect anything to work for everyone.** … **Any method is extremely valid for your context** and if this is how you write your CSS, **keep doing what works for you and your team**.
> — [Smashing Ep.19](https://www.smashingmagazine.com/2020/06/smashing-podcast-episode-19/) ＋ [piccalil.li/blog/cube-css](https://piccalil.li/blog/cube-css/) [一手]

**处理**：前者是玩笑（对话语气明确），后者是正式立场。但**两者的并置本身是他公开形象的一部分**，不消解。保留。

### 10.2 他对 Sass 的支持 vs 他 2025 年不用 Sass

已在 4.1 逐条列出。**未解决的点是：他从未公开解释过为什么放弃 Sass。** 2022 年那次放弃是被项目条件逼的（能理解），2025 年说"多年不用了"是主动的（无法解释）。**[未核实]**

### 10.3 他批评 Gatsby「5,500 页构建 45 分钟」，但自己把 Piccalilli 搬到 Next.js 后「全站构建要 8 分钟」

> **Andy**：And **this Next site is slow.** You know, it takes, like, **8 minutes for the whole site to build now.** Whereas I think in the Eleventy site, before I moved, it took **8 seconds** to build the entire site from scratch. … Can't beat it.

### 10.4 他反复批评 Tailwind，但他自己的文章标题就是「我用了 Tailwind 而且我喜欢」

已在 4.2 列出。第三条事实：**他在 2020 年就说过喜欢 Tailwind，但 2019 和 2020 的幻灯仍把它当反面教材。** 这三件事同时为真。
