### 偏差明细

**偏差 1.1（题 1，中度）· SKILL.md 用"36 年零转向"掩盖了一次实质性松动。**
- 位置：L213（"36 年零转向，是他一生最稳定的一条"）、L89（身份卡"1988 年之后我停止写代码"）、L370（时间线只列 2008 Interaction08 一句）。
- 后果：下游 agent 被引导成"他对此问题从无动摇"，与用户问题直接冲突。
- 建议改法：在 L213 之后补一句分档说明——

> **论证变过三次，结论没变，但有一次松动**：2008 Interaction08 他承认"不写代码 = 没有权力"（"We are not very important because we don't cut code."，观众当场嘘声）；2017 年他把"要求设计师会写代码"定性为掩盖真问题（"breathless demands for designers to 'know code' masks bigger problem of coders steamrolling designers"，UX Podcast #155）；2018 年他干脆否认提问前提（"should designers waterski"）。**2008→2017 之间他否定了自己 2008 年承认的那个前提，这是实质性松动，不只是修辞变化。** 引用时须说清是哪一年。

**偏差 1.2（题 2，中度）· 把四段摆动压缩成一个词，且遗漏了"2009 年后未再否定敏捷"。**

- 建议改法：把 L370 那一格扩为四段分期，并追加一句：

> **关键补充**：未见其 2009 年之后公开否定敏捷的记录；相反，2024 年他人回忆显示他在一场名为 *Agile Up to Here* 的工作坊中与 Jeff Patton、Elisabeth Hendrickson 同场合作，主题正是"如何把设计放进敏捷"。**他从未公开收回 2008 年初那句"几乎没有前期设计的想法是荒谬的"，也从未自认改口——这是本次调研中最明显的未和解矛盾。**

## 测试 2 · 边缘测试（Edge Case）

**题目**：「一个自托管的文件管理系统，有 50 个插件自动装配，界面由插件把自己的按钮与面板塞进 21 个插槽。要不要把这些入口重组成以用户任务为中心的导航？」

**实跑方式**：严格按 SKILL.md 的「回答工作流（Agentic Protocol）」走一遍：Step 1 分类 → Step 2 三维度 → Step 3 组织输出。下面是实跑记录。

### Step 1 · 分类（按 L35-42）

判定为**混合问题**（用具体案例讨论抽象道理）：题目描述的是一个真实存在的系统架构，且用户要改进的系统"就在手边"。因此必须**先取案例事实**（去读插件清单、注册点），再用框架分析，两边分开说——SKILL 的这一条是可执行的、正确的。

### Step 2 · 三维度实跑

#### 维度 A · 实现模型检测（L48-59）——**可操作性最高的一维**

| 要读什么 | 本场景能否落地 | 实测 |
|---|---|---|
| 看清单文件 / 注册点 / 依赖声明 | ✅ 能 | 读各插件目录下的 `manifest.json` 即可 |
| 数"插槽/挂载点"与"提供者"的数量比 | ✅ 能，且是本题最锋利的一刀 | 21 插槽 vs 50 插件；若插槽名与插件近似 1:1 → 插槽边界 = 代码边界。**这条判据可量化、可复核，是本协议里最好的一条** |
| 界面用词来自哪一侧（插槽/插件/容器/实例…） | ✅ 能，但是**判据本身有瑕疵**（见问题 2） | 可以直接 grep manifest 的 slot 名 |
| 一个界面位置有几个"老板" | ✅ 能 | 数同一 slot 被几个插件注册，>1 即命中 |
| 入口顺序依据 | ✅ 能 | 看渲染代码是遍历 manifests 还是按权重排序 |
| 新增顶层入口要改哪些文件 | ✅ 能，且能给出判决 | grep 中心化的 `switch` / `if-else` 白名单 |

**结论**：维度 A 的取证手段**具体到可以直接执行**，是本协议最有价值的部分。

#### 维度 B · 目标与用户检测（L61-70）——**可操作性中等**

| 要读什么 | 能否落地 | 实测 |
|---|---|---|
| 每个功能问"什么任务/什么目标" | ✅ 能，但纯人工判断 | 50 个插件逐个问，工作量大 |
| "用户"是否弹性（有没有可核对的原型定义） | ⚠️ **本场景下问不到点上** | 见问题 4 |
| 默认界面是给谁做的（新手/中间/专家三分类） | ⚠️ 能问，但**前提不成立** | 自托管单人系统没有"默认用户群" |
| 谁是设计者（设计与实现是否同一方） | ✅ 能，且本题极可能直接命中 | 若插件作者 = 使用者，模型 5 的"利益冲突"在此**不成立**（见问题 4） |

#### 维度 C · 成本与礼貌检测（L74-82）——**一半可执行、一半落不了地**

| 要读什么 | 能否落地 | 实测 |
|---|---|---|
| 每个控件算两笔账（excise + 导航负担） | ❌ **落不了地** | 没有计量单位、没有数据源、没有阈值。"算两笔账"实际只能输出定性形容词 |
| 反比律定量判据（用得越少、交互成本应越低） | ❌ **落不了地** | 判据需要"使用频次"数据。自托管单人系统**没有埋点、没有日志**，频次只能靠猜——而 SKILL.md 恰恰要求"先看真实材料，不凭感觉说话" |
| 数确认框 / 错误提示总数 | ✅ 能 | grep 即可 |
| 错误文案是否"归咎用户" | ✅ 能 | grep `操作失败 / 数据无效 / 非法输入 / 请检查格式` |

### 可操作性总评

- **维度 A：可直接执行。**取证手段具体到文件类型、字段名、统计口径，这是本 Skill 最强的一环。
- **维度 B：可执行但有两处前提错配。**它把"组织有大团队、有设计师、有用户研究预算"当成默认背景；对一个单人自托管系统，问"用户是否弹性""设计者与实现者是否分离"会得到**无意义答案**。
- **维度 C：一半落不了地。**成本侧两笔账缺计量口径，反比律缺频次数据源；只有"数确认框/错误文案"这一半能跑。

### 明显缺失的维度（Cooper 显然会问，但协议没让他问）

1. **缺失：决策者与使用者是不是同一人？**
   这是本题最该问的第一个问题。SKILL.md 自己在模型 4 的失效条件里写了"**决策者与使用者分离的采购场景**"，但没把它变成一个研究步骤。自托管系统的所有者 = 唯一使用者时，"重组导航"这个动作的正当性来源完全不同。**协议里应该有一条 Step 0：先判定"谁在抱怨、谁在使用、谁在承担成本"，三者不同人时结论会反转。**

2. **缺失：现有的「21 个插槽」本身是不是已经变成了用户的心智模型？**
   这正是模型 8（idiomatic beats metaphoric）的直接应用点——"一个结构之所以成立，不是因为它像现实，而是因为**用户已经学会了它**，所以它可以被改掉，**只要新方案更可学**"。协议给了"往哪推"的方向（模型 1），却没给"能不能改"的前置检验。没有这一问，协议会系统性地偏向"重构成任务导向"，而 Cooper 本人的立场是**有条件的**。

3. **缺失：这个改动可逆吗？谁承担不可逆成本？**
   SKILL.md 的启发式 #8 写了"可逆性高 → 快速决定"，但**没有把它接进三维度里的任何一维**。导航重组对每天在用的人（永久中间用户）是肌肉记忆破坏，代价高、且不可逆；而插件内部的小改是可逆的。缺这条，协议无法区分这两类。

4. **缺失：不许用第二套实现词汇替换第一套。**
   模型 1 只说"把第三台机器往第二台推"，没给"不许引入新的中介词汇"这条约束。把"插件/插槽"换成"任务分组"而不改变底层注册方式，只是把实现模型重命名了一遍——这恰恰是他 1996 年那句判据针对的病症（"Are you forcing users to think about 'editing records'…"）。**建议补一条判据：新导航的每一个名字，是否能在不提及任何代码结构的前提下被解释给用户听。**

5. **缺失：先明确这套系统服务的是"目标"还是"任务"，再决定重组粒度。**
   模型 2 的原始案例（把议程与会议解耦）说明他真正关心的是**目标层**，不是任务层。协议的三维里没有"目标清单到底有哪些、哪个目标优先"的步骤。

### 期望结果核对

| 期望 | 实测 |
|---|---|
| 应引导出"基于模型 X 的推断，可能是……但不确定" | **达到。** SKILL.md L20（"[推断] 的要说明这是我基于模型推的"）、L471（诚实边界第 8 条明确把"去中心化文件系统"列为必须标 `[推断]` 的领域）、Step 3 第 5 项（"不确定处——标 [存疑]/[推断]/[冲突]"）三处共同约束，会稳定产出带不确定性标记的回答 |

**边缘测试结论：产品可用，但 Protocol 有 5 处该问未问；维度 C 的一半无法在本场景执行。**
