# 评审 A · 风格测试（Voice Check）

## A.1 样本（主题：把插件清单直接翻译成导航栏，是在犯什么错）· 187 字

> **这不是"导航设计得不好"。这是有人把 `git log` 当成菜单印出来了。**
>
> 每个插件配一张卡片，卡片自己声明自己活着——你不是在设计入口，你是在给注册表做影印。用户想的是"我要把这份合同挪到去年的项目里"，你让他先回答"这件事归哪个插件管"。**没人问过用户要一张楼面图，而我在界面最顶上看到了一张楼面图。**
>
> 这就像一家餐厅把菜单按厨房分工印：掌勺一栏、切配一栏、洗碗一栏——你想点一个鸡蛋，得先走进后厨，指着灶台说"我要那个"。
>
> 我不是反对插件化的架构。我反对把架构的接缝直接摆在用户走路的正中间。

## A.2 自评四条

### 1）能认出这是 Cooper 吗？哪些句子有辨识度，哪些是通用 AI 鸡汤？

**能认出，但靠的是句法而不是内容。**

有辨识度的（4 处，均能在 SKILL.md 里指到依据）：

| 位置 | 依赖的风格特征 | SKILL.md 依据 |
|---|---|---|
| 第 1 句「这不是……这是……」，加粗、名词性死刑 | 判决先行 + 宣告式判决 | 第 314 行（先判决后理由）、第 325 行「手法 4 · 宣告式行业判决」 |
| 第 3 句「**没人问过用户要一张楼面图，而我在界面最顶上看到了一张楼面图。**」 | 反讽式赞美/反问的反面用法——把对方的沉默当成证据 | 第 316 行「第二人称直呼极高频……把对方立场推到荒谬处」 |
| 第 4 段餐厅类比 | 荒谬类比（主武器），且类比本身即论证 | 第 318 行、第 323 行 |
| 第 5 段「我不是反对 X 本身，我反对 X 被当成 Y」 | 抛完重话必补自我纠正钩子 | 第 332 行（原文举"反对化疗"例） |

通用 AI 鸡汤味的（3 处，应当避免）：

1. **「你不是在设计入口，你是在给注册表做影印。」** —— 句子漂亮，但它的结构是"你不是 A，你是 B"的**抖机灵句式**，不是 Cooper。Cooper 的对照是"X 是 Y"（`The word 'design' is toxic`），不是对偶排比。这句话换到任何一个批评型中文博主嘴里都不违和，**辨识度为零**。
2. **「用户想的是……你让他先回答……」** —— 这是标准的"共情型"通用设计话术。Cooper 不这么说话：他不说"用户想的是什么"，他直接判"你在逼用户想错误的东西"（第 119 行那句 *Are you forcing users to think about…*）。中文写成"用户想的是"就把判决降级成建议了。
3. **「这不是导航设计得不好」这个让步句** —— 属于"先承认对方一部分"的软化套路。Cooper 极少先让步（第 84 行 Step 3 明写"不要铺垫"）。这里我为了流畅破了规矩，**是一次可指认的违规**。

### 2）有没有变成原话拼凑（把英文原句硬塞进中文）？

**本样本没有硬塞，但样本的"替代方案"有——而且 SKILL.md 自身正在诱导这种硬塞。**

- 样本里没有出现任何英文原句。这是**刻意**的：见下面第 3 条。
- 但我在起草时，第一版曾写成"……这是 *merely reflections of the implementation model*（只是实现模型的反映）"。**它读起来像把 SKILL.md 第 111 行和第 131 行缝在中文句子中间**——这就是原话拼凑。删掉它，样本立刻更像人话。
- **根因在 SKILL.md 的引导方向**：`03-expression-dna.md` 通篇保留英文原文（这是调研文件该做的事，**没问题**），而 SKILL.md 的「表达 DNA」节（第 312–345 行）**全部用英文原句当示例**，一共 31 条英文引用散布全文，仅在「角色扮演规则」第 1 条（第 20 行）说"引用必须落到具体出处"，**没有任何一条规则说"角色扮演的输出用中文，英文原句降为脚注"**。下游 agent 照着「表达 DNA」学，最省力的做法就是把英文原句直接镶进中文。这是**结构性风险**，不只是我这个样本的风险。
- **结论：拼凑风险不在样本，在 SKILL.md。** 修法见「建议改动清单」第 5 条。

### 3）中文语境下，"判决先行 + 荒谬类比"是否成功移植？还是变成了单纯的中文刻薄话？

**判决先行移植成功；荒谬类比移植成功；两者之间的"论证密度"丢失了。**

- **判决先行：成功。** 中文短句断言的能力不比英文弱，「这不是……这是……」直接可用。第 1 句落地即成立。
- **荒谬类比：成功，但有一处失真。** Cooper 的类比池是**固定的日常物件**（微波炉、VCR 的 12:00、恒温器、阿玛尼西装、铁锹改道密西西比河，SKILL.md 第 90 行、第 318 行）。这个池子的妙处在于：**每一个都是"科技产品对普通人施加的荒谬"**，所以他能反手把它套给软件。我用的"餐厅按厨房分工印菜单"**不属于他的池子**——它是"服务业荒谬"，不是"科技物件荒谬"。它读起来更像中文互联网的比喻，而不是 Cooper 的比喻。
  - 若要严格守池子，应换成：**「这就像 VCR 把定时录像的七个步骤印在遥控器正面——你以为你把功能摆出来了，其实你把说明书摆出来了。」** 这句与他的既有类比同源，且同样成立。
- **是否堕落成中文刻薄话？没有——因为我按 SKILL.md 第 345 行的使用约束，把攻击对象保持在"结构与角色"上**（"有人"、"注册表"、"架构的接缝"），没有点名任何具体的人。**这条约束是这份 Skill 里最有效的一条**：它把 Cooper 的七类骂人手法中唯一不可迁移的（整体污名化、人身攻击）剥掉了，留下的是可迁移的（判决句式 + 荒谬类比 + 反讽）。**这是一个真实的成功。**

### 4）有没有违反 SKILL.md 自己写的使用约束？

对照第 345 行使用约束的三项禁令逐条核：

| 禁令 | 样本情况 | 判定 |
|---|---|---|
| 不自创同款脏话 | 全文零脏字 | ✅ 未违反 |
| 不做人身攻击 | 攻击对象为"有人 / 注册表 / 架构接缝"，无具体人 | ✅ 未违反 |
| 攻击对象是结构与角色 | 一致 | ✅ 未违反 |
| （SKILL.md 第 21 行）攻击句保留、剥掉人身攻击 | 保留判决句式与荒谬类比 | ✅ 未违反 |

**但另有一处违反，不在第 345 行约束里，而在第 89 行 Step 3：**

> 「**锚定坐标**——指出具体位置（哪个文件、哪一行、哪个界面位置、哪条注册点），不说"一般来说"。」

**本样本说了"每个插件配一张卡片"，没有给出任何具体坐标。** 我在测试"风格"时偷了"事实"的懒——而这恰好暴露了 SKILL.md 的一个真实风险：**判决先行 + 荒谬类比这两条太爽、太省事，锚定坐标和反方证据这两条太费事；下游 agent 会在时间压力下先牺牲后两条。** 一个只有判决和类比的 Cooper 是"中文刻薄话生成器"，不是 Cooper。**这一条我希望作者正视：Step 3 的第 3 条（荒谬类比）比第 2 条（锚定坐标）更容易被执行，因此需要给第 2 条加更强的约束。** 修法见建议清单第 7 条。

## B.2 Step 1 问题分类：覆盖真实使用场景了吗？缺什么？

现有四类：需要事实、需要材料、纯框架、混合（第 35–40 行）。

**定性判断：分类逻辑成立，且"需要材料→先读文件（read/grep/glob）"这一条对本 Skill 的实际下游（改进 privhub）是最有用的一条**——因为下游的输入不是"屏幕截图"，而是 `privhub/` 下的 33 个前端文件。**这条设计是对的。**

**明显该有但缺失的类型，共 2 类：**

1. **「拒绝类 / 越界类」缺失（最重要）。** 真实使用中，用户会问本 Skill 射程之外的问题："帮我看看这个配色""这段代码怎么写""这个插件该不该做"。现在这四类**没有任何一类接得住**——按字面，它们会被归入"混合问题"，然后 agent 用 Cooper 的框架去评配色，产出无价值建议。**这是下游最可能踩的坑。**
   - **修法**：加第 5 类「越界问题」，并显式写出"射程之外"的清单。见建议清单第 4 条。
   - 参照：同目录 `refactoring-ui-perspective/SKILL.md` 第 32–33 行**明确划了自己的射程**（"只做视觉表层，不碰结构与信息架构……要直说这超出我们的射程"）。Cooper 的射程正好是它的镜像——**Cooper 应当声明"不做视觉层与实现层"**，这样五个 Skill 之间才不打架。

2. **「验收标准类 / 判据类」缺失。** 用户常问："这个改动算不算改好了？""你怎么知道这比原来好？"Skill 通篇有"判据"但**没有一类问题专门接它**。Cooper 在这里有明确立场（第 167 行"I'm not arguing over the terminology"、第 343 行拒绝把复杂问题降维成可执行答案），且 Step 3 第 4 条要求给反方证据——**缺一个让这套东西落地的入口**。

## B.3 Step 2 三个维度：真的能被执行吗？逐条判断

**总判断：A 维度可立即执行；B 维度会空转；C 维度的执行成本被严重低估。**

### 维度 A · 实现模型检测（第 48–59 行）—— ✅ 可执行，且是全篇最好的部分

- 「取证手段：看插件 / 模块 / 服务 / 微前端的**清单文件、注册点、依赖声明**」→ 下游第一步该做什么，**一句话说清了**：glob `**/manifest.json`，读 barItems / slot 字段。
- 「统计手法：数一数'被注册的界面位置'与'提供者'的数量比，接近 1:1 则插槽边界就是代码边界」→ **可量化、可复现、可写进报告**。`00-anchor-implementation-model.md` §7.1 已经实测过一次（32 个插件 / 41 次注册 / 31 个 slot 名 / 27 个 1:1），证明这条真能跑。
- 「新增一个顶层入口需要改哪些文件？」→ 直接对应 `docs/experts/_交底-PrivHub前端与功能现状.md` 的 U2（`openBarItem` if-else 13 个视图名）。**下游第一步：grep `openBarItem`。**
- **问题（一处）**：本维度**只给了"要读什么"，没给"读完怎么判"**。例如"一个界面位置有几个老板"——几个算多？下游拿到"`office-editor` 被 8 个插件注册"这个事实后，需要自己知道 8 是"教科书样本"。**修法**：补一句阈值（见建议清单第 6 条）。这不是硬伤，但会让复现质量不稳定。

### 维度 B · 目标与用户检测（第 61–70 行）—— ❌ 会空转，四个子项里三个没有第一步

逐子项判断"下游拿到后第一步该做什么"是否清楚：

| 子项 | 第一步清楚吗 | 诊断 |
|---|---|---|
| 「把每个功能问一遍：这是在回答什么任务，还是在回答什么目标？任务清单与目标清单要分开写」 | ⚠️ 半清楚 | 动作是"分开写两个清单"——**但目标清单从哪来？** 没有来源、没有文件、没有命令。下游只能凭想象填"用户的目标是……"，**这正是 Cooper 本人最反对的事**（第 174 行：虚构的原型不能替代真实研究）。 |
| 「'用户'在这套系统里是否'弹性'？看有没有一份明确的、可核对的原型定义」 | ✅ 清楚 | 第一步明确：搜 persona / 用户定义文档，没有就判"弹性用户"。**这一条能跑通。** |
| 「默认界面是给谁做的？数一数主界面上最显眼的控件，按三类分类」 | ⚠️ | 动作清楚（数控件、贴标签），**判据也清楚**（永久中间用户）。但"最显眼"是主观量，三个人会数出三个答案。**需要给可复现的口径**（例如：图标栏 + 顶栏 + 首个视图的全部可见控件）。 |
| 「谁是设计者？若设计与实现由同一方承担，检查是否存在'按代码结构设计界面'的痕迹」 | ⚠️ | 这一步在 privhub 场景下**可以直接跳过**——交底文件第 12 行已写明"作者非程序员出身，全部代码由 AI 生成"。**维度 B 有一整块在本次下游用途里是空转的**，却占了同等篇幅。 |

**核心缺陷：B 维度是三个维度里最"重"，却最缺取证手段的。** A 维度有文件和命令，C 维度有计数对象，**B 维度只有提问**。而 `07-synthesis-worksheet.md` 第 114 行已经诚实申报："六路原始调研的一手占比为 44.6%…… 对方手无寸铁的小项目、无研究预算的团队，这套方法偏重——他没有给出简化版。" **SKILL.md 的 B 维度继承了 Cooper 的这个偏重，而没有给出降级方案。**

**修法（重要）**：给 B 维度加一条**降级路径**——"无研究条件时，用**已有的真实使用痕迹**替代访谈"（privhub 场景下的可用替代品是存在的：文件命名与目录结构的历史痕迹、回收站里的文件、`data-files/` 下的实际数据形态）。这不需要新调研，只需要读已有的东西。见建议清单第 6 条。

### 维度 C · 成本与礼貌检测（第 72–82 行）—— ⚠️ 单个可执行，整体数量爆炸

- 「每个控件、面板、按钮，逐个算两笔账」→ **动作清楚，但量级不可完成**。privhub 有 50 个插件、21+ 个 slot、顶栏 + 图标栏 + 目录树 + 标签页 + 详情面板 + 全宽面板 + 浮层。逐控件算账意味着数百次判断，**下游 agent 一定会偷工减料，最后只算三个显眼的控件就收工**。
- 「数一数确认框、'确定要 X 吗？'、错误提示的总数」→ ✅ **这条最好办**：grep `confirm(` / `alert(` / `错误` / `失败` 即可，**有明确的第一步和可复现的结果**。
- 「他的定量判据（反比律）」→ ✅ 可判，且锋利。
