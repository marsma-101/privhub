## 1. 一句话判断：施工队最该防什么

**这支施工队最该防的，不是"改错代码"，而是"AI 报告改完了，但没有任何东西能够证明它是真的"。**

说细一点，本项目有三个已经发生的、结构性的失败模式：

| # | 失败模式 | 它为什么在本项目必然发生 | 证据 |
|---|---|---|---|
| **F1** | **测试被改造成"证明现况"而不是"钉住应然"** | Beck 2026 说得很直白：AI 会把测试删掉好让它们"通过"。本项目测试是自研断言，没人复核 | 见 §2.4；`tests/lib.mjs:20-40` 的 `ok/eq/includes` 是唯一断言机制，改起来比改代码容易 |
| **F2** | **"结构改动"和"行为改动"混成一次改动，一旦出事无法判断是谁干的** | 本项目**唯一的验证手段是那一套回归测试**，而它覆盖不到前端和大部分插件。混做之后，绿了也说明不了问题 | `tests/run-all.mjs:87-90,98`（96 个路由测试点覆盖 32/112 条路由）；§2.3 |
| **F3** | **验收标准落在"改造者的转述"上，而非"另一个会话能复现的动作"** | 单人 + 非程序员 + 全 AI 写代码，**没有第二个人**能看穿"改好了"和"AI 说改好了"的差别 | 交底 `:12`（作者非程序员出身，全部代码由 AI 生成） |

**Beck 对本项目的核心诊断（这是我的判断，不是他的话）**：
PrivHub 的问题不是"没有 TDD 的习惯"，而是**反馈回路本身太细太脆**。`--spawn` 那套 87 个用例 + 185 处静态断言（§2.3）是一条真实存在的回路，但它的**探测半径只覆盖后端 HTTP 层**，而本轮要动的地方（`frontend/index.html`、`plugins/*/client/*`）**几乎全在探测半径之外**。
⇒ **所以施工队的第一份工作不是改代码，是把探测半径铺到要动的地方。** 这是我与 Fowler、Feathers 三者都同意、但**做法完全不同**的地方（见 §3）。

**⚠️ 一个必须先修的坑（否则本轮建立的一切反馈回路都不可靠）**

> `run-all.mjs:108-114` 的 `runChild()` **不向子进程传递 `env`**，而 `run-all.mjs:66` 只在 `--spawn` 分支里设置 `process.env.PRIVHUB_TEST_ROOT`。
> 也就是说：**6 个静态脚本（admin-console / personal-ui / frontend-templates / integrity / audit-reliability / first-run）在 `--spawn` 下拿不到 `PRIVHUB_TEST_ROOT`**，靠 `cwd` 回退；而它们的 `cwd` 是 `privhub/`（`:110`）——**这是真实数据所在的目录**。
> 这批脚本当前是否真的会碰到真实数据：**只读勘察员判断"它们基本不读该变量"但因未运行而未能证实 → 我标 [未核实]**。
> **这件事必须在施工队开工之前查清。** 我要交给施工队的**第一条任务不是改产品代码，而是把这条回路本身钉死**（见 §4 第 0 道工序）。

**⚠️ 另一个必须先认识的现状：所有"跨插件耦合"都是静默失效。我逐处复核过。**

我亲自 grep 了 `privhub/plugins/**/*.js` 的 `v3-content` / `v3-loading` / `v3-md`，命中 **35 处**，分布在 **5 个插件**。但关键在于**它们不是同一种依赖**，破坏方式也不同：

**这张表本身就是一条施工情报**：
- 《00-汇总:44》说耦合者是"**4 个**"（纠正账本的 3 个），**成立**；
- 但**"4 个"这个数字掩盖了两种不同性质**：**3 个是真 DOM 操作（坏的是功能），1 个是样式复用（坏的只是外观）**。施工时**必须区别对待**——改函数契约能救前者，改类名值就能救后者。

**还有一条历史教训就写在代码注释里**（`privhub-files-office2/client/index.js:58-59` 原文）：
> 「作为内容区首个子元素插入：V3 已移除 `.v3-content-head`（内容区不再有顶栏），**原先以它为锚点的写法会找不到元素而退化成 appendChild（顺序错乱）**。」

⇒ **这不是假想的风险，是已经发生过一次、并且被前一个 AI 在注释里记下来的。** 交底 `:131` 说"修订顶栏时已因此连撞两次"，**我找到了其中一次的现场证据。**

### 2.4 Beck 那套东西的**前提**，与本项目的实际落差（诚实边界，必须写在前面）

Beck 全部方法的地基是一句话：**「有测试，有快速反馈回路」**。他不是在真空中提倡先写测试——他提倡的是"**在一个一两分钟内能拿到可信红/绿信号的环境里**，用它来驱动设计"。
本项目的地基是：**测试薄、无自动化 UI 验证、无第二个人复核、所有代码由 AI 生成**。四句话，逐条对照：

| Beck 的前提 | PrivHub 的现状 | 后果 |
|---|---|---|
| 有自动化测试 | 有，但只覆盖后端 HTTP 层（32/112 条路由）；前端与 21 个插件零覆盖 | 「先写会失败的测试」在**前端几乎无处可写**——没有可断言的挂点 |
| 反馈在一分钟内 | 有 `--spawn`，但整套要拉起服务、跑 13 个套件；**单次改动的前端可见反馈 = 人工刷新页面** | 红绿循环的**周期从秒变成分钟**，节奏纪律必须重译（§5） |
| 有人复核 | **没有第二个人**。交底 `:12` 明说作者非程序员、代码全部由 AI 生成 | 「code review」在本项目只能换形为"**另一个不带上下文的 AI 会话做对抗性盘问**"（这也正是 `05-shape-up.md:238` 那道外部闸门的形态） |
| 人可以判断"这是不是真设计洞见" | 判断者是**非程序员 + AI**，无法独立审代码 | Beck 说「难测是缺设计洞见的信号，出去走一圈」——**这句在本项目无法执行**，因为"难测"的感知者不具备判断力。必须改为"**把不可测的点列出来，交给一个明确角色去砍范围**" |

**结论**：Beck 的方法可以用，但**必须重译，且重译幅度不小于 Shape Up 那一路**。本方案第 5 节给的就是重译版本。

## 3. 三者分工表：同一件事，我 / Fowler / Feathers 各自怎么做

**这是本方案最核心的一节。**

### 3.1 一句话分工

> **Feathers 管"没有测试的地方怎么先弄出一个安全的立足点"；我（Beck）管"这个立足点必须是会失败的，而且结构改动与行为改动必须分两次提交"；Fowler 管"你把行为钉住之后，怎么把结构本身收拾成好读的样子，以及给每个收拾动作起一个准确的名字"。**
>
> 顺序固定：**Feathers 找立足点 → Beck 钉住行为并切开提交 → Fowler 收拾结构并命名。**

### 3.2 同一个案例走三遍

**案例就是题面给的：改掉 `frontend/index.html` 里的硬编码 `openBarItem`**（真实位置 `index.html:748-764`）。

先说清这件事为什么难：这串 if/else 是**骨架自己手写的视图白名单**——`'trash'`、`'search'`、`'favorites'`、`'files'`、`'admin'` 五条有专属跳转逻辑，剩下 9 个视图名塌缩成一句 `nav.setActiveView(view)`。它同时牵着**下面一组东西**，缺一个就静默失效：

| 牵动项 | 位置 | 会不会报错 |
|---|---|---|
| 五条专属分支的语义 | `index.html:750-753` | 改错会破语义，不报错 |
| `setActiveView` 的 toggle 行为 | `index.html:462`（`if (!noToggle && nav.activeView === v) v = 'files'`） | 不报错 |
| 12 条 `<component v-else-if>` | `index.html:1029-1064` | 视图空白，不报错 |
| `.v3-content` 类名的 4 个外部插件 | `files-office2` / `files-edit-md` / `files-comments` / `shell-agent-console`（据 `00-汇总:36,44`、`03:620`） | **静默失效，不报错** |
| `barItems` 从哪来 | `shell/server/index.ts:48`（`readdir` 枚举序，非设计序） | 不报错 |

**这三条"不报错"的特征，正是本案例必须走三者串联的原因。**

| 步骤 | **Feathers（遗留代码）** | **我 · Beck（TDD / Tidy First）** | **Fowler（重构）** |
|---|---|---|---|
| **第 1 步：面对这团代码先做什么** | **先找接缝（seam）**。判断"这里现在有没有一个能插测试而不改行为的点"。他的判断会很直接：**没有**——`openBarItem` 挂在 `window.PrivHub` 上（`:748`），要调它得先有一个 `nav`、一个 `document`；而 `nav` 是模块级 `reactive`（`:425`），没有导出。⇒ 他会说：**"这里没有接缝，先造一个。"** | **先写测试清单（Test List）**。不是先写代码，也不是先写一条测试——**先把"应该成立的场景"全列出来**：`trash` 跳回收站、`files` 无项目时回欢迎页、`admin` 不 toggle、`settings` 要 toggle、未知视图名不炸、`bi.view` 缺失时回退到 `bi.slot`… 列完才动 | **先给这段代码起名字**。他会指出：`openBarItem` 现在同时在干**三件事**——(a) 从 `bi.view || bi.slot` 取键、(b) 分派到五种不同的导航语义、(c) 兜住 toggle 例外。**这是"一个函数承担多个抽象层级"，先给它命名与分层，再谈改** |
| **第 2 步：怎么让改动安全** | **写"刻画测试（characterization test）"**：先不判断现有行为对不对，**只把现有行为记下来**。他的原话（《Working Effectively with Legacy Code》的核心）：没有测试的代码，先给它套上一条能通过的测试，**哪怕记的是错的**——因为自此你才有"我改了它会不会变"的能力。他会先写：*给定 `{view:'settings'}`，`activeView` 变成 `'settings'`*；*给定 `{view:'admin'}` 且已是 admin，`activeView` 不变* | **不接受"记下来就算数"**。他要问一句 Feathers 不会问的：**"这条测试现在会不会失败？"** 如果新写的测试一开始就是绿的，它**没有证明任何东西**——它只是把现值抄了一遍。他会要求**至少一条测试在写完之后处于红的状态**（例如：先写"`bi.view` 缺失时应回退到 `bi.slot`"——现状下这条可能是绿的；那就换成"未知视图名应被记录/上报"——现状下**这条必然红**，因为现在未知视图名被静默吞掉） | **给每个动作命名**。不急着动：他先建一份"这次要做的结构改动"的清单，每条一个名字——`Extract Function`（把 12 条 v-else-if 的分派抽成映射）、`Introduce Parameter Object`、`Replace Conditional with Polymorphism`（如果值得）、`Rename Variable`。**每条都必须是《重构》里有名字的动作**——有名字才可机械执行、可复核、可回退 |
| **第 3 步：真正的施工顺序** | 造好接缝后**交棒**。他的活到此为止：**"现在有安全网了，去改吧。"** | **切两刀，分两次提交。** 第 1 刀：把 12 条 `v-else-if` 换成 `VIEW_SLOT` 映射 + `v-for`——**行为完全不变，测试一行不删，跑完必须全绿**。第 2 刀：才动那五条专属分支的语义（如果确实要动）。**这两刀绝不合并提交** | **在第 1 刀（结构改动）里做他的事**：一边换映射，一边按名字执行 `Extract Function` / `Rename`，让"分派表"成为代码里一个**独立可指认的东西**。他不碰行为 |
| **第 4 步：怎么知道成了** | 复跑刻画测试全绿 ⇒ 行为未变 | **结构改动那次的验收证据是"测试文件一行没改，且全绿"**；行为改动那次的验收证据是"**新增了一条一开始会红的测试，现在绿了**"。**两个证据必须分开存在、分开取证** | 结构改动的验收标准是**可读性**：「现在读这段代码的人，能不能一眼说出第 7 个视图会走到哪？」——他会要求一个"读得出来"的证据，而不是"跑得过" |
| **第 5 步：各自会犯的错（失效条件）** | **风险：把错误行为也钉死**。如果刻画测试记的是"未知视图名被静默吞掉"，那条测试**会给这个缺陷上锁**——以后想修它，测试会拦你。所以 Feathers 的产物**必须有一条"已登记的已知缺陷"清单**，交叉着一起提交 | **风险：教条化**。他会要求"先红后绿"，但如果这个项目代价太高（前端无接缝、反馈周期以分钟计），死守仪式就会变成纯负担。**他自己在 2014 年就说过：“it depends，and that's going to be the beginning to all of my answers to any question that's interesting.”** 本项目必须允许"**降级模式**"（见 §5） | **风险：把结构改动做得太大、太久**。Fowler 的重构是"**每一步小且行为保持**"，但它的目标常常是**结构好读**，不是"下一次行为改动更便宜"。**我（Beck）与他的分界正在这里**：他问「这样写好不好读」，我问「**这样写，下一次改动还需要回来改这个文件吗**」。`05-shape-up.md:260` 那条"新增一个 `barItems.view` 不需要改 `frontend/index.html`"——**那是我要的验收标准，不是他的** |

### 3.3 分工汇总（可直接贴墙）

| 问 | Feathers | Beck（我） | Fowler |
|---|---|---|---|
| 核心问题 | **"这块代码现在可测吗？"** | **"这个改动现在会不会失败？"** | **"这段代码现在叫什么名字？"** |
| 面对无测试代码 | 造接缝 → 写刻画测试 | 拒绝把"抄现值"当测试 | 先命名与分层 |
| 对"结构 vs 行为"的态度 | 不区分——他只是需要**安全网** | **必须分两次提交**，因为**证据不同** | 关心结构改动**做得对不对**，不关心**提交切不切** |
| 交付物 | 接缝 + 能跑的刻画测试 | 测试清单 + 红绿证据 + **切开的两次提交** | 有名字的结构动作清单 + 可读的成品 |
| 什么时候交棒 | 安全网建好即交棒 | 结构改动做完 → 交回行为改动 | 结构改动做完即收工 |
| **本项目里绝不能让他单独干的事** | 让他同时改行为（他会把缺陷锁进去） | 让他定"改哪个值"（那是 Refactoring UI 的活） | 让他决定"要不要做这件事"（那是 Shape Up 的活） |

### 3.4 三者的**不可替代性**，一句话各一条

- **Feathers 不可替代**：本项目**21 个插件零覆盖、前端骨架零测试**——面对这种代码，只有他有成套的"先造立足点"的做法。我和 Fowler 都**预设已有测试**，在这个项目的地面上直接悬空。
- **我（Beck）不可替代**：《Tidy First?》那条 **"结构改动 / 行为改动分两次提交"** 以及"**测试必须先是红的**"，是唯一能治 F1（AI 伪造测试）与 F2（混做无法归因）的东西。Fowler 给结构改动提供**质量**标准，但**不含提交切分纪律**；Feathers 给安全网，但**不校验安全网是否有效**。
- **Fowler 不可替代**：他给出**每个结构动作的准确名字**。没有名字，结构改动就无法被机械执行、无法被复核、无法被回退——而本项目**唯一能做到"机械且可复核"的手段，就是用有名字的重构动作**，因为改造者是 AI，"给它一个标准名字"比"描述你想干什么"精确得多。

### 4.1 《Tidy First?》的提交纪律落到本项目（含版本号方案）

**这是本方案的第二个核心。** 结合您现有流程（每步人工确认 → CHANGELOG → 递增版本 → 提交推送）来落地。

#### (a) 为什么必须分两次提交——两条"证据"不能共存于一次提交

| 改动类型 | 改的是什么 | **验收凭据** | 风险 |
|---|---|---|---|
| **结构改动** | 代码怎么摆（名字、顺序、阶层、抽函数、换映射） | **既有测试"一行未改"且全绿** | 低且有界 |
| **行为改动** | 代码算什么（输出、副作用、用户看见什么） | **新增/修改的测试从红转绿** | 无界，可能是一次事故 |

**混在一起出什么事**（这是您问的，我一条条说）：

1. **两条证据同时失效。** 结构改动那条证据是"测试文件没动"——可你改了行为，测试必然动过，**证据不存在了**。行为改动那条证据是"新测试由红转绿"——可它埋在结构改动那一大堆 diff 里，**没人分得清哪一行是新的、哪一行是搬的**。
2. **回退变成一个不可执行的命令。** 混做的改动一旦出事，你只能整块回退——**把结构改动一起撤了**。而结构改动本来是"下次改动更便宜"的投资，撤了等于白干，下次还要重来。分开提交时，你**只回退第二刀**，结构留在原地。
3. **版本号失去意义。** 分两次提交 ⇒ 两次 CHANGELOG 条目 ⇒ 两个版本号 ⇒ **能一眼看出"这一版只搬了家，没换家具"**。混做 ⇒ 一条条目 ⇒ 一个号 ⇒ 出事时你**说不清这一版到底干了什么**。您现在的 `[3.1.0]` 条目写得非常好——它明说了"不改后端 API / 数据库 / 权限校验 / 插件业务逻辑"。**混做会让这种声明无法成立**。
4. **对 AI 特别致命。** 改造者是 AI。**"结构改动"是一个可以被机械校验的命题**（测试没动、全绿），而"结构调整 + 行为调整"是一个**只能被叙述、不能被校验**的命题。给 AI 一个不可校验的命题，等于放弃唯一的把关手段。

#### (b) 分几个版本号？——落到您现有三段式规则

您 CHANGELOG 开篇已定的规则（我已核实原文）：

| 段位 | 何时递增 | 例子 |
|---|---|---|
| **主版本** | 不兼容的架构或数据格式变更 | 存储格式改版、接口契约破坏性调整 |
| **次版本** | 向后兼容的**新功能** | 新增插件、新增权限模型、新增接口 |
| **修订号** | **缺陷修复、文档与界面微调、内部重构、文档同步** | 修 bug、改提示语、补测试 |

**⇒ 结论：结构改动属于「内部重构」⇒ 走修订号（patch）。** 这是您自己的规则已经给出的答案，我不需要发明新规则。

**一次典型改动的版本号方案（示范）**：

| 序 | 提交 | 类型 | 版本号 | CHANGELOG 条目开头（建议写法） |
|---|---|---|---|---|
| 1 | `tidy: 把 openBarItem 的视图分派抽成映射表，行为不变` | **结构** | `3.1.1` | **`### 内部重构 · 无行为变更`** ／「本次只做视图分派表的抽取与命名；**测试文件零改动**；后端、数据、权限、插件业务逻辑均未触碰。验收方式：`node tests/run-all.mjs --spawn` 全绿且 `git diff` 中 `privhub/tests/` 为空。」 |
| 2 | `feat: 新增 barItems.view 直连 activeView，无需改骨架` | **行为** | `3.2.0` | **`### 新功能`** ／「新增 `barItems.view` 直连 `nav.activeView`；功能面板改 `VIEW_SLOT` 映射 + `v-for`。验收方式：① 新增一个 `barItems.view` 不改 `frontend/index.html`；② 12 个图标栏入口逐个点一遍无回归（含「新建文档」，此条为防回归）；③ 新增测试 `<名>` 由红转绿（附原始输出）。」 |

**为什么第 2 步是次版本而不是修订**：因为它**向后兼容地新增了能力**（插件可以用新方式声明视图）——正好是您规则表里"次版本"的定义。

**⚠️ 冲突提醒（必须写明白）**：
这条纪律**与 `05-shape-up.md` 的 S1「同一时刻只允许 1 项处于 Shape Go」不冲突**，但**与"多线并行小步提交"冲突**——`00-汇总:92` 已把顺序问题定为「唯一一条"顺序错了会出事"的建议」。**本项目的编排偏好是排队，不是并行。** 这一点我在 §5 里正面处理。

#### (c) 四道闸门（每次提交前逐条过，缺一条不许提交）

| 闸门 | 具体动作 | 用什么证明 | 谁签字 |
|---|---|---|---|
| **闸 1 · 分类** | 说清这次是**结构**还是**行为**。说不清 ⇒ **不许提交** | 一句话 + 它属于哪一类 | K2 |
| **闸 2 · 结构改动的证据** | `git diff --stat` 里 **`privhub/tests/` 为空**，且全套测试绿 | **原始命令输出**（不是转述） | 外部 AI 会话 |
| **闸 3 · 行为改动的证据** | **新增的那条测试，在此之前是红的**（有原始红态输出） | K1 的红态证据 | 外部 AI 会话 |
| **闸 4 · 静默失效点** | 若动了任何**跨插件类名**（`.v3-content`、`.v3-md`、`.v3-loading`）⇒ 必须真机点查那 4 个插件 | 真机验收记录（K4） | **人**（主子） |

**静默失效点为什么单列一道闸门**：`03-refactoring-ui.md:636` 那句话是本批材料里最直接的警告——「**任何改名/删除都必须是独立的、有明确契约说明的改动，不能夹在"视觉优化"里顺手做。**」而**测试抓不到这类失效**（不报错、就是不工作）。这一道闸门**只能靠人的眼睛**。

## 5. 工序：谁先谁后、哪些可并行、哪些绝不并行

### 5.1 主工序（串行，一次只推一格）

```
第 0 道（前置，必做）
  └─ 把回归回路本身钉死：查清 runChild 不传 env 的真实后果（§2.3 的 ⚠️）
      └─ 若确有真实数据风险 ⇒ 这本身就是一次"会动数据"的改动 ⇒ 排进数据车道，先做它
          └─ 否则 ⇒ 直接进第 1 道

第 1 道  K1 出红态证据 ──(外部会话验证)──▶
第 2 道  K3 做结构改动（有名字的动作）──(测试未改 + 全绿)──▶
第 3 道  K4 真机点查结构改动无回归 ──▶  ★ 人工确认 #1 ──▶ 3.x.y 提交（patch）
第 4 道  K2 切出行为改动 ──(红转绿证据)──▶
第 5 道  K4 真机验收行为改动 ──▶  ★ 人工确认 #2 ──▶ 3.Y.0 提交（minor）
第 6 道  K5 车道判定：本次是否碰到会动数据的部分 ──▶ 若有 ⇒ 单独组织，不进本流程
```

**为什么第 2 道（结构）在第 4 道（行为）之前**：
这**不是**我的偏好，是《Tidy First?》的**唯一硬主张**——「**先让改动变容易，再做那个容易的改动**」。落到这个案例上：先把 12 条 `v-else-if` 抽成映射表（结构），新增一个视图才会变成"改一行数据"而不是"改骨架"（行为）。
**⚠️ 但这里有一个真实的顺序冲突，必须由主子拍板**：`00-汇总:92` 把「先解 `explorer-v3` 耦合，再动渲染层」定为**唯一一条"顺序错了会出事"的建议**。我的结构刀恰好走在同一片区域。
⇒ **合并方案（我的建议，供拍板）**：把"解 `.v3-content` 耦合"**吸收进第 2 道的结构改动**，作为**同一次结构改动里的第一条动作**——因为解耦本身**正是行为保持的结构改动**（把 `querySelector` 换成插槽/事件，三个插件的行为不变）。这样两条纪律不打架：**一次结构改动，包含两条动作：① 解 `.v3-content` 耦合；② 抽视图分派表。** 两者都行为不变，都靠"测试未改 + 真机点查三个插件"验证。

| 绝不并行 | 理由 |
|---|---|

| **数据车道 ↔ 任何前端 scope** | `05-shape-up.md:311`（G1）已定；理由是代价不对称：「前端出错的代价是"点不动"，数据出错是"文件没了"」 |

### 5.5 降级模式（本项目的现实约束必须承认）

Beck 的节奏（红→绿→重构，秒级）在本项目**不可能原样成立**：前端没有接缝、反馈以分钟计、无第二个人复核。
⇒ 本方案允许一个**明确定义的降级模式**：

| 情形 | 正常模式 | 降级模式 | 谁批准降级 |
|---|---|---|---|
| 前端 UI 改动 | 先写会失败的前端测试 | **先真机确认"现状确实坏"（K4 出一条"现状复现"记录），再改，改完再真机确认** | K2 提案，主子批 |
| 无法自动化的交互 | 自动化断言 | **pair of "改前录像/截图 + 改后录像/截图"**——这是 `00-汇总:105` 诺曼要的那份材料的形态 | 同上 |
| 一行修复、无测试挂点 | 先写测试 | **允许先改，但必须在同一提交里补一条"能复现原缺陷"的测试**（否则该提交不许过闸 3） | 同上 |

**降级不是取消纪律**：降级模式下，**"证据"这一项仍然必须存在**，只是从"自动化红态输出"换成"可复现的人眼记录"。
**⚠️ 降级模式的风险**：它会缓慢地退化成"什么都不验"。所以我要求**每次降级都在 CHANGELOG 里写明"本次为降级模式，理由是 X"**——让降级留下痕迹。这是本项目能做到的最低成本的自我约束。

## 6. 我建议不要设立的岗位

| # | 不建议设立的岗位 | 为什么不要 | 它会杀掉什么 |
|---|---|---|---|
| **N1** | **"重构智能体"（专职做大规模重构）** | 单人 + 无打包链 + 测试薄 ⇒ 一次大重构**没有任何东西能证明它安全**。`05-shape-up.md:291-294` 已把 `svc-rag` 大文件拆分判为"退回 Candidate"（它是工程风险陈述，不是用户的失败时刻）。**结构改动必须挂在一次具体的行为改动上**，不能独立立项 | 换掉了"改了一堆、说不清哪一处弄坏了"的长期排查负担 |
| **N2** | **"测试覆盖率提升智能体"（专职补测试）** | Beck 明确说过：**测试行数 / 生产代码行数是个"bogus metric"**。更致命的是——**让 AI 去补测试，就是让 F1（伪造测试）工业化**：它会写出一堆断言现况的绿色测试，把缺陷锁死，然后覆盖率数字很好看 | 换掉了"看着有 80% 覆盖率，实际一个真缺陷都抓不到"的自欺 |
| **N3** | **"前端 UI 视觉智能体"（常驻改样式）** | 视觉层改动**打不到测试**，且**撞约束 1**（图标栏加宽 `00-汇总:88` 已定为"真冲突"）。Refactoring UI 那一路的价值**主要在"从零建令牌层"这一次性工程**（`03` 的方案），做完即沉淀为代码——**常驻岗位的收益递减最快**（`00-汇总:117` 的判词："低，但收益递减最快"） | 换掉了"每轮都在微调像素、却没人验证过真机"的精力消耗 |
| **N4** | **"架构守护智能体"（常驻扫描架构违规）** | 本项目真实的架构问题（跨插件 `querySelector`）**不是"扫描出来"的**，而是**改渲染层时静默炸出来的**。守护岗会产出源源不断的报告，而**报告不构成任何一次改动** | 换掉了"多一个永远在报警、永远没人处理的看板" |
| **N5** | **"CHANGELOG / 版本号智能体"（专职管提交）** | 这是**闸门**，不是岗位。把它做成常驻智能体，就会出现"它自己判断这算 patch 还是 minor"——而**版本号语义的判断权正是需要留给人的那部分**（约束 8 明写"人工确认无误后"） | 换掉了"版本号由 AI 自己说了算"这个最不该出现的结果 |
| **N6** | **"测试修复智能体"（专门让失败的测试变绿）** | **这就是 F1 的岗位化。** Beck 2026 的观察是：AI 会**删掉测试好让它们通过**。专门设一个"让测试变绿"的岗，等于把这个已知失效模式写成职位说明书 | 换掉了"红着的测试被悄悄改绿"的最坏路径 |

**加一条元规则**：**N1–N6 不是永久否决，是"not now"**（沿 `05-shape-up.md:351` 的口径）。它们可以重新被提出——**但必须挂到一次具体的、有失败时刻的改动上，不能独立立项。**

| **U-2** | **三个插件被"静默失效"的真实发生概率与代价。** | 我知道它**静默**（不报错、就是不工作），也知道**历史上已连撞两次**（交底 `:131`）。但我**没有见过这个界面跑起来的样子**（`00-汇总:98`：五份方案里有四份写下同一句话）。**"它现在到底能不能用"这件事，我只能靠代码推断，不能靠观察。** |

| **U-5** | **"本次改动的基线"——即不做它会损失什么。** | 这是 Shape Up 漏斗第②列的硬要求（说不出来 = 基线太低，直接砍）。**而我拿不到真实使用数据**（无埋点、无日志、无用户）。五份方案一致承认这个盲区（`00-汇总:98-105`），**我不能替它们补上。** |

| **U-7** | **我对前端 / UI 没有任何专门论述。** | Beck 公开材料里**没有**关于现代前端框架、无打包链单页应用、插件化前端架构的系统论述。他的案例库是 Smalltalk / Java / Facebook 后端与工具链。**凡本方案涉及前端的部分，全部是我的外推，不是他的原话。** 这一点必须写在最显眼的地方。 |

### 7.2 我这把视角该不该当"总工"

**我的答案：不该当"总工"，该当"施工监理"。** 三条理由：

1. **我缺"做什么"的判断力。** 我全部的方法都建立在"已经知道要改什么"之上——Test List 要先有一个行为目标，Tidy First 要先有一次行为改动。**"这个功能该不该做"完全不是我这一路的问题**，那是 Shape Up 的活；"用户为什么找不到"是诺曼和克鲁格的活；"改成什么值"是 Refactoring UI 的活。我若当总工，必然把"能不能测"当成"该不该做"的替代判据——**那是最坏的一种技术官僚**。

2. **我最大的价值恰恰在"不当总工"才成立。** 我的不可替代性只有两条：**① 结构改动与行为改动分两次提交；② 测试必须先是红的**。这两条都是**否决性纪律**，不是**建设性方向**。否决性纪律的正确位置是**闸门**，不是**总工**。总工要拍板"先做 A 还是先做 B"，而我只会说"不管先做哪个，都得切成两次提交"。

3. **本项目的"总工"位置，在制度上本来就空着，而且不该用智能体填。** 约束 8 写明"**人工确认无误后**提交推送"。这是一个**明确保留给人的闸门**。若让某个智能体当总工，它就会自然滑向"替您确认"，而那正是这条约束要防的事。

**⇒ 我建议的总工形态**：**主子 = 总工（管"做不做、先做哪个、要不要提交"）；Shape Up = 范围闸门（管"这件事成形了没有"）；Beck（我）= 施工监理（管"不管做什么，都必须切成两次提交、都必须先有红的测试"）；Norman / Krug / Cooper / Refactoring UI = 顾问（管"改哪里、叫什么、改成什么值"）。**

**⇒ 最少可行编制（只能设 1 个智能体时）**：
> **选「K2 · 把改动切成两次提交的人」**（挂 Beck skill，法②指路）。

**为什么是它，而不是 K1 或 K4**：
- 本项目**当前的实际风险**集中在 F2（混做无法归因）——因为改动马上要开始，而**改动一旦混做，本项目没有第二道防线**（测试覆盖不到前端）。
- **K1 的活可以被 K2 顺手做掉**（K2 为了切分，必须先要红态证据）；**K4 的活是人的活，本来就不该由智能体顶替**（它是唯一能替代用户测试的环节）。
- **K2 的纪律一旦立住，其余岗位的产出都能被它校验**——它是一个**能自下而上带动整套纪律**的位置。
- **成本最低**：只需 `files` / `shell` / `skills` / `todo` / `present` / `planning`，不碰 `web`、不碰 `delegation`、不碰 `orchestration`。

### 7.3 理想编制

> **说明：本节是"理想"，不是"建议一次建完"。** 按 §5 的串行纪律，**同一时刻只应有 1 个岗位在推**（沿 `05-shape-up.md:238` 的出口动作与 S1）。

| 岗位 | 通俗名 | 挂哪份 skill | 挂法 | 能力包 | 什么时候启用 |
|---|---|---|---|---|---|
| **K2** | 把改动切成两次提交的人 | Kent Beck | **法②** | files / shell / skills / todo / present / planning | **先做**。这是最少可行编制 |
| **K1** | 先弄出一条会失败的测试的人 | Kent Beck（+ Feathers） | **法②** | files / shell / skills / todo / present | **次做**。K2 立住纪律后立刻补 |
| **K3** | 收拾结构并给动作起名的人 | Fowler（+ Beck 纪律） | **法②** | files / shell / skills / todo / present | **次做**。与 K1 配套 |
| **K4** | 真机点一遍的人 | Steve Krug（判据引 Beck / Norman） | **法②** | files / skills / todo / present / ask | **次做**。它是补全场最大盲区的唯一手段（`00-汇总:114`） |
| **K5** | 数据车道的守门人 | Shape Up | **法②** | files / shell / skills / todo / present / planning | **可缓**。主子已明示数据往后放，且它当前只要**保持空车道** |

**关于"该不该装进 `.dsh/skills`"（法①）的总体建议**：
**五个岗位全部建议用法②（指路）。** 理由三条：
1. 法① 要写**工作区之外**的目录，**沙箱默认不许写，需要您授权**；
2. 法② 的 skill 随仓库走，**能被 git 版本管理**——而 skill 的建议会随项目演进（比如本方案 §5.5 的降级模式），版本管理在这里是刚需；
3. 法② 让**"读了哪一版 skill"变成可追溯的证据**（`AGENT.md` 里写明路径，CHANGELOG 里可引用），这对"单人 + 全 AI 写代码"的场景特别重要。

**法① 的唯一适用场合**：您希望某个纪律**跨项目、跨会话常驻生效**（例如"结构/行为必须分两次提交"这条通用铁律）。**若确实要，我建议只把它装一次，并且优先装"提交纪律"这一条，不装整份 SKILL.md。**
