## 1. 一句话判断（施工队最该防什么）

**施工队最该防的不是"改错代码"，是"一次改动里同时戴两顶帽子"——因为在本项目里，这个错误不可检测：200 项回归只能告诉你"坏没坏"，永远不能告诉你"做完没做完"，一旦两顶帽子混在一个提交里，你既定位不出是谁弄坏的，也回退不掉，CHANGELOG 还会跟着失真。**

依据：`docs/PrivHub-插件实现规则.md:368-374` 已经把这道伤疤写下来了——S16 那次事故的本质是"测试断言写成了『现在如此』而不是『应该如此』"，**84 项测试全绿，缺陷照样流进交付物**。这说明本项目的测试体系**善于证明"没有更坏"，不善于证明"变好了"**。两顶帽子混戴，恰恰是让"变好了"这件事彻底无法验证的操作。

第二句：**施工队最该防的第二件，是让 AI 自己担任"我做得对不对"的唯一裁判。** 本项目没有设计师、没有团队评审、没有 CI、没有 lint（见§2）。Fowler 整套方法的成立前提里有两条在本项目**不成立**（见§7 与 Skill 的诚实边界），必须用"外部闸门"顶上——但外部闸门要额外花你的注意力，所以施工队的人数不能按"能力"定，只能按**验证方式**定。

## 3. 编制表

> **先说清一件事**：本项目"所有角色都是 AI"。所以下表每一个岗位的「准出条件」栏里，**"谁来验"绝不能写成"由某岗位自验"**。能用的人只有三种验法：
> ① **机器验**（跑 `tests/run-all.mjs` 之类，可复现）；
> ② **不带本次上下文的另一个 AI 会话验**（对抗性复核，只保证"找得到反例"，不保证"找得对"）；
> ③ **人眼验**（你本人看界面 / 拍板）。
> 每个岗位下面我都标了它**只能靠哪一种**。

## 4. 工序

### 4.1 谁先谁后（一次改动的完整链）

```
Step 0  立基线            ── ②跑一次全量回归，把结果存下来（"改之前是绿的"必须是个事实，不是回忆）
                            ↓
Step 1  收窄与定稿         ── 你来定：这次改什么、明确不做什么、什么算完成
                            ↓  （七项施工单：目标 / 判据 / 明确不做 / 涉及文件 / 验证方式 / 帽子类型 / 版本段位）
Step 2  开出一条干净的分支？ ── ⚠️ 本机 git 未核实可用（`PrivHub-插件实现规则.md:336` 说 git 不在 PATH；
                              本次 `git` 命令沙箱拒绝执行）。这一格我判不了，见§7。
                            ↓
Step 3  改代码             ── ①（改结构帽）或 ①＋③（若涉及令牌层）
                            ↓
Step 4  跑全量回归         ── ①先自己跑一遍，②再独立跑一遍
                            ↓
Step 5  独立审核           ── ⑤（临时会话）出反例清单
                            ↓
Step 6  反向验证           ── 一条"改前必失败、改后必通过"的现象当场复现（跳过此步＝绿灯不值钱）
                            ↓
Step 7  写记录             ── ④：CHANGELOG + 递增 version + 说明文件核对单 + 提交说明草稿
                            ↓
Step 8  机器闸门           ── 版本号一致性检查（见 4.3，这是**补上的那一环**）
                            ↓
Step 9  人工确认           ── **你**看：界面 / 反例清单 / CHANGELOG 有没有混节
                            ↓
Step 10 提交推送           ── **你**执行（AI 不得代劳）
```

### 4.2 哪些可并行、哪些绝不并行

**可以并行的三组**：
1. **②与任何人**——它只读源码、只写 `tests/`，与源码改动零文件重叠。
2. **③的长表工作**（把 45 个离散 px 逐个映射到令牌）与 **①在别的文件上干活**——但**前提是文件清单不重叠**。
3. **⑤的准备**（读施工单、读 skill）与**任何人的收尾**。

**绝不并行的四条（每条都有具体事故依据）**：

| # | 绝不并行 | 依据 |
|---|---|---|
| **1** | **①与①**：任何两个"能改源码的会话"，不得同时改动**同一个文件**。本项目的头号热点是 `frontend/index.html`（1130 行，含 `openBarItem` 与 15 条面板枚举）、`explorer-v3/client/*`（styles.js / panel.js）、`privhub/package.json` | `PrivHub-插件实现规则.md:330-334` 的事故就是"批量改动 6 个插件被写坏"；双会话改同一文件比批量脚本更难事后归因 |

### 4.3 现有纪律缺的那一环 —— 怎么补

**现有的纪律（你明示的）是四步**：

> 每步人工确认 → 写 `CHANGELOG.md` → 递增版本号（唯一来源 `privhub/package.json`）→ git 提交推送 + 同步项目说明文件

**它其实已经包含了 Fowler 框架里最难的两项**——这一点得说句公道话：
- **"小步"有了**：一次一个小功能、改完就提交；
- **"持续集成"的等价物也有了**：`tests/run-all.mjs --spawn` 就是一条能在隔离实例（3190）上、不碰真实数据（`run-all.mjs:32,44-48`）跑完的全量回归。**这是绝大多数单人项目根本没有的东西。**

**缺的只有一环：这条链上没有任何一个环节，把"回归是绿的"设成"允许进入下一步"的条件。**

具体表现，四条，全部有据：

| # | 缺口的形态 | 证据 |
|---|---|---|
| **M1** | **"测试要跑"没有落成任何一条必须执行的命令**。`privhub/package.json:7-10` 只有 `start` 与 `dev`，**没有 `test` 脚本**；没有任何 git hook、没有 CI | E9。回归要不要跑、什么时候跑，**全靠当时记得**。 |
| **M2** | **顺序反了**：现在是"人工确认无误后"才写 CHANGELOG、递增版本。但**帽子类型（改结构 / 加功能）和版本段位，应该在动手之前就定死**——等改完再归类，你已经没有能力判断自己有没有混戴了（人总会把混戴的东西归到自己想归的那一类）。 | 你明示的纪律原文（`_交底:144` 第 8 条）＋ `CHANGELOG.md:10-16` 的段位表（"次版本 = 向后兼容的**新功能**"／"修订号 = 缺陷修复、文案与界面微调、**内部重构**、文档同步"） |
| **M3** | **"同步项目说明文件"没有核对单**，所以它不是可执行动作，是一句愿望。三处已知漂移可证（D1/D2/D3）。 | §3 岗位④ 的 D1~D3 |
| **M4** | **"变好了"从来没被验过，只验过"没坏"**。S16 事故（84 项全绿、缺陷照流，`PrivHub-插件实现规则.md:368-374`）＋ 首屏测试全是 HTTP/slot 级断言（E5）＋ 4 处跳过也算通过（E6） | E5、E6 |

**补哪一环、怎么补（四条，按成本从低到高）**：

| 补法 | 具体动作 | 成本 | 为什么值 |
|---|---|---|---|
| **补 1（必做·近乎零成本）** | 把"跑回归"变成**一条不可绕过的命令**：在 `privhub/package.json` 的 `scripts` 里加 `"test": "node tests/run-all.mjs --spawn"`。**只加一行，不改任何代码。** | 一行 | 从此"跑测试"不需要记路径、不需要记参数；AI 与人都只能用同一条 |
| **补 2（必做·本视角最推荐）** | 把**版本号一致性**做成机器闸门——`tests/integrity.mjs` 里**已经预留了 `--release` 闸门位**（`:12`、`:36`、`:65`、`:97`），只需在其中补三条断言：① `privhub/package.json` 的 `version` == `CHANGELOG.md` 顶部声明的当前版本；② `CHANGELOG.md` 中存在 `## [x.y.z]` 且 x.y.z 与之相等；③ 该段落**只含一节**（"新功能"与"内部重构/缺陷修复"不同时出现）。 | 一个文件、几十行 | **这是把"两顶帽子"从口头纪律变成机器纪律的唯一办法**。第③条尤其关键：**混戴会当场被机器抓出来。** |
| **补 3（建议做）** | **顺序改一下**：把"定帽子类型与版本段位"从**事后**移到**事前**（Step 1 的施工单里就写死）。CHANGELOG 与 version 仍在改完之后写（Step 7），但**"这次是哪顶帽子"在动手前就不可更改**。 | 零代码，只改习惯 | 人不能在改完之后诚实地判断自己混没混；只能在改之前约束自己 |
| **补 4（建议做，但需要你的注意力）** | **每轮至少做一次"反向验证"**（Step 6）。写进施工单的固定字段，没写就不许开工。 | 每轮几分钟 | 这是唯一能把"变好了"变成事实的动作。**它不可自动化**——本项目没有浏览器、没有截图、没有界面级测试。 |

**一句总结**：**绿卡已经印好了，就是没人规定进场必须刷卡。** 补 1 + 补 2 的代价是"一行 + 几十行"，收益是把本项目**唯一**能自动化的一环，真正接到你的改动纪律上。

### 4.3.1 用 Fowler 自己的"导轨与传感器"来看这套流程（4.3 的更锋利版本）

Fowler 2026 年给这件事起了名字：**harness engineering**——**打磨 AI 周围的「导轨（guides）」与「传感器（sensors）」。** 原话：

**导轨**＝上下文、架构约束、给它读的规则文件；**传感器**＝测试、类型检查、不变量、安全检查。

**把这个框架套到 PrivHub，结论很刺眼——这个项目的"导轨"厚得罕见，"传感器"薄得罕见：**

| | 本项目现有的 | 证据 |
|---|---|---|
| **导轨（厚）** | `README.md` / `CHANGELOG.md`（354 行，带版本号规则表）/ `docs/PrivHub-插件实现规则.md`（383 行，含新增插件 SOP、代码修改纪律 §6、环境操作纪律 §6.1）/ `docs/PrivHub-架构与功能说明.md` / `_交底` / 五份顾问方案 / 本次蒸馏的 skill —— **一个非程序员能攒出这一叠规则文档，是很少见的。** | §2.1 |

### 4.4 「两顶帽子」在本项目的操作定义（本视角的核心交付）

#### A. 哪类算"改结构"（对外可观察行为必须完全不变）

判据一句话：**用户能看见的、别的插件能依赖的、磁盘上能读到的，全都不能变。**

| 算改结构（举例） | 为什么 |
|---|---|
| 把 `openBarItem` 的 9 个视图名 `else if` 换成一张映射表 + `v-for` | 点击同一个图标仍到同一个视图（前提：5 条专属跳转分支不动，`05-shape-up.md:207`） |
| 清掉骨架里已退役的 `tabs` slot 渲染（`frontend/index.html:1029`） | 全仓 0 个 manifest 声明它，删掉后没有任何东西可观察地改变（E3） |
| 把 `querySelector('.v3-content')` 换成插槽/事件（岗位⑥） | 4 个插件的功能不变，只是连接方式从"偷看"变成"明说"（E4） |
| 把 `svc-rag/client/index.js`（1025 行）拆成多个模块 | `_交底:115` E2 —— 文件搬动，功能不动 |
| **只加** `:root` 令牌定义、**不改**任何现有 CSS 规则 | `03-refactoring-ui.md:340` —— 零影响，这是"建表"那一半 |
| 合并 5 份同构 Markdown 渲染器（`_交底:116` E4） | **⚠️ 高风险**：它含一个历史 XSS（S3）。改结构帽必须**先补测试再动手**，否则一步从"改结构"滑成"改行为" |

#### B. 哪类算"加功能"

**任何让用户可观察行为发生变化的东西**，包括看起来很"小"的：新增入口/按钮/字段、改文案、改排序、改默认值、改提示语、**把硬编码颜色换成变量（视觉呈现会变）**、新增键盘快捷键键位。

**⚠️ 这里有一处本项目特有的粘连，必须点名**：`CHANGELOG.md:16` 把"**文案与界面微调**"和"**内部重构**"都归在**修订号**段位，但按 Fowler 的判据它们分属两顶帽子——**改文案是"加功能"（行为变了），内部重构是"改结构"。** 它们共用同一个版本段位，于是**特别容易在同一个提交里混戴**（"我改个提示语顺便把这段代码抽出来"）。

**建议**：不要动版本号规则表（那是你定的），而是在**施工单里加一个必填字段**——`帽子类型`，与`版本段位`分开填。段位可以相同，帽子必须唯一。

#### C. 同一个提交里混戴，会出什么事（四条具体后果，不是原则）

| # | 后果 | 在本项目的具体形态 |
|---|---|---|
| **1** | **出问题了，查不出是谁弄坏的** | 回归红了。你手里有一个提交，里面既有"把 9 个视图名换成映射表"（理应行为不变）又有"顺手加了 F5 刷新快捷键"（行为变了）。红的是哪一半？**没有任何办法从测试结果区分**——因为测试只告诉你"某个地方坏了"。 |
| **2** | **回退的时候连好东西一起回退** | 想退掉那个出问题的改动，`git revert` 会把**两半一起**拿掉。于是你"改结构"的那部分工作全部作废，而且会倾向于"算了我手工改一下"——**手工改回来的东西没有经过回归。** |
| **3** | **"行为不变"这个唯一的判据没法证伪** | 改结构帽的全部价值，就建立在"我可以断言对外行为没变"这句话上。一旦同一个提交里还有改行为的东西，**这句话就没法验了**——你分不清观测到的变化是来自哪一顶。于是"改结构"退化成"我又改了一遍代码，希望没坏"。 |
| **4** | **CHANGELOG 与版本号当场失真** | `CHANGELOG.md:12-16` 的段位表要求"新功能→次版本""内部重构→修订号"。混戴的提交**两个段位都说得通、也都不对**。你会被迫选一个，而这一选就是永久记录失真——下一次翻 CHANGELOG 时，你无法回答"3.1.1 到底改了什么"。三年后唯一能读懂这个项目的东西，就是这份 CHANGELOG。 |

**还有一条更隐蔽的（Fowler 没明说，但本项目必然会遇到）**：**混戴会让"测试"失去方向。** 改结构帽的测试要求是"**测试必须原封不动，而且必须还是绿的**"（测试是行为的证人）；加功能帽的测试要求是"**必须新增一条测试**"（测试是行为的定义）。混戴的时候，两边的规矩互相抵消——**最省事的做法变成"改一下那条测试让它过"**，而那正是 S16 事故的形态。

### 4.5 一处必须澄清的判据：什么叫"对外可观察"（这条直接决定 E4 那颗雷怎么拆）

Fowler 的"不改变可观察行为"里，**"可观察"指的是"已经发布出去、别人已经在依赖的东西"**——`references/research/01-writings.md` 第 3 条把这条分界线单独列了出来。**它的另一面同样重要**：如果那个东西的**使用方全都在你自己手里**，那么改它就**算改结构，不算加功能**。

**把这条判据套到 PrivHub，结论对一半、错一半，必须说清：**

| 对象 | 按严格判据算不算"对外可观察" | 但本项目该怎么办 |
|---|---|---|
| `explorer-v3` 的 `.v3-content` / `.v3-md` / `.v3-loading` 类名 | **不算**——它从未被承诺给任何外部使用方。**使用方是 4 个同仓插件，全在你自己手里。**（E4） | **仍然必须先当"加功能"处理一次。** 理由：4 个插件会**静默失效、不报错**（`_交底:131`"修订顶栏时已因此连撞两次"）。"改结构"这个分类**不能拿来当免责声明**——它只说明"你没违反对外承诺"，**不说明"你没弄坏东西"**。所以顺序是：**先补上"四个插件逐个点名跑一遍"的验证、确认它们还能用，再把它降级成"改结构"帽。** |
| `GET /privhub/api/shell/manifest` 的返回字段（`id/title/icon/slots/entry/barItems`） | **算**——它是插件前端与骨架之间的公开契约，第三方插件按它写（`PrivHub-插件实现规则.md:318-320`） | **字段增删必须当"加功能"帽**，并且按 Tolerant Reader 的思路做（读取方更宽容，而不是给它加版本号） |
| `frontend/index.html` 里 `.topbar` / `.side-wrap` 的 CSS 类名 | **不算**——没有外部使用方 | 可以当"改结构"帽，但**必须先确认 E4 那四个插件没在偷看它们** |
| 磁盘上的 `data/`、`data-files/` 格式 | **算**（旧数据要能继续读） | 按数据车道处理（`05-shape-up.md:307-327`），**不属于本施工队权限** |

**一句话**：**"这不算对外行为" 是"你有权改"的证明，不是"改了不会出事"的证明。** 本项目 4 个插件的静默失效，正是"有权改"和"不会出事"之间的那条缝。**岗位⑥（拆线工）存在的全部理由，就是先把这条缝补上，再让岗位①动渲染层。**

**最后一条必须留在这里的诚实标注**：**Fowler 这套"改结构"的方向本身，收到过一条直击根基的批评**（Mike Taylor, 2010，见 `martin-fowler-perspective/references/research/04-external-views.md` 第 1 条）：他逐行追了《重构》开篇的例子，发现"改进"之后**要搞懂租金怎么算反而得读 6 个类而不是 1 个方法**；他的结论是**"一个人的简单就是另一个人的复杂"，属口味而非对错**。
**在单人项目里这条批评的杀伤力小一些**（只有一种口味，不会爆发"重构战争"）；**但它提醒一件事**：**"我以为我在改进结构"和"我真的改进了结构"是两句话。** 前者你说了算，后者**需要一个不是你的判断**——这就是岗位⑤（独立审核员）在单人编制里也**不能省**的原因。

### 4.6 从 Fowler 的版本主张里，再补两条本项目的具体动作

**补 5（建议做·成本近乎零）：把"依赖升级"也当成一次显式的功能改动。**
Fowler 的版本主张里有一条：**依赖要钉住具体版本，绝不引用"最新版本"**（`references/research/01-writings.md` 五条主张之②）。本项目的 `privhub/package.json:11-27` **全部用 `^` 范围**（如 `"better-sqlite3": "^13.0.3"`），实际版本钉在 `package-lock.json`。
→ **含义**：`package-lock.json` 是"行为"的一部分。**锁文件一旦被更新，那就是一次行为变化**，即使源码一个字没改。
→ **动作**：① 把"**本轮的锁文件有没有被动过**"写进施工单的必填字段；② 锁文件真动了，**单独一次提交、单独一顶帽子（算功能帽）、单独一条 CHANGELOG**——**绝不和任何结构改动混在一起**。这在单人 + AI 生成代码的项目里尤其要紧：AI 改代码时顺带跑一次安装，锁文件就变了，而**没有任何测试会因此变红**。

**补 6（建议做）：CHANGELOG 的条目要写"意图"，不只是"改了哪些文件"。**
Fowler 在 2004 年给这件事造过一个词：**semantic diff**（语义差分）。**"改了 3 个文件"不是变更记录；"把视图分发从骨架白名单改成插件声明"才是。**
→ **动作**：给 CHANGELOG 条目的第一行定一个固定格式——**一句"这次改动的意图"**，然后再列文件与细节。这条目前在本项目的 CHANGELOG 里已经做得不错（`CHANGELOG.md:27-34` 的 3.1.0 条目有"动机（用户要求）/ 范围"两栏），**要做的只是把它从"写得好"变成"必须写"**。

### 5.1 最少可行编制（只能设 1 个智能体时选谁）

## 6. 我建议不要设立的岗位

| # | 不建议设的岗位 | 为什么 |
|---|---|---|
| **N1** | **不设"验收员"作为独立岗位** | 本项目的验收**无法由 AI 完成**：没有浏览器、没有截图、没有界面级测试（E5）。设了这个岗位，它只能给你"我看过代码了，应该没问题"——**这句话没有信息量，还会稀释"必须人眼看"这件事的严肃性**。验收只能是**你**，或者退化成"机器能验的那部分"（回归 + grep 归零 + 反向验证）。 |
| **N2** | **不设"部署同步员"** | `PrivHub-插件实现规则.md:352-360` 是铁律：生产同步必须经你明确授权。**把这件事交给一个常驻 AI，等于把一条已经吃过事故（`:342-348`）的纪律重新暴露出去。** 同步是一件低频、高风险、必须你亲手点头的事，做成岗位只会增加"顺手同步一下"的诱惑。 |
| **N3** | **不设"产品决策员 / 立项审批员"** | 那是**顾问组**（Shape Up 一路）的活，而且 `00-汇总与拍板建议.md:3` 已明确：顾问组只管提意见、不参与施工。**施工队自己决定"该不该做"，就会出现"自己给自己发施工许可"** ——这正是 `05-shape-up.md:238` 那道外部闸门要防的事。 |
| **N4** | **不设"代码风格 / lint 员"** | 项目**没有 lint 配置**（E9），这不是疏忽而是选择（无打包链、无构建步骤是既定特性，`_交底:138`）。为风格单设一个 AI 岗位，产出的是**无法验证的主观意见**，而它会消耗你的人工确认额度。 |
| **N5** | **不设"文档撰写员"独立于记录官** | 文档同步（D1/D2/D3）**必须跟改动绑定在同一次提交里**才有意义。独立成一个岗位，就会出现"代码改了、文档下个月补"——那正是当前漂移的成因。 |
| **N6** | **不设"性能优化员"** | 唯一的性能疑似项（`office2` 的 10.7 MB Univer 包）已被判定为"**进首屏之外、按需加载**"（`_交底:65-67`，已结案）；虚拟滚动 U5 的基线**从未测过**（`05-shape-up.md:342` N8 明确不做）。**设了也只能空转。** |
| **N7** | **不设"AI 代码质量裁判员"** | 这是我最想劝你**别设**的一个。它听起来最对症（"全是 AI 写的代码，找个人审一审"），但 `05-shape-up.md:381` 已经把结论写死了：**"非程序员最难判断的恰恰是『AI 说这个能做，是真的能做吗』"**，而**AI 审 AI 无法解决这一点**。它的产出会让你产生"已经审过了"的安全感，而那个安全感是假的。**要审，就用岗位⑤那种"不带上下文的对抗性反例"，而不是"给份评分"。** |

### 7.1.1 我这把视角能补上的、和补不上的（一句话版）

Fowler 在 2026 年给"AI 当执行者"这件事的答案非常集中，而且**恰好命中本项目**：

| 他的话 | 本项目的对应动作 | 我能不能替你做完 |
|---|---|---|
| **"在验证上的投入，必须超过在生成上的投入"**（否则是强引擎弱刹车） | 补 1 + 补 2 + 补 4（§4.3） | **能给出具体动作与成本（一行 + 几十行 + 每轮几分钟），但要不要做是你的决定** |
| **"不能外包验收标准"** | 施工单里"什么算完成（可当场验证）"必须**你写**，不能由执行者定义 | **只能提醒，写不了**——我不知道你的验收标准 |
| **"导轨与传感器"**（harness engineering） | 你的导轨已经够厚（§4.3.1），缺的是传感器 | **能列出缺哪几个传感器**（§4.3 补 1/2） |
| **"不要贴着边缘滑行"**（容差） | T1/T2/T3 三处（§4.3.1） | **只能【推断】指出位置，量不出来** |
| **"不能只把 prompt 存进 git 就指望行为复现"** | 提交信息 + CHANGELOG 是唯一的行为留痕 | **能定格式，做不到替你执行** |

**⇒ 我在这把视角上最实在的贡献，是把"缺哪几个传感器、装在哪里、代价多少"写成可执行清单（§4.3 的补 1~4）。这是本方案里唯一"你今晚就能做完"的部分。**

**判不了的最大一块**：**U-3 + U-4 合起来，就是"改结构"这个动作在本项目到底安不安全。**
Fowler 整套方法的两个隐含前提是：**① 有测试覆盖当安全网；② 有团队评审当第二双眼睛。** 本项目**两个都没有**（E5/E6/E9 是"覆盖不足"的证据，单人 + 无设计师是"没有第二双眼睛"的证据）。
所以 —— **我能设计编制、能设计闸门、能设计帽子纪律，但"改结构"这个动作本身的风险，我判不了。** 而这恰恰是你请这套视角来的原因。**这一条建议当作整份编制方案的最高风险项。**

### 7.2 我这把视角该不该当"总工"

**结论：该当，但"总工"这个词要改。**

**该当的理由**：本项目当前最缺的不是创意，是**把已有的纪律焊到自动化闸门上**（§4.3 缺的那一环，代价只有"一行 + 几十行"）。"小步 / 每步重新变绿 / 两顶帽子 / 版本号与变更日志"这一套，**正好是给"AI 改代码 + 单人维护"这个场景配的**——因为 Fowler 的整套方法本来就是为"我不敢一次改太多"发明的。这是我最有把握的一块。

**补一句更有力的理由**：**Fowler 对这个场景是有直接表态的，而且他讲的就是"导轨 / 传感器"。** 一个非程序员在"全部代码由 AI 生成、没有团队、没有 CI"的条件下要动手改，**他 2026 年那三句话是现成的地图**：验证投入要超过生成投入、验收标准不能外包、不要贴着边缘滑行。**这三句翻译成本项目的动作，就是 §4.3 的补 1~4 与 §4.3.1 的 T1~T3。**

**但我不该是"总工"，我只该是"施工规范制定者"。** 三条边界：

| # | 我不当的事 | 理由 |
|---|---|---|
| **1** | **不替你把关"要不要做"** | 那是顾问组（Shape Up 一路）的位置，且 `00-汇总与拍板建议.md:3` 已明确顾问组不参与施工。我若既管"做什么"又管"怎么做"，**就变成了自己给自己放行**。 |
| **2** | **不替你判断"AI 有没有骗你"** | `05-shape-up.md:381` 的结论对我也一样成立：**我无法验证另一个 AI 的工程判断是不是真的。** 我能做的只是把"该被追问的问题"写具体（§4.3 的补 2、岗位⑤的三问）。 |
| **3** | **不替你决定验收标准里的"好不好看"** | 令牌层那类改动，验收只能你人眼看（`03-refactoring-ui.md` 全篇的前提是"有个改前改后的对照"，而不是"有个好看的算法"）。 |

**一句话**：**我该当的是"编制与闸门的设计者"，不是"验收官"。**
具体来说，我这把视角最该常驻的时机是**三个时刻**：
1. **每次动手之前**——把这次改动定成"改结构"还是"加功能"，并把"什么算完成"写成能当场做给你看的动作；
2. **每次改动收工之后**——检查回归是否真的全绿、反向验证有没有做、CHANGELOG 有没有混节；
3. **每次你想"顺手一起改了"的时候**——那正是两顶帽子要混戴的那一刻。

**而"动手改代码"这个动作，应该由另一个挂着本 skill、但不带设计上下文的会话来执行** —— 因为**设计和执行由同一个会话完成时，"我设计得对不对"就永远没人问**。
