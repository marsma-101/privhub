## 1. 一句话判断：施工队最该防什么

**施工队最该防的不是"改错一个颜色"，是"改对了颜色、却让 27 个插件里某个功能静默不工作"——因为在这个项目里，样式层没有产权边界：32 个带前端插件里，只有 5 个自己写 CSS，剩下 27 个的界面长相 100% 由骨架那 331 行 `<style>` 决定。**

一句话再压缩：**骨架的 `<style>` 事实上是一个被 20 多个插件共用的组件库，只是从来没人这么叫它。改它的"值"是高杠杆，改它的"名"是静默事故。**

所以这把视角给施工队定的第一条纪律是：

> **只改值，不改名。改名必须是一次独立的、有契约说明的改动，绝不能夹在"视觉优化"里顺手做。**

（依据：§2.3、§2.4。这条不是我发明的，是 `03-refactoring-ui.md:620-621` 已经点出的事实，我复核后把它提到了"第一条纪律"的高度。）

### 2.4 状态类三套并存 —— **"例外必须显式命名"这条规则在本项目的现场标本**

| 组件 | 类名 | 证据 |
|---|---|---|

### 3.1 先落地：PrivHub 的 CUBE CSS 分层方案

这是我这份方案的核心。**四层不是四个文件夹，是四个"该放什么"的判据。**

#### 层 1 · Composition（构图）——决定"东西怎么排"

| 归属 | 现状类名（`frontend/index.html` 行号） |
|---|---|
| **骨架独有，且应该独有** | `.app:86`、`.topbar:91`、`.body:104`、`.sidebar:106`、`.main:128`、`.main-head:137`、`.main-body:143`、`.right-panel:227`、`.appbar:203`、`.view-inner:265`、`.file-list:144`、`.file-table-head/.file-table-row:156`、`.auth-wrap:32`、`.tp-right:96`、`.side-wrap`（模板 `:1010` 行内） |

**判据（他的原话）**：Composition 层**不该提供视觉处理（颜色、字体）、不该提供装饰样式（阴影、图案）、不该逼浏览器生成像素级完美布局**（`cube.fyi/composition`）。

**我在项目里找到的 5 处 Composition/Utility 串层**（这是要改的）：

| # | 位置 | 问题 | CUBE 的说法 |
|---|---|---|---|
| 1 | `.btn:76` `padding:10px 16px; border-radius:6px; border:none` | 一个类同时定义了**布局尺度 + 视觉外观** | 同时定义一组不相关属性 → 官方指名说"这该是 Block，不是 utility"（`cube.fyi/utility`） |
| 2 | `.btn-primary:77` `width:100%` | **视觉变体类里塞了布局约束** | 于是 `index.html:987` 和 `:1072` 只能靠行内 `style="width:auto"` 反搓回来——**这是 Composition 缺位的直接症状** |

#### 层 2 · Utility（工具类）——**本项目的重头戏**

**关键判断：骨架 `<style>` 里那 137 个类名，绝大多数是 Utility 层。** 依据是 §2.3 那个事实：**27 个插件一行 CSS 都不写，它们全靠这些类名**。

| 子类 | 类名 | 被引用插件数 |
|---|---|---|
| **共享交互元素**（最大杠杆） | `.btn` `.btn-primary` `.btn-ghost` `.icon-btn` `.small-btn` | `.btn-primary` **20**、`.small-btn` **15**、`.btn-ghost` **14**、`.icon-btn` **10** |
| **共享容器/浮层** | `.modal` `.modal-mask` `.modal-body` `.modal-foot` `.ctx-menu` `.ctx-mask` `.ctx-item` | `.modal` **16** |
| **共享文字/状态** | `.empty` `.crumb` `.badge` `.kv` `.k` `.v` | `.empty` **12**、`.crumb` **10**、`.badge` **9** |
| **共享表格** | `.u-table` `.u-row` `.u-project-chip` | — |

**⇒ 结论（这一句是给施工队的）**：**改这一层的"值"，受益面是 20 多个插件、风险为零；改这一层的"名"，是静默事故。** 这是全项目投产比最高的一个动作，也是我最想守住的纪律。

**其余 27 个插件在 CUBE 意义上没有 Block**——它们把界面完全交给 Utility 层（骨架）。**这不是缺陷，恰恰是 CUBE 描述的理想形态**：他的原话是到了 block 这层"全局 CSS / composition / utility 已经做完大部分工作"，block 只负责"**running against the grain**"（逆着全局走一小段）。

**但有一个必须点名的越界**：`files-office2/client/index.js:20-21` 用 `.v3-content:has(iframe.office2-frame)` —— **一个插件的 CSS 在改另一个插件的元素**。这在 CUBE 里不是"层错位"，是**根本没有层**。违反硬约束第 5 条。

#### 层 4 · Exception（例外）——**本项目最需要、也最容易做错的一层**

**先纠正一个常见误解（我调研后确认的）**：CUBE 的 Exception **不是用 CSS 类，而是用 data attribute**。`cube.fyi/exception` 把这条写成了硬规则：

> "**What should an exception do?** 1. Provide a concise variation to a block 2. **Use data attributes**"
> "**What shouldn't an exception do?** 1. Variate a block to the point where it isn't recognisable anymore… 2. **Use CSS classes**"

**为什么**（他给的理由，`Complete CSS` 第 9 课）：BEM 的 modifier 是类名制，而"**你可以往元素上挂任意多个类，因此你无法保证哪个 modifier 会赢**"；他"**把 modifier 当作状态变化**"来对待，而状态变化由 JS 驱动、JS 又很不稳定。用 data attribute 之后，例外是**有限的（finite）**——同一个属性只能有一个值。

**⇒ 这条规则在 PrivHub 的具体落地：命名成什么？**

**我建议采用两个属性、固定取值表**：

| 属性 | 取值 | 覆盖的现有状态类 |
|---|---|---|
| `data-state` | `active` / `selected` / `disabled` / `loading` / `error` / `success` | `.on`、`.active`、`.sel` |
| `data-variant` | `primary` / `ghost` / `danger` / `admin` | `.btn-primary`、`.btn-ghost`、`.danger`、`.badge.admin` |

**现状 → 目标 的逐条对照**（全部是我从源码读出的真实用法）：

| `.abar-item.on`（`index.html:212`；模板 `shell/client/index.js:104,114`） | `data-state="active"` |
| `.ptab.on`（`index.html:187`；`shell/client/index.js:34`） | `data-state="active"` |

**⚠ 三条必须写进契约的限制（否则会把项目改坏）**：

1. **必须先加"双锚"，不能直接换。** 那 10 个引用点全在插件里（§2.4 实测：`abar-item` 在 `shell/client/index.js:104,114`，`ptab` 在 `:34`，`v3-tab` 在 `explorer-v3/panel.js:369`，`v3-tn` 在 `tree.js:46`）。**直接换 = 10 处静默失效**。做法：新 data 规则与旧类规则**并存**，插件**保留旧类**、另加 `data-*`；新代码只用 `data-*`；等 32 个插件的细节改造轮到它时，再删旧类选择器。
2. **⚠ 特异性会从 0-1-0 升到 0-2-0。** `.tree-item.active` 是 (0,2,0)……更正：`.tree-item.active` 是 **(0,2,0)**，而 `[data-state="active"]` 单属性选择器是 **(0,1,0)**。**若写成 `.tree-item[data-state="active"]` 则是 (0,2,0)**，与现状持平；**若写成裸 `[data-state="active"]` 则是 (0,1,0)，反而变弱**，可能被插件里任何 `.v3-xxx` 规则盖掉。**→ 契约必须规定：一律写成 `.<block>[data-state="…"]`，保持特异性不降。** 这是我建议里最容易踩的坑，单独列出来。
3. **不是所有 `.on` 都该归 Exception。** `.abar-item.on` 表达的是"当前视图"，是**导航选中状态**，用 `data-state="active"` 合适；但 `admin-console` 里 `.on: r.code === st.selectedId`（`panels.js:318`）是**数据选中**，语义更接近 `aria-selected`。**施工队遇到"到底算不算状态"要问，不要猜**——本视角不替主子判这个。

### 3.2 回答一：无打包链下，令牌层怎么落地

**结论先说：令牌层天然不需要打包链，因为 CSS 自定义属性就是平台能力本身。** 这正好落在本视角的主线上——**用平台自身的机制做系统，而不是靠工具链**。所以硬约束第 2 条（无打包链是特性）与"建令牌层"**不冲突，一个字都不用让步**。

**⚠ 但必须点明一处"他的做法在本项目不适用"**（这是诚实的边界，不能装看不见）：

Andy Bell 在 Set Studio 的官方 boilerplate 里，令牌是 **`colors.json` → PostCSS 插件 → 同时生成 Tailwind config 与 `:root` 自定义属性块**（`Set-Creative-Studio/cube-boilerplate`）。**这个生成步骤本项目不能抄**，因为硬约束第 2 条不允许引入构建步骤。

**⇒ 所以本项目改用他体系里的另一半，而这一半恰好是纯 CSS 的**：他主题化文章给的**三层变量结构**（`01-writings.md:467-479`）。逐层落到 PrivHub：

| 他的层 | 内容 | PrivHub 怎么落 | 现状对照 |
|---|---|---|---|
| ① **原始令牌** | `--size-step--2`、`--space-3xs`、`--color-midnight`；纯数值，从 JSON 生成 | **手写 `--sp-*` / `--fs-*` / `--r-*` / `--sh-*`，值直接取 `03-refactoring-ui.md` 表 1–4**；不生成，就写死在 `:root` | **完全没有** ← 要新建 |
| ② **语义变量** | `--text-size-base: var(--size-step-0)`、`--color-global-bg`；**CSS 实际只用这一层** | 把 `--bg/--panel/--text/--muted/--accent/--danger/--warn/--line` 重写成 `var(--色阶-*)` 的别名；**并且按 `03` 的 P0-1 拆出 `--accent-solid` / `--accent-hover`** | 现有 9 个颜色变量**就是**这一层的雏形 |
| ③ **组件变量** | `--button-bg`、`--flow-space`、`--sidebar-target-width` | `--admin-*`（16 个）、`--v3-preview-font`（1 个）**保持独立，暂不动**；新增组件变量必须带组件前缀 | 已有两套平行体系 |

**他明说的那条硬规则**（`01-writings.md:476`）：
> "The really important thing about theming though is you **need to abstract into more specific, semantic variables** when applying to your CSS styles."

**⇒ 这解释了为什么 `--admin-*` 那 16 个变量不算"重复建设"**：它们是**第 ③ 层**（组件变量），本来就该存在、本来就该有前缀。**施工队不要去"统一"它们**——那会把三层结构压成两层，反而丢掉主题翻盘的着力点。

**分三步，每步可独立回滚。这个划分不是我发明的，是 `03-refactoring-ui.md:511-518` 已经给的，我复核后照用并补了验收手段**：

| **步 1** | **只在 `index.html` 的 `<style>` 最前面加令牌定义块，一条现有规则都不改** | **1** | **零** | 删掉即回到原状 |
| **步 2** | 骨架内部逐条把 px 换成 `var(--sp-*)` 等 | **1** | 全站视觉（但只有骨架自己的规则） | `git revert` 一个文件 |

**步 3b 的落点必须按"值的来源"分三类**（这三类的改法完全不同，混了就改不动）：

| 来源类型 | 具体位置 | 改法 |
|---|---|---|
| **① 注入式 CSS 字符串** | `explorer-v3/styles.js:14,90`、`admin-console/styles.js:30`、`svc-rag/index.js` 的 `S.*` | **纯字符串替换**，不用管运行时 |
| **② Vue 内联 `:style` 绑定** | `admin/client/index.js:117`、`admin-acl:154`、`explorer-v3/panel.js:561,564`、`files-template:243,260,267,299,305`、`files-tags:99`、`files-versions:108` | **纯字符串替换**——把 `'rgba(90,130,200,.12)'` 换成 `'var(--accent-soft, rgba(90,130,200,.12))'` |

**"带上原值做回退"这个写法是必须的**，不是讲究：`var(--accent-soft, rgba(90,130,200,.12))` 保证**插件单独加载、骨架令牌还没定义时，它仍然显示成原来的样子**。这正是他讲的 **Progressive Custom Properties**——`var()` 的 fallback 机制让"合理默认"可以按需被覆盖（`01-writings.md:459-465`）。

2. **令牌确实生效**：DevTools `Computed` 面板里 `padding`/`font-size`/`border-radius` 能看到 `--sp-*` / `--fs-*` 的结果。
3. **⚠ 不要用"看着没变"当失败**——刻度收敛的价值在于"**后来加东西时不再多一个值**"，第一次改完看着差不多**是成功**（`03:528` 说得对，我同意）。

### 3.3 回答二：怎么避免"改骨架 CSS 把 32 个插件弄坏"

**先给结论：这个风险是真实存在的、有确切数值的，但它也是全项目最容易防住的一类风险——因为防线只是一条命名纪律。**

风险的准确形状（§2.3 实测）：**改"值"→ 20 多个插件同时受益、风险为零；改"名"→ 引用它的插件静默失效、不报错、只是不工作。**

**五条防线，按重要性排**：

**防线 1（最重要）· 只改值，不改名。**
> 这是本文的第一条纪律（§1）。**"视觉优化"这批施工里，任何一个类名的改动都应被直接拒绝**，无论它看起来多顺眼。

**防线 2 · 已知的静默失效清单（施工前必须贴在手边）**

| 依赖方 | 依赖什么 | 证据 |
|---|---|---|
| `files-office2` | `.v3-content`（还往里写 CSS） | `client/index.js:41`、`:50-51`、`:20-21` |
| `files-edit-md` | `querySelector('.v3-content')` + `teleport to` | `client/index.js:220`、`:270`、`:428`、`:237` |
| `files-comments` | `querySelector('.v3-content .v3-md')` | `client/index.js:112` |
| **`shell-agent-console`** | **复用 explorer-v3 的 `.v3-loading` 类**（自己不定义、靠对方注入） | `client/index.js:174,175,293` |

**注意第 4 条**：账本原记 3 个插件，实为 **4 个**（`03:160` 首先发现，`00-汇总:44` 已复核）。**它的危害形态最隐蔽**：explorer-v3 不在场时，"正在加载…"没有颜色也没有内边距——**静默降级，不报错**。

**防线 3 · 用 `:where()` 做兜底，而不是 `!important`**
```css
/* ✅ 特异性 0，任何现有规则都能盖过它 —— 安全的兜底 */
:where(.tree-item[data-state="active"]) { background: var(--accent-soft); }
```
`03:520-526` 给的做法我认可。**⚠ 但必须同时说清它的两个局限**：① 它**盖不过内联样式**（所以步 3b 那批必须改 JS）；② **当"当前写法特异性更高"时，`:where()` 兜底会静默失效**——这时不能靠加 `!important` 硬顶（官方文档明确把 `!important` 列为 utility 的"不该做"），**要回头改选择器**。

**防线 4 · 删掉名称从未被使用的死代码，这是唯一安全的"删名"**
`index.html:876` 那个已退役的 `tabs` slot（全仓 0 个 manifest 声明它）——**删它是安全的**，因为它没有引用方。**这类改动与防线 1 不冲突**：防线 1 保护的是"有引用方的名字"。施工前用 `grep` 确认"0 引用方"即可动手。

**防线 5 · 每改完一个插件，卸载它再看一遍界面**
`03:624` 给的这个验收手段非常好，我把它升级为**准出条件**：**卸载该插件 → 界面应无残影、无变差**。这是对硬约束第 3 条（插件前端必须完全在自己目录内）**唯一可执行的检测手段**。

### 3.4 回答三：无障碍的施工顺序，以及为什么是这个顺序

**顺序：① 对比度 → ② 焦点态 → ③ 键盘可达。**

**为什么是这个顺序——三条理由，都是"成本 ÷ 收益 ÷ 依赖"：**

**① 对比度排第一，因为它是唯一"用户说不出、但一直在受损"的一项。**
视觉上"不够精致"用户会说；"我 45 岁看这小字有点累"用户**不会说，只会少用**。而修它的成本是**改 2 个 CSS 块、1 个文件、16 行以内，零插件风险**（§2.6 我已独立复算全部数值、全部达标）。`03:268` 说"投入产出比在这一项上是压倒性的"，我复核后**完全同意**。

**② 焦点态排第二，因为它与对比度共用同一个变量，必须紧接着做。**
`:focus-visible` 的 `outline: 2px solid var(--accent)`（`index.html:340`）**用的是 `--accent`**。而 `--accent` 在 P0-1 里刚被拆成 `--accent`（当文字）与 `--accent-solid`（当按钮底）。**如果先改焦点态、后调对比度，焦点环的颜色会在后一步被意外改掉**——`--accent` 从 `#4a7bd6` 变 `#3a63be`，焦点环跟着变深。**先定色、再上焦点态，就只用验一次。**

**③ 键盘可达排第三，因为它是"结构问题"，成本量级完全不同。**
- 焦点**能看见**（②）→ 1 条 CSS 规则，**零风险**。
- 焦点**到得了、Tab 顺序对不对、Esc 管不管用**（③）→ **要改插件的交互结构**，超出视觉层射程。

**⚠ 一个必须写在明处的现成缺口**：骨架里被补过焦点态的一共 6 个选择器（`.btn / .icon-btn / .small-btn / input / select / textarea`），而**最高频的点击目标一个都没有**——`.tree-item:124`（目录树）、`.ptab:182`、`.abar-item:207`、`.file-card:145`、`.file-table-row:161`、`.ctx-item:239` **全部只声明了 `:hover`**。键盘用户 Tab 到目录树上，**界面上看不到焦点在哪**。

**④ 为什么这三步"不能合并成一次做完"**：不是技术原因，是**验收原因**。②的验收是"Tab 过去能看到 2px 蓝框"（可机器/人工判定），③的验收是"Tab 顺序合理"（需要产品判断）。**把可判定的事与需判断的事混在一批，验收就废了。**

**⑤ 与"护眼配色"的张力（我不替你拍板）**：`--muted` 要**压深**才过 4.5:1，而浅色主题压深 = 对比更强 = 更"硬"，与注释里写的"两套护眼配色"（`index.html:13`）**轻微冲突**。`03:656` 已把这列为需要主子拍板的事，**我这把视角的判断是对比度优先**（依据：`01-writings.md` 里他反复讲的"**We build for everyone. Not just for ourselves or our peer groups.**"，以及"修 hover 的活里顺手修语义与无障碍"那篇 2025-09 的文章）——**但这是取舍，不是对错，请主子拍。**

## 4. 工序

### 4.1 依赖顺序（不可颠倒）

```
第 0 批（建表，零影响）
  岗位 A ── 在 <style> 最前面加令牌定义块，一条现有规则都不改
         └─ 产出：令牌清单（交给 B）、对比度应验算的配对（交给 C）
              │
第 1 批（修硬伤，两个岗位并行，互不干扰）
  ┌───────────┴───────────┐
  A ─ 对比度（改 16 行内）    A ─ 焦点态（加 1 条规则）
  C ─ 验算对比度（独立复算）   D ─ 键盘走查
  └───────────┬───────────┘
              │  ← 这两件都必须 A 先出货；C/D 才能验
第 2 批（骨架内映射）
  A ─ 骨架 45 个离散 px 逐条换 var(--sp-*) 等
         └─ 每换一组就提交一次
              │
第 3 批（插件，串行，一次一个）
  for 每个插件 in 需要改的清单:
      B ─ 改这一个插件（换色罩 / 行内样式改令牌 / 状态加 data 锚）
      E ─ 立即验（卸载插件看界面 + 复现准出条件）
      → 验过才轮到下一个
```

### 4.2 可以并行的

| 可并行 | 为什么安全 |
|---|---|
| **对比度（A）与焦点态（A）** | 都只改 `index.html` 一个文件里的**不相邻的两段**；但**建议还是 A 一个人顺序做**，因为它俩共用 `--accent`，并行容易撞 |
| **C 的验算 与 D 的键盘走查** | 两件事的验收手段完全不同（算 vs 只用键盘），互不影响 |
| **第 3 批里的"纯换色罩"插件** | 如果两个插件都只是把 `rgba(90,130,200,α)` 换成 `var(--accent-soft, …)`，且**都不含跨插件引用**，理论可并行。**但我不建议**——见 §4.3 |

### 4.3 绝不并行的（**这一节比上一节重要**）

| 绝不并行 | 后果 |
|---|---|
| **A 改骨架 与 B 改插件** | B 用的令牌由 A 提供。A 没落地时 B 改出来的全是回退值——**看着对、其实没生效**，是最难查的一类"假成功" |
| **两个 B 同时改两个插件** | `files-template` 一个文件就占 5 处（§2.2）、`explorer-v3/styles.js` 反向改骨架的 `.file-table-row`（§2.5）。**并行改两个插件时，跨插件那 4 处依赖（§3.3 防线 2）无法定位是谁弄坏的** |
| **改"名"与改"值"同批** | 硬约束级别的禁令（H5）。**改名必须独立成批、独立提交、独立验证** |
| **改 Exception 锚点 与 改视觉值同批** | 状态类换 data attribute 会动 HTML 属性；视觉改动动 CSS 值。**两者混在一批，diff 里分不清"失效"是名字改的还是值改的** |
| **动 explorer-v3 或 admin-console 与 动别的插件** | 这两个是 5 个"有自己 CSS 的插件"里最大的两个（92.9KB / 94.7KB），且 explorer-v3 被 **4 个插件**依赖（§3.3 防线 2）。**它们必须单独成批** |

### 4.4 一次改动的完整走法（给非程序员看的版本）

1. **主子说一句需求** → 岗位 A 判断"这次只改值、还是也改名"
2. **只改值** → 直接进第 3 步。**要改名** → 停下，先出契约说明，请主子确认
3. **A 改骨架**（如果是插件的事，A 先把令牌准备好，再交给 B）
4. **C 算对比度**（若本次涉及颜色）／**D 用键盘走一遍**（若本次涉及焦点态）
5. **E 独立复核 diff**：碰了不该碰的文件吗？改了不该改的名吗？准出条件能复现吗？
6. **主子确认** → 写 `CHANGELOG.md` + 递增 `privhub/package.json` 版本号 → 提交推送

> ⚠ **第 6 步的记账该由谁做，我和 Ousterhout 一路不一致**：他把"写 CHANGELOG + 递增版本号"设成了**岗位 A（施工队长）**的职责（`05-john-ousterhout.md:122`）。**我这把视角不另设记账岗，但也不反对设**——因为硬约束第 8 条要求"人工确认后提交推送"，**这一步无论如何都是主子本人按的钮**。见 §6.1。

## 5. 两档编制

### 5.1 最少可行编制：**只能设 1 个智能体时，选「岗位 C 数字验算员」以外的那个——选「岗位 A 总样式管家」**

**先说清楚这个选择的性质**：它是个**妥协**，不是最优解。

**选 A 的理由**：
1. **它的活占总收益的绝大部分**。§3.4 已论证：对比度 + 焦点态 + 建令牌表，**全部只需要改 `frontend/index.html` 一个文件**，且**插件零风险**。§2.3 实测也支持：改骨架的值，20 多个插件同时受益。
2. **它是唯一能"一个人干完一批活"的岗位**。B 需要 A 先给令牌，C 需要 A 先改颜色，D 需要 A 先加焦点态——**A 是所有工序的上游**。设 A，等于设了整条链的起点。
3. **它的权限边界最容易写清楚**，也就最不容易出事：**只改一个文件、只改值不改名。** 单人编制下，边界清晰比职责完整更重要。
4. **它自带记账的自然位置**：它改完就是提交点，顺手写 `CHANGELOG.md` 不额外增加交接。

**为什么不选 C（数字验算员）**：
- 它**不改任何文件**，所以设了它，项目**一步也不会前进**。它的价值建立在"已经有人改了东西"之上。
- ⚠ 但**如果主子的意图是"先摸清现状、暂不动手"**，那 C 是最好的选择——它能产出全项目的对比度体检表（§2.6 我已算过一遍，可以直接复用），且**零风险**。

**为什么不选 B（插件细节匠）**：
- **它必须等 A**。没有令牌，它只能写回退值，等于白干。
- 而且它一次只碰一个插件，**单独设它，收益面非常窄**。

**这个编制的代价，必须写明**：
> **单人编制下，"谁来验"这个问题没有答案。** A 改完自己验，就是自评。§2.7 那张表里我核出的 5 处计数偏差，全部是"打开文件数一遍"就能发现的——**说明原作者也没做这一步。**
> **⇒ 折中办法**：主子**必须亲自按一次穷举验证**。最省事的一条：改完后在浏览器 DevTools 里全仓搜 `rgba(90,` 应为 0 命中；再用键盘 Tab 一遍目录树看有没有蓝框。**两条命令，五分钟，能替掉一整个验证岗位。**
