## 1. 一句话判断：施工队最该防什么

**最该防的不是"干得慢"，也不是"干错了"——是"干完了没人知道坏了"。**

这个项目里已经有一类故障是**不报错的**：`files-office2`、`files-edit-md`、`files-comments` 三个插件靠 explorer-v3 内部的 CSS 类名工作（`docs/experts/_交底-PrivHub前端与功能现状.md:127-129`）。改渲染层，它们**不抛异常、不写控制台、就是不动**。`privhub/plugins/privhub-shell-agent-console/client/index.js:174,175,293` 是第四个，而且它连类名都不声明，直接借用 `.v3-loading`（`privhub/plugins/privhub-files-explorer-v3/client/styles.js:70`）。

按我的用词，这属于**「隐藏的依赖」（hidden dependency）**，比"明显写错的代码"危险一个量级：明显的错误会在第一次运行就被抓住；隐藏的依赖会在第 N 次改动后才爆，而那时**没人记得它存在过**。

施工队的第一职责因此不是写代码快，而是：**让"哪里连着哪里"变成可查询的事实，而不是需要记忆的东西。**

第二该防的：**把"无打包链、改完刷新即生效"这个特性，当成技术欠债去还。** 它是这个项目最贵的资产之一（理由见第 7 节），而工程团队的肌肉记忆天然会想给它加构建步骤。施工队里必须有人负责说不。

## 3. 编制表

> **先说清楚这份编制的形状**：本项目的施工是**单人 + AI**，所以下表里的"岗位"是**要 `agent_create` 出来的常驻智能体**，不是招人。每个岗位都写清了**它不许干什么**——按我的框架，**一个岗位的价值一半在职责，一半在禁令**。
>
> **能力包 key 只能从这 14 个里选**：`files` / `web` / `shell` / `jobs` / `skills` / `instructions` / `ask` / `todo` / `present` / `goals` / `planning` / `compaction` / `delegation` / `orchestration`（需先开 `delegation`）/ `forge`
>
> **skill 挂载两法的代价（每位岗位都要选一个）**：
> - **法①（装到全局）**：写进 `C:\Users\Administrator\.dsh\skills\<名>\SKILL.md`。**代价：该路径在工作区之外，沙箱默认不许写，需要主子每次授权**；好处是该 skill 对**所有**会话可见。
> - **法②（工作区内直读）**：在 `AGENT.md` 里写一句"开工前先读 `docs/experts/john-ousterhout-perspective/SKILL.md`"。**代价：多花一次读文件的开销，且要靠纪律（智能体可能忘）**；好处是**零授权成本**，且 skill 与代码同仓、同版本、可被 `CHANGELOG.md` 一起追溯。
> - **我的建议**：本项目**一律用法②**。理由是硬约束第 2 条的同一逻辑——**随时可改、改完即生效**。把 skill 锁在工作区外，等于给"改 skill"加了一道构建步骤。

### 岗位 A ｜ 施工调度（对外名：施工队长）

| 字段 | 内容 |

| **准出条件 + 谁来验** | ① 派工单上的每一条准出条件都有**当场可复现**的验证记录（命令 + 输出）② `CHANGELOG.md` 与 `package.json` 版本号一致 ③ **由主子本人**确认；主子不在场时由**岗位 E（外部验官）**顶，但**不许由它自己宣布通过** |
| **权限边界** | **不许改 `privhub/frontend/index.html`**；**不许改任何插件代码**；**不许在自己没看懂派工单的情况下派工**；**不许在主子确认前执行 git 提交/推送** |
| **交接契约** | 对岗位 B/C/D：一句话需求 + 本条车道的判定理由 + 准出条件清单（**必须是可复现的句子，不是"优化了""更好了"**）。对主子：`CHANGELOG.md` 段落 + 版本号 + 一句话风险说明 |

**为什么这个岗位值得设**：硬约束第 8 条（写 CHANGELOG + 递增版本号 + 人工确认后提交）**本来就是个人工流程**。单人项目最容易发生的不是"忘了做"，是"做了但没记账，三周后不知道现在是第几版"。这个岗位把记账变成自动化，代价只有一份 `AGENT.md`。

## 4. 工序

> 判据只有一条：**谁的产出是别人的输入，谁就必须排在前面。** 与工作量无关。

### 4.1 依赖顺序（不可颠倒）

```
① 契约盘点（岗位 B）
      ↓ 产出 docs/施工契约.md，且必须包含那 14 条 view↔slot 的真实对照
② 静默耦合变成会报错的（岗位 B 出题 / 岗位 C 实施 / 岗位 D 审计）
      ↓ 产出 privhub/tests/ 下的断言（照 tests/personal-ui.mjs:311-321 的现成范式）
③ 解耦合（岗位 C，一次只解一个名字）
      ↓
④ 改渲染层 / 加视图入口（岗位 C）
      ↓
⑤ 外部验官逐条盘问（岗位 E）
      ↓
⑥ 记账与提交（岗位 A，等主子确认）
```

**①→②这一步是我与 Shape Up 的方案分歧所在。** 它把"把 `.v3-content` 改名后三个插件仍工作"当准出条件（`05-shape-up.md:220`）。这个判据**方向对，但顺序上漏了一步**：改名是"制造故障"，而故障是静默的——**改完之后，三个插件不工作，界面不会告诉你。**

所以②必须先于③：**先写一条会失败的断言**（`.v3-content` 类名存在 / 那三个插件仍能拿到内容锚点），**再动渲染层**。这样"静默失效"就变成了"红色测试"。

**这一步的成本约等于零**（`privhub/tests/personal-ui.mjs:311-321` 已经在对 `.v3-content-head` 做同样的事），**而它把整个施工过程里最危险的那一类故障，从"事后靠人回忆"变成"事前靠机器报警"。** 按我的复杂度尺度，这是本次投入产出比最高的一步——**比本体改动还高**。

### 4.2 可以并行的

| 可并行 | 为什么安全 |
|---|---|
| 岗位 D 的越界审计 与 岗位 E 的准出判定 | 一个看静态 diff，一个看运行行为，**互不依赖** |
| 契约盘点（B）与"未越界基线"扫描（D） | D 只需要"当下有没有跨插件类名引用"，不依赖 B 的产出 |
| 两个**互不相干**的插件各自的改动（两个各自独立的 C 实例） | **前提**：两者都不改 `frontend/index.html`、不共享 slot。**一旦共享（例如都注册 `office-editor`）→ 立刻串行** |

### 4.3 绝不并行的（这一节比上一节重要）

| 绝不并行 | 原因 |
|---|---|
| **改 `frontend/index.html` 与改 explorer-v3 渲染层** | 后者一动，四个插件静默失效；前者一动，整个界面都可能白屏。**两个"全局爆炸半径"的操作同时进行，出问题时无法归因** |
| **改契约（B）与按旧契约施工（C）** | C 会照着已经不成立的表干活，产出"看起来合规、实际对不上"的代码。**必须等 B 宣布契约冻结** |
| **`office-editor` 那 8 个注册者的任何两个同时改** | 它们共用同一个界面位置，且**规则从没被写下来**（Cooper `04:317-319`）。同时改 → 谁该在什么时候出现会变成猜测 |
| **任何改动 与 `CHANGELOG.md` 的提交** | 硬约束第 8 条要求人工确认后提交。**先提交再确认 = 把"可回退"变成了"已污染"** |
| **多个 C 同时改同一个插件目录** | 单人项目最常见的事故：两个 AI 会话各自以为自己在改"当前版本" |

### 4.4 一次改动的完整走法（给非程序员看的版本）

1. 主子说一句要改什么 → **A** 判断它是不是"能用一句话说清改完之后能多做哪件事"。说不清 → **停**。
2. **B** 先说清楚这次要碰哪条契约、会影响哪几个插件（**逐个点名**，不是"可能影响若干"）。
3. **C** 改一个插件，一次只改一个。
4. **D** 只看 diff，报越界（有 file:line 才算数）。
5. **E** 用全新会话，只拿准出条件去验；缺手段就写"无法判定"。
6. **A** 写 `CHANGELOG.md` + 递增版本号，**等主子点头**，才提交推送。

**任何一步的产出对不上，都退回上一步，不许"先往下走、回头补"。** —— 单人项目里"回头补"= 永远不补。

## 5. 两档编制

### 5.1 最少可行编制：**只能设 1 个智能体时，选「岗位 B 接口契约守门人」**

**为什么是 B，不是别人**：

- **只有 B 的产出是"别人的输入"**。A 的派工单可以临时口述；C 的活儿主子自己也能盯；D 的审计可以退化成一条 `grep` 命令；E 的判定可以退化成主子自己点一遍。
- **但"哪个 `view` 对应哪个 `slot`、`window.PrivHub` 哪些是公开面"这件事，没有任何替代品。** 它现在只存在于 `index.html:748-764` 那 17 行 if-else 里，和每个改代码的人（或 AI 会话）的短期记忆里。**这正是本项目反复出事的那一处**——"修订顶栏时已因此连撞两次"（`_交底…md:131`）。
- 而且 B 的职责**天然只读+只写一份 md**，风险最低。一个智能体做不完所有事，但**它能做完"把连线画出来"这件事**，而这件事是所有其他事的前提。

**只设 1 个时的具体配置**：
- `agent_create(id: "privhub-contract-keeper", capabilities: ["files","instructions","todo","ask","present","planning","skills"])`
- skill 用法②（`AGENT.md` 里写明"开工前先读 `docs/experts/john-ousterhout-perspective/SKILL.md`"）——**一次多余的读文件，换零授权成本**
- **第一件事**：读全部 31 个活跃 `client/manifest.json` + `frontend/index.html:740-764,1027-1085` + `privhub-shell/client/index.js:68-122`，产出一份 `docs/施工契约.md`。
- **它的第一条准出**：`docs/施工契约.md` 里的 `view`↔`slot` 表，与我第 2.2 节那张表**逐行一致**。不一致 → 说明它没真读 manifest，重做。

### 5.2 理想编制：**5 个岗位**（A 施工队长 / B 接口管家 / C 改插件的人 / D 查越界的人 / E 挑刺的人）

**为什么恰好是 5 个，不是 8 个**：多出来的每一个岗位都要**自己与自己交接**（单人项目，没有"部门"）。按我的框架，**每多一层交接就多一层依赖，而依赖是复杂度的根源**。5 个岗位里，A 和 E 是**流程岗**（不产设计意见），B 是**唯一的设计决策岗**，C 是**唯一有写权限的岗**，D 是**唯一的审计岗**。

**关键的不对称**：**C（干活的人）只有 1 个，且不设"第二个 C"。** 理由是单人的注意力无法并行——多开一个 C，收益是"快一点"，代价是"两个会话可能改同一个插件的当前版本"。

**第一阶段建议只开 3 个**（B + C + E），先把"契约→改动→独立验证"这条最小闭环跑通。A 的记账在闭环稳定后再自动化（记账本身是可以用一次性的提示词完成的）。**D 的职责可以先退化成一条 `grep` 命令**，等跨插件引用真的开始增长时再立岗。

| D 查越界的人 | `privhub-coupling-auditor` | `files,instructions,todo,ask,present,shell` | 法②（只用部分章节） | 第二期（先用手动 grep 顶） |

## 6. 我建议不要设立的岗位

### 6.1 ❌ 视觉/设计施工岗（改配色、间距、圆角、动效的那一类）

**理由（按我的尺度，不是按"没必要"）**：
- 我**不谈前端与 UI**——这是我的诚实边界。我判不了"这个颜色对不对"。
- 更实际的理由：这个项目**没有设计师、没有令牌层**（`_交底…md:69-81`：10 个自定义属性、**间距与字号刻度完全没有**、45 个互不相同的 px 值）。要立"视觉岗"，等于**从零建层**，而且要触及 32 个插件前端。这是一次**极高成本的横向改动**，收益却取决于"有没有人看界面"——而全场最大盲区恰恰是**没人看过界面**（`00-汇总…md:96-106`）。
- **该做的是先补一次观察，不是先立岗。** 用 `02-steve-krug.md` 附的 3 人测试脚本，或主子自己操作 5 分钟的录像。**在没有观察之前立视觉岗，等于给一个没量过的尺寸定公差。**

### 6.2 ❌ 项目管理 / 排期 / 看板岗

单人 + 一个主子的项目，**排期的信息量不足以支撑一个岗位**。§4 那六步已经够了。多一个"项目经理"只会多一次交接。

### 6.3 ❌ 专职文档撰写岗

写文档的活儿全部已经落在具体岗位里（B 的 `docs/施工契约.md`、A 的 `CHANGELOG.md`、D 的越界报告）。**单独设一个写文档的人，会产生"文档与代码谁先谁后"的新问题**——而正确做法是**谁的改动谁写它那一段**。

### 6.4 ❌ 键盘快捷键 / 虚拟滚动 / 标签页上限的专职实施岗

不是"不值得做"，是**这三件事各自都不需要专属岗位**——它们是单个插件的普通改动（`F2`/`Delete` 那半更要走数据车道，见 `05-shape-up.md:273-275`）。立"快捷键岗"会凭空造出一个**跨所有插件的横向权限**，与"插件自治"直接冲突。

### 6.5 ❌ 插槽合并 / 插槽体系统一岗

**这一条我很坚决**。Cooper 实测：**41 次注册落在 31 个插槽名上，其中 28 个只服务 1 个插件**（`04-alan-cooper.md:50-53,422-423`）。

一个"插槽体系统一岗"会自然地想去合并这 28 个 1:1 插槽、给插槽加契约版本号、建声明式注册表。**按我的复杂度尺度，这是典型的"为抽象而抽象"**：
- **它解决的是谁的问题？** 用户看不到插槽（名字只在 `manifest.json` 里）。
- **它要付什么代价？** 重写 32 个插件的前端契约。
- **它产生的依赖呢？** 插槽语义、版本协商、兼容规则——**净增**。

**判据**：一项结构改动的价值，等于它**消除的依赖与不可见性**减去它**新增的**。合并 1:1 插槽，两边都算完是**负数**。

### 7.2 「接口优于实现」在"无打包链 + 插件自治"下怎么落地，哪里必须让步

这是本方案的核心，我分四段答。

#### （a）我认为可以落地到位的：`openBarItem` 白名单

**先说清楚我不同意 Shape Up 砍掉的那半。** `05-shape-up.md:207` 收窄为"只做视图分发表"，并**砍掉"插件声明式路由注册表"**。我尊重它的成本判断，但**砍掉这半就等于放弃了这条改造的全部价值**——因为**纯查表仍然要求"新增视图必须回来改中心文件"**，只是从写 if-else 变成写表项。**问题的本体没动。**

**我的设计：一个深模块，藏在骨架里。**

```
模块名（对插件而言）：「视图口」
放在哪：   privhub/frontend/index.html 内，一个 IIFE，作用域内私有
                （不需要新文件、不需要打包、不需要 ES 模块）
暴露面（就这 3 件事，插件只许知道这 3 件）：
    ① manifest.barItems[].view          —— 一个字符串，插件的视图名
    ② 我注册了同名 slot                 —— 约定：slot 名 = view 名（10 个视图已符合）
    ③ 不一致时，我在 manifest 里多写一行 —— "viewSlot": "trash-view"
不暴露（内部实现，任何插件不得引用）：
    · 内部函数 loadBarItems / go / bottomGroups / 状态表
    · 谁在什么顺序上被渲染、toggle 怎么算、Escape 怎么处理
    · 「底部管理组」这个分组概念本身
```

**为什么这叫深模块**：插件只需要说"我叫 `kg`"，剩下全部由它处理。**接口面 = 1 个字符串 + 1 条命名约定**；实现面 = 视图→slot 解析、四个特殊路由（`trash`/`search`/`favorites`/`files` 的专属跳转）、管理组分组、toggle 语义、Escape 语义、以及**兜底**（找不到对应 slot 时不白屏）。

**"调用方需要知道多少"的准确答案**：**一个字符串。** 今天它需要知道的东西是——自己的 view 名、那个 view 必须被写进 `index.html:759-761` 的 if-else 列表里、以及必须再在 `:1037-1045` 找一个坑把它插进去。**从"两处中心文件的坑位"降到"一个字符串"。**

**证据支撑（这不是为假想的未来设计）**：`view` 与 `slot` 同名的情况**已经有 10 个**（§2.2）。命名约定不是在发明抽象，是在**把一个已经存在 10 次的规律写下来**。

**必须承认的三处让步**：
1. **4 个特殊路由必须留在骨架里**（`trash`/`search`/`favorites` 有专属函数 `nav.openTrash()` 等；`files` 要判断"有没有选项目"；`admin` 是 `noToggle` 的）。这 4 个**不是枚举，是语义**——把它们也声明化，等于让插件去实现"回落到欢迎页"这种骨架知识。**这是我主动接受的浅化：我留下 5 条分支，换掉 12 遍历举。**
2. **"声明式"只能落在 manifest 里，不能落在运行时的注册 API 里。** 因为插件模块是从 URL `import()` 来的（`index.html:838`），**骨架无法在 import 之前知道插件想注册什么 view**。想把注册放到运行时，就得让插件先执行一次——那会引入启动时序依赖，那是**更贵的依赖**。
3. **这条改造的"准出"必须是 diff 为空，不是"能跑"。** 能跑是弱判据（今天也能跑）。**唯一强的判据**是：在某个 manifest 里加一个 `barItems.view`，**`privhub/frontend/index.html` 一个字节都不改，界面就多了一个入口。**

#### （b）我认为可以落地到位的：把"静默失效"变成"会报错"

在 §4.1 第②步。**这是本方案里唯一一条"零成本、高收益"的动作**，而且范式现成（`privhub/tests/personal-ui.mjs:311-321` 已经在做同类断言）。

**断言内容（三条，都可当场跑）**：
1. explorer-v3 的 content 元素类名（`.v3-content`）**存在**；
2. `grep` 全仓 `querySelector('.v3-` 的跨插件命中**逐条在案**；
3. `privhub-shell` / `air-console` / `files-comments` 这三个「借用方」**各自能否在不依赖 explorer-v3 类名的前提下工作**。

**这是"接口优于实现"最便宜的落地形式**：不要求任何一方改代码，只要求**依赖关系被显式写下来**。

#### （c）我认为必须让步的：`.v3-content` 的位置

**先说清楚`.v3-content`是什么。** 它是 `explorer-v3/client/panel.js:402` 内部的一个 div 类名。它不写在任何 manifest 里，不在契约表里，`styles.js` 也只当它是自己的私有样式目标（`styles.js:26,28,52-54`）。

**它是一段"实现"，被四个插件当成"接口"用。** 这就是《软件设计哲学》里"信息泄漏"的教科书案例：**一个模块的内部选择穿透了边界，别处的代码知道了它不该知道的东西。**

**两种修法，我倾向后者**：

| 修法 | 做法 | 我的判断 |
|---|---|---|
| **甲：把它升格成正式接口** | 在 explorer-v3 里**显式声明**"content 区是一个对外承诺的挂载点"，类名冻结、写进 `docs/施工契约.md`、加测试锁住 | **可行、成本最低。但它是"认输式接口"**——边界确实划清了，代价是 explorer-v3 被判了"必须永远有这个 div"的无期徒刑 |
| **乙：骨架提供一个"内容挂载点插槽"** | 骨架在 panel 位置渲染一个**具名容器**，4 个插件注册到它；容器归**骨架**所有，explorer-v3 只往里面放东西 | **这是我想要的形状，但它在当前架构下做不到——这就是必须让步的地方** |

**为什么乙做不到（这一步必须说清，否则就是纸上谈兵）**：

当前插槽系统是**扁平的、骨架级的**：`manifest.slots` 声明的是"骨架某个位置我放一个组件"（`index.html:839-843` 把 slot 名映射成组件数组）。**它没有"插件内部再开一个挂载点"的能力**——`.v3-content` 是 explorer-v3 渲染出来的 div，骨架**在 explorer-v3 渲染之前不知道它在哪**。

要做乙，就得引入一套**运行时挂载点机制**（类似"渲染阶段，插件拿到一个容器 ref 后注册"）。那要新增：挂载点生命周期、渲染时序、CSS 归属规则、以及"卸载时谁清理"。

**按我的复杂度尺度算这笔账**：
- **消除的**：4 处跨插件 DOM 耦合（其中 2 处还在操作别人的 DOM：`office2:53` 隐藏元素、`edit-md:274` 删除节点）。
- **新增的**：一套挂载点运行时 + 32 个插件里"我要不要用挂载点"的新判断 + 一套新的时序 bug 面。
- **结论：账算不平。** 因为有一个更便宜的中间态存在——

#### （d）**我推荐的中间态：契约式挂载点（不引入新机制）**

**不新建机制。只用两样已经存在的东西**：`bus`（`index.html:376`，插件已在用）和 `slot`（骨架已有）。

```
契约（写进 docs/施工契约.md）：

  名称：内容区挂载点
  提供方：privhub-files-explorer-v3（因为它拥有那个位置）
  使用方：office2 / edit-md / comments / shell-agent-console
  接口：bus.emit('v3:content-ready', { mount(el) {…}, unmount() {…}, state })
        —— 一个对象，两个方法。使用方只调这两个，不碰任何类名
  归属：使用方"借"这个位置，提供方保留所有权与回收权
  边界：使用方不许保留 el 的引用去改 explorer-v3 的其他元素
```

**我推荐它的理由（三条，按重要性）**：
1. **它把"谁拥有什么"写下来了。** 今天的耦合问题是"大家都以为 `.v3-content` 是自己的"——`office2:20-21` 甚至还在往它上面加 `:has()` 选择器改它的布局。**契约的价值一半在于把所有权说清。**
2. **它是"提供方主动交出接口"，而不是"使用方伸手去抓"。** 方向反过来了，这在 API 设计上是有意义的差别：提供方知道自己的实现会变，所以在交出时**主动承诺一个稳定的面**。
3. **零新机制。** `bus.emit` / `bus.on` 是现成的（`office2:69`、`edit-md:247,276` 都已在用）。**这满足"无打包链"下的所有约束。**

**这一步还要补一条纪律**（否则契约会被绕过）：在 `docs/施工契约.md` 里加一行明示——**"`.v3-content` / `.v3-md` / `.v3-text` / `.v3-loading` 是 explorer-v3 的内部实现名，任何其它插件引用它们视为越界（约束第 5 条）"**，并由岗位 D 在每次 diff 上检。**当代码里能一眼看出"这行是越界"时，约束才真正生效**——今天的 `.v3-` 前缀没有任何语义，谁也看不出它是越界。

**这就是我在第 5 条硬约束下能给出的最诚实的答案**：**不是"加一层抽象"，而是"给已有的类名一个法律地位"。** 它不漂亮，但它**消除的依赖多于它新增的**——这在我的尺度上，是唯一算得平的方案。

**给 #15 的补充（这条是"无打包链"下我唯一想说的技术判断）**：

**共享模块 ≠ 打包链。** 依据是 `index.html:838` 的 `await import(p.entry)`——插件前端**本来就是按 URL 直载的 ES 模块**。所以放一份 `frontend/shared/markdown.js`（或 `privhub-core` 里挂一条静态路由），插件用 `import('/shared/markdown.js')` 即可，**改完刷新即生效，304 缓存照旧，不需要任何构建步骤**。

**但我不为它背书**，理由是：它把一个"插件自治"的项目变成了"有一个必须永远向后兼容的公共库"，而**公共库的兼容成本是这个项目里唯一会随时间单调增长的东西**。E4 的 XSS 事故说明重复有代价；但它也说明**在无打包链的项目里，"共享"要付出一种很特殊的代价——共享的东西无法回滚**（一旦某插件依赖它，改它就等于改所有插件）。**这是 Shape Up 或主子该拍的板，不是我的。**

### 7.4 归纳：三句话

1. **值得做的结构改动，全部集中在"让连线可见"** —— 契约表（#4）、会报错的测试（#1）、白名单变数据表（#2/#3/#8）。
2. **不值得做的，全部集中在"让结构变整齐"** —— 合并 1:1 插槽（#13）、插槽版本号（#14）、收敛 `window.PrivHub`（#12/7）、运行时挂载点（#17）。**它们的共同特征是：消除的是"看着别扭"，不是"改起来会出事"。**
3. **中间的灰色地带（#6/#15/#16）我不替主子拍板**——尤其 #16（令牌层），**它是本方案里我唯一明确拒绝用"复杂度"当理由的项目**：视觉层的收益不该用我的尺子量。

### 7.5 我判不了的最大一块

**「我从没看过这个界面跑起来的样子。」**

这不是客套。它具体废掉了我下面这些判断的能力：

| 我本该能判 | 实际做不到 |
|---|---|
| 加了视图分发表之后，图标栏是不是真的更好用了 | 不知道；它可能让入口顺序变得更没有依据（现在至少还是扫描顺序，改完可能变成随机的） |
| 那 4 处跨插件耦合，改完之后**用户能不能感知到差别** | **完全不知道。** 它今天"能用"，所以从使用视角，这条改动的收益是 **0**——它的全部价值在"以后改渲染层时不会静默失效" |
| `.v3-content` 契约化，会不会让 explorer-v3 的演进被冻住 | 判不了。**乙案（骨架挂载点）在纸面上更好，但我没有实际跑过，不知道它会不会引入新的时序问题** |
| 施工队的 5 个岗位，主子管不管得过来 | 判不了。**单人项目的真实瓶颈是注意力，而这个数只有主子知道** |

**但有一条我能判，而且我认为它比上面所有判断都重要**：

> **在没有人看过界面的情况下，施工队的第一批活儿不该是"改结构"，而该是"让结构可查"。**
>
> 因为"让结构可查"这件事，**它的收益不依赖任何我没看到的观察**：不管界面好不好用，"改一次骨架连撞两次"都是事实，"第 9 个人不知道该不该注册 `office-editor`"都是事实。**它是我在信息不全的条件下唯一敢背书的改动。**

### 7.6 我这把视角该不该当"总工"——认真回答

**先给结论：不该当总工。该当"结构审查官"。**

**理由一：我的框架有明确的、会在这里害人的偏向。**

《软件设计哲学》的全部论证，建立在**大团队、长期维护**的前提上。我书里反复举的例子是"六个月后另一个人来改这段代码"。**但本项目是单人 + AI 生成 + 无团队 + 没有设计师**——这里恰恰**没有"另一个人"**。我的整套度量（"别人能不能读懂""信息泄漏给下一个改动者"）要打的靶子，在这个项目里**大部分不存在**。

更具体地说，我有三处**已知会冲突**的主张：

| 我的主张 | 在本项目的冲突 |
|---|---|
| **"设计两次"（Design It Twice）** | 本项目是**改完刷新即生效**的无打包链。我的方法论假设"设计的代价可以用测试和评审摊薄"，而这里摊薄的机制**一个都没有**（无自动测试、无评审、无构建期校验）。照搬我这条，会变成"反复讨论、不落地" |
| **注释描述设计意图** | 这条假设**读者是人**。当代码由 AI 生成、下一个改动者也是 AI 时，"注释写给谁看"这个问题**整个变了**。我对此**没有立场**（见 §7.7） |
| **"接口优于实现"、"不同层不同抽象"** | 在**无打包链**下，抽象层不能靠 import 边界强制，只能靠**纪律和命名**。这削弱了我主张的力度——**我的主张在这里会打折扣，我必须自己说出来** |

**理由二：我的盲区正好覆盖了这个项目最大的那一块。**

**我不谈前端与 UI。** 而本项目的题面（`_交底…md:153`）**就是前端交互 + 功能**。五份顾问方案里，真正在看"用户找得到吗"的是 Krug，在看"出错怎么回来"的是 Norman。**我不该去占他们的位置。**

**理由三：我判不了"做不做"，而总工必须判。**

我只会说"这个改动净值是正是负"。**但净值是正的改动，也可能不该做**——因为它不解决主子关心的任何问题。这不是我的决定，是主子的。

**那我该当什么**：

| 该我拍板的 | 不该我拍板的 |
|---|---|
| **接口面的形状**（`view`↔`slot` 怎么声明、`bus` 契约怎么设计、模块藏在哪、暴露几个名字） | **做什么**（下一批做哪条） |
| **"这次改动让哪几个模块产生了新依赖"**——这是纯结构判断，我有资格 | **好不好用**（要 Krug / Norman） |
| **"这件事值不值得做"的复杂度那一半** | **视觉**（要 Refactoring UI） |
| **"这是一个隐藏依赖还是一个显式契约"** | **排期与胃口**（要 Shape Up） |

**一句话**：**我可以是施工队里的「结构审查官」或「接口管家」（就是 §3 的岗位 B），但不能是「总工」。**

**最后一条（这条是给主子的）**：如果主子只是想找一个"能帮我把架构想清楚、并在每次改动时替我把住接口这条线"的角色——**那正是岗位 B，也正是我这把视角能诚实交付的东西**。如果要找一个"统筹全部决策"的总工，**那个位置该由主子自己坐**——因为本项目里唯一掌握完整上下文（界面长什么样、用了多久、哪疼）的人，只有主子。**我们五个顾问都没看过这个界面。这不是谦辞，是事实。**

### 7.7 我对自己这把视角的三条诚实边界（用在本项目）

1. **我偏"大团队长期维护"，与本项目的"无构建链、改完刷新即生效"有真实冲突。** 具体表现：我不会主动建议加构建步骤，但**我也不会主动反对**——因为我的框架里没有"局域网下多几次请求无感""二访全 304"这类变量（`_交底…md:28`）。**这道权衡必须由主子拍板，我给不了倾向。** 硬约束第 2 条把"无打包链"定为特性，我照办，并据此**否决了 #17（运行时挂载点）**——但请注意，我否决它的真实理由是"账算不平"（§7.2c），**不是"我尊重约束"**。
2. **我不谈前端与 UI。** 本方案里凡涉及"用户能不能找到""这样标注清不清楚"的判断，我一律推给 Krug / Norman / Cooper。**§6.1 建议不设立视觉岗，理由正是"我判不了"，不是"它不重要"。**
3. **我对"注释"的主张，在 AI 生成代码的场景下适用性存疑。** 我书里的论证前提是"下一个读者是人，且他不具备写这段代码时的上下文"。本项目里**代码由 AI 生成、改动也由 AI 执行**，「下一个读者」很可能是另一个没有本次上下文的 AI 会话。**注释该写什么、写给谁，我在这里没有可靠答案。** 我在本方案里刻意回避了"要求施工队多写注释"这类建议——**不是因为不重要，是因为我不知道在这个前提下该怎么要求。**

### 7.7b ⚠️ 我这条视角最该被打掉的地方（这条我必须主动写出来）

**主子若只看我一个人的方案，最该知道的是这件事：我的核心概念"深模块"，被人在技术上完整地反驳过。**

| 项 | 内容 |
|---|---|
| **批评者** | **Jimmy Koppel**（Path-Sensitive 博客，2018-10-29 长篇书评） |
| **指控** | 我主张的"接口应短于实现"**无法被检验**；"**Beautiful, obvious, and impossible to disagree with. Unfortunately, it's also objectively wrong.**" |
| **他的定性** | "To Ousterhout, the interface is just a comment and some discussion […] **Intuition and experience are the sole arbiters here.**" |
| **三个反例** | **栈**：实现 30 tokens vs 接口 54 tokens —— 按我的标准"我们不该用栈"。**POSIX `open`**：我在书里称 Unix I/O 是 "a beautiful example of a deep interface"，但 SibylFS 为 `open` 写的精确规范超 3000 词，而实现 "a mere 40 lines"。**崩溃恢复的 `write`**：规格 70 行 vs 实现 29 行。 |
| **他的原则性反驳** | "there are times when it's **actually desirable** to have a specification more complicated than the code"——**规格有时理应比实现长**，因为它要抽象、要弱化对模块的假设以便替换。 |
| **我的回应** | "You're just talking about the specification, rather than **how easy they are to use to write code that works**." —— **他没有买账。** |
| **结论** | **双方未达成一致。这是唯一一条被完整论证过、且我本人参与讨论后仍未达成一致的批评。** |

**⇒ 这条对我的方案意味着什么（我必须自己说清）**：

**我在 §7.2 里推荐的那套"接口面越窄越好"，落在一个具体项目上时，会正好撞上 Koppel 指出的那个缺口——"窄"没有客观度量。**

具体到本项目的风险：
- 我说"插件只需要知道**一个字符串**"（§7.2a）。**这个说法听起来漂亮，但它是在比较"接口的词数"，而 Koppel 的反例恰恰证明：词数少 ≠ 接口浅。**
- 一个插件作者为了用对那个 `view` 名，实际需要知道的事情可能包括：它必须与某个 slot 同名（或另写一行）、同一个 view 不能有两个提供者、管理组的 view 会被过滤掉、点同一个视图图标会 toggle 回 `files`。**这些"必须知道的事"加起来，远多于一个字符串。**
- **⇒ 所以我在 §7.2a 里那句"从两处中心文件的坑位降到只有一个字符串"是乐观的，不是准确的。** 准确的说法应该是：**"调用方需要知道的事情从『分布在一个 1130 行文件的两处』变成了『集中在一张表里 + 若干条约定』"——总量降了，但没有降到"一个字符串"。**

**⇒ 这条批评对本施工队的实操含义（这是本节最有用的一段）**：

1. **不要用"这个接口够不够深"当验收标准。** 它不可检验，用它验收会变成"谁声音大按谁说的算"。
2. **改用可检验的替代判据**（这些是 Koppel 那条批评逼出来的，不是原书里的）：
   - **"改完之后，`frontend/index.html` 的 git 差异是不是空？"** —— 可当场跑 `git diff --stat`，**是二值的，不靠判断。**
   - **"调用方需要知道的事情，能不能写成一份清单，并且这份清单有确定的条数？"** —— **条数可数。**
   - **"把那个内部类名改掉，有几个插件会坏？有多少个会在改的时候报错？"** —— **可实测。**
3. **因此 §3 岗位 B 的准出条件，我坚持用"diff 为空"而不是"接口够深"。** 这不是我随口选的——**是因为按我自己的判据会给不出可检验的答案，我必须换一个能给出来的。**
4. **⇒ 反过来，我对 Koppel 也有一句反驳，而且我认为它成立**（同时也是对我自己的限制）：**他为"规格可以比代码复杂"给出的三个反例，全部是"规格本身就是要被很多人实现/替换的标准"**（栈公理、POSIX、崩溃恢复 write）。**在一个只有一个人、一份实现、没有外部实现者的项目里，"为了可替换而把规格写复杂"这个理由不成立。** —— **所以：Koppel 的批评在"你有一个公共标准接口"时成立；在本项目这种"只有一份实现"的场景下，它的适用性要打折扣。** 我把两面都摆出来，**判断权交回主子。**
