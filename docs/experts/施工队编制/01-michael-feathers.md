## 1. 一句话判断（施工队最该防什么）

**施工队最该防的不是「把代码改坏」，是「改完之后没人能说出到底变了什么」——因为在这个项目里，这件事没有探测手段：现有回归全部打在 HTTP 层，而所有要动的地方（视图分发、四插件耦合、静默淘汰）都活在浏览器里；`tests/` 里没有任何一条断言会因为你改坏了那四个插件而变红。**

依据（三条，全部亲自打开确认）：

1. **回归只验「接线」，不验「界面跑起来」**：首屏链路的断言全部是 HTTP 状态码、清单条数、slot 是否齐全（`privhub/tests/first-screen.mjs`，逐环断言）。这等于「电线通不通」，不等于「灯亮不亮」。**【实体】**
2. **四个插件已经处在「静默失效」状态边缘**：`files-office2`、`files-edit-md`、`files-comments`、`shell-agent-console` 都依赖 `explorer-v3` 注入的 `.v3-*` 内部类名。**这不是我推断的——我逐处打开了文件**（见 §2.2 之 E4）。其中前三个是 `querySelector`，第四个更脆弱：它只是复用了 `.v3-loading` 这个**样式类**，而类定义在 `explorer-v3/client/styles.js:70`。**【实体】**
3. **现有改动纪律的最后一步完全没有机械化**：`CHANGELOG.md` + 版本号递增全靠人的自觉，`tests/` 里没有任何一条检查它们一致（`docs/experts/改进方案/02-martin-fowler.md` 已实测 grep 为 0 命中；我未复跑该 grep，**标 [二手转引]**）。

**所以我这一把视角的结论很直接**：本项目**不缺写代码的手**，缺的是**一个能在改动之前把「现在实际是怎么运行的」钉住的岗位**。Feathers 一辈子只干这一件事：

> 「**When a system goes into production, in a way, it becomes its own specification.** We need to know when we are changing existing behavior regardless of whether we think it's right or not.」
> —— [Characterization Testing, 2016-08-08](https://michaelfeathers.silvrback.com/characterization-testing) **[一手]**

第二句（同样重要）：**这个项目最缺的能力不是「改」，是「识别哪里能下手」。** Feathers 的原话是：

> 「The seam view of software helps us see the **opportunities that are already in the code base**.」
> —— WELC 第 4 章，[InformIT 官方免费样章](https://www.informit.com/articles/article.aspx?p=359417&seqNum=2) **[一手]**

**第三句，是说给主子听的**：按这把视角，本轮施工的**第一个动作不应该是改任何一行代码**，而是拿到一份「**接缝清单 + 现状钉子清单**」。原因不是保守——是因为这个项目的「改完怎么知道好了」这一环现在**根本不存在**，先补它，成本最低、回报最高。

## 3. 编制表

> **先说清三件事，否则下表读不下来。**
>
> **第一，本项目所有角色都是 AI。** 所以每个岗位的「准出条件」栏里，**绝不许写「由本岗位自验」**。能用的验法只有三种：
> ① **机器验**——跑 `tests/`，可复现、可回读（F10 保证了它安全）；
> ② **不带本次上下文的另一个 AI 会话验**——对抗性复核，只保证「找得到反例」，不保证「找得对」；
> ③ **人眼验**——主子本人看界面 / 拍板。
> 每个岗位下面我都标了**它只能靠哪一种**。
>
> **第二，按 Feathers 的视角，岗位不能按「能力」分，只能按「能不能独立验证」分。** 他的原话是「**必须有人在责任席上**」——在这个项目里，责任席就是「谁敢说这条改变了什么，并且能证明」。
>
> **第三，下表只列我建议设的岗位（5 个）。** 我建议**不要设**的岗位在 §6。

| **准入条件** | ①②③④四份产出**全部在手**（缺一份不接）。 |
| **准出条件 + 谁来验** | ① 反例清单里**每条都挂了 `文件:行号`**（**机器验**：主子随机抽 2 条，打开核对）；<br>② 「找不到反例」那一节**非空**（**人眼验**）；<br>③ **严重度为「阻断」的条目 = 0**，或者**已被修理工按新施工单处理**（**人眼验，由主子拍板**）。 |
| **权限边界** | ✅ 可读任何文件；可跑任何只读命令；**可跑全量回归**（独立复现是它的核心武器）<br>❌ **不得修改任何文件**（它只产出报告）<br>❌ 不得因为「我知道更好的做法」而提出重构建议 —— **它只负责找反例，不负责给方案**（给了方案，它就从审核员变成了第二个修理工） |
| **交接契约** | → 交给主子：反例清单（**由主子决定接不接**）<br>→ 若严重度=阻断：退回**③**并开新施工单；若涉及钉子本身写错：退回**②**<br>**明确不交接给**：①和④（它们不因审核结果改动自己的产出，只做记录） |

### 3.1 为什么我记得这么细：这一张表里最要紧的一栏

**是「它是『正确行为』还是『已知怪癖』」这一栏。**

Feathers 的特征测试有一个反直觉的性质，必须写进每一个岗位的脑子里：

> 「The purpose of characterization testing is to document your system's actual behavior, **not check for the behavior you wish your system had**.」
> —— [Characterization Testing](https://michaelfeathers.silvrback.com/characterization-testing) **[一手]**

**用大白话说**：特征测试的作用是**给现状拍一张照片**，所以它**会把 bug 也一起拍进去**，并且**断言那个 bug 存在**。

这不是设计缺陷，是刻意的。因为「**先判断对错，会让你把『我不喜欢的行为』当成 bug 删掉，而那个行为可能正是别人依赖的**」。他讲过一个开场事故：他年轻时被派去修一个 bug，修完用户来投诉 —— **他们依赖的正是他删掉的那个行为。他们不认为那是 bug，他们认为那是功能。**

**所以在 PrivHub 上，这一条会立刻变成一个真实的两难**：本项目已知的几处怪癖（标签超过 30 个静默淘汰、点开头的名字建得成但看不见、拖到设置页也能静默上传），**钉住它们就等于断言它们是对的**。

**本视角给的处置办法（写进岗位②的 AGENT.md）**：

| 情况 | 怎么做 |
|---|---|
| 这个行为是**有意的** | 钉住它，并在钉子清单里标注「有意行为，依据：___」 |
| 这个行为是**已知缺陷但本轮不修** | **照样钉住它**（保证改动不会顺手改坏它），但钉子清单里必须标「**已知怪癖，本轮不修**」 |
| 这个行为是**已知缺陷且本轮就要修** | **分两次**：先钉住现状（绿）→ 再改 → 钉子变红 → **明确地更新这颗钉子为新行为**。**「更新钉子」这个动作必须是一次独立的、被记录的改动，不许混在修 bug 的提交里** |

**第三行是这份方案与普通「写测试」最大的区别**：普通做法是「写一个断言正确的测试，然后修代码让它通过」——那样你**永远不知道你改坏了什么**。这里是「先拍照片，再改，再显影对比」。

## 4. 工序

### 4.1 谁先谁后（一次施工的完整链）

```
【第 0 步 · 量基线】  岗位②跑一次全量回归，记下：几绿几红、耗时多少
                      ↓  （这一步没做，后面全部无效 —— 没有「改之前」）
【第 1 步 · 勘察】    岗位①出《接缝清单》+ 效果草图 + 收束点清单
                      ↓  ← 主子在这里拍板：本次改什么、不改什么
【第 2 步 · 钉现状】  岗位②在收束点上写特征测试，钉住「改之前」的行为
                      ↓  ← 闸门：钉子必须绿、且必须能证明会红
【第 3 步 · 下手】    岗位③按施工单做最小改动，跑全量回归
                      ↓  ← 闸门：钉子依然全绿 + 反向验证能复现
【第 4 步 · 记账】    岗位④写 CHANGELOG、改 version、同步说明文件
                      ↓  ← 到这里，主子才做「人工确认无误后提交推送」
【第 5 步 · 外审】    岗位⑤（按需）出反例清单
```

**这个顺序里有两处绝不可调换**：

- **第 2 步必须在第 3 步之前。** 这一条就是整份方案的核心。**「没有测试就重写 = 你现在有两个问题」**——他把这话说得很直白：
  > 「The thing with rewrites is that it's great if you have tests. If you have tests, you're really in a **golden space**. And if you don't, then… **you've got two problems**, right?」
  > —— Tech Lead Journal #195 **[一手]**
- **第 4 步必须在第 3 步之后。** 先写 CHANGELOG 再改代码，等于先写结论再找证据。

### 4.2 哪些可并行、哪些绝不并行

**✅ 可以并行**

| 组合 | 为什么可以 |
|---|---|
| ①勘察 **×** ②量基线 | 两个都是只读的，互不干扰 |
| ①勘察不同区域 **× 并行** | 只要各自在清单里写清覆盖范围，两份清单可以合并 |
| ②钉**互不相干**的行为 **× 并行** | 前提是**各自钉在不同的测试文件里**，否则会互相覆盖 |

**❌ 绝不并行（这几条会出事）**

| 组合 | 为什么绝不能并行 |
|---|---|
| **③改 explorer-v3 的渲染层 × ③（或任何人）改那四个插件** | **这是本项目的头号地雷（F4）**：改类名 → 四个插件静默失效，**不报错、不报红**。四个插件是 `files-office2:41,50`、`files-edit-md:220,237,270,428`、`files-comments:112`、`shell-agent-console:174,175,293`。**必须先拆掉这个耦合，才能动渲染层** —— 这一条 `05-shape-up.md:122` 的 C5 也已经点出（「这一条决定了 U2 之后必须先修 DOM 契约，否则 U2 一改类名就静默炸三个插件」）。**注意：C5 记的是 3 个，实测是 4 个，我逐处打开确认过。** |
| **③改 `frontend/index.html` × 任何人改它** | 1130 行单文件、没有合并工具能帮上忙。**这个文件同一时刻只能有一个人动。** |
| **②改 `tests/` × ③改 `privhub/` 中的同一处行为** | 改考卷与答题不能同时进行——「这条红是因为代码变了，还是因为断言变了」会变成无法回答的问题 |
| **④改 `package.json` 的 version × 任何还在跑的③** | 版本号是「这次改动完成了」的声明；还在改的时候递增，历史就失真了 |

#### 4.3.4 服务端侧：这里才是特征测试性价比最高的地方

**必须说清楚**：按 Feathers 的判据（「从改动点向外爬树，找能观察的收束点」），**PrivHub 的服务端接缝（S1）远比前端便宜**，因为：

- 112 条路由是**精确匹配**的 → **每一条 URL 就是一个接缝，使能点就是 URL 本身**；
- `tests/lib.mjs:51-89` 是**唯一的请求出口** → 加记录/回放只改一处（S2）；
- **不需要浏览器、不需要打包、不需要桩**；
- 而且**已经可以安全地跑**（3190 隔离实例 + `.testroot` + 生产端口黑名单，`run-all.mjs:32,36,37,44-48`）。

→ **建议：施工队的第一批特征测试，从服务端开始。** 具体钉哪几处的 HTTP 契约，应由岗位②在跑过基线之后决定；我只给方向：**凡是「会动数据」的路由（上传/覆盖/重命名/移动/删除/彻底删除），它的现状契约必须先被钉住**——因为按 `05-shape-up.md:296-327` 的 B2 硬约束，**这些操作属于「会弄丢数据」的最高关键性，出错时没有第二次机会**。

### 4.4 一个立刻可做、成本极低的具体动作

**把 `tests/lib.mjs` 的 `req()`（`:51-89`）包一层「请求/响应记录器」，记录到 `.testroot` 下。**

- **它是什么**：Feathers 讲的**黄金主（golden master）**——先录下现状，之后拿录下来的当基准比对。
  > 「There is a **chicken-and-egg moment** when covering a system with tests… The golden master technique allows you to get your system under test **without performing too much invasive surgery**.」**[一手]**
- **为什么现在做**：这是全项目**最便宜的一个使能点**（只改一个函数，`:51-89`），而且**它给后面所有工作提供「改之前」那张照片**——没有它，第 2 步与第 3 步之间的对比就无从谈起。
- **代价**：小。`lib.mjs` 已有 `cookieOf`（`:110-115`）、`loginOkWithCookie`（`:124-128`）等辅助函数，加一个记录器不破坏现有结构。
- **风险**：**低**，但要提醒岗位②：**记录下来的东西是「当前行为」，不要顺手把里面的错字/错码当 bug 报**（那就是它的职责边界）。

## 5. 两档编制

### 5.1 最少可行编制（只能设 1 个智能体，我选谁）

**我选「岗位②钉行为验收工」。**

**为什么是它，而不是最像「干活」的那个：**

| 候选 | 不选的理由 |
|---|---|
| ③修理工（最像干活的那个） | **它的价值建立在「知道改之前是什么样」之上，而这个前提现在不存在。** 只设它，等于让一个人在没有病历的医院里开刀——改完新功能能用，但**没人知道它是踩在什么上面用起来的**，下一次改动会踩到同样的地方。 |
| ①接缝侦察兵 | 它是最该**先**做的事，但它**不产出任何可重复验证的东西**。只设它，主子会得到一份很漂亮但无法验收的清单——**而且下一次改动的风险一分没降**。 |
| ④仓管 / ⑤审核员 | 它们都依赖上游产出，只设它们等于设了个空岗位。 |

**选②的三条实质理由：**

1. **它是唯一能产出「机器验」证据的岗位。** 按 `02-martin-fowler.md:68-72` 的分类，本项目能用的验法只有三种（机器验 / 另一个 AI 会话验 / 人眼验），而**只有②产出「机器验」**。独立 AI 会不会重复上一个 AI 的错？会。人眼会不会漏？会。**只有「这条断言今天绿、改完红了、我知道为什么」是不可争辩的。**
2. **它的产出永久有用。** 特征测试写下来就是资产：**新功能上线时它在，下一轮改动时它还在。** 相比之下，①的清单会被消耗掉，③的改动会被下一次改动覆盖。
3. **它同时能补上本项目最缺的那个数字**：全量回归的耗时基线。**没有这个数，所有「这次做多少」的判断都是猜的**（`02-martin-fowler.md:100` 也点了这一条）。②在做基线的时候顺手就量了。

**但必须一并说清②的边界**（这是诚实的部分）：

- **只设②，等于「先建病历、暂不开刀」。** 主子如果此刻就想看到界面变化，这个选择会让你等一轮。**这是本视角的立场：先建病历，值这一轮。**
- **②不许改业务代码**（防火墙）。所以如果只能设一人，那这个人**不能同时当修理工**——**同一个 AI 会话既当选手又当裁判，它的「验」就失去意义了**。
- **②也不知道该钉哪里**——它需要①的清单。所以「最少可行编制」的完整形态应是：**一个常驻的② ＋ 每次开工前临时起一个①**（①不需要常驻，它是项目级的、做完一次可以复用很久）。
- **②判不了「界面好不好看」。** 它钉的是行为，不是观感。**观感这件事在本项目里没有任何 AI 能验**（见 §7.1）。

### 5.2 理想编制（不设上限）

**建议设 4 个常驻 + 1 个按需。**

| 序 | 岗位 | 常驻？ | 为什么是这个数 |
|---|---|---|---|
| ① | 接缝侦察兵 | **按需起，不必常驻** | 它的产出（接缝清单）**保质期长**——接缝不会每个月都变。做一次可以复用很久。常驻会变成一个只会重复劳动的岗位 |
| ② | 钉行为验收工 | **常驻（必设）** | 特征测试的维护是**持续**的：每次改动都可能让某颗钉子变红，需要有个人解释「为什么红」。而且它是唯一产出机器验证据的岗位 |
| ③ | 外科修理工 | **常驻** | 干活的手。但**必须与②分开持有写权限** |
| ④ | 仓管 | **常驻** | 单人的项目最容易被跳过的一环就是记账。**它常驻的成本极低（改动很小），收益是「三个月后的你还能读懂今天」** |
| ⑤ | 对抗审核员 | **按需起** | 常驻会退化成「每次都说过得去」。**它的价值恰恰来自「不常在场」**：每次带着新的、不带本次上下文的视角回来看 |

**为什么不是 6 个、7 个：**

Feathers 的一句话可以直接回答：
> 「…people that are like, 'I find a better way of doing things in the organization,' they try to go and lead and say, 'We have to do it this way'… **They just create enemies.**」
> —— GOTO 2023 **[一手]**

**在单人手维护、没有团队、没有 CI 的项目里，每多一个常驻岗位，主子就多一份「要读的报告」。** 五个岗位已经是「①③④加起来的产出量」的上限了。**再多，报告本身会取代工作。**

## 6. 我建议不要设立的岗位

| 不要设 | 看着像该设的理由 | 我为什么不建议 |
|---|---|---|

| **「覆盖率看板工」** | 「量化一下测试进度，好排期」 | **三重问题**：① 本视角的主人公**明确反对把测试数量当目标**（「we can **overly valorize the tests**」）；② 他关心的是**生产环境实际执行覆盖率**，不是测试覆盖率（他为此专门做了 Scythe 工具）；③ 更现实的：**本项目的测试全是 HTTP 层断言，一行覆盖率数字会严重误导**——它会把「接线通了」算成「功能测了」。**若真要看指标，看他 2026 年自己预警的那条**：「**Metrics creep** — lines of code (or token usage) returning; **Goodhart's Law** incoming」。 |
| **「跨插件 DOM 接口统一工」（专门去把 `querySelector` 都改成插槽契约）** | 交底硬约束 5 明确禁止跨插件 `querySelector` | **方向对，做法错。** 这是一个「一次性、跨 4 个插件、无法机器验证」的大动作（改完之后**坏不坏看不出来**，正是 F4 描述的那种静默失效）。**正确顺序是：先钉住现状（P1）→ 再逐个插件改 → 每改一个跑一次回归。** 这属于岗位②③的日常活，**不该变成一个新岗位**。顺便说：**「修 DOM 契约」这个说法本身就该被替换成「消除 DOM 依赖」**——前者是在既有的耦合上加一层规范，后者是把耦合去掉。 |
| **「UI/交互专用重构工」** | 「界面问题最多」 | **本视角完全不管 UI。** 而且更硬的事实是：**本项目没有任何人能验 UI**——没设计师、没测试用户、没截图工具、没浏览器自动化，骨架零响应式（`00-汇总与拍板建议.md:58`）。设了这个岗位，它会产出**无法被任何方式验收**的改动。**UI 的事应该先走「人眼看一次」那条路（Krug 那路的 3 人测试脚本，或主子自己操作 5 分钟的一段录像），不是先设岗位。** |
| **「AI 自审工」（让同一个模型审自己的输出）** | 「多一道把关」 | **它不产生独立信息。** 同一个模型、同一套上下文、同一个盲区，审出来的是同一批结论。**这就是为什么⑤必须挂在另一份 skill 上**（不同的镜片）**并且必须是不带本次上下文的会话**。如果要设「审核」，就按⑤的规矩设；**不要设一个假的审核岗来给自己发绿卡。** |

### 7.2 我这把视角该不该当「总工」

**不该。**

**一句话版本**：**我这把视角是「术前检查科 + 病历科」，不是「手术主刀 + 术后决策」。我能告诉施工队「哪里能下刀、下刀前先拍哪张片子、下完刀怎么知道没切错」，但「这台手术值不值得做、先做哪台、做完长什么样」不属于我。**

**三句拆开说：**

1. **我这把视角能覆盖的**：改动前的勘察、接缝与使能点的识别、特征的建立、改动的边界控制、复杂度搬家的计价、以及「没有测试就重写 = 两个问题」这道闸门。**这已经是一整套施工纪律了。**
2. **我这把视角明确不管的**：**UI 与交互（完全不碰）、视觉与令牌、功能的取舍与排期、安全与数据的合规判断、以及「用户到底找不找得到」。** 这些分别属于库里另外五份视角，以及主子的产品判断。
3. **所以「总工」应该由谁当 —— 我的建议是：** 不是任何一个智能体，而是**主子**。理由不是我推卸责任，而是这个项目的真实结构：**单人维护、没有团队、没有 CI、没有设计师，所有验收的最后一环本来就只能是主子本人**（`02-martin-fowler.md:68-72` 把这件事说得很清楚：本项目能用的验法只有机器验 / 另一个 AI 会话验 / 人眼验三种）。**任何智能体当「总工」，都会变成「让一个 AI 宣布自己合格」。**

**如果一定要有一个智能体做「流程总管」，我建议它的职责被限制在一件事上：**
**「确保第 2 步（钉现状）在第 3 步（动手改）之前发生，并且在它没发生时拒绝放行。」**
——**这就是 Feathers 那把视角能给出的最硬的一条管理动作，也是本方案唯一值得托付给一个常驻岗位的「闸门」。**
