## 1. 一句话判断

**这支施工队最该防的不是"改错代码"，是"没人能证伪"。**

主子不是程序员，所以这支队伍里**唯一的"人"也无法用读代码来否决任何结论**。这时候施工队会自然退化成一种结构：**干活的智能体自己说干完了，自己说验证过了，主子只能点头**。Simon Willison 把这种局面说得最直接：这不是技术问题，是问责问题——他说 coding agent 没有职业声誉，也没法为做过的事负责，"**A computer can never be held accountable. That's your job as the human in the loop.**"（2025-12-18）。主子在这个结构里就是那个 in the loop 的人，但主子**看不懂代码**。

所以整套编制的核心不是"让 AI 更小心"，而是**把"干完了"这句话改造成一份可以被人看的证据包**：出一张前后对照的界面截图、贴一段能自己重跑的命令、留一份改动前后都跑过的回归记录。

一句话：**这支队伍招的不是更聪明的写手，是一个会把活儿摆到主子眼前、并且摆得住的人。**

软着陆一句：这套东西治不了"AI 改得对不对"这个根本问题——**它只能把"对不对"从一句无法核实的声明，变成一份主子能当面掀开的纸**。掀开之后能不能看懂，是另一个问题，我写在第 7 节。

### 2.2 三种"跑法"能力不同，别混着说

| 跑法 | 需要服务 | 能验什么 | 我实测的结论 |
|---|---|---|---|
| `node tests/integrity.mjs` | **不需要** | 交付完整性、加密契约、隐私边界、前端模块化契约、首屏守卫（纯读文件+正则断言） | ✅ **我跑通了：50/50** |
| `node tests/<静态脚本>.mjs` | 不需要 | 模板编译、管理控制台、个人 UI、审计可靠性、首次部署 | 本环境被沙箱拦（见 2.5），**未核实** |
| `node tests/run-all.mjs --spawn` | 需要（自动拉起） | 上面全部 + 174 条打真实 HTTP 的行为用例 | ❌ 本环境 `spawn EPERM`，**未核实** |

**这条区分对闸门设计是关键**：`integrity.mjs` 这类**静态契约检查**是本项目最便宜、最稳的一道网——它不需要起服务、不会碰数据、跑一次几秒钟，而且它守的恰好是"不能被无声改回去"的那些性质（个人空间隐私边界、fail-closed 鉴权、模块化契约）。

### 2.3 为什么"改 A 坏 B"在这个项目里**几乎必然发生**（而且不报错）

这是全仓最要命的一处结构性事实。**4 个插件靠另一个插件的内部类名工作**：

| 插件 | 依赖的类名 | 证据（我核过） |
|---|---|---|
| `privhub-files-office2` | `document.querySelector('.v3-content')`，再在里面找 `.v3-md` / `.v3-text` / `iframe.office2-frame` | `privhub-files-office2/client/index.js:41,44,50,51` |
| `privhub-files-edit-md` | `document.querySelector('.v3-content')` ×3 + `teleport to=".v3-content"` | `privhub-files-edit-md/client/index.js:220,237,270,428` |
| `privhub-files-comments` | `document.querySelector('.v3-content .v3-md')` | `privhub-files-comments/client/index.js:112`（另 `:192` 在其内部再找 `mark.v3-cmt`） |
| `privhub-shell-agent-console` | 复用 `.v3-loading` 类 | `privhub-shell-agent-console/client/index.js:174,175,293` |

而这些类名**由 `explorer-v3` 定义**：`.v3-content`（`explorer-v3/client/styles.js:26`）、`.v3-md`（`:57`）、`.v3-loading`（`:70`）。

**后果**：谁改一下 `explorer-v3` 的样式文件里这几个类名，或者只改 `client/index.js` 的模板结构，**这四个插件会静默失效——不报错、不抛异常、日志里什么都没有**。交底里写着"修订顶栏时已因此**连撞两次**"【引用】，`00-汇总与拍板建议.md` 把"必须先解 explorer-v3 耦合"标为**唯一一条"顺序错了会出事"的建议**【引用】。

**我的补充判断**（这是我要施工队记住的一条）：**这类故障对现成的 174 条回归套件也是隐形的**——因为回归套件是**打 HTTP 接口**的，它看不见浏览器里的 DOM（`tests/lib.mjs` 用的是 `node:http` `request`）。所以"回归全绿"**不能证明**这四个插件没坏。**这是"改 A 坏 B"在本项目的主形态，而现有闸门抓不到它。**

### 2.4 观察手段：现状是"零"，但零得很干净

| 检查项 | 实测值 |
|---|---|
| 前端全局错误捕获（`window.onerror` / `unhandledrejection` / `addEventListener('error')`） | **0 处**（骨架与全部插件 client 合计） |
| 前端埋点（`sendBeacon` / `trackEvent` / `analytics` / `telemetry` / `Sentry`） | **0 处** |
| 骨架里的 `console.error` / `console.warn` | **3 处 / 2 处**（只在插件加载失败与重试路径上） |

| 服务端日志文件 | `server-dev.log` **1757 字节**，最后写入 **2026-09-06**——内容只有启动时的插件装配清单与端口横幅 |
| 审计（`ctx.audit.log`） | 存在，但**只覆盖十来个写操作插件**（edit-md 2 / office-ai 1 / trash 1 / svc-rag 1 / office-ui 1 / admin-audit 1 / admin 1 / auth 1 / files-agent 1 / files 1），**记的是数据变更，不是界面被点了什么** |

**结论**：子系统里**唯一被记录下来的东西是"谁改了哪些数据"**。界面本身**完全不产生任何可查的记录**。"我从没看过这个界面跑起来的样子"——五份方案里四份写下这句话【引用】——不是懒，是**这个系统确实没有留下任何可看的东西**。

| 想做 | 结果 | 原因 |
|---|---|---|
| 跑 `run-all.mjs --spawn`（174 条行为用例） | ❌ `Error: spawn EPERM`，发生在 `run-all.mjs:68` 拉起服务子进程时 | 本会话为受限沙箱，**Node 子进程用管道 stdio 被拒**（这是环境的既定边界，不是命令写错） |

## 3. 编制表

### 3.0 先说清"谁在验谁"——这是整张表的地基

主子不是程序员，所以**验收不能依赖"人读懂代码"**。Simon 给的办法不是让人去读代码，是**让人去看证据**：他要求提交者把改动配上一串"能粘贴的命令 + 它的输出"，另加自动化测试，并且**"回退实现时那条测试必须失败"**（2025-12-18）。

于是本编制里"验收"的定义被改造成：

> **验收 = 有人打开一个文件，看见一样东西，并且那样东西的生成方式可以被重新执行一遍。**

**关键推论（这条决定了岗位怎么分）**：既然验收看的是证据，那么**"由谁产证据"就成了唯一重要的分工线**。

- 谁**改**，谁就有动机把证据说得好看 → **改的人不得单独签自己的字**；
- 谁**只验不改**，谁的产出就是"证据文件本身"，可以被追溯、可以被打回。

**我不假装能做出真正的独立性。** 两个智能体都是同一模型的产物，不存在人类的"不同利益"。我能做的只有一件事：**把唯一能独立检验的东西——可重新执行的命令和可打开的实物文件——抬成签字的唯一凭据，并规定"说不出的、打不开的、算不上的，一律不算"。** 这一点在第 7 节我还会自己打自己一次。

## 4. 工序

### 4.1 开工前必须先立的"证据三件"（每个工单都一样，不因改动大小而减免）

**① 前后对照（看得见）**
- 视觉/交互类改动：`screenshots/<工单号>/before-*.png` 与 `after-*.png`，**同一窗口尺寸**（固定 1280×800）。
- 逻辑/文案类改动：`before.txt` / `after.txt`（同一条命令的两次输出，逐字粘贴）。
- **不变量**：两张图的**文件字节数必须不同**。相同 = 没改动 = 直接打回。（这是最省事的"AI 说改好了其实没改"的抓法。）

**② 一条命令 + 它的真实输出**
- 命令必须**逐字可粘贴**，不许写"我跑了测试"。
- 输出必须是**汇总行原文**（例如 `50 通过 / 0 失败` 或 `174 通过 / 0 失败`），不许是改动手的转述。
- 断言：**命令的退出码要一并写下来**（0 才算通过）。`run-all.mjs` 的成败就是看退出码（`run-all.mjs:104`）。

**③ 改动文件清单**
- 逐行列出**被改动的文件路径**，与工单的"改动范围"对照。
- 出现工单外的文件 = **直接打回**，不看理由。

### 4.3 「先冻基线，再动手」——这是防"改 A 坏 B"的核心动作

**顺序不可颠倒。** 理由：`run-all.mjs` 现在是**绿是红我不知道**（我在本环境跑不通，见 2.5）。如果基线本身就是红的，那"改动后跑到红"你分不清是新伤还是旧伤——**盲人骑瞎马**。

**改动前（动手之前，先做这一步）**

```
cd G:\program\dsh-SQL\privhub
node tests/integrity.mjs                                    > screenshots\<工单号>\before-integrity.txt 2>&1
node tests/run-all.mjs --spawn                              > screenshots\<工单号>\before-regression.txt 2>&1
echo 退出码=%ERRORLEVEL%                                    >> screenshots\<工单号>\before-regression.txt
```

**改动后（同样两条，文件名换 `after-`）**

**然后做这三项对照（写进证据 md）**

| 对照项 | 判据 |
|---|---|
| 通过数 | `after` 的通过数 **≥** `before` 的通过数 |
| 失败清单 | `after` 的**失败项名称集合** 与 `before` **完全相同**（不是"数量相同"，是**逐条同名**） |
| 退出码 | `after` 为 0；若 `before` 也是非 0，则**必须点名是哪几条、并证明不是本次引入** |

**为什么是"逐条同名"而不是"数量相同"**：数量相同可能是一条旧的修好了、一条新的坏了——**净零，但性质完全不同**。这条规矩一写下来，"AI 说修好了其实没有"就没地方藏了。

**只跑不动数据的那个（最省事的常用形态）**

日常小改动，用这两条就够，几秒钟、不用起服务：

```
cd G:\program\dsh-SQL\privhub
node tests/integrity.mjs
```

它守的是"不该被无声改回去"的那些性质（个人空间隐私边界、fail-closed 鉴权、前端模块化契约、首屏守卫）。**我实测它是 50/50 全绿**，所以它一旦变红，**一定是有人动了不该动的东西**——这就是一个好闸门该有的性质：**基线可靠，红了就是你的错。**

### 4.4 「给非程序员的验收单」长什么样

> 设计目标：主子**不看代码、不看 diff、不读测试输出**，只看这一张纸。
> **凡是主子看不懂的栏目，验证手不许填"通过"，只能填"待主子目视"。**

```markdown
# 验收单 · 工单 NNN
日期：____   验证手：验证手实例（第 N 次）   工单：<链接>

## 一、这次到底动了什么（一句人话）
<例：把左侧图标栏第 1 个图标下面加了"文件"两个字。没动别的地方。>

## 二、我怎么知道的（照这个顺序看）
| # | 你打开这个文件 | 你应该看到什么 | 实际 | 勾 |
|---|---|---|---|---|
| 1 | screenshots\NNN\before-1.png | 图标栏一列图标，图标下面**没有字** | | [ ] |
| 2 | screenshots\NNN\after-1.png  | 同一个位置，图标下面**有"文件"两个字** | | [ ] |
| 3 | screenshots\NNN\after-regression.txt 最后三行 | `174 通过 / 0 失败`，退出码 0 | | [ ] |
| 4 | docs\...\证据\NNN.md 的"改动文件清单" | 只有 2 个文件，且都在工单允许清单里 | | [ ] |

## 三、我最担心的事，这次有没有发生
| 担心 | 这次 | 依据 |
|---|---|---|
| 改了 A 坏了 B（尤其是那 4 个靠 .v3-* 类名活着的插件） | 未发生 / 未验证 / **发生了** | <回归 after 与 before 失败清单逐条同名 / 我复跑过 / 我没法复跑> |
| 回归里混进了新的失败项 | 无新增 | <列出 after 的全部失败项，一条不省> |
| 动了不许动的文件（权限边界） | 未越界 | 清单 4 个文件，逐条比过 |

## 四、我自己复跑的结果（不许抄改动手的）
我跑的命令：____________
我的输出汇总行：____________
我跑不了，原因：____________ → 本次结论降级为 **未验证**

## 五、我还看得见、但不敢下结论的地方
<例：我确认两张图的字节数不同，但我看不出差异是不是"加了两个字"——这一步要主子自己看。>

## 六、结论（三选一，不许含糊）
- [ ] **通过**——五项全勾，且我复跑一致
- [ ] **打回**——不成立的是第 ___ 条，因为 ____________
- [ ] **待主子目视**——技术上我没法判，需要主子看第 ___ 个文件然后决定

## 七、主子要自己看的话，只看这一处
<一个文件路径。只给一处。>
```

**为什么这张单子长这样**——三条来自 Simon 的做法，抄的是结构不是话：他要求"能粘贴的命令 + 它的输出"（所以第二节是"打开哪个文件"而不是"我检查过了"）；他要求自动化测试**在回退实现时失败**（所以第四节是"我自己复跑"，而不是"改动手说他跑过"）；他强调"**如果你没看见它跑起来，它就不算一个能用的系统**"（所以第二节每一行的判据都是**看得见的东西**，不是"已确认"）。

### 4.5 「观察手段」的补救方案：把"界面跑起来的样子"变成可看的证据

**目标**：以最小代价，让"我从没看过这个界面跑起来的样子"这句话在项目里**再也不成立**。

**第 0 步 · 隔离实例（已有，不用建）**
```
cd G:\program\dsh-SQL\privhub
node tests/run-all.mjs --spawn
```
端口 3190、数据在 `tests\.testroot\`、**拒绝打生产端口 3180/3181**（`run-all.mjs:32,44-48`）。**已经有人替我们把这件最难的事做好了**——一个不碰真实数据、可以随便折腾的实例。

## 5. 工序（谁先谁后 / 哪些能并行 / 哪些绝不并行）

### 5.1 一条工单的标准流水

```
   ┌─────────────────────────────────────────────────────────┐
   │ 0. 守范围的：这件事现在该不该做？（一句话裁决）           │
   │    —— 若并入主任工，就是主任工开工前的三条硬规矩          │
   └───────────────────────┬─────────────────────────────────┘
                           ↓ 只准一件事
   ┌─────────────────────────────────────────────────────────┐
   │ 1. 主任工：出工单（含"撞不撞 8 条约束"表 + 允许改动文件） │
   └───────────────────────┬─────────────────────────────────┘
                           ↓
   ┌─────────────────────────────────────────────────────────┐
   │ 2. 改动手：**先冻基线**（before-integrity / before-regression）│
   │    ⚠ 基线不冻，不许动第一行代码                           │
   └───────────────────────┬─────────────────────────────────┘
                           ↓
   ┌─────────────────────────────────────────────────────────┐
   │ 3. 改动手：改 → 跑 after-* → 存前后对照图 → 交证据包     │
   └───────────────────────┬─────────────────────────────────┘
                           ↓
   ┌─────────────────────────────────────────────────────────┐
   │ 4. 验证手：**自己复跑** → 逐条对失败清单 → 出验收单       │
   │    打回则回到 3（同一工单最多打回 3 次）                  │
   └───────────────────────┬─────────────────────────────────┘
                           ↓
   ┌─────────────────────────────────────────────────────────┐
   │ 5. 主任工：写 CHANGELOG + 递增版本号（唯一来源 package.json）│
   │    ⚠ 只有在第 4 步"通过"之后才准写                        │
   └───────────────────────┬─────────────────────────────────┘
                           ↓
   ┌─────────────────────────────────────────────────────────┐
   │ 6. 主子：看验收单第七节"只看这一处" → 人工确认             │
   │    ⚠ 主子没点头，不许 git commit / push                   │
   └─────────────────────────────────────────────────────────┘
```

### 5.2 谁先谁后（硬顺序）

| 顺序 | 为什么不能颠倒 |
|---|---|
| **冻基线 → 动手** | 基线没冻，之后所有"没变坏"的结论都不可信（见 4.3） |
| **解 explorer-v3 耦合 → 改渲染层（U2）** | `00-汇总与拍板建议.md` 明确标它是**唯一一条"顺序错了会出事"**的建议【引用】；我复核了 4 个插件的依赖（2.3），**成立** |
| **验证手复跑 → 主任工写 CHANGELOG** | 反过来的话，版本号会记录一件未被验证的事。**CHANGELOG 一旦写了就是"已确认"的语义** |
| **主子点头 → commit/push** | 交底第 8 条是用户明示的纪律【引用】，不许由任何智能体自行加速 |

### 5.3 可以并行的

| 可并行 | 条件 |
|---|---|
| ④ 看界面的 与 ①②③ 的施工流水 | 观察是**只读+录音**，不碰代码；两条线互不干扰。而且观察的产出（数票表）正好是下一条工单的输入——**并行收益最高的一条** |
| 多个**互不触碰同一文件**的工单 | 例：一条改 `privhub-shell/client/index.js`，一条改 `files-tags/client/index.js`。**要求主任工在工单里写明文件清单，并在派发前做一次"文件不重叠"检查** |
| 验证手复跑 与 改动手做**下一条**工单的基线 | 两条命令都跑在同一个隔离实例端口上会冲突——**必须错开**，或各用一个端口 |

### 5.4 **绝不并行**（写死）

| 绝不并行 | 为什么 |
|---|---|
| **两个改动手同时改同一个文件** | 后写的覆盖先写的，而两边的证据都会显示"我改成了"→ **两边都通过验收，代码里只有一个改动**。这是最难查的一类事故 |
| **任何改动 与 改 `explorer-v3`** | 它是 4 个插件的隐式依赖源（2.3）。**改它 = 同时改 5 个插件的行为**，而回归套件看不见 DOM，抓不到。必须**单独一条工单、单独一轮验证**，不许和别的改动拼车 |
| **验证手复跑 与 改动手正在改** | 验证手跑的是"某一刻的状态"，中途改文件 → 跑出来的结果不对应任何一个版本，**证据作废** |
| **写 CHANGELOG 与 还在验证中** | 见 5.2 |
| **跑回归 与 有人在真实实例上操作** | 回归会清自己创建的产物（`run-all.mjs` 注释与 `lib.mjs` 的 `safeDelete`/`purgeTrashOfProject`）。真实数据在 3180/3181 上，**物理隔离**，但仍要守住"任何测试不许指向生产端口"这条（已被 `run-all.mjs:44-48` 硬挡住，**不要绕过它**） |
| **"顺手把那条测试也改一下" 与 任何事** | 验证手的权限边界里写死了：`privhub/tests/` 只读。**改测试让测试通过，是这支队伍最危险的一个动作**——它会同时毁掉基线、毁掉对照、毁掉全部此后的证据。若要改测试，**单开一条工单**，且改测试这件事本身必须由验证手以外的角色做、并由验证手复核 |

## 6. 两档编制

### 6.1 最少可行编制：**只设 1 个智能体时，选"主任工 + 改动手"的合并体**

**选谁**：**一个人，但给他两道自动闸门**。名字叫**施工员（自证型）**，`agent_create` 时按下面配：

| 字段 | 内容 |
|---|---|
| **id** | `privhub-builder` |
| **一句话职责** | 一次只做一件事；做完必须交出"能重新跑的命令 + 能打开的前后对照图 + 没越过改动范围"三样，交不出就算没做完。 |
| **能力包** | `files` `shell` `jobs` `skills` `todo` `ask` `present` `planning` `compaction`（**不给** `web`、**不给** `delegation`） |
| **挂 skill** | 工作区内：`docs/experts/simon-willison-perspective/SKILL.md` |
| **权限边界** | 可写 `frontend/` `plugins/` `src/` `tests/` `screenshots/`；**只读** `data/` `data-files/`；`CHANGELOG.md` 与 `package.json.version` **只读**（留给主子手工写一条） |

**为什么是这个组合，而不是"只留一个验证手"**：

一个只会验不会改的智能体，**在这个项目里没有活干**——它没有"别人的代码"可验，主子又不会派活给它改。而一个能改的智能体，**至少能把事情推进**。所以单岗只能选"能干活的那个"，再把 Simon 的两条硬规矩**烧进它的 AGENT.md**：

> **规矩一：改任何东西之前，先把基线跑出来存好；改完之后再跑一遍，两份失败清单必须逐条同名。**
> **规矩二：不许说"应该好了"「大概没问题」「理论上可以」。要么给一条能重新跑的命令加它的输出，要么给两张能打开的前后图。两样都交不出，直接说"我没验证"。**

**这个最少编制能防什么、不能防什么（必须说清）**：

| 能防 | 怎么防 |
|---|---|
| **"AI 说修好了其实没有"** | 规矩二把它逼到"交不出证据就说没验证"。它**自己说自己没验证**，就是这条规矩在起作用 |
| **"改了 A 坏了 B"** | 规矩一把"前后失败清单逐条同名"变成硬动作。**净零（一条修好一条坏）也会被抓到** |
| **改到不该改的文件** | 权限边界 + 工单文件清单 |
| **把真实数据改坏** | `data/` `data-files/` 只读 + 回归只跑 3190 隔离实例 |

| 防不了 | 为什么 |
|---|---|
| **自己签自己的字** | 它既是改的人又是验的人。它要是想蒙，**它有能力蒙**（它写得出像样的证据） |
| **那 4 个靠 `.v3-*` 类名活着的插件坏了** | 回归是打 HTTP 的，看不见 DOM。**单岗编制里没有任何人看着界面** |
| **优先级排错** | 没有任何人做过观察，所以"先做哪一条"仍然是猜的——**这正是五份顾问方案栽的那个坑，单岗编制没有补上它** |

**所以单岗是一个"能开工但漏着两处"的编制。** 我把它列出来是因为主子说了先设一个——**但我要把话说在前面：它把"没人看界面"这块最大的盲区原样留着了。** 如果只能设一个，请至少配上 4.5 的第 2 步：**主子每月录一段 5 分钟的操作视频**丢给它。这不需要多一个智能体，只要主子每月花 5 分钟。

### 6.2 理想编制：**4 个岗位**

| # | 岗位 | 一句话为什么必须有它 |
|---|---|---|
| ① | **主任工** | 因为"派活、守门、记账"三件事必须和"改代码"分开，否则工单会越写越大、证据会越写越像 |
| ② | **改动手** | 因为总得有人真的动手；而且他必须是**唯一**有权改代码的那个 |
| ③ | **验证手** | 因为"改的人不许签自己的字"是这套编制里唯一一条能真正咬住的规矩 |
| ④ | **看界面的** | 因为当前**最大**的盲区不是代码质量，是"从没看过界面跑起来的样子"；而治它的方法（Krug 的 3 人脚本）已经写好了，缺的只是有人去执行 |
| ⑤ | ~~守范围的~~ | **建议并入 ①**。判据太轻，不值得单独养一个常驻智能体（三条硬规矩写进 ① 的 AGENT.md 即可） |

**理想编制的关键设计点（三个，都是刻意的）**：

1. **① 主任工故意没有 `shell`。** 他不能说"我跑过了"。他要说这句话，就得回去找改动手或验证手。**这道限制是有意给自己上的枷锁**——它让"谁真的跑过"这件事在结构上无法含糊。
2. **③ 验证手对 `privhub/` 全目录只读。** 包括 `tests/`。"顺手修一下那条测试"是这套编制里唯一能一次性毁掉全部证据的动作。
3. **④ 看界面的 产出是"票数"，不是"报告"。** 报告可以写得很好看；票数只有九行、每行几道勾，**没法美化**。而票数第一名的那个数字，直接决定下一个工单做哪一条——**这是这套编制里唯一一条从"看见的事实"出发的优先级通路**。

**四个智能体的相互关系**：①②③ 是一条竖线（派→改→验），④ 是一条横线（观察→投票→喂给 ① 排序）。**④ 不参与审批，只提供票数。** 这样设计的理由：观察的产出是"哪条最疼"这种**排序信息**，而不是"这条改得对不对"这种**放行信息**，两种信息不该混在一个岗位里。

## 7. 我建议不要设立的岗位

| 不要设 | 为什么 |
|---|---|
| **"代码审查员"** | 主子看不懂代码，所以这个岗位的**唯一产出**（"我看过代码了，没问题"）**在结构上无法被任何人核实**。它是"看起来在防守，其实是把风险换成了一句好听话"。**Simon 已经说得很直**：*"No amount of meticulous code review—or even comprehensive automated tests—will demonstrably prove that code actually does the right thing. You have to run it yourself!"*（2025-03-02）。而"自己跑"这件事，改动手和验证手已经在做了 |
| **"架构师"** | 这个项目的架构已经被**定义**了（Cordis 底座 + 插件 + 无打包链 + 单主界面），而且**8 条硬约束把它钉死了**。再养一个"架构视角"的岗位，它的产出会是"我觉得应该重构一下"这类**无法验收**的建议。**顾问阶段已经有五份这种东西了，不参与施工**（题面明示） |
| **"测试编写员"（独立岗位）** | 危险。它会自然演化成"为了让回归通过而改回归"。**在本项目里，改测试必须是一件需要单独工单、单独理由、单独验证的罕见动作**——把常驻岗位给它，等于把这个罕见动作日常化 |
| **"安全审计"（独立常驻岗位）** | 主子已明示安全（S）与数据可靠性（D）**本轮往后放**（交底第 5 节）。现在设一个安全岗位，它会立刻开始产出**没人会去处理**的清单——制造焦虑而不产生动作。**等要动"谁能不能看哪个文件"这件事时再单开**（Krug 也明确说了这类判断不归他的方法管【引用】） |
| **"五个顾问视角各配一个常驻智能体"** | 顾问组管提意见、**不参与施工**（题面明示）。把 5 个顾问变成 5 个常驻智能体，等于养 5 个**只会提意见不会干活**的角色去和施工队抢上下文。其中真正需要留下来的只有两把：**Krug 的"看人做"**（→ 岗位④）与**Shape Up 的"该不该做"**（→ 并入 ① 的三条硬规矩）。其余三把（诺曼 / Cooper / Refactoring UI）**在具体工单要改的那一刻按需临时挂载即可**，不必常驻 |
| **"文档同步员"** | 交底第 8 条要求"同步项目说明文件"，但这件事**只要在工单模板里加一行勾选项**就解决了（主任工的活）。单设岗位属于过度编制 |

## 8. 我判不了的

**（1）最大的一块：这套编制能不能真的防住"AI 说自己修好了其实没有"——我只能说到一个程度，说不到底。**

我把闸门设计成"证据必须存在、必须能打开、必须能重新执行"——这能挡住**偷懒**和**含糊**。但它挡不住**伪造**：改动手有能力写出一份格式完美的证据包，也有能力在报告里把"我没跑"说成"我跑了"。

**能不能真的咬住，取决于一个我无法验证的前提**：验证手会不会"真的自己去跑一遍"，而不是照着改动手的报告誊抄。这**不是**一个技术问题，是一个**意愿问题**——而两个智能体都是同一个模型的产物，不构成人类的"利益对立"。

**我给主子的实话**：这套编制的实际强度，靠的是**可核验的实物**（一张图、一个文件、一条能重跑的命令），**不是靠"两个智能体互相监督"**。所以它**必须有人偶尔抽一次**——抽的方式很便宜：**随便挑一个已通过的工单，自己把那条命令再跑一次，看输出对不对得上验收单。** 抽一次的成本是几分钟，但它把这整套编制的"可信度"从"希望"变成"被检验过"。**这件事只能主子做，因为只有主子有不配合的动机之外的理由去做它。**

**（2）"给非程序员的验收单"到底够不够用——我没法通过"我读代码"来回答。**

我设计这张单子时用的是判断：非程序员能看懂"两张图不一样""文件里有这行字"。但**这张单子到底能不能让主子在 30 秒内真的判断"改对了"，只有主子拿一张真的单子试一次才知道**。这个答案不在代码里。

**（3）我在本环境跑不通的每一条，主子都得在有权限的环境里先跑一次。**

见 2.5。`run-all.mjs --spawn` 那 174 条行为用例，**我一次都没跑成功过**（`spawn EPERM`）。所以我在 4.3 里写的那些命令，**是按源码读出来的，不是跑出来的**。这是我的诚实边界里最实的一条：**闸门本身需要先被人跑通一次**，否则它只是一段好看的文字。**建议主子做的第一件事就是这个**，而且它恰好会顺手验证一件更重要的事——**当前基线到底是几绿几红**（这个数字现在没人知道）。

**（4）那 4 个插件的静默失效，现有闸门真的抓不到吗——我有一个推断，但只到推断为止。**

我的依据是：`tests/lib.mjs` 用的是 `node:http` 的 `request`，也就是**打 HTTP 接口**，而 `.v3-content` 这类东西是**浏览器里的 DOM 类名**。逻辑上接口测试看不见 DOM。**但我没有读过全部 174 条用例的每一条断言**，所以"一条都没覆盖"这句话我**不敢下**——万一有一条用了字符串匹配去查前端源码呢（`integrity.mjs` 就是这么干的）。**正确的做法是派一个人把这 174 条用例逐条读一遍、把"可能覆盖到前端 DOM 契约"的挑出来。** 这是一条很值的工单，但它超出我这次只读勘察的范围。

**（5）给 4 个插件补一道"DOM 契约看守"值不值得——判不了。**

方向上，应该有一道静态检查：**如果 `explorer-v3` 的模板/样式里不再出现 `.v3-content` / `.v3-md` / `.v3-loading`，就让回归变红**（写法照抄 `integrity.mjs` 那套正则断言就行，它已经在干同类的事）。这能补上 2.3 那个洞。**但我判不了的是"该不该现在做"**——它要动 `privhub/tests/`（本项目里最敏感的一个目录），而交底第 8 条的改动纪律意味着它要走一遍完整的工单流程。**这是取舍，交给主子。**

**（6）窄屏、10.7MB 的 Office 预览、标签页 30 上限这些题——我不接。**

不是我判不了，是**它们不在这个题面里**（题面是"编制"，不是"改什么"）。这些是顾问方案的射程，我这次不抢。
