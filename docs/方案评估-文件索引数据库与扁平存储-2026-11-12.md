# 方案评估：文件索引数据库 + 扁平存储（用户第四轮提案）

> 2026-11-12 · 只读评估，**不改代码、不改现有 v3 计划**
> 对照文档：[改动计划-存储分层与临时SSD-2026-11-12.md](改动计划-存储分层与临时SSD-2026-11-12.md)（v3）

---

## 0. 提案复述与一个必须先澄清的歧义

你的四点：

1. **前端直接创建一个文件储存数据库**，按项目划分，字段：文件 id / 文件名 / 后缀名 / 虚拟地址 / url 地址（可加更多）。
2. **每次显示直接从数据库读**并渲染到前端。
3. **只有读取文件内容和改写具体文件时**，才通过 url 地址抓源文件读写。
4. **所有文件放同一层级**（扁平）；上传先判断**重名**和**重复文件**，让用户选「覆盖」还是「自动选择」，自动选择以**最后修改时间**为保留。

**歧义**：「前端直接创建数据库」有两种读法，后果完全不同：

- **(A) 浏览器端 IndexedDB** —— 索引在用户浏览器里。
- **(B) 服务端常驻索引**（SQLite / JSON）—— 前端只负责渲染，数据由 Node 提供。

下面的结论按 **(B) 才成立** 展开；若你指的是 (A)，见 §3.2，那里有四条硬伤（权限泄露 / 同步 / 多设备 / 蓝绿）。

---

## 1. 先给结论

**这个方案的方向是对的，而且仓库里已经有 70% 的地基**——但「扁平存储 + 前端数据库」这两个具体做法需要改：

| 判断 | 结论 |
|---|---|
| 「显示从索引读，不每次扫盘」 | ✅ **完全正确**，且正是解决「点文件夹慢」的正解 |
| 「文件 id + 虚拟地址 + url」 | ✅ **仓库已有同类设计**：`svc-links` 就是「文件 → 稳定 ID + 退役文件名」，只是目前只服务双链，没扶正成主索引 |
| 「按项目划分」 | ✅ 与现有 `project` 语义一致 |
| **「前端直接创建数据库」** | ❌ **应放服务端**（放浏览器会泄密、无同步、蓝绿失效） |
| **「所有文件放同一层级」** | ⚠ **代价最大的一条**：会破坏目录树/面包屑/移动/mkdir/子路径权限，且收益几乎为零（有 ID 后无需扁平） |
| 「上传判断重名+重复，让用户选」 | ✅ 查重引擎已存在（`svc-dup` sha256 exact/near）；缺的只是**上传时的交互** |
| **「自动选择以最后修改时间为保留」** | ⚠ 需你确认语义：同名不同内容按 mtime 保留 = **静默丢弃另一份数据**，建议改「保留两者/自动改名」 |

**一句话**：把提案改成「**服务端主索引表（ID 化）+ 保留分层目录 + 上传冲突交互**」，就是比当前架构更好的方案，而且能**顺带解决 v3 里剩下的权限难题**；但「扁平 + 浏览器数据库」这两点会引入比解决的问题更多的新问题。

## 2. 能解决多少问题（对照 v3 剩余清单）

| v3 里的问题 | 本方案能否解决 | 说明 |
|---|---|---|
| **点文件夹慢**（`listFiles` O(N) 次 `isEncrypted` open） | ✅ **根治** | 查索引表，不再 `readdir`+逐文件 stat+读头。比 v3 阶段 2 的「去掉 isEncrypted + ETag/304」更彻底 |
| nginx 直读的**权限/防穿越**难题 | ✅ **大幅缓解，甚至可绕开** | 见 §2.1，这是本方案最大的隐藏收益 |
| 存量密文迁移 | ⚠ 不解决 | 仍是前置条件（索引里可加 `encrypted` 字段标记，反而更好管混合库） |
| 蓝绿单槽 | ✅ 已满足，不相关 | 但新增索引作为「可写内存态」会**新增**蓝绿约束（§3.3） |
| 上传临时 SSD | ✅ 不冲突 | 索引只记元数据，字节落盘路径不变 |
| 写链路的事件/审计/锁/版本 | ✅ 不破坏 | 只要索引维护**复用 `file:changed`**，写仍走 `svc.route` |
| 显示/内容分流 | ✅ 天然成立 | 索引给清单（显示），url 给字节（内容），正是你说的第 2/3 点 |

### 2.1 隐藏收益：ID 化能绕开 nginx 直读的 P0 难题

v3 里最硬的一关是「nginx `alias` 直读会绕过权限 + 防穿越」，方案 A 要新建逐文件授权端点、显式判个人空间、补 SVG CSP、`X-Original-URI`……

**如果索引里每个文件有稳定 ID，就可以改成**：

```
前端拿 id 请求 → Node 授权端点：requireUser + canAccess + acl.can + 个人空间判断
               → 用 id 从索引查出已校验的物理路径（不经用户可控的路径解析）
               → X-Accel-Redirect 交给 nginx sendfile
```

用户从头到尾**不接触物理路径**：没有 `$uri` 解码、没有 `%2e%2e%5c`、没有中文名/反斜杠穿越面，nginx `alias` 只认 Node 给的绝对路径。个人空间判断也能集中在一处。**这比 v3 方案 A 更干净**，而且天然对齐你「虚拟地址 / url 地址」的设想。

> 但注意：v3 评审发现的 **SVG CSP、切换窗口 502、auth_request 每请求一次往返、MIME/响应头** 这几条仍然存在，与 ID 化无关。

## 3. 会有什么新问题

### 3.1 索引与磁盘的一致性（无论放哪，都是头号新问题）

现在 `/api/list` 是**每次读盘**，磁盘就是唯一真相，不存在不一致。引入索引表后：

- 谁负责登记/删除/改名？→ 必须挂到 `file:changed`（created/saved/deleted/renamed/moved/restored/purged）与 `audit:logged`。
- 索引丢了/落后了怎么办？→ `svc-links` 的现成答案值得抄：**「登记表是派生数据，丢了能重建（名→路径从磁盘重扫）；绝不因登记表出问题而挡住任何文件操作」**（`svc-links/src/index.ts:19-20`）。索引必须可全量重建 + 宽容读取 + 有上限。
- 直接手工往 `data-files/` 放文件（运维/迁移/外部程序）→ 索引不知道。需要「启动扫描对账」或 `ensureAll` 惰性补登记（`svc-links:25-26` 已有队列+每轮上限的做法）。
- 蓝绿 `reload` 清单：索引是**可写内存态**，必须实现 `reload()` 并加进 `main.ts:348-356` 清单，否则预热槽供陈旧数据（`CLAUDE.md` 明写）。
- 新增周期写者（对账/补登记）须包 `ctx.privhub.onActivate()`、写经 `svc.route`、登记 `runtime-contract.mjs` onActivate 名单 —— v3 §2 的六条硬约束一条不少。

### 3.2 如果「前端数据库」= 浏览器 IndexedDB（四条硬伤）

| 硬伤 | 证据 |
|---|---|
| **权限泄露**：索引若含全量清单，浏览器就拿到了「有哪些项目/个人空间」。个人空间连管理员都不可见（`core:1014-1020`），下发给任何浏览器都是越权 | `core:816-823,1001-1003` |
| **无同步通道**：`file:changed` 是 Node 事件总线，浏览器收不到。全仓唯一 SSE 是 `/privhub/_version/stream`（版本广播），不是文件变更流 | `nginx.conf.template:80-90`、`core/events.ts` |
| **多设备/多标签**：A 机上传、B 机索引不更新；首次登录要拉全量清单（等于把慢从每次点击挪到登录时） | — |
| **蓝绿切换**：`reload` 只刷服务端内存态，浏览器索引无从知晓 | `main.ts:333-356` |

→ **结论：索引必须放服务端**。浏览器只拿「当前用户可见的当前目录」那一页清单，且仍走 Node 鉴权。

### 3.3 「所有文件放同一层级」—— 代价最大的一条

现有模型是 `data-files/<项目>/<子路径…>/<文件>`，`resolveInProject` 支持多级（`core:1043`）。扁平化后：

| 被破坏的功能 | 证据 |
|---|---|
| 目录树 / 面包屑 / 文件夹显示 | `index.html:888,914,941-996,1398-1402`、`tree.js:101-105`、`ops.js:132-160,285-318,328-370` |
| 新建文件夹 `mkdir`、移动/重命名到子目录 | `core:1190-1206`、`files:759-771,792-845` |
| `resolveInProject` 的子路径语义、`resolveReal` 的 realpath 基准；扁平后 `isDir` 恒假 | `core:1043-1047,1053-1072,1075-1104` |
| **按 `project|path` 键的侧车状态（会跟 `file:changed` 搬迁的那批）**：双链 ID、查重索引、全文索引 docId、RAG docId、KG 节点、引用缓存、edit-md 版本索引 | `links:133,257-295,417-428`、`dup:220-239,326-336`、`fulltext:51,98-119`、`rag:130,1465-1476`、`kg:403`、`refcheck:50-58`、`edit-md:38,84` |
| **按 `project|path` 键但「不监听 `file:changed`」的侧车状态 —— 改名即成孤儿**：评论、版本快照、标签、收藏、最近 | `comments:10,67,75,100,138`、`versions:70,89,122,129`、`meta:54-58,162-174`、`favorites:74,94`、`recent:111,53` |
| 文件级 ACL 的路径规则（可针对某目录设 allow/deny） | `admin-acl:241-251` |
| 「重名」的定义本身 | 现在同名在不同目录可共存（`files:457,685` 只在同一目标目录判重），扁平后全库同名 = 冲突暴增 |
| 个人空间「顶层目录 = 显示名」 | `core:826-839,954-961,1001-1003,1163-1164`；判据全是顶层目录名，扁平后失去载体，须整体重做 |

**而且扁平化几乎不带来收益**：你已经有「文件 id + 虚拟地址」了，**虚拟路径完全可以继续是分层字符串**，物理文件名用 id 即可（像 `svc-links` 那样 ID 只活在服务端、界面照旧认名）。这样目录树、权限、侧车状态全部保留，只把「磁盘名 ↔ 展示名」解耦。

> 建议：**保留分层虚拟路径 + 物理用稳定 ID 命名**，而不是「所有文件放同一层级」。

### 3.4 「重名 / 重复 / 自动选择」需要拆成三件事

你把它们混在一起了，代码里其实是三条不同的链：

| 概念 | 现状 | 缺口 |
|---|---|---|
| **同名**（同名不同内容） | `/upload`、`/upload/complete` 直接 **409 拒绝**（`files:457-458,556-557,685-686`），注释明说「不做自动备份/版本历史随覆盖清空另立项」（`files:448-458`）；前端 rename 时只提示不拦（`tree.js:79-81`、`panel.js:933-935`）。**矛盾点**：文件夹上传确认框却写「同名文件将被覆盖」（`upload/client:225,240`），与实现不符 | 缺「让用户选覆盖/改名」的交互；全仓无 `overwrite/force` |
| **重复**（不同名、内容相同） | `svc-dup` 已有 **sha256 原始/规范化哈希 + MinHash**（`dup/core.ts:95,158-166`）→ exact/near（`dup/index.ts:269-301`）；上传后回 `{duplicates:{exact,near}}`（`files:505,739`），toast 已明说「两份都保留了，可自行删除其一」（`upload/client:451-457`）；前端有「🔁 查重」按钮（`panel.js:881`） | 引擎与提示都已就绪，**只缺「上传前拦截 + 让用户选」**；注意 `check` 刻意限同项目（`dup/core.ts:263-265`），不能跨项目查 |
| **自动选择以最后修改时间为保留** | `listFiles` 仅回 `stat.mtime`（`core:1088`）；上传是流式 `createWriteStream` 落盘、分片会话用 `Date.now()`（`files:230,473,566,575,650,701`），**不采客户端 `lastModified`、无 `utimes`、无按 mtime 留一的策略** | ⚠ **危险**：同名不同内容按 mtime 保留一个 = **静默丢弃用户刚上传的那份**，而现状是 409 明确拒绝（属倒退）。建议改为「保留两者（自动加后缀）」或「明确二次确认覆盖」，mtime 只用于展示/冲突提示 |

另外，扁平化会让 `svc-dup` 的 `project::path` 键（`svc-dup:128-130`）失去子路径区分，但**按项目隔离仍在**；若改用稳定 ID 作键反而更干净（内容指纹与位置解耦）。

### 3.5 「url 地址」存进索引的两个风险

- **不要把可直接访问的绝对 url 下发给前端**：它等于把内部物理路径/主机名暴露到浏览器、可分享、可进地址栏历史；且蓝绿 release 切换后可能失效。应存 `id / virtualPath`，url 由 Node 在鉴权后现场生成（`X-Accel-Redirect` 或短时效签名）。
- v3 的 nginx 直读鉴权**不能省**：就算有 id，也必须判 `canAccess` + 文件级 ACL + 个人空间。ID 只是让「路径解析」更安全，不是免鉴权。

## 4. 仓库已有的地基（不是从零造）

| 你想要的 | 仓库里已有的 |
|---|---|
| 文件 → 稳定 ID + 退役名 | `privhub-svc-links`（`data/links.json`，`src/index.ts:2-26`，「双链 ID 化，改名不断链」）；`reload()`（`:98`）、惰性补登记 `ensureAll`（`:224`）、`MAX_ENTRIES=20000` 按 at 淘汰（`core.ts:51`） |
| 按项目的内容指纹查重 | `privhub-svc-dup`（`data/dup-index.json`，exact/near，`src/index.ts:186-202`）；`reload()`（`:99`）、订阅 `file:changed`（`:323-338`）；**`check` 刻意限同一项目以防「泄漏 B 项目存在」**（`core.ts:263-265`） |
| 文件元数据（标签） | `privhub-svc-meta`（`data/meta.json`）；无 `reload()`，蓝绿由 `main.ts:352-353` 调 `load()` 代替 |
| 服务端 SQLite 能力 | `privhub-svc-rag/src/vec.ts`（`better-sqlite3` + `sqlite-vec`，`src/vec.ts:12-42`） |
| 全文/向量索引的重建范式 | `fulltext` 全量 rebuild 延后到 `onActivate`（`fulltext:83-87,133`）；个人空间显式排除（`fulltext:58,71,144-168`） |
| 变更事件（可用于维护索引） | `file:changed` / `file:saved` / `audit:logged`，已有 **9+ 个订阅者**（`svc-events/src/index.ts:13-32`） |
| 蓝绿 reload 清单 | `main.ts:348-356`（links/dup/meta 均在列） |
| 「派生数据、可重建、不挡操作」的现成范式 | `svc-links/src/index.ts:19-20,25-26` |

**仓库里没有「按项目组织的文件主表」**：最接近的是 `links.byPath` 登记表与每次构建临时的 `LiveIndex`（`links/core.ts:150-168`），但都惰性、派生、有淘汰上限。所以更准确的说法是：把 `svc-links` 的「稳定 ID + 侧车登记表」**扶正成唯一权威主表**，并让 `/api/list` 改查它 —— 而不是新造一个前端数据库。

### 4.1 ⚠ 一条必须写进设计的隐私教训（评审补充，我评估初稿漏了）

`svc-rag/src/vec.ts:16-26` 记录了 **D9 事故**：向量库是**明文 SQLite**（`better-sqlite3` 直接打开，无法像其它数据那样整体加密），原始实现把 `chunk_id` 写成 `project::path#cN`，结果**宿主机直接打开 `vectors.db` 就能读出全部文件名与目录结构**。修复方式是表里只存 `sha256(docId)` 摘要，真实 docId 只留在已加密的 `manifest.json` / 语料 jsonl 里。

**推论**：如果主索引表用 SQLite 且把 `name` / `virtualPath` / `url` 明文写进去，等于**重犯 D9**。两条出路：
- **(a) 索引存 JSON 并走 `ctx.storage` 加密**（与 `meta.json`/`links.json`/`dup-index.json` 同规格，`better-sqlite3` 用不上，但表规模到十万级前 JSON 内存表够用）；
- **(b) 若必须用 SQLite**，则表里**不存可读路径**，只存 `id` + 路径摘要 + 密文字段，可读映射留在加密 JSON 里（抄 `docKeyOf` 的做法）。

**建议 (a)**：与现有三类索引一致、无需引入新的明文落盘面、蓝绿 `reload()` 范式现成。

## 5. 三种走法的代价对比

| 走法 | 解决列目录慢 | 权限/防穿越 | 改动量 | 新风险 |
|---|---|---|---|---|
| **v3 阶段 2**（去掉 `isEncrypted` + ETag/304） | ✅ 足够 | 仍需 v3 方案 A | **最小**：局部改动，不引入任何需一致性维护的新状态；ETag 有现成范式 `web-server.ts:257-281` | 几乎无 |
| **本方案改良版**（服务端主索引 + 保留分层 + ID 化） | ✅ 根治 | ✅ **更干净**（id 直出，不经路径解析） | 中（新增 1 个 L2 服务 + 改 `/api/list` + 挂 `file:changed` + `reload()` 清单 + `GUARD_PATHS` + 契约断言 + 存量全量对账 + **明文索引库隐私评审**） | 一致性、蓝绿、重建、D9 重犯风险 |
| **原样提案**（浏览器 DB + 全扁平） | ⚠ 反而更复杂 | ❌ 泄密 | 极大（近乎重写）：九类 `project/path` 身份键整体迁到 id、重做树/面包屑/移动/mkdir、个人空间语义重做 | 权限泄露、多设备、功能倒退 |

**评审补充的一致性问题**：`file:changed` 订阅者虽是现成范式，但**「绕过事件总线的写会漏登记」是已知边界**——`dup:27-28` 自认「编辑器保存不进索引」，`agent/v1/write`、直接落盘同理。所以主索引必须**「全量 rebuild + 事件增量」双保险**（`fulltext:83-87` 就是范式），不能只靠事件。

## 6. 建议

**采纳「服务端主索引 + ID 化 + 保留分层 + 上传冲突交互」，放弃「浏览器端数据库 + 全扁平」。** 具体落点：

1. 新 L2 服务 `privhub-svc-fileindex`：表 `files(id, project, virtual_path, name, ext, size, mtime, encrypted, physical_id)`；**派生、可全量重建、宽容读取、有上限**（抄 `svc-links` 范式）。**存加密 JSON 走 `ctx.storage`（同 `meta.json`/`links.json`/`dup-index.json`），不要用明文 SQLite 存可读路径**（D9 教训，§4.1）。
2. `/api/list` 改查索引（按 `visibleProjects` 过滤后分页）；索引 miss/落后时回退 `readdir` 并补登记。
3. 索引维护挂 `file:changed` / `file:saved`（与现有 9+ 订阅者并列，写仍走 `svc.route`，功能零损失）。
4. `reload()` + 加进 `main.ts` 清单 + `onActivate` + `runtime-contract.mjs` 断言。
5. **虚拟路径继续分层**；物理文件名可用稳定 id，但**目录树/面包屑/mkdir/移动/ACL 路径规则全部保留**。
6. 上传冲突：把 `svc-dup.check` 从「上传后告知」提前到「上传前拦截」，UI 给三选一 **覆盖 / 自动改名保留两者 / 取消**；「重复文件」沿用现有 exact/near；**不要用 mtime 自动删数据**。
7. nginx 直读改为「按 id 授权 → Node 查表得物理路径 → `X-Accel-Redirect`」，顺带解掉 v3 的路径穿越 P0；SVG CSP 等响应头仍需补。

**这比 v3 更进一步**：v3 只是「不每次扫盘」，本方案是「磁盘不再是列表的真相来源」，且 ID 化让后续所有按路径键的侧车状态（评论/标签/双链/查重/版本）都有了统一的稳定锚点。

**但请先看 §3.1 与 §3.3**：一致性与扁平化是这个方案的真正成本。若你的核心诉求只是「点文件夹快」，v3 阶段 2 两天就能上线、零新风险；若你愿意为「ID 化 + 干净的权限模型」付一次架构改造，本方案改良版值得做。
