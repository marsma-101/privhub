## 一、问题现象

打开页面后**永久停在"加载中…"**，登录框不出现，无法登录。开发环境（3180）与生产包（3181）均可复现。

---

## 二、根因（已定位，证据确凿）

这是一个**先有鸡还是先有蛋的死锁**：

| # | 环节 | 位置 | 事实 |
|---|---|---|---|
| 1 | 登录框由**插件**提供 | `privhub/frontend/index.html:884` | `<component v-for="c in slotComps.auth" ... v-if="!loggedIn && slotComps.auth && slotComps.auth.length">` |
| 2 | `slotComps.auth` 来自 manifest | `index.html` 的 `loadManifests()` | 拉 `/privhub/api/shell/manifest` → `import()` 各插件 → 按 slot 注册 |
| 3 | manifest 接口**要求登录** | `plugins/privhub-shell/server/index.ts:83` | `const u = svc.requireUser(req, res); if (!u) return` → 未登录直接 401 |
| 4 | 骨架**只在有 token 时**才拉 manifest | `index.html:837` | `if (AUTH.token) await this.loadManifests()` |
| 5 | 兜底文案是"加载中…" | `index.html:885` | 没有 auth 组件时显示加载提示，**永不结束** |

**死锁链**：未登录 → 不拉 manifest（无 token）→ `slotComps.auth` 为空 → 登录框不渲染 → 显示"加载中…" → **用户无从登录** → 永远出不来。

### 责任归属

环节 3 是本会话为修复《改进建议》**S16（manifest 泄露插件清单）**时引入的改动。
原意图（不向未登录者暴露完整插件清单）是合理的，但**没有考虑骨架的登录界面本身依赖该接口**。

### 为什么 84 项测试全部通过却漏掉

`tests/security.mjs` 的 S16 用例断言写的是：

```js
ok(r.status === 401, '未登录拉取 manifest 应 401，实际 ' + r.status)
```

**这条断言把 bug 本身固化成了"预期行为"** —— 测试通过得越多，越掩盖了缺陷。
根因是断言写的是"现在如此"而非"应该如此"。此教训已固化到 §6.1 第 8 条。

---

## 三、修复方案

### 推荐方案 A：未登录返回"最小可用清单"

**核心思路**：把 manifest 接口的语义从"要么全给、要么不给"改为**按登录态分级返回**。

**服务端**（`plugins/privhub-shell/server/index.ts`）

```ts
const u = svc.me(tokenOf(req))          // 不再直接 401
const manifests = await collectManifests()   // 缓存逻辑不变（见下方说明）
if (!u) {
  // 未登录：只返回"渲染登录界面所需的最小集合" = 声明了 auth slot 的插件
  const minimal = manifests.filter((m) => (m.slots || []).includes('auth'))
  return json(res, 200, { ok: true, manifests: minimal, partial: true })
}
json(res, 200, { ok: true, manifests })  // 已登录：完整清单
```

实测最小集合为 **2 个插件**（`privhub-auth`、`privhub-shell`），其余 46 个插件均不暴露。

> **缓存说明**：`collectManifests()` 的 5s TTL 缓存返回的是**完整清单**，过滤发生在缓存之后，
> 因此未登录/已登录请求共享同一份缓存但各自过滤，**不会互相污染**。

**前端**（`frontend/index.html`）

1. 挂载时**无条件**调用一次 `loadManifests()`（去掉 `if (AUTH.token)` 前置条件）——
   这是断死锁的关键，否则未登录时永远拉不到 auth 插件；
2. 登录成功后再调用一次拿完整清单（现有 `loggedIn` watch 已有此逻辑，只需修正触发条件）；
3. `partial` 标记用于判断"当前是否只有最小集合"，登录后据此决定是否重拉。

**兜底加固**（建议一并做，成本极低）

`index.html:885` 的"加载中…"改为**超时兜底**：若 8 秒内仍未渲染出登录界面，显示
"界面加载失败 + 重新加载按钮"，把"静默卡死"变成"可见可操作"。这样即使将来 manifest 再出问题，用户也有出路。

### 备选方案对比

| 方案 | 做法 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| **A** | 未登录返回含 auth slot 的最小集合 | 改动小；保留 S16 信息保护意图；彻底断死锁 | 未登录仍可见 2 个插件的标题/描述（登录界面本就需要） | ✅ **推荐** |
| B | 完全回退 S16（manifest 恢复公开） | 一行改动 | 放弃信息保护，S16 白做 | 不推荐 |
| C | 骨架内置登录表单（不依赖插件） | 与 manifest 彻底解耦 | 登录 UI 逻辑重复，维护成本 | 作为 A 的后续加固 |
| D | A + C | 双保险 | 改动最多 | 可后续演进 |

## 四、测试计划

### 4.1 回归测试（自动化，纳入 `privhub/tests/`）

| 编号 | 用例 | 断言要点 | 防线作用 |
|---|---|---|---|
| **R1** | 修正 S16 用例（**必做**） | 未登录 GET manifest → **200**；返回清单**仅含**声明 auth slot 的插件；断言**不含** `privhub-files-agent`、`privhub-admin` 等敏感插件 | 同时守住"不泄露完整清单"与"登录可达"两个目标，纠正被固化的错误断言 |
| **R2** | 首屏可登录 | 未登录清单中存在**可加载**的 auth 插件；其 `entry`（`/privhub-plugins/privhub-auth/index.js`）HTTP 200 | 保证登录界面真的能渲染出来 |
| **R3** | 登录后完整清单 | 登录后 manifest 插件数 ≥ 30；关键 slot 齐全（`tree`/`panel`/`preview`/`app-iconbar`/`user-area`/`trash-view`/`search-view`/`settings`） | 防止"能登录但进去是空壳" |
| **R4** | **骨架首屏链路模拟**（核心） | 严格复刻浏览器时序：`GET /` → `GET manifest(无token)` → 逐个 `import(entry)` 断言 200 → `POST login` → `GET manifest(带token)` → 逐个 `import` 断言 200 | **本事故的直接防线**，任一步失败即红 |

> R4 不依赖浏览器：它复刻的是骨架 `mounted()` 的真实请求序列，能捕获本次这类"链路断点"。

## 六、变更范围与风险评估

### 预计改动文件（4 个）

| 文件 | 改动 | 风险 |
|---|---|---|
| `plugins/privhub-shell/server/index.ts` | 未登录返回最小集合 | 低（仅过滤逻辑） |
| `frontend/index.html` | 无条件拉 manifest + 超时兜底 | 中（骨架启动流程，需真机验证） |
| `tests/security.mjs` | 修正 S16 断言 | 低 |
| `tests/first-screen.mjs`（新增） | R2/R4 首屏链路 | 低 |

### 回滚预案

- **本机无 git**（不在 PATH），改动前先手工备份这 2 个源文件到 `_archive/2026-09-11-登录死锁修复/`；
- 若修复后出现新问题，用备份还原即可回到"当前已知坏状态"。

### 已知风险点

| 风险 | 说明 | 缓解 |
|---|---|---|
| manifest 缓存与过滤交互 | 未登录/已登录共享 5s 缓存 | 过滤在缓存之后执行，不污染；R4 用例覆盖两种登录态连续请求 |
| 登录后未重拉完整清单 | 会出现"能登录但只有登录组件" | R3 断言登录后插件数 ≥ 30 |
| `privhub-shell` 声明了 auth 但未导出 | 属既有元数据不一致（无害） | 最小集合过滤按"声明"判定，`privhub-auth` 确实导出，故可用；清理该声明列为后续小项 |
