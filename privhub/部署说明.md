# 私域枢纽 PrivHub 部署说明（纯 Cordis 架构 · 2026-11-11 同步至 v3.5.0）

> 底座：**纯 Cordis**（npm 依赖 `@deepseek-ai/cordis` 4.0.1 + `@deepseek-ai/schemastery` + `tsx`），无 DSH 底座源码。
> 开发主目录（本目录 `privhub/`）完全自包含：整个文件夹搬走即可运行；仓库根的 `references/` 只是参考副本，删除不影响运行。

## 目录结构

```
privhub/
├── src/             装配入口（main.ts：cordis Context + 自研 webServer + 插件挂载）
│   └── web-server.ts  自研 HTTP 服务（exact 路由 + 静态前端 + /privhub-plugins 映射）
├── plugins/         65 个插件目录（L1 六枢纽 / L2 十四个能力 Service / L3 自动发现，含 9 个纯前端）
├── frontend/        前端（Vue3 全局构建单页骨架 index.html + manifest/slot 加载器，无打包步骤）
├── tests/           回归测试套件（交付物，进 git；run-all.mjs 一键跑，隔离实例端口 3190）
├── scripts/         辅助脚本（build-release.mjs 蓝绿打包 / verify-store.mjs 存储体检 / fetch-nginx.ps1 / doc2md.py）
├── mcp/             宿主机智能体 MCP 转接器（零依赖）
├── runtime/         蓝绿稳定层（control.mjs / update.mjs / nginx.conf.template / nginx/）
├── releases/        蓝绿 release（每个版本一个自包含目录，运行时生成、不入库）
├── config/          蓝绿状态（active.json / runtime.json / control.token / update.json）
│                     + store.json（可选：存储根配置，跨 release 保留）
├── store/           蓝绿共享数据根（data/ + data-files/；不入库；文件库可另指他处）
├── node_modules/    npm install 还原（含 better-sqlite3 / sqlite-vec 原生模块）
├── data/            单进程运行数据（users/sessions/trash/audit 等，首次启动自动生成）
├── data-files/      单进程文件存储根（顶层文件夹即项目 / 个人空间）
├── start.bat        单进程启动器（开发 3180 / 生产 3181）
├── start-runtime.bat 蓝绿启动器（控制层 + nginx，对外默认 3181）
├── package.json     依赖声明（15 个运行时依赖）
├── .gitignore       上传 git 自动排除依赖与数据
└── 部署说明.md
```

## 环境要求

- **Node.js 20+**（实测环境 **v24.21.0**）；单进程模式无需其它运行时，蓝绿模式另需官方 nginx
  （`scripts/fetch-nginx.ps1` 自动下载并校验 SHA256）及 git（更新器使用 git 源时）；
- `better-sqlite3` 为原生编译模块，需与 Node 版本匹配（更换 Node 大版本后重新 `npm install`）；
  **同一批蓝绿 release 必须用同一 Node 大版本构建/运行**；
- Windows 开发 / 部署；git 仅在需要「自动备份」插件或 git 更新源时才用到
  （未安装时该插件显式告警并停用定时器，不影响主功能）。

## 启动

```bat
npm install
REM --- 单进程（开发 / 小规模；更新时需要停服）---
start.bat            -> 开发环境 http://127.0.0.1:3180
start.bat 3181       -> 生产环境 http://127.0.0.1:3181（设置 PRIVHUB_ROOT）

REM --- 蓝绿（生产推荐；更新不停服）---
powershell -ExecutionPolicy Bypass -File scripts\fetch-nginx.ps1
node scripts\build-release.mjs
start-runtime.bat     -> 对外 nginx http://127.0.0.1:3181（槽在 3301/3302）
```

默认账号：

- `admin` / `admin123`（系统管理员，**登录后请立即修改密码**）
- `user1` / `user123`（普通员工，仅 公共 / A项目）

## 架构（纯 Cordis 三层）

- **L1 六枢纽**：core（`ctx.privhub` 持久化/权限/回收站）+ auth + files + trash + admin + shell（manifest 聚合）；
- **L2 十四个能力 Service**：storage / events / audit / acl / watermark / search / meta / collab / lock / office / model / links / dup / cap；
- **L3 功能插件**：`src/main.ts` 的 `CORE_PLUGINS` 清单之外，扫描 `plugins/*/src/index.ts` 自动发现（按目录名排序，`_` 开头跳过）；
- **webServer**：自研 Service（node:http），扁平路由表**仅精确匹配**（当前 174 条路由：172 条分布于 41 个插件 + `main.ts` 2 条运行时路由）；
  静态服务直接提供 `frontend/`，插件 client 经 `/privhub-plugins/<名>/<文件>` 映射加载；
- **数据根（三个，别混）**：代码根 `PRIVHUB_ROOT`（插件/前端/node_modules）、
  系统数据根 `PRIVHUB_DATA_ROOT`（`data/`：账号/会话/审计/回收站/密钥）、
  文件库根 `PRIVHUB_DATA_FILES`（项目与个人空间）。
  解析优先级统一为 **环境变量 > `config/store.json` > 默认值**，三根可以分别放在不同磁盘；
  蓝绿两槽共享同一份配置与同一批根。`PRIVHUB_ROOT` 只表示代码根，**绝不用于数据路径**。

## 插件开发

- 插件目录：`plugins/<名>/`。后端 `src/index.ts`（`export const name / inject / apply(ctx)`），前端 `client/`（`manifest.json` + `index.js`）；
- **新增 L3 插件只需建目录**（含 `src/index.ts` 即被自动装配；只有 `client/` 则为纯前端插件），无需改 `main.ts`；
- 新增 L1/L2 插件才需要改 `src/main.ts` 的装配顺序（Service 必须先于消费方挂载）；
- 无构建步骤：tsx 直接加载 TS 源码，改完重启 `start.bat` 即生效；
- 完整契约见仓库文档《PrivHub-插件实现规则.md》。

## 依赖

- `npm install` 还原 **15 个运行时依赖**：底座三件套（cordis / schemastery / tsx）、
  原生模块 `better-sqlite3` + `sqlite-vec`（全文与向量检索），
  以及 Office 文档库（docx / exceljs / xlsx / pptxgenjs / mammoth / word-extractor / pdf-lib / pdf-parse / pdfkit / jszip）；
- 仓库根 `references/`：底座与 llm-wiki 等参考资料，**仅供查阅/借鉴**，不参与运行（`.gitignore` 已排除）。

## 静态加密（默认开启）

- 用户文件与大部分系统 JSON 以 **AES-256-GCM** 加密落盘（文件头 `PHENC1`），审计为独立加密块（`PHAUD1`）；
  读取对旧明文文件透明兼容。
- ⚠️ **例外**：`comments.json`、`invites.json` 目前可能仍为**明文存储**（以启动日志列出的
  「明文落盘」清单为准；管理员可执行 `POST /privhub/api/storage/migrate` 迁移）。
- 密钥：默认 `<系统数据根>/data/secret.key`（单进程即 `data/secret.key`，蓝绿即 `store/data/secret.key`；
  可用 `PRIVHUB_SECRET_KEY_FILE` 改位置）。32 字节，首次启动自动生成；
  也可用环境变量 `PRIVHUB_SECRET` 覆盖（优先级最高）。
- **密钥文件必须随数据一起备份到异地——丢失密钥 = 数据无法恢复！**
- **启动保护（v3.5.0）**：如果目标根里已经存在 `PHENC1`/`PHAUD1` 密文，却找不到对应密钥，
  进程**拒绝自动生成新密钥**并退出（否则会用新密钥「覆盖」旧库，等于判死刑）。
  确属全新空库时可显式设 `PRIVHUB_ALLOW_NEW_KEY=1`。密钥不匹配时读取报
  `PrivHubKeyMismatchError`，不再静默当成「文件不存在」去写回空配置。
- 关闭加密：`privhub/src/main.ts` 中 `svcStorage` 配置 `enabled: false`（读取仍自动识别密文）。
- 备注：旧版《部署说明》提到的 `scripts/encrypt-migrate.mjs` 批量迁移脚本**目前在仓库中不存在**
  （属已知缺口 D13：长期不写回的旧明文文件不会自动加密），请勿照该旧说明执行。

## 存储根配置与体检（v3.5.0，GitHub issue #2）

### 配置位置

优先级：**环境变量 > `config/store.json` > 默认值**。`store.json` 位于 `<home>/config/`，
在 release 目录之外，`git pull` / 一键更新 / 回滚都不会覆盖它。文件可用记事本直接编辑；
带不带 UTF-8 BOM 都能读取（PowerShell 5.1 / 记事本写出的 BOM 不会被当成坏配置）。

```json
{
  "dataRoot": "D:/privhub-data",
  "dataFiles": "E:/公司文件库",
  "secretKey": "D:/privhub-data/data/secret.key",
  "strict": true
}
```

| 键 | 环境变量 | 含义 |
|---|---|---|
| `dataRoot` | `PRIVHUB_DATA_ROOT` | 系统数据根（`data/` 在其下） |
| `dataFiles` | `PRIVHUB_DATA_FILES` | 文件库根（项目 / 个人空间） |
| `secretKey` | `PRIVHUB_SECRET_KEY_FILE` | 密钥文件位置 |
| `strict` | `PRIVHUB_STORE_STRICT=1` | 启动自检不通过时拒绝启动 |

- 显式配置的 `dataFiles` **必须已存在且是目录**，否则拒绝启动（并提示「父目录下有 data-files」，
  防止把上级目录误当库根）。仅首次初始化空库时用 `PRIVHUB_ALLOW_INIT_DATA_FILES=1` 放行。
- 不配置时：系统数据根默认等于代码根，文件库默认 `<数据根>/data-files`（与旧行为一致）。
- 配置写坏（JSON 非法）时拒绝启动并指出文件路径，**不会**悄悄回退默认根。

### 启动自检与切换闸门

- 启动时打印三根与来源，并执行 `storeCheck()`：顶层项目数 / 个人空间数 / 密钥来源 /
  抽样解密账号文件与库内一个密文文件；有异常写警告，`strict` 下直接退出。
- 蓝绿切换前，控制层会调用新槽的 `GET /privhub/api/runtime/store-check`；
  **不通过就取消切换，旧槽继续服务**（`PRIVHUB_STORE_CHECK_FAILED`），
  不会出现「切到一个看不见老库的空实例」。
- 只读体检（不写盘、不建目录、不生成密钥）：

  ```bat
  node scripts\verify-store.mjs
  node scripts\verify-store.mjs --json
  ```

  退出码 0 = 通过；1 = 有硬失败（库不可读 / 有密文但缺密钥 / 解密失败）。
  纯使用版的体检脚本在 `<home>/scripts/verify-store.mjs`，会自动读取 `config/active.json`
  找到当前 release 的解析逻辑。

### 从旧单进程布局迁移

1. 停旧服务，备份整个 `data/`、`data-files/` **和 `data/secret.key`**；
2. 新部署启动一次，确认日志里的「系统数据根 / 文件库根」指向真实数据；
3. 若库在别处，写 `config/store.json`（或设 `PRIVHUB_DATA_FILES`）后再启动；
4. 跑 `node scripts\verify-store.mjs`，看到项目数正确、抽样解密通过再开放访问。

**多数情况下第 3 步可以省掉 —— 首次启动会自动沿用。** 只要旧单进程布局是
「`data/` 与 `data-files/` 都和 `runtime/` 在同一个 home 下」，控制层第一次以蓝绿启动时会：

- 探测到旧布局 → 把 `dataRoot=<home>`、`dataFiles=<home>/data-files` 写进 `config/store.json`，
  并在日志里逐行说明沿用了什么；
- **已经配置过就一个字都不改**（有 `config/store.json` 或设了 `PRIVHUB_DATA_ROOT/FILES` 一律让路）；
- 旧布局里只有 `data/`、没有 `data-files/`（库在别的盘）时，**不猜库根**，
  只提示你去写 `config/store.json` —— 猜错等于给一个空库。

想先看「会沿用成什么」而不真落盘：

```bat
node runtime\control.mjs adopt-legacy --dry-run
node runtime\control.mjs adopt-legacy            :: 真写入
```

> 端口提醒：单进程生产与蓝绿 nginx 历史上都用过 `3181`。**不要同时启动两者**。
> 如需把蓝绿对外端口改成 `3180`，设 `PRIVHUB_PUBLIC_PORT=3180`（或写入 `config/runtime.json`），
> 并先停掉占用该端口的单进程实例；`start.bat` 与 `start-runtime.bat` 不能指向同一端口。
> 首次自动沿用旧布局时，若把旧端口传给控制层（`PRIVHUB_LEGACY_PORT=3180`），会一并沿用对外端口。

### 破坏性操作守卫

- 明文 → 密文迁移只允许发生在**当前配置的系统数据根 `data/` 下**；路径不在该根内一律拒绝
  （根指错时不会去改另一棵树），密钥/审计/日志/git 备份继续单独拒绝并说明原因。
- **回收站物理删除**（单条清空 / 定时清理）在动手前校验「回收站目录必须落在配置的文件库根内」。
  两个入口都过这道守卫：`purgeTrash` 拒绝并返回失败，定时清理 `purgeExpiredTrash` 一条都不删
  并留下日志。启动自检 `/runtime/store-check` 的 `trash` 段会回报这条一致性，
  蓝绿切换前的闸门因此也能拦住「库根配错」。
- git 自动备份镜像使用配置的文件库根；库根不存在时启动显式告警，界面 `gitbackup/status`
  返回 `libraryMissing`，避免「备份在跑、实际为空」。

## 生产部署（单进程包）

需要「更新不停服」时直接看下一节「蓝绿热更新」；本节是传统的单进程整包部署。

- 打包（在**仓库根**执行 PowerShell）：
  ```powershell
  powershell -ExecutionPolicy Bypass -File scripts/build-deploy.ps1            # 实际构建
  powershell -ExecutionPolicy Bypass -File scripts/build-deploy.ps1 -WhatIfOnly # 只预演不动文件
  ```
  产物在 `deploy/privhub-deploy/`；脚本默认**跳过 `data/` 与 `data-files/`**，除非显式传 `-IncludeData`。
- 整包传输到宿主机 → 解压（任意路径）→ 双击 `start.bat 3181`；首次启动自动生成密钥、数据目录与默认账号。
- **升级携带旧数据时**：把原 `data/`、`data-files/` 连同 `secret.key` 一并复制到新目录（数据在旧密钥下加密，复制密钥即可解密）。
- 同步后必做发布闸门：`node tests/integrity.mjs --release`（校验插件目录数与关键文件逐字节一致）。
- ⚠️ **历史 `deploy/` 包不作为发布源**：它们落后于开发源码，**上线前必须重新打包同步**；
  同步生产按项目规矩需经显式授权。

## 蓝绿热更新（可选部署形态，2026-11 新增）

上面 `start.bat` 是**单进程**部署：更新时必须停服、用户会看到一段不可用。
需要「用户无感更新」时改用 `runtime/` 稳定层（详见 `runtime/README.md`）：

```bat
powershell -ExecutionPolicy Bypass -File scripts\fetch-nginx.ps1   REM 一次性：下载并校验官方 nginx
node scripts\build-release.mjs                                     REM 把当前源码打包到 releases\<version>\
node runtime\control.mjs serve                                      REM 启动控制层（或双击 start-runtime.bat）
```

- 对外入口是 nginx（默认 `3181`），槽进程只在 `127.0.0.1:3301/3302`；
- 两个槽共享**同一个**存储配置（`config/store.json` 或环境变量）；默认系统数据根
  `<privhub>/store/`、文件库在其下。旧布局的 `data/`、`data-files/` 会被保守识别，无需搬数据；
  第一次切换后建议把旧目录移进 `store/`，避免误以为有两个数据根；
- 切换前会对新槽做存储自检（`runtime/store-check`）；自检不过则**取消切换**，旧槽继续服务；
- `config/store.json` 放在 release 目录之外，更新/回滚不会丢失；改完配置重启控制层生效；
- 更新流程：`node runtime\update.mjs check` → `apply`（或 `daemon` 按 `config/update.json` 定时执行）。
  控制层先让新槽待命预热，再冻结旧槽、排空在途写、重读共享状态、激活新槽、切 nginx；
  旧页面会被版本门拦住并弹「立即刷新」；
- `config/update.json`（严格 JSON，不能写 `//` 注释）：
  ```json
  { "source": "http", "manifestUrl": "https://example.com/privhub/latest.json",
    "autoApply": false, "intervalMinutes": 360, "requireNewer": true, "keepReleases": 3 }
  ```
  也可用 `"source": "dir", "path": "\\\\nas\\privhub\\releases"` 从共享目录投放，
  或 `"source": "git"` 从仓库浅克隆（需要使用方安装 git）；
- `source: "http"` 读取的 `latest.json` 由发布端生成（见下节），字段为
  `{version,url,sha256,notes,publishedAt}`；下载后强制校验 sha256，不一致直接拒绝。
  `autoApply: false` 时守护只检查、由人工在界面点「立即更新」；
- 管理界面：**管理控制台 → 系统运维 → 系统更新** 可查看当前版本/更新源/进度/日志，
  一键「检查更新」「立即更新」「回滚到上一版」，并可直接修改更新源（保存即生效，无需重启）；
- 回滚：`node runtime\control.mjs rollback`；旧 release 清理：`node runtime\update.mjs prune`
  （保留最近 `keepReleases` 个 + 当前/上一版本）；
- 首次从旧单进程升级到蓝绿时，旧版本没有运行时能力声明，控制层会回落到「先冻结再启动」的
  保守路径，建议低峰执行；
- 单进程 `start.bat` 仍可用于开发/小规模部署；两种方式不要同时指向同一个端口。

## 纯使用版交付（v3.5.0 新增）

目标是让「使用方」机器上没有源码、没有 npm、也不需要智能体：
解压一个 zip、双击启动器即可运行；之后开发机发布新版本，使用方在界面上一键更新。

**① 开发机：构建 release 并打成使用版**

```bat
node scripts\build-release.mjs
node scripts\build-standalone.mjs --manifest-url https://example.com/privhub/latest.json --with-node
```

产物 `dist/privhub-<version>-standalone.zip`，内含：

```
privhub/
├── runtime/                 稳定层（control / update / 模板；带 nginx 二进制）
├── releases/<version>/      业务 release（自带 node_modules）
├── config/update.json       预置更新源（未传 --manifest-url 时首次在界面填）
├── runtime/node/node.exe    --with-node 时内置（使用方无需预装 Node）
├── start-runtime.bat
└── 使用说明.md
```

使用方：解压到普通目录（不要放 `Program Files`，nginx 写日志可能被拦）→ 双击
`start-runtime.bat` → 浏览器打开 `http://<本机IP>:3181`。数据与密钥默认在 `store/`；
若库已在别处，在 `<home>/config/store.json` 里写 `dataFiles`（更新不会覆盖该文件）。
包内 `<home>/scripts/verify-store.mjs` 可随时做只读体检。

**② 开发机：发布新版本到更新源**

```bat
node scripts\build-release.mjs --package --public-base https://example.com/privhub/
```

得到 `dist/privhub-<ver>.zip` 与 `dist/latest.json`，把两个文件一起上传到该 Web 目录即可
（GitHub Release、内网静态服务器都行）。默认更新包**不含 node_modules**（体积小）；
若本次改了依赖，加 `--with-modules` 重打 —— 否则更新器会以 `PRIVHUB_DEPS_CHANGED`
拒绝自动切换。

**③ 使用方：一键更新**

守护按 `intervalMinutes` 检查清单 → 界面显示新版本与更新说明 → 点「立即更新到 x.y.z」→
后台下载（边下边算 sha256）→ 待命槽预热 → 冻结旧槽排空 → 切 nginx → 页面提示刷新。
旧版本在切换完成前持续服务；异常时同页「回滚到上一版」。
